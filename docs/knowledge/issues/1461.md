## Asked

`LawfulBasisHealthCheck` (`Encina.Compliance.LawfulBasis`) embedded the raw `EncinaError.Message`
from `ILawfulBasisService.GetAllRegistrationsAsync`/`GetPendingLIAReviewsAsync`'s `Left` branches
directly into its `Degraded`-status warning text, and the raw `Exception.Message` from its two
`catch (Exception ex)` blocks (one via a warning string, one via the raw exception object passed
to `HealthCheckResult.Degraded`'s `exception:` parameter). Same defect class as #1314, #1415/#1429,
#1426 and #1435, this time under the "health-check results" channel AGENTS.md names explicitly
alongside logs, activity tags and plaintext storage — found by an `adversarial-reviewer` while
fixing #1435 and left out of that issue's scope as a follow-up.

## Outcome

Delivered: `LawfulBasisHealthCheck` no longer puts a raw `EncinaError.Message` or a raw exception
message into any part of its `HealthCheckResult`. The two `Left` branches now record
`error.GetCode().IfNone("encina.unknown")`. The `catch` block around `GetAllRegistrationsAsync` no
longer passes the raw exception object to `HealthCheckResult.Degraded`'s `exception:` parameter;
it records `data["exception_type"] = ex.GetType().Name` instead. The `catch` block around
`GetPendingLIAReviewsAsync` records `ex.GetType().Name` in its warning text instead of `ex.Message`.
While in the area, `DefaultLawfulBasisService`'s `RegisterAsync`/`CreateLIAAsync` argument-validation
logging stopped passing `ex.Message` as a redundant log template argument (the exception object
passed to `LogWarning` already carries it); the `EncinaError` returned to the caller is unchanged.
A new test file, `LawfulBasisHealthCheckLeakTests.cs`, proves a sentinel `EncinaError` message and a
sentinel exception message never appear in `HealthCheckResult.Description`, `Data` values, or
`Exception.Message`, across four scenarios: registrations-query `Left`, LIA-query `Left`,
registrations-query throws, LIA-query throws.
