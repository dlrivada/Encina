## Asked

Make `TenantAwareFunctionalRepositoryDapper` in `Encina.Dapper.SqlServer` return `Left(Repository.TenantRequired)` instead of throwing or returning `Repository.PersistenceError` when the tenant context is missing, as the MongoDB repository does since #2938. This is the SQL Server part of #2995.

## Outcome

Delivered: every operation (`GetById`, `List`, `FirstOrDefault`, `Count`, `Any`, `GetPaged`, `Add`, `AddRange`, `Update`, `UpdateRange`, `Delete`, `DeleteRange`) checks the tenant context before any database call. With `ThrowOnMissingTenantContext` on (the default) and no tenant, it returns `Left(Repository.TenantRequired)` built with `RepositoryErrors.TenantRequired<TEntity>(operation)`, where the operation is the calling method name. `Update` and `UpdateRange` check up front, before audit fields are populated, even when `ValidateTenantOnModify` is off. A tenant mismatch still returns `Repository.InvalidOperation`, now naming the calling operation instead of "Modify". The public members `BuildWhereClause` and `BuildSelectStatement` of `TenantAwareSpecificationSqlBuilder` take a trailing `string operation` and return `Either`. The option keeps its name; the rename is #3007.

- `src/Encina.Dapper.SqlServer/Tenancy/DapperTenancyOptions.cs` - XML docs of the option only.
- `tests/Encina.UnitTests/Dapper/SqlServer/Tenancy/TenantAwareFunctionalRepositoryDapperTenantRequiredTests.cs` - every operation without a tenant returns `TenantRequired` and never touches the connection.

- `tests/Encina.IntegrationTests/Dapper/SqlServer/Tenancy/TenancyDapperIntegrationTests.cs` - a missing tenant against a real SQL Server leaves the data untouched.
- `docs/features/multi-tenancy.md` - the per-family description of a missing tenant.
