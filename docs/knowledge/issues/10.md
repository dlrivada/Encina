## Asked

Three FsCheck property tests in `Encina.DataAnnotations.PropertyTests` failed with `ValidationContext` errors during `Validator.TryValidateObject`, because a private nested test type (`ContextAwareCommand`) used `[CustomValidation]`, which requires its target type to be reflection-visible (public).

## Outcome

Delivered. Commit `3f20fec` (2025-12-23, message "Fixes #7", closed by a manual comment on #10 since the same commit also fixed this issue's tests) made `ContextAwareCommand` and `NoValidationCommand` public top-level records instead of private nested ones. No pull request exists for this fix; it was a direct commit to `main`.

## Where the knowledge lives

- The specific scenario (CustomValidationAttribute + context enrichment) no longer exists in the codebase: the file was replaced wholesale by test consolidation (commit `d7b7b8ac`) with `tests/Encina.PropertyTests/Validation/DataAnnotations/ValidationInvariantProperties.cs`, which tests a narrower claim (validation still succeeds with context present) and explicitly disclaims verifying propagation.
- No rule, ADR or checklist entry records the "reflection needs public types" lesson; it is narrow enough that it is tracked as a test gap rather than promoted (see Audit).

## Audit

Verdict: `findings-tracked`. Two remediation drafts written (not yet opened, pending orchestrator): `artifacts/issues/10-guard-tests-validation-providers.md` (guard-test gap shared by DataAnnotations/FluentValidation/MiniValidator) and `artifacts/issues/10-dataannotations-context-propagation-and-di-gaps.md` (context-propagation, DI ValidateOnBuild, and cancellation-token gaps specific to DataAnnotations). Full checklist in `docs/knowledge/audits/issue-10.md`.
