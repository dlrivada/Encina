## Asked

`EncinaError.Message` reached both a log message and an OpenTelemetry activity tag/status
description in `Encina.Messaging.Encryption`, violating the `AGENTS.md` rule: *"`EncinaError.Message`
NEVER reaches logs, activity tags, health-check results or plaintext storage; record only the error
code or the exception type"* (why: #1168, #1173, #1259, #1274). Found by an adversarial review of
PR #1490 (#1454's fix), out of that PR's scope: #1454 fixed the activity-tag channel of this same
defect class in `Encina.Compliance.DataSubjectRights`, `Encina.Compliance.DPIA` and
`Encina.Compliance.Retention`, but `Encina.Messaging.Encryption` — where both the log and the
activity-tag channel were still live — was not covered by that sweep or by any of the earlier
#1168/#1173/#1259/#1274 log-channel fixes.

## Outcome

Delivered: `EncryptingMessageSerializer.Serialize<T>` and `DecryptIfNeeded` (encrypt and decrypt
failure paths) now log and tag `error.GetCode().IfNone("encina.unknown")` instead of
`error.Message`, at all four original call sites. Sweeping the rest of the
`Encina.Messaging.Encryption` folder for the same pattern (per the brief's decision, not limited to
the issue's four call sites) found `MessageEncryptionHealthCheck` leaking `error.Message` into both
its `HealthCheckResult.Unhealthy` description and its own log, on both the encrypt-phase and
decrypt-phase probes; those two call sites were fixed the same way, extending the rule's
health-check-result channel to this package as well. `EncinaError.Message` still reaches the
`InvalidOperationException` thrown on both failure paths (out of scope: the `AGENTS.md` rule names
logs, activity tags, health-check results and plaintext storage, not exception messages, and no
precedent fix in this defect class has touched an exception message).

Fixing the log/tag call sites required renaming the `EncryptionFailed`/`DecryptionFailed`
`[LoggerMessage]` parameters and `RecordFailure`'s parameter from `errorMessage`/`ErrorMessage` to
`errorCode`/`ErrorCode` (and `HealthCheckFailed`'s to `reason`) so the parameter name matches what it
now carries — the issue's own proposed fix flagged this as worth checking.

`EncryptingMessageSerializer.Serialize<T>` and `DecryptIfNeeded` needed a CRAP-gate refactor (see
the gotcha below) once the fix touched a line inside each: extracting each `Either.Match` arm into
its own method (`OnEncryptSucceeded`/`OnEncryptFailed`, `OnDecryptSucceeded`/`OnDecryptFailed`)
cleared both methods, since the pre-existing complexity (10 and 12) lived in the closures Coverlet
was attributing to the enclosing method.

## Where the knowledge lives

- `src/Encina.Messaging.Encryption/Serialization/EncryptingMessageSerializer.cs` — four call sites
  fixed (`Serialize<T>`'s and `DecryptIfNeeded`'s failure branches), refactored into
  `OnEncryptSucceeded`/`OnEncryptFailed`/`OnDecryptSucceeded`/`OnDecryptFailed` to clear the CRAP
  gate.
- `src/Encina.Messaging.Encryption/Health/MessageEncryptionHealthCheck.cs` — two call sites fixed
  (encrypt-phase and decrypt-phase probe failures).
- `src/Encina.Messaging.Encryption/Diagnostics/MessageEncryptionLogMessages.cs` — `EncryptionFailed`,
  `DecryptionFailed` and `HealthCheckFailed` `[LoggerMessage]` parameters renamed to match what they
  now carry.
- `src/Encina.Messaging.Encryption/Diagnostics/MessageEncryptionDiagnostics.cs` — `RecordFailure`
  parameter renamed `errorMessage` -> `errorCode`.
- `tests/Encina.UnitTests/Messaging/Encryption/EncryptingMessageSerializerErrorMessageLeakTests.cs`
  (new) — a `FakeLogger` capture plus an `AsyncLocal`-scoped `ActivityListener` (following #1454's
  `DiagnosticsCapture` pattern and the #1423 lesson against a process-global listener) assert a
  sentinel `EncinaError.Message` never reaches the log or the activity tag/status description on
  encrypt/decrypt failures, and that `MessageEncryptionHealthCheck`'s result description and log
  never carry it either.
- `changelog.d/1489-encryption-serializer-error-message.security.md` — user-visible changelog
  fragment.
