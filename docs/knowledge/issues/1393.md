## Asked

`Test-DuplicateEvidence` (`tools/ai/audit/_remediation-checks.ps1`) accepted a candidate open issue as the same
defect as an audit finding once one cited file and one backticked symbol of the finding appeared anywhere in the
candidate's title or body. #1393 reported that a verbatim house-rule quote such as `EncinaError.Message` was
still counted as specific symbol evidence. After #1424 made the check run over every search candidate, audit #16
verification pass 5 showed the wider problem: four false duplicates built from mentions, not from the
candidate's own subject -- an example in #1393's Description, a generic `src/` token, and file stems ('sagas',
'README') found in a directory segment or in prose.

## Outcome

Delivered: both anchors are now looked up only in the candidate's title and location sections, taken from the
issue templates; file matching no longer accepts a generic stem in a directory segment or prose; and folders,
line references and AGENTS.md/CLAUDE.md house-rule tokens are never symbol evidence. A candidate that matches
only part of a finding is "partially related". The deterministic, all-candidates design of #1424 is unchanged.

## Where the knowledge lives

- `tools/ai/audit/_remediation-checks.ps1` -- `Get-CandidateLocationText` and `Test-SymbolAnchorMatch` (new),
  the location-section and house-rule token lists, the narrowed `Test-FileAnchorMatch`, and the updated
  `Get-FindingAnchors`, `Test-DuplicateEvidence` and `Test-PartialDuplicateEvidence`.
- `.claude/hooks/tests/Test-Hooks.ps1` -- the `#1393` block, with the real fixtures in
  `.claude/hooks/tests/fixtures/1393/`.
- `.claude/skills/issue-audit/SKILL.md` -- the remediation stage's description of the duplicate rule.
