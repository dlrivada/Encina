## Asked

After a failed `SaveChangesAsync` the Marten aggregate repositories must leave the `IDocumentSession` clean, so a later write in the same scope succeeds. Found through #3769, where a repeated consent grant hits `StreamAlreadyExists` by design and the following withdrawal failed with `marten.save_failed`.

## Outcome

`EjectAllPendingChanges()` runs in the failure paths of `MartenAggregateRepository` and `SnapshotAwareAggregateRepository` (`CreateAsync` and `SaveAsync`, including the concurrency-conflict path), and in the same pattern of `MartenSnapshotStore`, `MartenReadModelRepository` and `InlineProjectionDispatcher`. Unit tests assert the eject on each failure path; Marten/PostgreSQL integration tests prove that a collision or a concurrency conflict followed by a write on the same session succeeds, for both repositories (they fail on the unfixed code).

## Where the knowledge lives

- `src/Encina.Marten/MartenAggregateRepository.cs` and `src/Encina.Marten/Snapshots/SnapshotAwareAggregateRepository.cs` -- the eject in every catch block.
- `tests/Encina.IntegrationTests/Infrastructure/Marten/Core/MartenAggregateRepositoryIntegrationTests.cs` -- the regression tests.
