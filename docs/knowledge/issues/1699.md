## Asked

`PostgreSqlSubjectKeyProvider` queried for an active key and then upserted `subject:{id}:v1`, so two concurrent first writers could each return a different key while only the last one was stored (ciphertext of the other became undecryptable); rotation repeated the pattern; a writer that passed the forgotten-marker check could create a key after an erasure committed; and a repeated erasure stopped at the marker without deleting such a key. The extended criteria (issue comment) asked for insert semantics, per-subject serialization, idempotent erasure, PostgreSQL concurrency tests, and a check of `InMemorySubjectKeyProvider`.

## Outcome

Delivered: key creation, rotation and erasure of one subject now run in one transaction under a PostgreSQL transaction-scoped advisory lock, so no key can be created after an erasure commits; creation and rotation insert with duplicate-key conflict handling to return the stored winner to every concurrent caller; erasure is idempotent and complete. InMemorySubjectKeyProvider returns key-material copies and clears subjects before zeroing keys, closing the shared-array race.
