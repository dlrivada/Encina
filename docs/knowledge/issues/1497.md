## Asked

The coverage manifest validation only checked for `src/` files missing from `.github/coverage-manifest/{Package}.json`,
not the reverse: manifest entries whose source file was deleted. Stale entries accumulated (found via #1463, where
deleting `LawfulBasisLogMessages.cs` left a stale entry manually removed in PR #1495) and required manual cleanup.
The issue asked for a check mode that fails CI when a manifest key names a file that no longer exists under
`src/<Package>/`, listing each stale key, and for the existing stale entries to be cleaned in the same change.

## Outcome

Delivered: `.github/scripts/coverage-report.cs` gained a `--check-stale-manifest` mode that reads every
`.github/coverage-manifest/*.json` file, resolves each key the same way `BuildDocRefIndex` already does
(`src/<Package>/<relPath>`, `File.Exists`), and exits non-zero listing every key whose file does not exist. It runs
with no coverage data and no build. A follow-up fix makes it also fail (distinctly) when no manifest was loaded at
all, so a misconfigured `--manifest` path cannot make the gate pass vacuously. The two stale keys found in
`Encina.Security.PII.json` (`Abstractions/IPIIPropertyCache.cs`, `GlobalSuppressions.cs`) were removed, and the
file's `totalFiles` metadata was corrected to match. CI wiring (adding a step to the `coverage-citations` job in
`.github/workflows/ci.yml`, which already runs on every PR with no build) is left to the orchestrator, as it is out
of this worker's scope.

## Where the knowledge lives

- `.github/scripts/coverage-report.cs` -- the `--check-stale-manifest` mode and its manifest-not-loaded guard.
- `.github/coverage-manifest/Encina.Security.PII.json` -- the cleaned manifest.
