## Asked

Make a message's handler run exactly `InboxOptions.MaxRetries` times before the inbox rejects it, identically on all 10 providers, and make every store `Left` inside `InboxOrchestrator` fail the operation.

## Outcome

`MarkAsFailedAsync` is the only increment, `IncrementRetryCountAsync` is gone, store `Left`s are returned, caller cancellation is not a failed attempt, a default-valued cached success is returned as success, and the inbox record has a fixed boundary with the business transaction (ADR-048): the processed mark commits with it, the entry, the retry count and a cached handler Left survive its rollback. It is proven through the real pipeline on ADO.NET, Dapper, EF Core (SQL Server, PostgreSQL) and MongoDB, including a business commit that fails after a successful handler. Unit tests cover the boundary for `MaxRetries` 1 and 3 and every store call; integration tests run the same scenario against each real provider (EF MySQL keeps its fixture skip, tracked in #2086).
