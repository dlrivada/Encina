## Asked

The adversarial review of #1333 found that the six ADO.NET and Dapper packages' only DI regression test, `SagaRunnerDiRegistrationTests`, resolved `ISagaRunner` against a plain `BuildServiceProvider()` (no `ValidateOnBuild`/`ValidateScopes`) and checked nothing else, unlike the new EF Core and MongoDB tests added for that issue. AGENTS.md §3 requires a registration method to be proven by a DI test that builds the provider under `ValidateOnBuild` and `ValidateScopes`; a future drift in the shared `Encina.Messaging` helper or in one provider's call to it would not be caught for ADO.NET/Dapper.

## Outcome

Delivered: one shared, provider-parameterised `AdoDapperMessagingDiRegistrationTests` class replaces `SagaRunnerDiRegistrationTests`. Its five `[Theory]` methods run over `MemberData(ProviderCases)` (the six `AddEncinaADO`/`AddEncinaDapper` delegates) and assert: the provider builds under `ValidateOnBuild`/`ValidateScopes` with every messaging pattern enabled and every registered service (`OutboxOptions`, `InboxOptions`, `SagaOptions`, `SchedulingOptions`, `IOutboxStore`, `IInboxStore`, `IScheduledMessageStore`, `ISagaRunner`, `ISagaNotFoundDispatcher`) resolves; `InboxPipelineBehavior<,>` is registered as an `IPipelineBehavior<,>` when `UseInbox` is on and absent when it is off; and `ISagaRunner`/`ISagaNotFoundDispatcher` resolve inside a scope when `UseSagas` is on (and are absent when it is off). All 30 cases (5 theories x 6 providers) passed on two consecutive runs; no provider failed `ValidateOnBuild`, so no `[BUG]` follow-up was needed. The old `SagaRunnerDiRegistrationTests.cs` was deleted in the same commit since every case it covered is a strict subset of the new theory.

## Where the knowledge lives

- `tests/Encina.UnitTests/Messaging/Sagas/AdoDapperMessagingDiRegistrationTests.cs` — the shared, provider-parameterised DI registration-completeness test for all six ADO.NET and Dapper packages.
