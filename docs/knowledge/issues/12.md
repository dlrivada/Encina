## Asked

Reduce the Dapper and ADO provider code duplication that SonarCloud reported (5.66% against a 3% threshold) without breaking provider independence.

## Outcome

`partial`. Closed on 2025-12-23 by commit `c66625f5` ("Closes #12"), but the bulk of the work is in an earlier same-day commit that does not mention the issue (`cf6cadbe`); the shared `Log`/`TransactionPipelineBehavior` follow-up (`760e27c0`, 2025-12-24) belongs to #20; no pull request exists. The audit found the centralization incomplete (EF Core and MongoDB bypassed the shared registration helper) and the 3% criterion unverifiable, so the outcome moved from `delivered` to `partial`.

## Where the knowledge lives

- The centralized behavior and its single DI seam: `src/Encina.Messaging/MessagingServiceCollectionExtensions.cs`; all six Dapper/ADO packages call `AddMessagingServices<...>`. No documentation page describes the factory seam yet.
- The accepted Store duplication and the CPD exclusion: `.github/workflows/sonarcloud.yml`; no ADR records the decision yet (#1336, open).
- The migration from `sonar-project.properties` to workflow flags is routine CI maintenance, not a design decision.

## Audit

Verdict: `findings-tracked`. Two registration gaps (fixed by #1333), the MongoDB inbox metadata loss (#1334), the unverifiable duplication claim (#1335) and the undocumented SQL-dialect decision (#1336). See [docs/knowledge/audits/issue-12.md](../audits/issue-12.md).
