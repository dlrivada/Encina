## Asked

Rewrite the Entity Framework Core section of `docs/features/multi-tenancy.md` against the real API, and check the Dapper, ADO.NET and MongoDB sections and the FAQ for option names their own options classes do not declare.

## Outcome

The section now shows an `ITenantEntity` entity, a `TenantDbContext`-derived context with its real constructor and the registration `AddEncinaTenancy()` plus `AddEncinaEntityFrameworkCore<TDbContext>(config => { config.UseTenancy = true; config.TenancyOptions... })`, with a table of the four options and what each does. The sample compiles and its service provider builds with `ValidateOnBuild` and `ValidateScopes` in a scratch project. The Dapper, ADO.NET and MongoDB samples were checked against their options classes and registration methods for option names; the FAQ lists the option names per provider. The first version of the Dapper handler sample did not match the real contracts (`Handle` returning `Task<Either<EncinaError, TResponse>>` with `(TRequest, CancellationToken)`, and `IFunctionalReadRepository<TEntity, TId>.ListAsync` in place of a non-existent `GetAllAsync`). A follow-up commit fixed that handler, the FAQ connection-factory sample (it now uses the real `ITenantConnectionFactory`) and the global-entity registration (`AddTenantAwareRepository`, there is no `AddRepository`), and compiled the handler, the query, the tenant-aware repository registrations and the connection-factory sample in a throwaway scratch project against `Encina.Dapper.SqlServer`. The other samples on the page were not compiled.

Out of scope and tracked elsewhere: the XML example on `EfCoreTenancyOptions` shows a `config.UseTenancy(tenancy => ...)` form that does not match the `bool UseTenancy` property (a follow-up issue for `src/`).

## Where the knowledge lives

- `docs/features/multi-tenancy.md` — the rewritten sections.
- `src/Encina.EntityFrameworkCore/Tenancy/EfCoreTenancyOptions.cs` — the four options.
- `src/Encina.EntityFrameworkCore/Tenancy/TenantDbContext.cs` — the base class.
