## Asked

Fix the `Encina.ADO.Oracle` and `Encina.ADO.Sqlite` `Scripts/*.sql` files, which were copy-pasted from the SQL Server dialect and used syntax invalid on their target databases (`sys.objects`, `GO`, `PRINT`, `NVARCHAR(MAX)`, `DATETIME2(7)`, `BIT`, `[dbo]` prefix).

## Outcome

Delivered directly by commit `cf4d3287a6ac58287530a778e34d2b4ebdb575c9` (2025-12-23), no pull request, no comments. The commit rewrote both providers' scripts in their native dialect (Oracle: `VARCHAR2`/`CLOB`/`NUMBER`/`TIMESTAMP`, PL/SQL `EXECUTE IMMEDIATE` blocks; SQLite: `TEXT`/`INTEGER`, `CREATE TABLE/INDEX IF NOT EXISTS`).

## Where the knowledge lives

- The general rule (check each provider's native SQL dialect) already lives in `CLAUDE.md`'s Multi-Provider Implementation Rule, "Provider-specific SQL differences to consider" table.
- The specific decision (Oracle/SQLite script dialects) has no current destination: both providers were later removed from the 1.0 provider matrix (ADR-009 for Oracle, commit `6121713c`, 2026-01-26; ADR-024 for SQLite, commit `22494a97`, 2026-03-28), which supersedes the need for their scripts to be correct at all.

## Audit

Verdict: `code-removed` (see `../audits/issue-2.md`). `Encina.ADO.Oracle` no longer exists anywhere in the repository (deleted, not backed up); `Encina.ADO.Sqlite` was moved to `.backup/sqlite/` (gitignored, not built or tested). No remediation opened.
