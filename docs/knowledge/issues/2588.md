## Asked

Give a `Retry-After` an upper bound: today any parsed value, up to `int.MaxValue` seconds, becomes the delay of the next delayed or outbox attempt, so a hostile or buggy server parks a message for decades without any alert.

## Outcome

A configurable ceiling (`RecoverabilityOptions.MaxRetryAfter`, `OutboxOptions.MaxRetryAfter`, 24 h by default). Up to the ceiling the behavior is unchanged; above it `RecoverabilityPipelineBehavior`, `DelayedRetryProcessor` and `OutboxBatchProcessor` schedule nothing and dead-letter the message with `recoverability.retry_after_exceeds_ceiling`, log a warning and count the skip. The outbox exhausts through the new store operation `IOutboxStore.MarkAsExhaustedAsync`, implemented in all ten providers, because the stores have no exhausted flag and raise `RetryCount` by one only.

## Where the knowledge lives

- `src/Encina.Messaging/Recoverability/RecoverabilityPipelineBehavior.cs` — the rule for the first delayed retry and the error code.
- `src/Encina.Messaging/Recoverability/DelayedRetryProcessor.cs` — the rule for the next delayed retry.
- `src/Encina.Messaging/Outbox/OutboxBatchProcessor.cs` — the rule for the outbox, exhausting the message at once.
- `src/Encina.Messaging/Outbox/IOutboxStore.cs` — `MarkAsExhaustedAsync`, the atomic exhausted state every store implements.
