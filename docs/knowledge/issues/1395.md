## Asked

Since the mutation-testing build was restored (#1088), the weekly Mutation Tests workflow's 17-shard matrix used one fixed 60-minute `timeout-minutes` for every shard regardless of scope size. Run 36089523656 (2026-09-25) showed 8 of 17 shards cancelled at that limit and several completed shards already close to it, so the run concluded `cancelled` and `publish-mutations.yml` never published — the mutation dashboard stayed frozen since 2026-04-17.

## Outcome

Delivered: `.github/workflows/mutation-tests.yml`'s `select-matrix` job gained a `TIMEOUTS` array kept in lock-step with `FOLDERS` and `FILTERS` (a three-way length check), sized per shard from run 36089523656's evidence — completed shards from their observed duration x1.5 (floor 60), cancelled shards from an estimate (setup time + mutant count x the completed shards' average per-mutant rate) x1.3, both capped at 340 minutes. The `run-mutation-tests` job now reads `timeout-minutes: ${{ matrix.timeout }}` from the matrix instead of a fixed 60. The `custom_scope` dispatch path reuses the matched entry's timeout or falls back to the largest configured value; `full_mode`/`diff_mode` get the 340-minute ceiling directly. Shard 15 (`**/Results/*.cs`) is a documented exception: its empty `FILTERS` entry makes every mutant rerun the full ~24k-test default suite, so the completed shards' per-mutant rate cannot size it reliably; it is capped at 340 minutes as a stopgap, with a follow-up issue tracking the real fix (a correctness-safe narrow filter, or folding it into the #1087 per-test coverage runner spike).

## Where the knowledge lives

- `.github/workflows/mutation-tests.yml` — the `TIMEOUTS` array, its lock-step length check, the per-entry `timeout` field in every matrix mode, and the `run-mutation-tests` job's matrix-driven `timeout-minutes`.
- `docs/testing/mutation-measurement-methodology.md` — the sizing method and the shard-15 exception, in prose for future maintainers.
