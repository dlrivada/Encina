## Asked

Since the mutation-testing build was restored (#1088), the weekly Mutation Tests workflow's 17-shard matrix used one fixed 60-minute `timeout-minutes` for every shard regardless of scope size. Run 36089523656 (2026-09-25) showed 8 of 17 shards cancelled at that limit and several completed shards already close to it, so the run concluded `cancelled` and `publish-mutations.yml` never published — the mutation dashboard stayed frozen since 2026-04-17.

## Outcome

Delivered: `.github/workflows/mutation-tests.yml`'s `select-matrix` job gained a `TIMEOUTS` array kept in lock-step with `FOLDERS` and `FILTERS` (a three-way length check), sized per shard from evidence — completed shards from their observed duration x1.5 (floor 60), cancelled shards from an estimate (setup time + mutant count x the completed shards' average per-mutant rate) x1.3, both capped at 340 minutes. The `run-mutation-tests` job now reads `timeout-minutes: ${{ matrix.timeout }}` from the matrix instead of a fixed 60. The `custom_scope` dispatch path reuses the matched entry's timeout or falls back to the largest configured value; `full_mode`/`diff_mode` get the 340-minute ceiling directly.

The fix was validated with a real dispatch of the branch (run 36240706037, 2026-09-26): 15 of 17 shards completed and the `TIMEOUTS` array was re-sized from their real durations, superseding the first estimate. Shard 15 (Results) completed for the first time and is no longer an exception (its timeout is now computed at 110, like every other completed shard); its empty `FILTERS` entry is still tracked as a correctness/efficiency follow-up in #1401. Shard 2 (Pipeline) became a *new* documented exception: it was cancelled a second time (72-minute budget, still not enough) despite having a real filter and a fast baseline pass, so its cost does not fit the pool-average formula for reasons not yet identified; it is capped at 340 minutes with a follow-up issue drafted. Shard 10 (Sharding.Colocation) crashed with an unhandled Stryker.Core exception (exit 134) unrelated to timeout sizing, tracked in a separate follow-up issue; its timeout is unchanged since the same shard succeeded normally the prior day.

## Where the knowledge lives

- `.github/workflows/mutation-tests.yml` — the `TIMEOUTS` array, its lock-step length check, the per-entry `timeout` field in every matrix mode, and the `run-mutation-tests` job's matrix-driven `timeout-minutes`.
- `docs/testing/mutation-measurement-methodology.md` — the sizing method and the shard-15/shard-2 exceptions, in prose for future maintainers.
