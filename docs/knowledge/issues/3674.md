## Asked

Part of #3617: make the three ADO.NET `TenantConnectionFactory` classes (SQL Server, PostgreSQL, MySQL) fail closed. An unknown tenant id or a missing tenant under `RequireTenant` must return a coded `Left` instead of a connection to the default database, and the explicit-id path must use the same coded error.

## Outcome

`GetConnectionStringAsync` and `CreateConnectionAsync` return `tenancy.tenant_not_found` for a present unknown tenant id and `tenancy.tenant_required` for a blank tenant id while `TenancyOptions.RequireTenant` is true; the default connection string is used for a missing tenant only when `RequireTenant` is false. `CreateConnectionForTenantAsync` returns `tenancy.tenant_not_found` for an unknown tenant and rejects a null, empty or whitespace id as an argument error. The three classes keep one implementation shape.

## Where the knowledge lives

- `src/Encina.ADO.{SqlServer,PostgreSQL,MySQL}/Tenancy/TenantConnectionFactory.cs` — the fail-closed resolution.
- `tests/Encina.UnitTests/ADO/*/Tenancy/TenantConnectionFactoryTests.cs` — the behavior, pinned per provider.
- `tests/Encina.IntegrationTests/ADO/*/Tenancy/TenancyADOIntegrationTests.cs` — the behavior against real databases in the shared collections.
- `tests/Encina.GuardTests/ADO/TenantConnectionFactoryGuardTests.cs` — the argument guards of the three classes.

## Known limits

- A known `DatabasePerTenant` tenant without a connection string still gets the default database (#3686).
- The factories do not log the denial or the `RequireTenant = false` fallback; they have no logger.
- The scoped `IDbConnection` registered by `AddEncinaADOWithTenancy` now throws when it is resolved without a tenant while `RequireTenant` is true, so tenant-less background work must set `RequireTenant = false`.
- The `ITenantConnectionFactory` interface documentation of the three packages still shows the old fallback in its example.
