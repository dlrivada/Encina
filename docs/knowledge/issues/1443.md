## Asked

`tests/Encina.UnitTests/Cdc/Sharding/ShardedCdcProcessorTests.cs` used the same flaky "start the real hosted
processor, `Task.Delay(n)`, cancel, then assert" pattern that #1430 fixed for every `OutboxProcessorTests`,
`DeadLetterCleanupProcessorTests` and `DelayedRetryProcessorTests` class, six times in that file. It races the
processor's first cycle the same way, and can fail sporadically on a loaded CI runner. The brief also asked to
grep every other `*Cdc*Tests.cs` file for the same pattern and fix it in the same PR.

## Outcome

Delivered for both CDC processor test classes that used the fixed-delay pattern:

- `tests/Encina.UnitTests/Cdc/Sharding/ShardedCdcProcessorTests.cs` (six tests): every
  `start; Task.Delay(n); cancel; assert` replaced by a `TaskCompletionSource` completed from the substitute call
  the test asserts on, awaited with `.WaitAsync(TimeSpan.FromSeconds(10))` before cancelling.
  `ExecuteAsync_WhenDisabled_ExitsImmediately` drops the wait entirely, since a disabled `ShardedCdcProcessor`
  returns from `ExecuteAsync` before any `await`. The two `DidNotReceive()` tests
  (`ExecuteAsync_PositionTrackingDisabled_DoesNotSavePositions`, `ExecuteAsync_DispatchFailure_IncrementsFailureCount`)
  wait on the dispatcher call they do expect before asserting the negative.
  `ExecuteAsync_LeftValueFromStream_CountsAsFailure` has no substitute call to hook (the dispatcher is never
  invoked for a `Left` stream value), so its `ToShardedAsyncEnumerable` test helper gained an overload that
  completes a `TaskCompletionSource` after it finishes yielding all items - which, because `await foreach`
  fully processes an item before requesting the next, only fires once the consumer has already handled the
  last one. `CreateChangeEvent`'s `DateTime.UtcNow` became a fixed timestamp.
- `tests/Encina.UnitTests/Cdc/CdcProcessorDeadLetterTests.cs` (grep found this sibling file with the identical
  pattern, four tests): `ExecuteAsync_RetriesExhausted_PersistsToDeadLetterStore` waits on a new
  `SignalingDeadLetterStore` decorator around the real `FakeCdcDeadLetterStore` (which is not an NSubstitute
  mock and so has no `.Returns` callback to hook directly). `ExecuteAsync_DlqStoreFails_ContinuesProcessing`
  waits on the failing (NSubstitute) DLQ store's `AddAsync` being invoked. `ExecuteAsync_NoDlqStore_DoesNotThrow`
  waits on a connector-call counter proving the retry-exhaustion path ran and the loop kept going afterward.
  `ExecuteAsync_ProcessorDisabled_DoesNotUseDlq` drops the wait entirely (same disabled-returns-immediately
  reasoning as `CdcProcessor.ExecuteAsync`). The `try { ... } catch (OperationCanceledException) { }` wrapper
  in three of these tests, which only existed to swallow the auto-cancelling `CancellationTokenSource`'s own
  timeout, is gone along with that timeout.

Verification: `dotnet build` of `Encina.UnitTests` clean (0 warnings); the 15 tests across both files passed 10
consecutive `dotnet test --no-build` runs and again under two `dotnet test` processes running concurrently;
`grep`-equivalent search confirmed no `Task.Delay` remains anywhere under `tests/Encina.UnitTests/Cdc/`;
`dotnet format --verify-no-changes` reported no changes for the two changed files.

## Where the knowledge lives

- `tests/Encina.UnitTests/Cdc/Sharding/ShardedCdcProcessorTests.cs` - TCS-based synchronisation for all six
  tests, the completion-signalling `ToShardedAsyncEnumerable` overload, fixed `CapturedAtUtc`.
- `tests/Encina.UnitTests/Cdc/CdcProcessorDeadLetterTests.cs` - TCS-based synchronisation for all four tests,
  the `SignalingDeadLetterStore` decorator, delay dropped for the disabled-processor test.
