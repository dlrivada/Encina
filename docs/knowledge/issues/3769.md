## Asked

First sub-issue of #3518: `GrantConsentAsync` gave every grant a random consent id, so two grants for one tenant, data subject and purpose created two active records and withdrawing one left the other active (GDPR Art. 7(3)). Make the grant create at most one stream per key, atomically, with a deterministic stream id.

## Outcome

`src/Encina.Compliance.Consent/ConsentStreamId.cs` derives the id; `DefaultConsentService.GrantConsentAsync` uses it with the effective tenant and turns `MartenErrorCodes.StreamAlreadyExists` into a re-read that returns the existing consent id. The `ConsentAggregate` remark and the `IConsentService.GrantConsentAsync` XML docs state the one-record-per-key rule and the interim behavior. A Marten/PostgreSQL integration test proves the name-based stream collision detection fires on a real store and that eight concurrent grants of one key create one stream and return one id.

## Known limits

- Until #3771, a withdrawn or expired key cannot be granted again through `GrantConsentAsync`; the call returns the existing id.
- A tenant whose id is the literal `-` shares the "no tenant" key.
- A later write in the same request scope after a repeated grant fails until the Marten session issue (see the gotcha) is fixed.
