## Asked

First sub-issue of #3518: `GrantConsentAsync` gave every grant a random consent id, so two grants for one tenant, data subject and purpose created two active records and withdrawing one left the other active (GDPR Art. 7(3)). Make the grant create at most one stream per key, atomically, with a deterministic stream id.

## Outcome

`src/Encina.Compliance.Consent/ConsentStreamId.cs` derives the id; `DefaultConsentService.GrantConsentAsync` uses it with the effective tenant and turns `MartenErrorCodes.StreamAlreadyExists` into a re-read of the existing stream. At the time of #3769 that branch returned the existing consent id and recorded nothing; #3771 (merged into the same branch) replaced it with the final rules: a renewal event while Active, `ConsentRegranted` from Withdrawn or Expired, and a coded rejection (`consent.reconsent_required`) for an older reconsent version. The `ConsentAggregate` remark and the `IConsentService.GrantConsentAsync` XML docs state the one-record-per-key rule. A Marten/PostgreSQL integration test proves the name-based stream collision detection fires on a real store and that eight concurrent grants of one key create one stream and return one id.

## Known limits

- At the time of #3769 a withdrawn or expired key could not be granted again; #3771 removed that limit (`ConsentRegranted`).
- A tenant whose id is the literal `-` shares the "no tenant" key.
