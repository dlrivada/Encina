## Asked

Run the automatic inbox purge that `InboxOptions` already configures: when `EnableAutomaticPurge` is on, a hosted service removes the processed inbox messages whose retention has passed, so personal data in inbox rows does not stay forever.

## Outcome

Delivered: with `InboxOptions.EnableAutomaticPurge` on (the default), the hosted `MessagePurgeService` runs one cycle shortly after start and then one every `PurgeInterval`. A cycle drains batches of `PurgeBatchSize` until a batch comes back shorter, through `IInboxStore.GetExpiredMessagesAsync`, `RemoveExpiredMessagesAsync` and `SaveChangesAsync` (called after each remove, which EF Core needs). With the flag off nothing is registered or run. A store `Left` or an exception fails that cycle only: it is logged by error code or exception type (EventIds 2107-2111 of `MessagingInbox`), counted in `encina.messaging.purge.cycle_failures_total`, and the next cycle still runs. No-progress guard: when a batch returns only ids that the same cycle already tried to remove in any earlier batch (a store that returns a full batch but deletes nothing, also when it alternates between batches), the cycle stops, logs warning EventId 2112 and returns success; the next interval runs normally and it is not counted as a failure. The setters of `MessageRetentionPeriod`, `PurgeInterval` and `PurgeBatchSize` reject non-positive values.

Not in this issue: Dapper SQL Server and MySQL chunking (#3045), the 10-provider integration tests (#3046), the MongoDB TTL index and the docs pages, including the `Encina.Messaging` README purge section (#3016), the outbox and scheduling purge (#1200).

Size-gate split (15 files / 1500 lines): the `InboxOptions` setter validation, with its `Task.Delay` upper bound for `PurgeInterval`, and its unit and guard tests moved to #3165 and land first; the property and contract tests of the purge cycle moved to #3166 and land after this issue. This issue merges only after #3010 (D6).
