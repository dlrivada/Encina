## Asked

Investigate whether to implement a Strategy + Orchestrator + Provider pattern for Encina's messaging transports (RabbitMQ, Kafka, NATS, AzureServiceBus, AmazonSQS, Redis.PubSub, InMemory, MQTT, plus gRPC/GraphQL as a separate RPC category), given that each transport has fundamentally different semantics (message broker vs. event streaming vs. pub/sub).

## Outcome

Rejected, with reasoning recorded in the issue: no Strategy pattern for transports. Each of the (then 8, now 10) transport packages stays independent, exposing its own native API; the differences between broker/streaming/pub/sub semantics are the reason users choose a specific transport, and unifying the APIs would erase that value. NATS keeps a single package with two explicit modes (Core for pub/sub, JetStream for streaming) rather than being split or forced into one strategy bucket. Instead of code, the issue delivered a documentation-only categorization: `docs/messaging/transports.md` (created in commit `6a72163a`, referenced from the issue as closing its action items), with a transport comparison table, a decision flowchart and per-transport guides, plus updates to `docs/messaging/index.md`. gRPC and GraphQL are explicitly excluded from the messaging-transport categorization as "API Bridge" (RPC), consistent with `AGENTS.md`'s current Transports category, which still lists all 10 as independent packages that "must stay coherent" without a shared strategy interface.

## Where the knowledge lives

- `AGENTS.md` §5 Providers, "Transports (10 + 6 planned)" row — the current rule still matches this decision: transports are independent packages required to share behavioral coherence (Send/Publish, subscription management, DLQ, metadata propagation), not a unified strategy abstraction.
- `docs/messaging/transports.md` — present today (14,986 bytes), still has the decision flowchart (4 mermaid diagrams), the transport categorization table, and the "Testing with InMemory" and API Bridge (gRPC/GraphQL) sections described in the issue. The FAQ ("Should I use a unified messaging interface? No.") is where the rejected Options A/B/C rationale lives today, in condensed form.
- `docs/messaging/index.md` — still links to `transports.md` under "Messaging Transports".
- No ADR exists for this decision (a case-insensitive search of all 32 files under `docs/architecture/adr/` for `IMessageBrokerStrategy`, `IEventStreamingStrategy`, `IMessageTransport`, `Strategy pattern`, `messaging transport` and `#18` found 0 matches; the bare words "transport" and "strategy" do occur in other ADRs on unrelated topics); the issue's own deliverables checklist listed an ADR as optional and none was created, consistent with a documentation-only outcome.
