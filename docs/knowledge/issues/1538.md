## Asked

`DataSubjectRightsHealthCheck.cs:119` embedded the raw `EncinaError.Message` from a failed overdue-request
lookup into the `Degraded` `HealthCheckResult` description, violating `AGENTS.md` §3 ("`EncinaError.Message`
NEVER reaches logs, activity tags, health-check results or plaintext storage"). Found during #1505's
self-review and scoped out of that issue (logger-only). The proposed fix named the same
`error.GetCode().IfNone("encina.unknown")` substitution #1499 used for DPIA's health check, and asked for a
one-pass sweep of every compliance and security package's `*HealthCheck.cs` for the same pattern.

## Outcome

Delivered in three commits on one branch. First, the named fix: `DataSubjectRightsHealthCheck.cs:119` now
uses `error.GetCode().IfNone("encina.unknown")`, with a regression test asserting a sentinel error message
does not appear in the Degraded description. Second, the sweep: a broad `\.Message\b` grep over every
`*HealthCheck.cs` under `src/Encina.Compliance.*` and `src/Encina.Security.*` found 14 more files with the
same pattern, none named in the issue (`Encina.Compliance.AIAct`, `.Attestation`, `.BreachNotification`,
`.ProcessorAgreements`, `.GDPR` (two files), `.NIS2`, `Encina.Security.ABAC`, `.AntiTampering`, `.Audit` (two
files), `.Encryption`, `.PII`, `.Sanitization`, `.Secrets`); `Encina.Compliance.DPIA` (already fixed by #1499)
and `Encina.Compliance.Retention` were re-checked and found clean. A 15th site was missed by that grep
because it leaked the raw exception object, not an interpolated `.Message` string: `ABACHealthCheck.cs`'s
outer PAP-query catch block. Found by adversarial-reviewer during self-review and fixed the same way in a
follow-up commit. All were fixed the same way, plus one
adjacent `_logger.LogWarning` call in `NIS2ComplianceHealthCheck.cs` that shared the exact same violation in
the same catch block. Third, one regression test per health check changed (two new test files for
`AttestationHealthCheck` and the two `Encina.Security.Audit` checks, which had none before), each with a
sentinel value proven not to leak into the result's description, data or (where applicable) the `Exception`
object.

The CRAP gate, reproduced locally, flagged 7 pre-existing high-complexity `CheckHealthAsync` methods once
this diff touched a line inside each. Only one (`EncryptionHealthCheck`, complexity=10) was mathematically
fixable by adding coverage; five new tests brought it to 100% coverage and CRAP=10. The other 6
(complexity 12-20) cannot reach CRAP<=10 at any coverage level — `CRAP = comp^2 x (1-cov)^3 + comp` bottoms
out at `comp` itself when coverage is 100%, and `comp` alone already exceeds 10 for all six. This is the
documented CRAP-gate attribution limit (AGENTS.md, "Known attribution limits: #1355, #1360"): a text-only
edit inside a large pre-existing method is attributed the method's whole complexity score. Reducing these six
methods' complexity is a design-level refactor left for a follow-up issue, not attempted here.
