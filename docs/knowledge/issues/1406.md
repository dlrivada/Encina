## Asked

PR #1399 (#1333) split `AddMessagingServices` and `AddOutboxInboxSagaSchedulingServices` in `src/Encina.Messaging/MessagingServiceCollectionExtensions.cs` into small per-pattern `Register*` helpers to pass the CRAP gate, but `AddMessagingServicesCore` in the same file - used by the ADO.NET tenancy extensions - kept its own inline copy of the same conditional registration blocks, so the two registration paths could drift again, which is the exact defect class #1333 fixed.

## Outcome

Delivered: `AddMessagingServicesCore` now calls `RegisterTransactions`, `RegisterOutbox<...>`, `RegisterInbox<...>`, `RegisterRoutingSlips`, `RegisterRecoverability`, `RegisterContentRouter`, `RegisterScatterGather` and `RegisterSoftDeleteServices` - the same helpers `AddMessagingServices` calls - instead of its own inline blocks. The outer `MessagingConfiguration` flag checks that used to guard each inline block are gone, since every helper already checks its own flag first. The method's cyclomatic complexity dropped from 10 (nine decision points: eight pattern flags plus one nested `EnableDelayedRetries` check, McCabe formula) to 1 (a straight sequence of calls, no branching left in the method body itself; the decision points now live inside the already-tested helpers). A new equivalence test snapshots the exact `ServiceDescriptor` set (service type, implementation type, lifetime) produced with all patterns on and with all patterns off, pinned to the pre-refactor values, and passes unchanged after the refactor - proving no behavior change for the ADO.NET tenancy extensions or any other caller.

## Where the knowledge lives

- `src/Encina.Messaging/MessagingServiceCollectionExtensions.cs` - `AddMessagingServicesCore` now shares every per-pattern helper with `AddMessagingServices`.
- `tests/Encina.UnitTests/Messaging/MessagingServiceCollectionExtensionsCoreEquivalenceTests.cs` - the registration-equivalence regression test with the pinned pre-refactor snapshots.
