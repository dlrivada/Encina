## Asked

`LawfulBasisValidationPipelineBehavior` (`Encina.Compliance.LawfulBasis`) resolved the data subject id
via `ILawfulBasisSubjectIdExtractor` and passed it directly into three structured log calls
(`ConsentCheckStarted`, `ConsentCheckPassed`, `ConsentCheckFailed`) on every consent-based lawful-basis
check, and additionally passed the raw `EncinaError.Message` from `IConsentStatusProvider`'s error
branch into `ConsentCheckFailed`'s `Reason` parameter. Same defect class as #1314
(`Encina.Compliance.Consent`), #1415/#1429 (`Encina.Compliance.DataSubjectRights`,
`Encina.Marten.GDPR`) and #1426 (`GDPRErrors.ConsentNotFound`'s details dictionary), this time in the
structured-logging path of a fourth package/call site. Found by an `adversarial-reviewer` while
reviewing #1426's fix.

## Outcome

Delivered: no `LawfulBasisValidationPipelineBehavior` log line carries the raw data subject id or a
raw `EncinaError.Message`. `ConsentCheckStarted`/`ConsentCheckPassed`/`ConsentCheckFailed` had
`subjectId` removed from both the message template and the method signature in
`Encina.Compliance.LawfulBasis.Diagnostics.LawfulBasisLogMessages` (the file actually invoked, EventIds
8353-8355) and, for consistency, in the unreferenced duplicate
`Encina.Compliance.GDPR.Diagnostics.LawfulBasisLogMessages` (EventIds 8120-8133) discovered to be dead
code during the fix. `providerError.Message` (`ConsentCheckFailed`), `error.Message`
(`LIACheckFailed`), and `error.Message` (`EnforcementWarning` in `ApplyEnforcement`) were all replaced
with `error.GetCode().IfNone("encina.unknown")`. A new unit test file,
`LawfulBasisSubjectIdLeakTests.cs`, attaches a `FakeLogger` and a scoped `ActivityListener` and proves a
sentinel subject id and two sentinel `EncinaError` messages never appear in captured logs or activity
tags across the valid-consent, no-consent, provider-error, unresolved-subject-id, LIA-service-error
(block and warn mode) paths. All EventIds were kept unchanged; the architecture EventId-allocation test
stays green. A sibling leak in `LawfulBasisHealthCheck.cs` (raw `EncinaError.Message` in health-check
warning strings, a different channel this issue did not name) was found but left out of scope and
written up as a follow-up issue.
