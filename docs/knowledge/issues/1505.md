## Asked

The mandated sweep after #1503 (which fixed the same `EncinaError.Message`/exception-`Message`-reaches-logger
pattern in `Encina.Compliance.DPIA`) found the pattern widespread in its two sibling packages,
`Encina.Compliance.DataSubjectRights` and `Encina.Compliance.Retention`: the same
wrap-`error.Message`-in-`new InvalidOperationException`-just-to-log-it anti-pattern #1503 fixed in DPIA's
auto-registration service, plus many direct `error.Message`/`ex.Message` logger arguments. `AGENTS.md` §3:
"`EncinaError.Message` NEVER reaches logs, activity tags, health-check results or plaintext storage; record
only the error code or the exception type" (why: #1168, #1173, #1259, #1274). #1505's own Location section
named 24 call sites and suggested splitting the fix by package given the likely size.

## Outcome

Delivered in one PR covering both packages (not split, since the mechanical substitution is identical in
both): every logger call in `Encina.Compliance.DataSubjectRights` and `Encina.Compliance.Retention` that
received `EncinaError.Message` or a caught exception's `Message` now logs
`error.GetCode().IfNone("encina.unknown")` or `ex.GetType().Name` instead. A full re-grep beyond the issue's
24 listed sites found roughly twice as many actual call sites once sinks reached via a cast expression
(`((EncinaError)result).Message`) and a shared `string? failure` local were counted; all were fixed to match
acceptance criterion 1 (`Select-String` over both packages' `src` for a logger call receiving `.Message`
returns empty). Two new logger overloads (`RetentionEnforcementCycleFailed(string)`,
`RetentionAutoRegistrationPolicyFailed(string, string)`) replace the `InvalidOperationException`-wrapping
anti-pattern, at EventIds 8595/8596 inside Retention's already-registered 8500-8599 range. One regression
test per distinct logger method was added (`DSRLoggerErrorMessageLeakTests.cs`,
`RetentionLoggerErrorMessageLeakTests.cs`, plus one existing `RetentionEnforcementServiceTests.cs` test
updated), each verified to fail against the pre-fix code (the sentinel string used to leak into the log
record) and pass against the fix, with the full DSR+Retention unit suite (959 tests) green twice in a row.

The logging fix pushed four Retention methods over the CRAP<=10 gate (`RetentionValidationPipelineBehavior.
TrackRetentionRecordAsync`, `RetentionEnforcementService.ProcessRecordAsync`, `DefaultLegalHoldService.
ReleaseRecordsAsync` and `.CascadeHoldToRecordsAsync`, up to complexity=24); these were fixed with
behaviour-preserving extract-method refactors in a follow-up commit on the same branch, bringing the local
gate to 0 violations (see the decision above). One finding was scoped out during self-review and written up
as follow-up material rather than fixed here: a second AGENTS.md sink — `EncinaError.Message` reaching a
health-check result, not a logger — still present at `DataSubjectRightsHealthCheck.cs:119`, outside this
issue's logger-only scope.
