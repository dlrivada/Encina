## Asked

Issue #1552's `-Resume` switch was meant to save a local-model call for every ranked issue whose
body had not changed since the last `-All` run, but its implementation (`score-issues.ps1` lines
253-258 at the time) did a shallow property copy of the *entire* previous `scores.json` entry for a
matching body hash, including fields that depend on the current repository state rather than the
issue body: title, milestone, dependency-derived flags and the `unblocking` score, the milestone
`fit` score, and the `age` score. A real run against 53 issues that had just been assigned
milestones showed all 53 still flagged `needs-milestone` and PR #1558's dependency-parser fixes
never reaching resumed issues, because the whole stale entry — not just its model-judged scores —
was carried forward untouched.

## Outcome

Complete: `New-ScoredEntry` (`tools/ai/priority/score-issues.ps1`) now takes an optional
`$PreviousJudged` argument instead of the `-All` loop performing its own shallow copy. On a body-
hash match with a previous non-`unscored` entry, only the five model-judged criteria (importance,
regulatory, transversality, method, and effort when its previous source was `model`) are reused,
each with its own `why`/`source`; title, milestone, flags, `unblocking`, `fit`, `age`, the effort
checkbox and overrides are always recomputed from the fresh issue record on every run, resumed or
not. A new `judgedAtUtc` field records when the judged scores were last actually produced by the
model, separate from `scoredAtUtc`, which is always stamped fresh. Three new self-test cases in
`Test-Priority.ps1` (now 85 cases) dot-source `score-issues.ps1` directly — safe because the script
now detects a dot-sourced invocation (`$MyInvocation.InvocationName -eq '.'`) and returns before its
`-All`/`-Issue` body runs, so no `gh` call, `collect-issues.ps1` refresh, or local-model call ever
happens in the test — and confirm: a fresh milestone/dependents/title win over a stale previous
entry while the previous judged scores and why are carried forward; a now-ticked effort checkbox
overrides a previously model-judged effort score; and a maintainer override still applies on top of
a resumed entry. All three cases fail against origin/main's `New-ScoredEntry` (it has no
`-PreviousJudged` parameter at all, so calling it that way throws a parameter-binding error),
confirming the tests exercise the fix rather than passing coincidentally. A second, unrelated defect
surfaced while building the fix: `ConvertFrom-Json` silently parses an ISO-8601-looking string
property into a `[datetime]`, which corrupted the new `judgedAtUtc` field's formatting on
round-trip; fixed by re-formatting explicitly through `[datetime]` rather than casting straight to
`[string]`.

## Where the knowledge lives

- `tools/ai/priority/score-issues.ps1` — `New-ScoredEntry`'s `$PreviousJudged` parameter and its
  per-criterion reuse-vs-recompute logic; the dot-source guard (`$MyInvocation.InvocationName -eq
  '.'`) right after `$overrides = Get-PriorityOverrides`; the `-All` loop passing
  `$previousJudged` instead of copying the previous entry.
- `tools/ai/priority/Test-Priority.ps1` — the three new `New-ScoredEntry -Resume` self-test cases
  (fresh milestone/dependents/title with reused judged scores; a newly ticked effort checkbox
  winning over a previously judged effort; an override re-applied on top of a resumed entry).
- `docs/knowledge/issues/1552.md` — the original `-Resume` feature record this issue corrects; its
  decision item for `score-issues.ps1`'s two modes on one shared scoring path still holds, amended
  by this record's narrower fix to what `-Resume` actually carries forward.
