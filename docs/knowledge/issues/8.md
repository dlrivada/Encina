## Asked

The issue requested fixing four failing FsCheck property tests in `Encina.Dapper.Sqlite.PropertyTests` that failed with `SqliteException: no such table` in `TransactionPipelineBehaviorPropertyTests` and `ScheduledMessageStoreDapperPropertyTests`.

## Outcome

Closed directly by commit `062b705e` (2025-12-23), no pull request. The fix added defensive `CREATE TABLE IF NOT EXISTS`, made schema cleanup tolerate missing tables, skipped two test cases that could not pass on SQLite (connection-close semantics, DateTime format), corrected one test's invalid past-reschedule assumption, and disabled test parallelization for the SQLite collection.

## Where the knowledge lives

- The three SQLite gotchas and the parallelization rule have no destination: every file the fix touched (`Encina.Dapper.Sqlite.PropertyTests`, `Encina.TestInfrastructure/Schemas/SqliteSchema.cs`) was deleted by commit `22494a97` when ADR-024 removed the SQLite provider from 1.0 scope, and ADR-024 already records the shared-connection, DateTime-format and single-writer burdens as removal rationale.
- The one still-current fact the fix exposed (reschedule-to-past throws) is enforced in `src/Encina.Dapper.SqlServer/Scheduling/ScheduledMessageStoreDapper.cs` (`RescheduleRecurringMessageAsync`, the `NextScheduledDateCannotBeInPast` check) and in the PostgreSQL and MySQL siblings, and guard-tested in `tests/Encina.GuardTests/Dapper/SqlServer/ScheduledMessageStoreDapperGuardTests.cs`.

## Audit

Verdict `code-removed` (ADR-024): the code this issue touched no longer exists in `src/` or `tests/`; per SPEC-003 §5.1 it is recorded and not further audited.
