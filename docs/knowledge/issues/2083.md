## Asked

A request that failed transiently started a new delayed-retry chain on every delayed re-dispatch, because the re-dispatch ran through the recoverability behavior like a first-time failure. Chains multiplied and the permanent-failure path could run more than once under different ids.

## Outcome

The processor re-dispatches under an internal marker; the behavior returns the result to the processor without scheduling or failing permanently. The processor restores the original context id, ends the chain on a permanent error, and no longer reports success when scheduling the next attempt fails.

## Where the knowledge lives

- `src/Encina.Messaging/Recoverability/DelayedRetryRedispatch.cs` — the marker and why it cannot be set by application code.
- `src/Encina.Messaging/Recoverability/DelayedRetryProcessor.cs` — the single decision point of the chain.
- `tests/Encina.UnitTests/Messaging/Recoverability/DelayedRetryChainTests.cs` — the chain invariant. Integration is justified as not applicable: no persistent `IDelayedRetryStore` exists yet (#594).
