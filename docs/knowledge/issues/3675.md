## Asked

Part of #3617: the three Dapper `TenantConnectionFactory` classes called `ITenantProvider.GetCurrentTenantAsync`, which returns `null` both for no tenant and for an unknown tenant, and then fell through to the default connection string. They must fail closed with the coded errors of `TenancyErrors` (#3673).

## Outcome

`GetConnectionStringAsync` (and so `CreateConnectionAsync`) in `src/Encina.Dapper.{SqlServer,PostgreSQL,MySQL}/Tenancy/TenantConnectionFactory.cs` reads the tenant id first: a blank id returns `tenancy.tenant_required` while `RequireTenant` is true and the default connection only when it is false; a present id the store does not know returns `tenancy.tenant_not_found`. `CreateConnectionForTenantAsync` returns the same `tenant_not_found` error. Unit tests per provider, one guard test class for the three factories, and integration tests in the shared `Dapper-SqlServer`, `Dapper-PostgreSQL` and `Dapper-MySQL` collections pin the behavior against real databases.

## Where the knowledge lives

- `src/Encina.Dapper.SqlServer/Tenancy/TenantConnectionFactory.cs` (and its PostgreSQL and MySQL siblings) — the fail-closed resolution.
- `tests/Encina.UnitTests/Dapper/*/Tenancy/TenantConnectionFactoryTests.cs` — the behavior, pinned per provider.
- `tests/Encina.IntegrationTests/Dapper/*/Tenancy/TenantConnectionFactoryIntegrationTests.cs` — unknown tenant, missing tenant, `RequireTenant = false` and a known database-per-tenant tenant against real databases.

## Known limits

- A known `DatabasePerTenant` tenant without a connection string still gets the default database (#3686).
- The factories do not log the denial; they have no logger (#3757).
- `AddEncinaDapperWithTenancy` resolves the scoped `IDbConnection` through `CreateConnectionAsync` and throws on a `Left`, so a scope without a tenant now fails when it resolves `IDbConnection` while `RequireTenant` is true.
