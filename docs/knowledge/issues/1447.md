## Asked

Add a `pr-reviewer` Claude Code agent that performs a CodeRabbit-style review of an already-published pull
request — its diff, its linked issue's acceptance criteria, and the repository's own rules (`AGENTS.md`,
`CLAUDE.md`, the `path_instructions` of `.coderabbit.yaml`) — and posts the result as a GitHub PR review, as
a fallback for when CodeRabbit is rate-limited or unavailable (observed continuously since 2026-09-26). It
must be read-only on the repository except its own report, spawn only `Explore`, and never publish to GitHub
itself, so it cannot conflict with the pre-push `adversarial-reviewer` or with the publishing hooks. This is
Phase 1 of epic #1453 (Fallback system for external review bots).

## Outcome

Delivered: `.claude/agents/pr-reviewer.md` (Sonnet/high, Opus by orchestrator exception) and
`.claude/agents/lessons/pr-reviewer.md`; wired into `block-worker-spawn.ps1` (`Explore` only),
`block-worker-publish.ps1`, `enforce-path-ownership.ps1` (`artifacts/pr-review/**` only) and
`no-background-specialists.ps1`; `.claude/agents/README.md`'s roster, delegation and hooks tables updated;
`.claude/hooks/tests/Test-Hooks.ps1` gained regression cases for the spawn allowlist, path ownership and
foreground-only rule (727 cases total, 0 failed, run from the worktree per #1368); the `pr-cycle` skill's
CodeRabbit-rate-limited row now triggers `pr-reviewer` instead of `adversarial-reviewer`, while the separate
gates/CI/`.github/scripts` trigger for `adversarial-reviewer` is unchanged; `docs/engineering/ai-task-routing.md`
and `docs/engineering/AI-DEVELOPMENT-MODEL.md` (item 15) were synced by `docs-writer`.

Acceptance evidence (Phase 6): the agent could not yet be spawned as a live subagent from this worktree,
because the `block-worker-spawn.ps1 -Agent orchestrator` allowlist change is loaded by Claude Code from the
**main checkout** once per session (per `.claude/agents/README.md`, "Limits": *"Claude Code loads every hook
from the main checkout... so a hook fixed on a branch governs nothing until that branch merges"*), so it is
not live until this branch merges. Instead, the implementing `issue-worker` manually followed the
`pr-reviewer` agent definition step by step as a dry run against two already-merged, CodeRabbit-reviewed PRs
and wrote the review artifacts in the exact output contract the agent specifies.

### Comparison vs. CodeRabbit

**PR #1397** (`fix(security): log the error code instead of EncinaError.Message in EF Core, Marten and
GraphQL`, closes #1328) — dry-run artifact: `artifacts/pr-review/1397.md`.

| Finding | Dry-run `pr-reviewer` said | CodeRabbit said | Agreement |
|---|---|---|---|
| Are all 5+1 call sites fixed to log only the error code? | Yes, verified file:line for each; verdict **merge** | Implicit pass — "No actionable comments were generated in the recent review. 🎉" | Same conclusion |
| Docstring coverage | Not checked (out of scope: only public APIs get XML docs per `AGENTS.md` §8, and this diff touches only private/internal members) | Flagged as a pre-merge **warning**: "Docstring Coverage is 18.42%... insufficient" | Different — CodeRabbit's docstring check is broader (counts non-public members too); noted as a lesson to consider for `pr-reviewer`'s method |
| Remaining `error.Message` uses (thrown exception, returned `EncinaError`) | Flagged as a **minor**, confirmed intentional per the PR description (ROP boundary) | Not mentioned (review found nothing actionable at all) | `pr-reviewer` found one confirmatory minor CodeRabbit did not surface |
| Linked-issue acceptance criteria | All 6 criteria checked individually against file:line evidence, all **met** | Its "Linked Issues check" pre-merge item passed with a one-line summary, no per-criterion breakdown | `pr-reviewer`'s output is more granular |

**PR #1399** (`fix(messaging): register EF Core and MongoDB messaging patterns through the shared helper`,
closes #1333) — dry-run artifact: `artifacts/pr-review/1399.md`.

| Finding | Dry-run `pr-reviewer` said | CodeRabbit said | Agreement |
|---|---|---|---|
| Did CodeRabbit review this PR at all? | N/A (this is the trigger condition) | **No** — only the standing "fewer than 10 stars, no automatic review" notice, confirmed by the maintainer's own PR comment: "CodeRabbit is rate-limited; the adversarial reviews stand in for it (pr-cycle)." | This is the exact gap `pr-reviewer` exists to fill |
| Are the 3 linked-issue acceptance criteria met? | All 3 checked individually against file:line/test evidence, all **met** | Not available | N/A — no CodeRabbit baseline to compare |
| CRAP figure claim ("cyclomatic complexity of about 6") | Marked explicitly **not verified** (the gate script was not run) rather than accepted on trust | Not available | N/A |
| Follow-up #1406 (duplicated blocks) and #1398 (ADO/Dapper DI test gap) | Carried over from the PR's own self-reported history, explicitly not claimed as independently found | Not available | N/A |

### Observations for the #1452 trial

- On a PR CodeRabbit *did* review (#1397), the dry run reached the same "nothing actionable" conclusion
  independently, plus one confirmatory minor CodeRabbit's summary did not call out, and a more granular
  per-acceptance-criterion table.
- On a PR CodeRabbit *did not* review at all (#1399, due to the "fewer than 10 stars" gate combined with the
  broader rate-limiting), the dry run produced the only PR-level review that exists for it — this is the
  strongest single piece of evidence that the fallback path has real value, not just parity.
- The dry run's own verification discipline (marking one claim "not verified" rather than repeating it as
  fact) matches `adversarial-reviewer`'s existing standard and should be preserved when the agent runs live.
- CodeRabbit's docstring-coverage pre-merge check has no `pr-reviewer` equivalent; whether to add one is left
  for a future issue, not decided here.
