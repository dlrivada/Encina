## Asked

Second sub-issue of #3518. `GrantConsentAsync` on a key that already has a consent stream must follow the maintainer decisions of 2026-11-12 (D4, D5) instead of the interim "return the existing id" seam of #3769: a renewal while Active, an explicit regrant from Withdrawn or Expired, reconsent only with the current version, and ordering by the act's own timestamp.

## Outcome

- `ConsentAggregate` gained `RenewByGrant`, `Regrant` and the `LastActAtUtc` watermark.
- `ConsentEvents.cs` gained `ConsentRenewedByGrant` and `ConsentRegranted`.
- `ConsentProjection` and `ConsentReadModel` apply the same ordering rule as the aggregate.
- `DefaultConsentService.RecordGrantOnExistingAsync` replaces the interim seam. Concurrency conflicts get bounded retries and the cache is invalidated after the save.
- `ConsentErrors.ReconsentRequired` rejects an older version on a consent that requires reconsent.
- `GrantConsentAsync` has an optional `occurredAtUtc` parameter.

Unit tests cover every branch, and a seeded property test checks that the aggregate and the projection agree. The Marten/PostgreSQL integration tests prove four cases:

- a repeat followed by a withdrawal in the same scope;
- a regrant after a withdrawal makes the key valid again;
- a late act after a withdrawal leaves the key withdrawn;
- concurrent first grants and concurrent regrants.

## Known limits

- An unsynchronised client clock can order acts inconsistently; Encina cannot detect or correct it.
- More than five concurrent writes on one key can return `marten.concurrency_conflict` to a caller.
- The minor rule (#1255) and channel/basis checks (#1199) still have to be added to the existing-stream path when they land.
- The inline projection of concurrent saves on one stream is not covered by these tests; the concurrent integration tests assert on the event stream.
