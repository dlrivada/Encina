## Asked

`audit-stage-guard.ps1` only allowed re-spawning a stage agent out of the normal fixed order when the last
`stages/verification.md` verdict was `FAIL`, with no notion of commit order. When a remediation (or any
earlier) stage was re-committed AFTER a PASS verdict -- as happened on audit #18 on 2026-09-28, when 7
remediation drafts were regenerated after the verifier's pass-2 PASS to apply the #1535 fix -- that PASS
became logically stale (the verifier never inspected the new content), but the guard still refused to
re-spawn `audit-verifier`, while `audit-done.ps1` would have let the orchestrator close the audit anyway,
publishing the unverified drafts.

## Outcome

Delivered: staleness is derived purely from git history, with a single shared helper
(`Get-StaleStageAfterVerification`, `tools/ai/audit/_audit-lib.ps1`) comparing the verifier stage artifact's
own newest commit against every other stage's newest commit -- no marker file, no new state, and a tied
commit second does not count as stale. `audit-stage-guard.ps1` gets the same logic inlined (matching its
existing `Test-StageCommitted` precedent, so the hook keeps no dependency beyond `pipeline.json`) and now
allows re-spawning `audit-verifier` when this condition holds, while every other out-of-order stage agent
still stays blocked under a PASS verdict. `audit-done.ps1` calls the shared helper directly and refuses to
close the audit while it is stale, naming the stale stage and telling the operator to re-run
`audit-verifier`. The `issue-audit` skill's FAIL-loop section gained one sentence describing this case.
