## Asked

`docs.yml`, the single Pages deployer since #1381, fetched the live dashboard data at the start of its build and
deployed it about fifteen minutes later, so a deploy landing in between was reverted (lost update). The `pages`
concurrency group also keeps a single pending deploy, and a newer one cancels it, so a publisher's data overlay could
be dropped with a cancelled deploy. The issue asked that dashboard data on Pages always reflect the latest successful
computation of every dashboard.

## Outcome

Delivered. The diagnosis of the 2026-09-27 instance confirmed the lost-update race: two docs pushes whose builds
fetched the data before Publish Mutations Data run 36323680322 deployed re-published the April mutation data after
it. `docs.yml` now builds the site without the dashboard data and assembles the data inside the `pages` lock in the
deploy job, and every publisher persists its data to the orphan branch `dashboard-data` before asking for a deploy, so
neither a concurrent deploy nor a cancelled pending one can lose dashboard data (the docs content of a cancelled docs
deploy is republished by the next docs run). Publishers also read their base files (history, the previous latest) from
that branch before the live site, so a lagging live copy cannot be persisted over newer data (#1567). The overlay
artifacts and the `overlay-artifact` input of `docs.yml` are gone. After the merge, seed the branch by dispatching
Publish Mutations Data for Mutation Tests run 36959365309; never re-publish run 36311960256, whose data is older than
the live data published on 2026-10-02.
