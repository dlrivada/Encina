## Asked

`crap-gate.cs` (the CRAP/Change Risk Anti-Patterns gate that blocks a PR touching `src/` when a changed
method's `CRAP = comp^2 * (1-cov)^3 + comp` exceeds 10) attributed a changed diff line to a Cobertura method by
a numeric range check: `l >= m.MinLine && l <= m.MaxLine`, where `MinLine`/`MaxLine` are just the min/max of
that method's own recorded `<line number>` entries. Because a lambda passed to a helper (e.g.
`Either<TL,TR>.Match(Right: ..., Left: error => { ... })`) is compiled to a separate method on a
compiler-generated closure class, but sits textually inside its enclosing method's source span, the enclosing
async state machine's own range still numerically covered the lambda's lines even though the state machine's
own `Lines` set never recorded them. Issue #1503 hit this concretely: fixing two lines inside a `Left:` lambda
in `DPIARequiredPipelineBehavior.Handle` and one line inside a `Left:` lambda in
`DPIAAutoRegistrationHostedService.StartAsync` flagged both the actual (small, well-covered) lambda methods and
the unrelated, untouched, much larger enclosing `MoveNext` state machines as CRAP violations.

## Outcome

Delivered: the attribution check now uses exact membership in a method's own recorded `Lines` dictionary
first, falling back to the old `MinLine..MaxLine` range check -- and then only the innermost (smallest-range)
match -- solely for a changed line no method records at all (a declaration/signature line with no sequence
point). Verified against the real #1503 reproduction (unit-test coverage for `Encina.Compliance.DPIA` collected
fresh, plus that PR's actual diff): the old gate reproduced both false positives exactly
(`<Handle>d__6.MoveNext` CRAP 18.00, `<StartAsync>d__5.MoveNext` CRAP 36.74); the new gate reports neither, and
instead the lambda methods' own real CRAP (`<Handle>b__2` CRAP 10.00, `<StartAsync>b__3` CRAP 1.00) shows up
only when `--threshold 0` makes every touched method visible, confirming they are correctly attributed but not
violations at the default threshold. A true positive (a changed line genuinely inside a large, poorly-covered
method's own body, not a lambda) is still caught, proven with a synthetic fixture. The merged PR #1500's real
diff, re-run with full per-flag coverage (unit, guard, contract, property) collected fresh, still passes under
both the old and the new gate, confirming no regression on a diff the gate already accepted. A 4th self-test
assertion and a `SampleLambda.*` fixture set under `.github/scripts/testdata/crap-gate/` now guard this exact
scenario going forward, after an adversarial review of the first commit found the issue's own "add a
regression test" step had been skipped.
