## Asked

Make `AesGcmFieldEncryptor` return `Left(EncryptionErrors.InvalidCiphertext())` for a stored value with a wrong-sized nonce or tag, instead of letting `AesGcm` throw `ArgumentException` through the `Either` API.

## Outcome

`ValidateEncryptedValue` now calls a private `HasValidNonceAndTagLength` helper that requires a 12-byte nonce and a 16-byte tag (default and empty still invalid). Unit tests cover nonce lengths 5, 11 and 13 and tag lengths 15 and 17 through both `DecryptStringAsync` and `DecryptBytesAsync`.

Follow-up round (decision D9 applied completely): the `CryptographicException` catch in `DecryptWithKey` now also returns the parameterless `EncryptionErrors.InvalidCiphertext()` instead of `EncryptionErrors.DecryptionFailed(keyId, exception)`. One unit test asserts that nonce, tag, flipped-tag, flipped-ciphertext and wrong-key failures, through both decrypt methods, return the identical code, message and details with no `keyId` and no cause. `EncryptionErrors.DecryptionFailed` is kept: its only remaining use is the `CryptographicException` catch of `EncryptCoreAsync` (a mislabelled encryption failure; a follow-up issue draft proposes `EncryptionFailed` for it).

## Where the knowledge lives

- `src/Encina.Security.Encryption/Algorithms/AesGcmFieldEncryptor.cs` — the length check before `AesGcm.Decrypt`.
