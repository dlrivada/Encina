## Findings
1. **Major** — The rejection recorded for #48 is contradicted by three open issues, none of which cites it. #48's close comment (2025-12-26) says that with .NET 10 native OpenAPI (OpenAPI 3.1, document transformers, YAML) "Encina no aportaría valor significativo" and that a package that wraps native functionality is not worth its maintenance. Open #446 (created 2025-12-28, 0 comments, milestone "Post-1.0: Web Advanced & Developer Experience", labels `p2-post-1.0`, `status:proposal`) proposes the same `Encina.OpenApi` package with `AddEncinaOpenApi` and `MapEncinaEndpoints`, and its References link to the ASP.NET Core OpenAPI page without saying why a package is still needed. Open #198 (milestone "Post-1.0: Web APIs & Source Generators", `p2-post-1.0`, 0 comments) also lists "Other: `Encina.OpenApi`" under Affected Packages and proposes `services.AddEncinaOpenApi(config => ...)` with `AddDocumentTransformer<EncinaErrorsDocumentTransformer>()`; the native document transformers are the exact reason #48 gave for closing. Epic #889 (v0.20.0, open) lists "OpenAPI 3.1 enhanced schema and SDK generation (#198, #446)" and orders #446 after #198, so the two overlap each other and #889 does not mention #48. `docs/engineering/PROJECT-HISTORY.md:530` records the rejection as a settled alternative while the backlog plans the opposite, and no ADR exists for either side (Grep `OpenApi|OpenAPI` over `docs/architecture/adr/*.md`, per archivist.md). Checks failed: AUD checklist item on consistency of a closed decision with the open backlog; AGENTS.md §8 (architectural decisions get an ADR); known failure pattern "re-proposal after a rejection". Nature of the conflict: #48's reason is "a wrapper adds no value", while #198 and #446 name Encina-specific value (schemas for `Either<EncinaError,T>` handlers, documentation of EncinaError error responses, FluentValidation-to-OpenAPI constraints, endpoint generation) that `Microsoft.AspNetCore.OpenApi` does not provide on its own; whether that value justifies a package is a design choice for the maintainer, so the options stay open: (a) keep the rejection, close or narrow #446 and #198 to what native transformers cannot do, (b) supersede the rejection with an ADR that states the added value, (c) a thin transformer set inside `Encina.AspNetCore` instead of a new package. The current trigger is not release-blocking (both issues are `p2-post-1.0`), which is why this is Major and not Blocker.
2. **Minor** — Live planning documents present `Encina.OpenApi` as planned with no mention of the rejection. `ROADMAP.md:647` ("OpenAPI Integration #446 — `Encina.OpenApi` auto-generation from Commands/Queries") and `ROADMAP.md:650` ("New packages planned: ... `Encina.OpenApi`") sit in the "Developer Tooling & DX" list (`ROADMAP.md:638`) under the heading "Legacy Phase 2 Details (Completed Items)" (`ROADMAP.md:320`; no heading between `:320` and `:647`), not in the v0.18.0 Developer Experience block (`ROADMAP.md:289-301`), whose only OpenAPI line is `ROADMAP.md:295` ("OpenAPI/Swagger integration", no package named); `ROADMAP.md:86` lists OpenAPI in the v0.18.0 row, and `ROADMAP.md:662` ("OpenAPI 3.1 Enhanced #198") is in the "Web/API Integration" list (`ROADMAP.md:652`), under the same "Legacy Phase 2 Details (Completed Items)" heading (`ROADMAP.md:320`). `docs/INVENTORY.md:2833` and `:5084` (the #198 "OpenAPI 3.1 Enhanced" rows, under "Mejoras Planificadas (Phase 2)" `:2820` and "Web/API Patterns - Nuevas Issues" `:5071`) list the same planned work without the rejection, and a search for `Encina.OpenApi` does not find them. `docs/INVENTORY.md:6714-6726, :6753, :7423` repeat it with `builder.Services.AddEncinaOpenApi(); app.MapEncinaEndpoints();` as the target API (INVENTORY states it was generated 2026-02-02, `INVENTORY.md:3`). A reader of the ROADMAP cannot learn that #48 rejected the same package, and PROJECT-HISTORY.md:530 states the opposite.
