## Findings
1. **Minor** — `tests/Encina.UnitTests/Messaging/Health/SagaHealthCheckTests.cs` and `SchedulingHealthCheckTests.cs` duplicate regions of `HealthChecksTests.cs`, so one behaviour is pinned in two or three places. Saga: the constructor null guard is at `SagaHealthCheckTests.cs:14`, `HealthChecksTests.cs:530` and `tests/Encina.GuardTests/Messaging/Health/HealthChecksGuardTests.cs:183`; the healthy, warning and critical scenarios are at `SagaHealthCheckTests.cs:20, :55, :76` and `HealthChecksTests.cs:537, :556, :581`. Scheduling: the null guard is at `SchedulingHealthCheckTests.cs:14`, `HealthChecksTests.cs:611` and `HealthChecksGuardTests.cs:171`; healthy, warning and critical are at `SchedulingHealthCheckTests.cs:44, :81, :57` and `HealthChecksTests.cs:618, :635, :664`. The Outbox and Inbox checks exist only in `HealthChecksTests.cs`, so the folder has two conventions. The duplication matters now because the Saga counting rule is wrong (the code stage's finding 2) and its fix has to rewrite `SagaHealthCheckTests.cs:76` and `HealthChecksTests.cs:581` together, and the Scheduling fix `SchedulingHealthCheckTests.cs:57, :81` and `HealthChecksTests.cs:635, :664`. Proposed: keep one test class per check (`SagaHealthCheckTests`, `SchedulingHealthCheckTests`), move the Outbox, Inbox and DatabaseHealthCheck regions of `HealthChecksTests.cs` into their own classes, delete the duplicated scenarios, and keep the constructor null guard in the guard project (`HealthChecksGuardTests.cs:171, :183`) only. The guard flag of these two checks (2/40 and 2/43 lines) is carried by those guard-project tests alone, so the deletions must be limited to the unit-project copies; the remediation measures the unit and guard flags of both files with only the surviving tests before it deletes anything (lesson #20: the "redundant" files were once the only source of a flag).
2. **Minor** — the Scheduling check's tests read the wall clock and never use the `TimeProvider` the class exposes for that purpose. `SchedulingHealthCheck.cs:34` accepts `TimeProvider? timeProvider` ("for testability") and `:65` computes `now` from it, yet every test builds the check without one: `SchedulingHealthCheckTests.cs:66, :90` and `HealthChecksTests.cs:642, :671, :700` create `ScheduledAtUtc` values from `DateTime.UtcNow` and rely on a 10-30 minute margin against the tolerance. No test passes a `FakeTimeProvider`, and `HealthCheckBuilderExtensionsTests.cs:463` (`AddEncinaScheduling_WithOptions_PassesOptionsToHealthCheck`) runs the registered check on the system clock, so nothing would fail if the registration kept ignoring the container's `TimeProvider` (the code stage's finding 3: `HealthCheckBuilderExtensions.cs:222` builds `new SchedulingHealthCheck(store, options)`). `AGENTS.md` section 9 asks for deterministic tests and section 3 for `TimeProvider`. Proposed: build the fixtures from a `FakeTimeProvider` passed to the constructor (a message due exactly at, just before and just after `OverdueTolerance`), and add a registration test that registers a `FakeTimeProvider` in the container, resolves the factory, and asserts the overdue count follows the fake clock (it fails today).
3. **Minor** — no test pins what the ASP.NET Core adapter and composite do with an `IEncinaHealthCheck` that throws, although the repository relies on that guarantee in a static scan. `EncinaHealthCheckAdapter.cs:41` and `CompositeEncinaHealthCheck.cs:52` await the check without a `try`, and `IEncinaHealthCheck.CheckHealthAsync` (`IEncinaHealthCheck.cs:66`) does not say implementations must not throw; the exception-safety of the library's own checks comes only from the base class (`EncinaHealthCheck.cs:75-93`). `HealthCheckExceptionMessageLeakStaticScanTests.cs:96-102` allowlists `EncinaHealthCheckAdapter` and `CompositeEncinaHealthCheck` on the stated reason that they wrap `IEncinaHealthCheck` whose base class reports the type only, and its own comment (`:105-108`) says a class that does not catch makes `DefaultHealthCheckService` copy `ex.Message` and the exception onto the report entry. The 10 tests of `EncinaHealthCheckAdapterTests.cs` (`:20` to `:206`) and the 4 of `CompositeEncinaHealthCheckTests.cs` (`:20, :30, :41, :53`) never make the substituted `IEncinaHealthCheck` throw (a search of both files for `Throw` finds only the adapter's constructor test at `EncinaHealthCheckAdapterTests.cs:198-203`). For a custom or third-party `IEncinaHealthCheck` the guarantee is therefore an unpinned assumption; the behaviour is derived from the source and not run. Proposed: decide the contract (catch in the adapter and composite and report the exception type name only, or document that implementations must not throw) and add the matching unit test: a substitute whose `CheckHealthAsync` throws `new InvalidOperationException("secret detail")`, asserting either an Unhealthy result whose description and data do not contain "secret detail" and whose `Exception` is null, or the documented propagation.
4. **Minor** — health checks have neither load and benchmark tests nor the `.md` justification the repository requires for a skipped type. `AGENTS.md` section 9 requires, for a non-database feature, a justification when a type is skipped, and "a folder with neither `.cs` tests nor a `.md` justification means the coverage was not evaluated". ## Lessons for the pipeline
- A suffix match for a file name must be anchored on the package: `AspNetCore/Health/HealthCheckBuilderExtensions.cs` also matches `Encina.Tenancy.AspNetCore`'s file of the same name and silently merged two files (248 instead of 221 coverable lines, and impossible "missed" lines inside XML comments); match `*Encina.<Package>/<path>` or the package node, and read one missed line in the source before trusting a table.
- When an earlier delta audit of a sibling issue already audited the same folder (here #24 for `src\Encina.Messaging\Health`), the tests stage of the new issue is mostly a confirmation: open the umbrella issues first (`gh issue view`, search the bodies for each scoped file name), build the tracker table, and spend the effort on what no tracker holds (duplicated test classes, wall-clock fixtures, unpinned contracts, missing justification files).
- Tests that pin a code-stage defect (`SagaHealthCheckTests.cs:76` and `HealthChecksTests.cs:581` assert the double-counting sum; the substitutes have no `SagaId`) are the first thing the remediation changes; listing them next to the code finding saves the worker a search.
