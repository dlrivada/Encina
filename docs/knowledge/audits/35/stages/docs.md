## Lessons for the pipeline
- A guide that says "Encina provides X" about a builder extension must be checked against what the extension registers: `AddEncinaHealthChecks` aggregates whatever is in DI, and the pattern checks come from four other extensions. Read the registration body, not only the signature.
- A sample that passes an `IServiceProvider` into a fluent builder method is a quick signature check: open the overload and compare the first optional parameter's type.
- For a feature whose delivered scope sits in `Encina.Messaging`, search the docs for the interface names (`IEncinaHealthCheck`, `HealthCheckResult`) as well as the guide title, to see that the abstraction has a reference page.
- Count inbound links with a repository-wide search for the file name (`health-checks.md`), not from the section index alone: the first pass said one inbound link and there are four (audit #35 verifier correction 6). When a page names what a README "mentions only", read the whole README section by heading before writing "only" (the Messaging README has a full Health Checks section at :533-617).
- A page that an earlier audit consolidated into an open umbrella (#1955 for #24) must have that umbrella's section headings compared with the findings before the stage closes; record the open trackers per finding in the stage, not only the prior issue (#115).
- Before writing that part of a finding is "not named" by an umbrella issue, grep the umbrella body for the finding's nouns (`tag`, `ready`, the symbol names), not only the section whose heading matches: #1955 held the tag table and the Outbox `ready` note in three sections besides its diagram item (audit #35 verifier pass 2, correction 1).
