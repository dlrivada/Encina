## Findings
1. **Major** — `SchedulingHealthCheck` counts dead-lettered scheduled messages as overdue forever, and the check is tagged `ready`. `SchedulingHealthCheck.cs:47-50` calls `GetDueMessagesAsync(..., maxRetries: int.MaxValue, ...)`, and `:64-74` counts every returned message whose `ScheduledAtUtc + OverdueTolerance` is in the past. The processor never touches a message that used its retries: `SchedulerOrchestrator.cs:295-297` fetches with `_options.MaxRetries`, and `ExponentialBackoffRetryPolicy.cs:59-60` returns `RetryDecision.DeadLetter()`, whose `NextRetryAtUtc` is null (`RetryDecision.cs:43`), so the store increments `RetryCount` and stores a null retry time. The store's due predicate for such a row is `RetryCount < @MaxRetries AND (NextRetryAtUtc IS NULL AND ScheduledAtUtc <= @NowUtc)` (`src/Encina.ADO.SqlServer/Scheduling/ScheduledMessageStoreADO.cs:93-98`, same shape in the Dapper SQL Server store `:76-81` and the EF store `:64-67`), so with `int.MaxValue` the dead-lettered row is returned on every probe, sorted first by `ORDER BY ScheduledAtUtc`. Each dead-lettered message is therefore reported as "overdue" until someone deletes it, although the scheduler will never run it; at the default 10 and 50 (`SchedulingHealthCheck.cs:118, :124`) the check goes Degraded then Unhealthy for good. The registration tags it `ready` (`SchedulingHealthCheck.cs:35`, `HealthCheckBuilderExtensions.cs:215` via `CombineTags`), so 50 dead-lettered messages take every replica out of readiness rotation, while the Outbox check deliberately does not (`HealthCheckBuilderExtensions.cs:34-38, :117`) for the same shared-store-backlog reason. `OutboxHealthCheck.cs:56-64` shows the intended design (it takes `OutboxOptions.MaxRetries` and reports exhausted messages as a separate count), and `IScheduledMessage.IsDeadLettered(int maxRetries)` already exists (`Scheduling/IScheduledMessage.cs:101`). `SchedulingHealthCheck` takes no `SchedulingOptions`, so it cannot know the limit. Fails: AGENTS.md section 3 provider coherence between the sibling checks, section 6 function 4 (health check that reports the wrong state), and the design intent recorded for the Outbox check. Derived from the code, not run.
2. **Major** — `SagaHealthCheck` double-counts a saga that is both stuck and expired, so the status escalates at half the configured threshold. `SagaHealthCheck.cs:46-62` queries the stuck set and the expired set separately and `:73` sums them (`totalProblematic = stuckCount + expiredCount`), which `:75-87` compares with the warning and critical thresholds. The two queries select the same status set: stuck is `Running OR Compensating AND LastUpdatedAtUtc < now - threshold` and expired is `Running OR Compensating AND TimeoutAtUtc <= now` (EF store `SagaStoreEF.cs:94-96` and `:115-118`; ADO SQL Server `SagaStoreADO.cs:158-159` and `:199-201`; the PostgreSQL ADO and Dapper stores read the same columns at `SagaStoreADO.cs:159, :201-202` and `SagaStoreDapper.cs:133, :166-167`). A saga whose timeout has passed and that nobody updates for 30 minutes is in both, which is the normal state of a timed-out saga. With the defaults (`SagaHealthCheck.cs:108, :114`) 25 such sagas are reported as 50 and the check is Unhealthy, and the registration is tagged `ready` (`SagaHealthCheck.cs:35`, `HealthCheckBuilderExtensions.cs:182`), so the replicas leave rotation at half the documented critical threshold. The description at `:78` and `:85` also prints two counts that overlap. The fix needs a distinct count (union by `SagaId`) or two separate thresholds. Fails: known failure pattern "a compound conclusion drawn from two queries that overlap". Derived from the SQL and LINQ, not run.
3. **Minor** — the registration of the Scheduling check ignores the container's `TimeProvider`. `HealthCheckBuilderExtensions.cs:222` builds `new SchedulingHealthCheck(store, options)` and the constructor defaults to `TimeProvider.System` (`SchedulingHealthCheck.cs:34, :40`), although the messaging registration puts a `TimeProvider` in the container (`MessagingServiceCollectionExtensions.cs:230`) and the ID-generation registration in the same file resolves it (`HealthCheckBuilderExtensions.cs:495`). An application or test that registers a `FakeTimeProvider` gets a scheduling check on the wall clock while the store (`ScheduledMessageStoreADO.cs:193`) uses the injected one. Fails: AGENTS.md section 3 ("Time comes from `TimeProvider`", taken by injection).
4. **Minor** — `ReferenceTableHealthCheck` reads the wall clock directly. `src/Encina.Messaging/Health/ReferenceTableHealthCheck.cs:74` is `var now = DateTime.UtcNow;`, the only time source in the file (a search for `TimeProvider` in it returns 0 matches), so the staleness thresholds cannot be tested deterministically. It is in the same folder and is not part of #35's diff (sibling audit). Fails: AGENTS.md section 3 (`TimeProvider`).
5. **Minor** — `DatabaseHealthCheck` keeps synchronous database fallbacks. `src/Encina.Messaging/Health/DatabaseHealthCheck.cs:114` calls `connection.Open()` and `:129` calls `command.ExecuteScalar()` for an `IDbConnection` that is not a `DbConnection`. Every provider check in the repository builds a `DbConnection` subclass (the six `*HealthCheck : DatabaseHealthCheck` classes, all in ADO.NET or Dapper packages), so the branches serve only a mocked `IDbConnection` in unit tests; they are fallbacks, not the primary path. The file was added by the closing commit 924ca2e5. Fails: AGENTS.md section 3 ("NEVER the synchronous overloads such as `IDbConnection.Open()`", AUD-16); `connection.Open()` here is not named in #2039's description, whose allowlist should include it or the branch should go.
6. **Minor** — `SagaHealthCheck` and `SchedulingHealthCheck` overflow when a threshold is `int.MaxValue`. `SagaHealthCheck.cs:48` and `:57` pass `SagaCriticalThreshold + 1` and `SchedulingHealthCheck.cs:48` passes `OverdueCriticalThreshold + 1` as the batch size; at `int.MaxValue` that wraps to a negative number and the stores throw (`src/Encina.ADO.SqlServer/Sagas/SagaStoreADO.cs:189-190`, `if (batchSize <= 0) throw new ArgumentException`). The base class turns it into Unhealthy "Health check failed: ArgumentException" (`EncinaHealthCheck.cs:85-93`). The Outbox options document `int.MaxValue` as the way to disable a level (`OutboxHealthCheck.cs:153, :162`), so the same idiom applied to these two options silently makes the check Unhealthy instead of never critical. Fails: input validation of public options (AGENTS.md section 6 function 5).
7. **Minor** — the `IEncinaHealthCheck` XML example does not compile and names an API that does not exist. `IEncinaHealthCheck.cs:23` declares `public string[] Tags => ...` while the interface member is `IReadOnlyCollection<string> Tags` (`:59`; an implicit implementation needs the identical type), `:28` calls `_store.CanConnectAsync(...)`, a method no store has (a search of `src/Encina.Messaging` for `CanConnectAsync` returns only this line and `IModuleHealthCheck.cs:27`, which uses `DbContext.Database`), and the example class is called `OutboxHealthCheck`, the name of the real class. It is the first thing a reader of the public interface sees. Fails: AGENTS.md section 8 (XML comments on public API, examples when helpful; a wrong example is worse than none).

## Lessons for the pipeline
- When one pattern's check was refactored later to separate "pending" from "exhausted" (Outbox), read the sibling checks of the other patterns for the same unseparated count; the Scheduling and Saga checks both still add dead states into one total.
- A health check that sums two store queries needs the two filters compared side by side before the sum is accepted; here the status predicate is identical in eight stores, so the overlap is structural, not a corner case.
- The open-issue search showed that the earlier delta audit of #24 (the Outbox issue) had already filed the Left-swallowing, tag and `FailureStatus` defects in this folder; a first-pass audit of a sibling issue should search open issues by file name before sizing the findings, so new effort goes to what no earlier audit read (here the Scheduling and Saga counting logic).
