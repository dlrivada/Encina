## Findings

1. **Blocker** — `RebuildAsync` fails for every handled event, so the only recovery path for a drifted read model does not work. `src/Encina.Marten/Projections/MartenProjectionManager.cs:547-551` looks up `LoadAsync` on `typeof(IDocumentSession)` and calls `loadMethod!.MakeGenericMethod(...)`; `:562-563` does the same for `Store` and `:569-572` for the generic `Delete`. In Marten 9.38.0 (`Directory.Packages.props`) those members are declared on `IQuerySession` and `IDocumentOperations`, and `Type.GetMethod`/`GetMethods` on an interface type does not search base interfaces, so the lookup is `null` and the call throws `NullReferenceException` (`Store` is also called with `[new[] { readModel }]` at `:564`, an `object[]` where `Store<T>(params T[])` needs a `T[]`). The exception is caught at `:89-92` and returned as `Left(RebuildFailed)`. The same defect in `InlineProjectionDispatcher` was fixed in #1095 by typed helpers, whose comment states the cause (`InlineProjectionDispatcher.cs:57-64`); the manager, which `da52fcd6` (#1557) touched later, kept the reflection. Six compliance modules register projections with `AddProjection<,>` (`ConsentMartenExtensions.cs:55`, `DPIAMartenExtensions.cs:54`, `DSRMartenExtensions.cs:51`, `RetentionMartenExtensions.cs:64-66`, `ProcessorAgreementsMartenExtensions.cs:61-62`, `BreachNotificationMartenExtensions.cs:53`) and `ProcessorAgreementsMartenExtensions.cs:31-34` documents `IProjectionManager` as the way to rebuild when inline projections are off. No test executes a handled-event rebuild (`MartenProjectionManagerTests.cs:271` and `:279` are the only `RebuildAsync` tests in `tests/`; no file under `tests/Encina.IntegrationTests` mentions `RebuildAsync` or `MartenProjectionManager`). Fails the issue's own acceptance criterion "Rebuild capabilities tested". Already filed as #1906 (open BUG); the remediation drafter should link it and not open a duplicate.

2. **Major** — A rebuild deletes the read models before replaying anything, in a separate committed session, and so a failed, cancelled or resumed rebuild leaves the read side empty or truncated. `MartenProjectionManager.cs:106-109` runs `DeleteExistingReadModelsAsync` (`:134-140`: `DeleteWhere<TReadModel>(_ => true)` then `SaveChangesAsync`) before the event count at `:111` and before the first batch; `RebuildOptions.DeleteExisting` defaults to `true` (`IProjectionManager.cs:153`). Combined with finding 1, a default `RebuildAsync` call on any real store today wipes the read models and then fails on the first handled event, leaving the projection `Faulted` with an empty read side. The same ordering breaks resume: `IProjectionManager.cs:164-169` says `StartPosition` is for resuming a failed rebuild, but with the default `DeleteExisting = true` the delete at `:108` removes every read model while the replay starts at `:173` from `StartPosition`, so the read models built before that position are lost. Batches are committed one by one (`:236`), so a failure in batch N leaves a read model that is partly built. Fails AGENTS.md §3 fail-closed intent for the six compliance read models (a consent or retention lookup that finds nothing denies or errs) and the known failure pattern "destructive step before the work it depends on succeeds". Not covered by #1906 (which asks only that the reflection be fixed).

3. **Major** — Within one rebuild batch an update event cannot see the read model created earlier in the same batch, so most of a rebuilt read side is wrong. `ProcessSingleBatchAsync` opens one `_store.LightweightSession()` per batch (`MartenProjectionManager.cs:207`) and, for each event, `ApplyEventAsync` loads the read model with `LoadAsync` (`:501-505`), then queues the result with `Store` (`:513`, `:522`) and calls `SaveChangesAsync` once after up to `BatchSize` (default 1000, `IProjectionManager.cs:144`) events (`:236`). A lightweight session has no identity map, so `LoadAsync` reads the database and does not see a document that was only queued by `Store`; for a stream whose creator and handler events fall in the same batch the handler finds `existingReadModel == null` and does nothing (`:519-523`), and for two updates to one stream the second starts from the pre-batch state. The inline dispatcher does not have the problem because it saves after every event (`InlineProjectionDispatcher.cs:327-338`). This follows from Marten's documented lightweight-session semantics and the code path; I could not run it (see Scope reviewed), so the verifier should confirm it with a Testcontainers rebuild of one stream with a creator and two handler events (the same test as #1906's regression test, with 3 events instead of 1). It becomes reachable once finding 1 is fixed, and it makes the idempotency claim of `IProjection.cs:17-19` ("safe replay and rebuild") false.

4. **Major** — A cancelled rebuild is reported as a successful, 100% complete rebuild. `ProcessSingleBatchAsync` returns `BatchResult.Cancelled` (`MartenProjectionManager.cs:225-228`), which is built with `EventCount = 0` (`:326`); `ProcessEventBatchesAsync` tests `batchResult.EventCount == 0` and breaks at `:181-184` before the `WasCancelled` check at `:186-190`, so the `Left(Cancelled)` branch is unreachable. The loop condition `!cancellationToken.IsCancellationRequested` (`:176`) has the same exit. Both fall through to `CompleteRebuild` (`:198`, `:279-293`), which sets the state to `Stopped`, progress to 100, and returns `Right(eventsProcessed)` with the partial count; the interrupted batch is discarded unsaved (`:236` not reached). The exception route (`OperationCanceledException` from a Marten call, `:85-88`) does return `Left`, so the result depends on where the token is observed. Fails AGENTS.md §3 (errors reported as success) and the known failure pattern "dead branch hidden by an earlier condition". No test reaches it.

5. **Major** — The lifecycle API and several options do nothing, and the documentation describes behaviour that does not exist. `StartAsync`, `StopAsync`, `PauseAsync` and `ResumeAsync` (`MartenProjectionManager.cs:363-458`) only set `ProjectionStatus.State` in a process-local dictionary (`:22`, `:472-487`); nothing outside the manager reads `ProjectionState` (a search of `src/Encina.Marten` finds it only in `MartenProjectionManager.cs`, `ProjectionStatus.cs`), so pausing or stopping a projection does not stop `MartenInlineProjectionDispatcher` from applying events. The states `Starting`, `CatchingUp` and `Stopping` and the property `EventLag` are never assigned. `ProjectionStatus.cs:27-30` says "On restart, processing resumes from this position" and `:8-14` lists "Catch-up processing after restart", but the status is not persisted and the inline path never updates it (`InlineProjectionDispatcher.cs` has no status write). `ProjectionOptions.RebuildBatchSize` (`ProjectionOptions.cs:38`), `ProjectionOptions.AutoRebuildOnStartup` (`:48`) and `RebuildOptions.RunInBackground` (`IProjectionManager.cs:187`) have no reader in `src/` (search for the three names over `src` matches only their declarations, `ProjectionOptions.cs` and `IProjectionManager.cs`); `RebuildBatchSize` is shadowed by `RebuildOptions.BatchSize`, which `MartenProjectionManager.cs:179` reads. `GetStatusAsync` also hands out the live mutable `ProjectionStatus` (`:343-345`), updated without a lock (`:472-487`). Fails AGENTS.md §1/§3 ("every line serves a current purpose"; pay-for-what-you-use applies to options that promise a behaviour) and the known failure pattern "aspirational API".

6. **Minor** — The singleton manager resolves a scoped projection from the root provider. `ServiceCollectionExtensions.cs:166` registers `IProjectionManager` as a singleton and `:204` registers `TProjection` as scoped; `MartenProjectionManager.cs:208` calls `_serviceProvider.GetRequiredService(registration.ProjectionType)` on the singleton's provider. With scope validation on (the default host setting in Development) this throws "Cannot resolve scoped service ... from root provider"; with it off it captures one scoped instance for the process lifetime. Fails AGENTS.md §3 registration completeness (the DI test `ValidateOnBuild`/`ValidateScopes` cannot see it because the resolution is at run time, and no Marten projection test uses `ValidateScopes`: the only `ValidateScopes` in `tests/**/Marten/**` is `CryptoShreddingWiringTests.cs:40`). The six compliance projections have no constructor (a search for their `public <Name>(` constructors in `src` finds none), so today the impact is the Development exception; it is latent for a projection with dependencies. Surfaces after finding 1.

7. **Minor** — Cancellation is converted into a projection failure and, with the default options, into success. `MartenInlineProjectionDispatcher.ApplyEventToProjectionAsync` catches `Exception` including `OperationCanceledException` and returns `Left(ApplyFailed)` (`InlineProjectionDispatcher.cs:185-194`); `InlineProjectionRelay.ProjectAsync` excludes `OperationCanceledException` from its own catch (`InlineProjectionRelay.cs:120`) and documents "cancellation propagates" (`:30-31`), but the dispatcher has already swallowed it, so with `ThrowOnProjectionError = false` the relay logs and returns `Right` (`:129-139`). `MartenReadModelRepository` does the same in all ten methods (`MartenReadModelRepository.cs:61`, `:94`, `:125`, `:155`, `:186`, `:214`, `:246`, `:271`, `:293`, `:318`): a cancelled query is logged at error level and returned as `QueryFailed`. Fails the relay's own documented contract and AGENTS.md §3 (errors reported as success).

8. **Minor** — Handler lookup is by exact event type although the handler interfaces are declared contravariant. `IProjectionHandler<in TEvent,...>`, `IProjectionCreator<in TEvent,...>` and `IProjectionDeleter<in TEvent,...>` (`IProjection.cs:83`, `:112`, `:136`) advertise that a handler of a base type or interface accepts derived events, but `ProjectionRegistry.cs:42-52` indexes handlers by the declared `TEvent` and `GetProjectionsForEvent`/`GetHandlerInfo` (`:60-67`, `:168-171`) are exact dictionary lookups on `domainEvent.GetType()` (`InlineProjectionDispatcher.cs:104`, `MartenProjectionManager.cs:248`). A projection written as `IProjectionHandler<IOrderEvent, OrderSummary>` is never invoked for `OrderPlaced : IOrderEvent`. Static reading only; I did not run it. Also `DiscoverHandlers` writes `_handlers[eventType] = ...` (`:187`, `:197`, `:207`), so a projection that implements two of the three interfaces for the same event type silently keeps whichever interface `GetInterfaces()` returns last.

9. **Minor** — The `IProjection<T>.ProjectionName` contract is ignored, and two registrations for one read model are not rejected. `ProjectionRegistration` computes the interface property and then discards it (`ProjectionRegistry.cs:121-137`: dead block, comment "We'll get the actual name when we have an instance", then `ProjectionName = projectionType.Name`), although `IProjection.cs:59-65` documents the property as the unique name used for tracking. Two projections in different namespaces with the same simple name share one entry in `_statuses` (`MartenProjectionManager.cs:464`). `ProjectionRegistry.Register` overwrites `_readModelToProjection[readModelType]` (`:38`) but still adds both registrations to `_allRegistrations` and `_eventToProjections` (`:39-52`), so two projections for one read model both run inline while the manager manages only the last.

10. **Minor** — With the default `ThrowOnProjectionError = false` a failed inline projection leaves the read model behind with no persistent record. `InlineProjectionRelay.cs:129-139` logs `InlineProjectionFailedAfterSave` and returns `Right`; `ProjectionOptions.cs:51-54` documents the default. The event is durable, so this is a documented decision, but nothing records which stream drifted: the inline path writes no `ProjectionStatus` (finding 5), `EventLag` is never set, no outbox or retry is involved, and the only repair is a full rebuild (finding 1). For compliance read models this is a silent divergence; the choice of default (fail the save, or record and retry) is a design decision for the maintainer.

11. **Minor** — Exception and error text reaches a stored status and a published example. `MartenProjectionManager.cs:316` stores `ex.Message` in `ProjectionStatus.ErrorMessage` (readable through `GetStatusAsync`/`GetAllStatusesAsync`, `:330-360`); Marten and Npgsql messages can carry SQL fragments and connection details, and AGENTS.md §3 allows only the error code or exception type in status-like outputs. There is no production reader today, so the leak is latent (a future health check or ProblemDetails mapper would publish it). `IProjectionManager.cs:31` still prints `error.Message` in the XML example, the pattern #1557 removed from the other examples.

12. **Minor** — The XML example of `IProjection<TReadModel>` does not compile and teaches the wrong interface. `IProjection.cs:23-53` implements `IProjectionHandler<OrderCreated, OrderSummary>` but supplies `Create(OrderCreated, ProjectionContext)` (which belongs to `IProjectionCreator<,>`) and no `Apply(OrderCreated, OrderSummary, ProjectionContext)`; the compiler rejects the class, and a reader who fixes it by following `IProjection.cs:78-80` gets the right shape only by reading the other interface. The surrounding `Idempotency` remark (`:17-19`) is not true of the shipped rebuild (finding 3).

13. **Minor** — The read side has no tracing, metrics or health check. A search for `ActivitySource`, `Meter`, `StartActivity` and `IEncinaHealthCheck` in `src/Encina.Marten` matches only `ServiceCollectionExtensions.cs` (the Marten provider health check, not projections) and `Instrumentation/MartenActivityEnricher.cs`; `Projections/` has none. AGENTS.md §6 requires an Integrate/Defer/N-A decision for OpenTelemetry (2) and health checks (4) for a new store or background-like component; no record of the decision for `MartenProjectionManager`, the inline dispatcher or the relay is in the knowledge record or the issue. A projection lag or failure count is the signal that findings 7 and 10 need.

## Lessons for the pipeline

- Run the open-issue search over file and type names before sizing the findings: #1906 (the blocker) was already filed by the #21 delta audit, the same-scope earlier issue. For a re-created issue (#36 after #21) read the earlier record's remediation first and spend the effort on what it did not read (here the rebuild's delete-first ordering, same-batch visibility, dead cancellation branch and the no-op lifecycle API).
- When one class in a package was fixed for a reflection defect (the dispatcher in #1095), grep the whole package for the same call shape (`typeof(I...Session).GetMethod`) and for `MakeGenericMethod`; the unfixed copy was in the sibling class of the same folder.
- A file-based `dotnet run <file>.cs` from the scratchpad is blocked by `guard-orchestrator-writes` for an issue-auditor ("whose script path the hook cannot resolve ... pass its literal path"); the stage text should either allow auditors a literal scratchpad path or say that reflection checks go to the verifier.
- A batch/session-semantics claim (Marten lightweight session visibility) is a static-reading finding; mark it as unexecuted and hand the verifier a concrete test (stream with a creator and two handler events) instead of asserting it as measured.
