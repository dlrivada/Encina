## Findings
1. **Major** — `src/Encina/Modules/ModuleServiceCollectionExtensions.cs:75` registers the real `IModuleHandlerRegistry` with `TryAddSingleton`, and `src/Encina/Core/ServiceCollectionExtensions.cs:73` registers `NullModuleHandlerRegistry.Instance` with `TryAddSingleton` and the comment "will be overwritten if AddEncinaModules is called" (`:71-72`). The comment is only true when `AddEncinaModules` runs first. With the usual order `services.AddEncina(...)` then `services.AddEncinaModules(...)` the Null registry is registered first and the `TryAdd` at `ModuleServiceCollectionExtensions.cs:75` is a no-op (the nested `AddEncina` at `:105` also keeps it). `ModuleBehaviorAdapter.IsTargetModule` (`ModuleBehaviorAdapter.cs:119-126`) then asks the Null registry, which returns `false` for every handler, so every module-scoped behavior registered with `AddEncinaModuleBehavior` (`ModuleBehaviorServiceCollectionExtensions.cs:59-69`) is silently skipped (`ModuleBehaviorAdapter.cs:101-105` calls `nextStep()`), and `Encina.EntityFrameworkCore/Modules/ModuleExecutionContextBehavior.cs:53` also receives the Null registry. A module-scoped authorization or validation behavior that does not run is a fail-open gate. Checks failed: AGENTS.md §3 registration completeness ("MUST win over a default in any registration order"), §3 fail-closed gates; known failure pattern "default registration wins over the real one". Unexecuted; reproduction for the verifier: build a provider with `AddEncina(typeof(X).Assembly)` followed by `AddEncinaModules(c => c.AddModule<M>())`, resolve `IModuleHandlerRegistry` and assert it is `ModuleHandlerRegistry`, then repeat in the reverse order. No test in `tests/` calls `AddEncinaModules` except `tests/Encina.UnitTests/AspNetCore/ModuleHealthCheckTests.cs:52, :81, :109, :137` (none resolves the handler registry).

2. **Major** — `src/Encina/Modules/ModuleServiceCollectionExtensions.cs:105` calls `services.AddEncina(assemblies)` with no configuration, and `src/Encina/Core/ServiceCollectionExtensions.cs:76-80` runs `services.Configure<NotificationDispatchOptions>` on every `AddEncina` call, assigning `Strategy` and `MaxDegreeOfParallelism` from the fresh default `EncinaConfiguration`. Options configure actions run in registration order, so `AddEncina(c => c.UseParallelNotificationDispatch(ParallelWhenAll, 4))` followed by `AddEncinaModules(...)` ends with the defaults (`Sequential`, `-1`, `src/Encina/Options/NotificationDispatchOptions.cs:26, :36`), silently discarding the application's setting. `AddEncinaModules` has no overload that takes an `EncinaConfiguration`, so the application cannot repeat the setting inside it. A feature registration that overrides the application's own configuration breaks AGENTS.md §3 registration completeness ("without overriding the application's own registration"). Unexecuted; verifier: build the provider in that order and read `IOptions<NotificationDispatchOptions>.Value.Strategy`.

3. **Minor** — `src/Encina/Modules/ModuleServiceCollectionExtensions.cs:70-71` builds a `ModuleRegistry` from this call's modules and registers it with `TryAddSingleton`; a second `AddEncinaModules` call (for example one per feature library) keeps the first registry and handler registry (`:75`), yet still runs `module.ConfigureServices` for the second call's modules (`:90-93`) and registers their types (`:80`). Those modules are absent from `IModuleRegistry`, so `ModuleLifecycleHostedService` (`ModuleLifecycleHostedService.cs:41`, reads the registry) never calls their `OnStartAsync`/`OnStopAsync`, the health check at `src/Encina.AspNetCore/Health/HealthCheckBuilderExtensions.cs:378` does not see them, and their handlers are unknown to the handler registry (finding 1's effect). A duplicate name across the two calls is not detected (`ModuleConfiguration.cs:73` and `ModuleRegistry.cs:72-87` only see one call's modules). No error, no log. Fails AGENTS.md §3 registration completeness and "errors are never swallowed". Unexecuted.

4. **Minor** — Module name and shared-assembly validation is missing. `ModuleConfiguration.AddModule` (`ModuleConfiguration.cs:73`, `:104`) calls `d.Module.Name.Equals(...)` on every earlier descriptor and `module.Name` is never checked for null, empty or whitespace (`IModule.cs:40` is non-nullable, a `string.Empty` name registers and shows up as `""` in logs); `ModuleRegistry.cs:36-43` would also throw `ArgumentNullException` from the dictionary for a null name. Separately `AddModule(module)` defaults the handler assembly to `module.GetType().Assembly` (`ModuleConfiguration.cs:80`, `:111`), so two modules declared in one assembly (the normal shape of a small modular monolith) are accepted, and `ModuleHandlerRegistry.cs:41-46` keeps only `g.Last().Module` ("this is an edge case that should be avoided in practice", `:39-40`): every handler of the assembly is attributed to the last module and module-scoped behaviors of the first never run. The remedy is a registration error, not a comment. The two `AddModule` overloads also copy the same 6-line duplicate check (`:73-78` and `:104-109`, AUD-18); the one-argument overload can call the two-argument one. Fails AGENTS.md §3 (errors are not silent) and AUD duplication.

5. **Minor** — Module lifecycle failure handling in `src/Encina/Modules/ModuleLifecycleHostedService.cs`. (a) `StartAsync` rethrows the failing module's exception (`:63-67`) and does not stop the modules already started (`:50-68`); `IModuleLifecycle.cs:57-59` documents only "subsequent modules will not be started". Whether the host calls `StopAsync` for services that started before a failure is runtime behavior of `Microsoft.Extensions.Hosting` that this stage did not execute; the verifier should check with a host whose second module throws in `OnStartAsync` and assert whether the first module's `OnStopAsync` runs. (b) In `StopAsync` a cancelled `OnStopAsync` is logged as a warning and dropped (`:97-101`, no entry in `exceptions`), and `LogAllModulesStopped` (`:110`) then reports "All N module(s) stopped" although a module did not finish; only non-cancellation failures reach the `AggregateException` (`:112-117`). Fails AGENTS.md §3 "errors are never swallowed in background infrastructure". Severity Minor because a cancelled stop means the host shutdown timeout fired.

6. **Minor** — Module telemetry is dead code and the lifecycle service does not use the logging that exists for it. `src/Encina/Modules/Diagnostics/ModuleLog.cs:19-117` is a public `[LoggerMessage]` class (EventIds 1900-1906, range `ModuleIsolation = (1900, 1999)`, `src/Encina/Diagnostics/EventIdRanges.cs:80`, so the module lifecycle shares the isolation range) with zero callers (`Grep "ModuleLog\."` over `src/` and `tests/`: no match outside its own file); `ModuleLifecycleHostedService.cs:122-156` instead defines twelve `logger.LogX(...)` wrappers under `#pragma warning disable CA1848` (`:120`) with no EventIds, which AGENTS.md §7 asks new code to avoid (source generator, registered range). `ModuleActivitySource` (`Diagnostics/ModuleActivitySource.cs:19`) has no caller (`Grep "ModuleActivitySource"` over `src/`: only the declaration), `ModuleMetrics.RecordDispatch` (`ModuleMetrics.cs:53`) has no caller (`Grep "RecordDispatch\("` over `src/`: only the declaration), and `ModuleMetricsCallbacks` is never constructed or registered anywhere in `src/` (`Grep "ModuleMetricsCallbacks"` over `src/`: declarations, `ModuleMetricsInitializer.cs:18, :35` reading it with `GetService`), so `ModuleMetrics` never creates the `encina.modules.active_count` gauge (`ModuleMetrics.cs:38-45`) and `encina.modules.dispatches_total` is never incremented. Fails AGENTS.md §6 functions 2 (OpenTelemetry) and 3 (structured logging) for a feature that creates a hosted service, and AUD dead public API.

7. **Minor** — `IModuleLifecycle` hooks cannot reach any service. Modules are created with `new TModule()` at registration time (`ModuleConfiguration.cs:53-56`), `OnStartAsync(CancellationToken)`/`OnStopAsync(CancellationToken)` (`IModuleLifecycle.cs:65`, `:84`) receive no `IServiceProvider`, and `ConfigureServices` runs before the provider exists (`ModuleServiceCollectionExtensions.cs:92`). The XML example (`IModuleLifecycle.cs:32-42`) calls `_orderProcessor.WarmupAsync(...)` on a field the class never declares and has no way to obtain; the described uses ("warming up caches", "running database migrations", `:12-18`) all need services. A module author has to capture a static or use a service locator. Fails AUD docs-versus-code accuracy for the XML example; the design gap is the larger half and overlaps with the feature proposal #360 (lifecycle context objects), which this finding does not duplicate because #360 does not describe the example as broken.

## Lessons for the pipeline
- A default registered with `TryAdd` and a comment saying "overwritten when X is called" is a standing check: read the real registration's method (`TryAdd` versus `Replace`) and ask for each registration order which one wins (finding 1).
- When a feature registration calls a core `AddX` internally (`AddEncinaModules` calls `AddEncina`), read the core method for non-idempotent side effects such as `services.Configure<T>` that overwrite the application's earlier setting (finding 2).
- Zero-caller checks over `src/` and `tests/` for diagnostics types (`*Log`, `*ActivitySource`, `*Metrics`, `*Callbacks`) found a whole dead telemetry layer that a per-file read never flags; run them for every folder with a `Diagnostics/` subfolder (finding 6).
