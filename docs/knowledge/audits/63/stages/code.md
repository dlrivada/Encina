## Findings

1. **Major** — The gather handler receives a token the runner has already cancelled, so an asynchronous gather fails with `scattergather.cancelled` in the default configuration for `WaitForFirst` and `WaitForQuorum`, and after any timeout for `WaitForAllAllowPartial`. `ScatterGatherRunner.cs:217-220` (first success) and `:303-306` (quorum reached) call `linkedCts.CancelAsync()` when `CancelRemainingOnStrategyComplete` is set, whose default is `true` (`ScatterGatherOptions.cs:61`). The scatter phase then returns and `ExecuteGatherPhaseAsync` is called with `linkedCts.Token` (`:70-74`), which passes it to the user's gather delegate (`:448`). Any gather that awaits something with that token throws `OperationCanceledException`, which `:457-461` turns into `Left` with `ScatterGatherErrorCodes.Cancelled` ("Gather handler was cancelled."), although nobody cancelled the operation. The same token is also the one the timeout cancels (`:56-57`), so after a timeout under `WaitForAllAllowPartial` (the partial-results case the feature exists for, `ValidateScatterResults` `:488` lets it through) the gather again starts on an expired token. The tests cannot see it: the `WaitForFirst` test (`ScatterGatherRunnerTests.cs:404-432`) and the shared `CreateDefinition` helper aggregate with `(results, _) => ...` and ignore the token (`:617-623`), and the builder's `TakeFirst` and `AggregateSuccessful(sync)` overloads also ignore it (`ScatterGatherBuilder.cs:422`, `:452`, `:461`). A failure of the gather is reported as a cancellation nobody requested (the cancellation-versus-failure class of #3307 and #2307). Derived from reading, not run. Reproduction for the verifier: default `ScatterGatherOptions`, two handlers (one returns `Right` at once, one awaits `Task.Delay(500, ct)`), `GatherFirst().Aggregate(async (results, ct) => { await Task.Delay(1, ct); return Right<EncinaError, int>(results.Count); })`; expected `Right`, by the code `Left` with `scattergather.cancelled`. Fix direction: run the gather under the caller's token (plus its own bound), never under the source the runner cancelled for the strategy or the timeout.

2. **Major** — `ScatterGatherOptions.IncludeFailedResultsInGather` is computed and then discarded: `ScatterGatherRunner.cs:440-442` builds `resultsToGather` (only successes when the option is `false`, its default), `:444` uses it only for the "executing gather handler with N results" log, and `:448` passes the unfiltered `scatterResults` to `definition.GatherHandler`. The option's documentation says "When false, only successful results are passed to the gather handler" (`ScatterGatherOptions.cs:44-52`), so with the default the user's `Aggregate` receives failed and cancelled results (for example every handler the `WaitForFirst` strategy cancelled), and the logged count differs from what the gather received. The shared test aggregator filters `IsSuccess` itself (`ScatterGatherRunnerTests.cs:619-621`), and `ScatterGatherOptionsTests.cs:88-95` only sets and reads the property, so nothing detects it. The documentation of `GatherStrategy.WaitForAllAllowPartial` says the gather "receives all available results, including failures" (`GatherStrategy.cs:26-29`), which contradicts the option's default; whether that strategy should override the option is a design choice for the maintainer that the fix must state, the dead computation is not. Fails the standing dead-option check and AGENTS.md section 3 ("every line serves a current purpose"). Derived from reading.

3. **Major** — `WaitForFirst` and `WaitForQuorum` ignore `ExecuteSequentially()`, `ExecuteInParallel(n)` and `MaxDegreeOfParallelism`. `ExecuteScatterPhaseAsync` computes `executeInParallel` and `maxParallelism` (`ScatterGatherRunner.cs:133-134`) but its switch sends both strategies to `ExecuteWaitForFirstAsync` and `ExecuteWaitForQuorumAsync` before it looks at them (`:138-141`), and both start every handler at once (`:208-229`, `:283-284`). A definition built with `GatherFirst()` and `ExecuteSequentially()` (the natural "try the vendors in priority order until one answers" use, for which `WithPriority` says "Lower values execute first in sequential mode", `ScatterGatherBuilder.cs:304`) therefore calls every vendor concurrently, and `MaxDegreeOfParallelism` (default `Environment.ProcessorCount`, `ScatterGatherOptions.cs:27`) does not bound the fan-out of these two strategies. No test sets a sequential or bounded definition with these strategies (`ScatterGatherRunnerTests.cs:523` uses the helper default `WaitForAllAllowPartial`). The configuration is accepted and silently not applied (the same class as #3305 for the routing slip timeouts). Fix direction: sequential mode stops at the first success or at the quorum; bounded parallelism applies the semaphore of `:158` to all strategies. Derived from reading.

4. **Major** — `WaitForAllAllowPartial` returns `Right` when every handler failed or was cancelled, and `TakeBest`, `TakeMin` and `TakeMax` then fabricate a value for value-type responses. `ValidateScatterResults` skips the "at least one must succeed" rule for that strategy (`ScatterGatherRunner.cs:488`), so a run with `SuccessCount == 0` (all handlers failed, or all timed out) reaches the gather. A test pins that outcome: `ExecuteAsync_WhenTimedOut_WithAllowPartial_ReturnsResult` expects `Right` with `SuccessCount.ShouldBe(0)` (`ScatterGatherRunnerTests.cs:316-341`). For a reference-type `TResponse` the built-in selectors return `Left` (`ScatterGatherBuilder.cs:486-490`, `:517-521`), but `results.OrderBy(selector).FirstOrDefault()` then `best is null` (`:485-486`, `:516-517`) is never true when `TResponse` is a value type (price quotes, a decimal, are the interface's first example use, `IScatterGatherRunner.cs:14-16`), so `TakeMin(q => q)` on zero successes returns `Right(0m)`: a total failure reported to the caller as a successful quote of zero. This is the shape of #3235 (sharded scatter-gather `Right` when every shard fails with partial results allowed), which is filed for `ShardedQueryExecutor` only (`src/Encina/Sharding/Execution/ShardedQueryExecutor.cs`); its fix principle (total failure is `Left`) applies here. Fails AGENTS.md section 3 (errors are never swallowed; a result with no successful handler must not read as success). Fix direction: `Left` with `AllScattersFailed` (or `Timeout`, see finding 5) when no handler succeeded, which flips the test at `:316-341`; independently, replace the null test in the three selectors by an emptiness test. Derived from reading, not run.

5. **Major** — The outcome of a timeout or a caller cancellation depends on which code path the cancellation reaches, so callers cannot tell a timeout from a failure, and completed work is discarded in one of the paths. `ScatterGatherErrorCodes.Timeout` is produced only at `ScatterGatherRunner.cs:110-117`, which runs only when an `OperationCanceledException` escapes the scatter phase; that happens only from `semaphore.WaitAsync` for a handler still queued (`:162`) and from `ThrowIfCancellationRequested` between sequential handlers (`:190`). A handler that is already running swallows the cancellation (`:406-417`, `:225-228`, `:311-314`) and returns a failed result, so: `WaitForAll` ends as `scattergather.scatter_failed` "Not all scatter handlers succeeded" (`:478-485`), `WaitForFirst` as `all_scatters_failed` (`:488-493`), `WaitForQuorum` as `quorum_not_reached` (`:348-355`), and a cancellation by the caller in mid-run gets the same codes instead of `Cancelled` (the only cancellation test uses a token cancelled before the call, `ScatterGatherRunnerTests.cs:258-283`; the timeout test accepts either code, "Either timeout error or scatter failed error", `:311`). Worse, with more handlers than `MaxDegreeOfParallelism`, a timeout while some are still queued throws out of `Task.WhenAll` (`:173`) and returns `Left` `Timeout`, discarding the successes already collected, while the same definition with enough parallelism returns `Right` with them under `WaitForAllAllowPartial` (pinned by `:316-341`). The sequential path discards earlier results the same way (`:190`). The maintainer decided for the routing slip and the core saga that the timeout promise stays and becomes true, with a timeout told apart from a caller cancellation (#3305, #2208, decision of 2026-10-10); `ScatterGatherOptions.DefaultTimeout` and `WithTimeout` carry the same promise. Fix direction: after the scatter phase test the caller's token first (`Cancelled`), then the timeout source (`Timeout` unless the strategy is satisfied, or, for partial results, at least one success), uniformly for all strategies and for queued and running handlers. Handlers must honour the token they receive (the precedent of #3305); the runner also awaits every handler after the first success or the quorum (`:243`, `:270`), so a handler that ignores its token delays the return. Derived from reading.

## Lessons for the pipeline

- A configuration option that the runner reads into a local variable and then does not pass on (`resultsToGather`, `ScatterGatherRunner.cs:440-448`) passes a "does the option have a reader" grep; the check has to follow the value to the call it was meant to reach, and the options test that only sets and gets the property (`ScatterGatherOptionsTests.cs:88-95`) is the pointer.
- For a runner that has its own cancellation source for strategy completion (`linkedCts.CancelAsync()`), trace which token every later phase receives: the gather phase got the source the runner itself had cancelled. Hand the verifier a reproduction with an asynchronous delegate that uses its token, because every test helper in the folder ignored it.
- For a family of copied runners, the sibling issues usually cite only their own file in Location (here #3307, #3305, #3311, #3309 each name `RoutingSlipRunner`), and a sentence such as "the same gap exists in ScatterGatherRunner" in one of them (#3311) is not coverage; the counterpart still gets its own finding, with the sibling issue as the precedent for the fix.
- A returned `Right` with zero successes under a "partial results allowed" strategy deserves a search for the selectors that follow it: `FirstOrDefault()` plus `is null` on an unconstrained generic is never null for a value type, which turns an empty gather into a successful default.
- `PublicAPI.Unshipped.txt` with 0 lines for a whole folder is a quick check for a package that does not reference the analyzer; it is owned by #1171 and should be recorded as Informational instead of re-filed per audit.
