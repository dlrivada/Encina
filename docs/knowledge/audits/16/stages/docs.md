## Lessons for the pipeline

- When a spike's deliverable is a single doc commit with no linked PR (as here, `8301a07c` pushed directly), no CI gate (`coverage-citations`, `markdownlint`, the docs build) ever ran against it, and none has run since — a stale or aspirational code example in such a page can survive indefinitely with no gate to catch it. The docs stage of this audit pipeline is, in practice, the first automated-adjacent check this page has ever had; future audits of doc-only spikes should treat "no linked PR" as a signal to check every code block against `src/` line by line rather than spot-checking, since the normal CI safety net for docs never applied.
- The same "interfaces exist, implementation does not" pattern the code stage flagged for Choreography (lesson: "a strong signal the docs were written aspirationally") is independently visible from the docs side as a distinct symptom: the *individual* Choreography interface members named in the doc's code (`IChoreographySaga`, `IEventReaction<T>.ReactAsync`, `IEventHandlerScope.PublishAsync`/`AddCompensation`, `IChoreographyStateStore.GetPendingCompensationsAsync`/`MarkCompensationCompletedAsync`/`GetStuckSagasAsync`) all exist and match their signatures exactly, while the *registration* surface (`AddEncinaChoreography`, `UseChoreography`) does not exist at all. A docs reviewer who only checks "does this type/member exist" symbol-by-symbol, as SKILL.md §5/§6 literally instructs, would pass every individual code example in the Choreography section and still miss that the feature as a whole cannot be wired up — the registration call is the one line that actually falsifies the whole section, and it is exactly the line a symbol-only search across a large interface surface is easiest to skim past. Future docs reviews of a page with many small code blocks should specifically isolate and separately verify the one or two DI-registration lines per pattern, not just every named type.
- The Encina.Messaging package README's "Fluent Builder (Alternative Syntax)" section (finding 4) was not in this stage's original assigned scope (`sagas.md`, `index.md`, "the README sections on sagas and choreography") but was found by reading the same README top-to-bottom for a `Saga|Choreography` grep and noticing the adjacent section a few lines below the Saga section. A future docs-stage brief that says "the README sections on X" should expect the reviewer to also skim the whole README once, since fabricated API surfaces are not confined to the section nominally about the audited feature.
