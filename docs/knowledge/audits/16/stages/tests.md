## Lessons for the pipeline
- The coverage manifest's `targets` block is a package-wide aggregate (e.g., `Encina.Messaging`'s `unit: 70` covers all 145 files), while the per-file `files{}` map is a boolean applicability list (which flags apply to which file), not a per-file percentage target. A brief that says "compare the scoped files against their manifest targets" is ambiguous until you've opened the manifest: there is no per-file number to compare against, only per-file flag applicability plus a package-wide aggregate that a scoped/filtered test run cannot validate. Future test-auditor runs should report measured per-file line coverage directly (as I did here) and treat the package `targets` block only as "which flags exist for this package," not as a per-file pass/fail threshold.
- The masking pattern the code stage found (a test fixture's synchronous `.Open()` hiding a broken async-open code path) is not just a code-review finding — it is *also* the reason the corresponding regression test does not exist: the integration test literally cannot exercise the broken branch as currently written, because the fixture never hands the store a closed connection. When a code-stage finding says "masked by the fixture," the test stage should always check whether that same masking is why no regression test exists (findings 3-6 here all follow this shape: a bug the auditor found and a happy-path-only test that structurally cannot catch it).
- For a "no implementation, only interfaces + options" folder like Choreography, the test-audit conclusion is symmetric with the code stage's: zero implementation means Integration/Load/Benchmark are correctly not-applicable, and Unit/Guard obligations shrink to just the options/error-code POCOs — worth stating explicitly so a later reviewer doesn't mistake the resulting near-zero test count for negligence rather than a consequence of the feature not existing yet.
- Before turning a coverage gap into a manifest-violation finding, quote the file's exact `defaultTests` array from the manifest and diff it against what the finding claims is "required" — this stage's own coverage table two sections above the dropped finding already had the correct answer (unit only, no guard) for `ChoreographyOptions.cs`, so the contradiction was self-detectable by re-reading the same document rather than needing a separate verification pass to catch it.
- A "zero files reference X" grep claim must state (and a verifier re-checking it must reproduce) which branch/commit it ran against, not just which directory. This audit worktree (`audit/16`) forked from `main` at `85b457ed` on 2026-09-25 and was never rebased; by the time the pass-6 verifier ran, `main` had gained 25 more commits, two of which (`28fc999f`/#1333/#1399, `832db393`/#1398/#1421) added `ISagaNotFoundDispatcher` DI-resolution smoke checks to `tests/`. The verifier's grep found those and failed this stage — but those commits are not ancestors of `audit/16`, so the references genuinely do not exist in the worktree this stage (and the verifier's own stage) is supposed to be analyzing. `git merge-base --is-ancestor <commit> HEAD` is the cheap, decisive check to run before trusting any "I found X in the repo" claim during a long-running audit: it answers whether X is even reachable from the branch under audit, independent of which physical directory a tool happened to be pointed at. This is a new failure mode, distinct from the prior lesson about substring/interface-name collisions in a "zero files" grep (that risk is about matching too narrowly within the correct branch; this one is about checking the wrong branch entirely) — both are real and a stage/verifier needs to guard against each independently.
