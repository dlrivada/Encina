## Findings

1. **Blocker** — `src/Encina.Messaging/Choreography/*.cs` (all 8 files), `src/Encina.Messaging/MessagingServiceCollectionExtensions.cs` (absence), `src/Encina.Messaging/MessagingConfiguration.cs` (absence): the Choreography feature is pure API surface — interfaces, an options class and error-code constants, all tracked in `PublicAPI.Unshipped.txt` — with **zero concrete implementation and zero DI registration anywhere in the repository**. `grep -r "AddEncinaChoreography\|AddEncinaSagas" src/` returns no matches; `MessagingConfiguration.cs` has no `UseChoreography` property (only `UseSagas`, line 106); `AddMessagingServices`/`AddMessagingServicesCore` never reference any `Encina.Messaging.Choreography.*` type. Nobody can wire `IChoreographyEventBus` or `IChoreographyStateStore` through any supported path. Yet `docs/messaging/sagas.md:289-408` presents a complete usage example (`config.UseChoreography = true;`, `services.AddEncinaChoreography(options => ...)`) and recommends Choreography as the answer for two of its decision-table rows (lines 484, 499). Fails AGENTS.md §1/§3 "pay-for-what-you-use" and registration completeness ("an `AddEncina*` method... MUST also register every option type and dependency it resolves") — inverted here, since no `AddEncina*` entry point exists at all for a feature documented as production-ready.

2. **Blocker** — `src/Encina.OpenTelemetry/MessagingStores/InstrumentedSagaStore.cs:49,59,69,87,104` (`result.IfLeft(err => Failed(activity, err.Message));`) and `:192-195` (`private static void Failed(Activity? activity, string? errorMessage) => activity?.SetStatus(ActivityStatusCode.Error, errorMessage);`): `EncinaError.Message` is written directly into the OpenTelemetry `Activity` status description on every failed saga-store operation. Fails AGENTS.md §3 verbatim: "`EncinaError.Message` NEVER reaches logs, activity tags, health-check results or plaintext storage; record only the error code or the exception type" (why: #1168, #1173, #1259, #1274).

3. **Blocker** — `src/Encina.Messaging/Sagas/LowCeremony/SagaRunner.cs:165` (`Log.SagaException(_logger, sagaId, ex.Message, ex)`), `:171` (`_orchestrator.FailAsync(sagaId, ex.Message, CancellationToken.None)`), `:174` (`EncinaErrors.Create(SagaErrorCodes.HandlerFailed, ex.Message)`); `src/Encina.Messaging/Sagas/SagaOrchestrator.cs:351` (`state.ErrorMessage = errorMessage;`, persisted at `:355` via `_store.UpdateAsync`) and `:359` (`Log.SagaFailed(_logger, sagaId, errorMessage)`): when a saga step throws, the raw `ex.Message` becomes the returned `EncinaError.Message` *and* is logged twice (once in `SagaRunner`, once in `SagaOrchestrator`) *and* is persisted as plaintext in the saga store's `ErrorMessage` column (confirmed column exists and is bound with no redaction in `ISagaState.ErrorMessage`, `src/Encina.Messaging/Sagas/ISagaState.cs:67`, and in every provider's `AddAsync`/`UpdateAsync` SQL, e.g. `src/Encina.ADO.SqlServer/Sagas/SagaStoreADO.cs:90,129`). The same file shows the rule was known and correctly applied three lines above (`SagaRunner.cs:111-113`, comment explicitly citing "#1259 review", only the error *code* is threaded through `StartCompensationAsync`) — but the `catch (Exception ex)` block a few lines below does not apply the same discipline. Fails the same AGENTS.md §3 rule as finding 2.

4. **Blocker** — `src/Encina.ADO.SqlServer/Sagas/SagaStoreADO.cs:264-268`, `src/Encina.ADO.PostgreSQL/Sagas/SagaStoreADO.cs:266-270`, `src/Encina.ADO.MySQL/Sagas/SagaStoreADO.cs:266-270`: `OpenConnectionAsync` is `{ cancellationToken.ThrowIfCancellationRequested(); return Task.CompletedTask; }` — it never calls `.Open()` or `.OpenAsync()` on the connection. Every public method (`GetAsync`, `AddAsync`, `UpdateAsync`, `GetStuckSagasAsync`, `GetExpiredSagasAsync`) guards with `if (_connection.State != ConnectionState.Open) await OpenConnectionAsync(cancellationToken);` (lines 55-56, 94-95, 133-134, 171-172, 213-214 in the SqlServer file) and then proceeds to execute the command regardless. The production registration path hands this store a freshly constructed, closed connection (`services.AddEncinaADO(string connectionString, ...)` → `_ => new SqlConnection(connectionString)`, `src/Encina.ADO.SqlServer/ServiceCollectionExtensions.cs:219`, never opened); nothing else opens it in the DI graph unless `config.UseTransactions = true` also registers `TransactionPipelineBehavior`. A consumer who enables `UseSagas` without `UseTransactions` — a perfectly valid, documented combination — gets `InvalidOperationException` on the very first saga call. This is masked in the integration test suite: `tests/Encina.TestInfrastructure/Fixtures/SqlServerFixture.cs:69-74`'s `CreateConnection()` calls the *synchronous* `connection.Open()` before handing the already-open connection straight to `new SagaStoreADO(...)` (`tests/Encina.IntegrationTests/ADO/SqlServer/Sagas/SagaStoreADOTests.cs:29`), so the broken branch never executes under test. Fails AGENTS.md §3 "Database calls MUST be asynchronous with a `CancellationToken` (`OpenAsync`, ...); NEVER the synchronous overloads" — here it is worse than a sync call, since the connection is never opened by any path at all in the store itself.

5. **Major** — `src/Encina.MongoDB/Sagas/SagaStoreMongoDB.cs:129-132`: `GetStuckSagasAsync`'s filter (`Filter.Eq(s => s.CompletedAtUtc, null)` + `Filter.Lt(s => s.LastUpdatedAtUtc, threshold)`) has no status filter at all, unlike the other 9 providers' `WHERE (Status = 'Running' OR Status = 'Compensating') AND LastUpdatedAtUtc < @ThresholdUtc` (e.g. `src/Encina.ADO.SqlServer/Sagas/SagaStoreADO.cs:158-159`) and unlike Mongo's own `GetExpiredSagasAsync` two methods below in the same file (`SagaStoreMongoDB.cs:154-158`), which correctly reuses the `ActiveSagaStatuses` (`Running`, `Compensating`) filter. `TimeoutAsync` (`SagaOrchestrator.cs:447`) sets `Status = TimedOut` without setting `CompletedAtUtc`, so on MongoDB a timed-out saga is incorrectly and *permanently* re-surfaced by `GetStuckSagasAsync` forever (its `CompletedAtUtc` never becomes non-null), while on the other 9 providers it is correctly excluded from "stuck" once its status leaves `Running`/`Compensating`. (Note: a `TimedOut` saga cannot also appear in the "expired" batch on MongoDB — `GetExpiredSagasAsync`'s own status filter, `SagaStoreMongoDB.cs:155`, restricts results to `Running`/`Compensating` and excludes `TimedOut` by construction; the two batches are mutually exclusive on this point, the defect is the stuck-batch misclassification alone, not a double-appearance.) Fails AGENTS.md §5 provider coherence ("providers share the same interfaces... and differ only in implementation").

## Lessons for the pipeline
- When a spike's "no code change" scope includes an abstraction folder (`Sagas/`, `Choreography/`), the code stage must still walk out to that abstraction's provider implementations and any cross-cutting decorators (OpenTelemetry, in this case) — the archivist's scope list stops at the interfaces, but AGENTS.md §5 provider coherence and known failure patterns (leaking `EncinaError.Message`, fake-async connection handling) live in the implementations, not the interfaces. All five findings here were in files one hop outside the literal scope list.
- A "no implementation, only interfaces + options + error codes" folder (Choreography) is a distinct, checkable smell worth a standing check in this agent's method: grep the folder's public types across `src/` outside their own directory; zero hits plus a documented, complete usage example in `docs/` is a strong signal the docs were written aspirationally, not against working code.
- The masking mechanism in finding 4 (a test fixture's synchronous `connection.Open()` hiding a broken async open path) is a pattern worth naming for future audits: whenever a store checks `if (_connection.State != ConnectionState.Open)` before executing, verify what actually happens in the branch, not just that a branch exists — and separately verify what the *production* DI registration hands to the constructor, since integration tests commonly construct these stores directly with a pre-opened connection instead of going through the real `AddEncinaADO` factory.
- When a finding draws a compound conclusion from two file citations (e.g., "X can appear in both the stuck and expired batches at once"), verify the second citation's filter logic as carefully as the first before asserting the compound claim — a citation can be line-accurate and still support a conclusion the cited code does not actually produce. Finding 5's "appears in both batches" clause did not survive this check on re-read (`GetExpiredSagasAsync`'s own status filter excludes `TimedOut` by construction) even though the underlying defect it was trying to describe (permanent stuck-misclassification) was real; state the narrower, directly-supported claim rather than the broader one that sounds more alarming.
