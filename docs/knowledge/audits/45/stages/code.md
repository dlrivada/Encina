1. **Major** — `ShouldBeConflictError` and `ShouldBeInternalError` (and their TUnit twins) require code prefixes that nothing in Encina emits, so they fail on every real error. Evidence: `src/Encina.Testing.Shouldly/EitherShouldlyExtensions.cs:312-326` (`StartsWith("encina.conflict")` at `:319`) and `:335-349` (`StartsWith("encina.internal")` at `:342`); `src/Encina.Testing.TUnit/TUnitEitherAssertions.cs:234-241` and `:244-251`. A case-insensitive search of `src/` outside the `Encina.Testing*` packages for `"encina\.[a-z_]+` finds the families authorization (17), audit, outbox, inbox, saga, scheduling, dlq, sharding and others, and none of conflict or internal; `EncinaErrorCodes.cs` has no Conflict or Internal constant (the only search hit is the comment at `:93`). The only exercise is a hand-built error: `tests/Encina.UnitTests/Testing/Shouldly/EitherShouldlyExtensionsTests.cs:280` (`TestEncinaErrors.Conflict("encina.conflict.duplicate", ...)`) and `:294`; a search of `src` and `tests` for the two method names finds no other caller. Fails: the same defect class as #1922 (assertion prefix with no producer; "who fails when the code drifts: nobody"), but #1922 lists only `EitherShouldlyExtensions.cs:250`, `:296` and TUnit `:211`, `:231` for validation and not-found, and #1917 is the Pact status mapping, so the conflict and internal assertions (4 methods, 2 packages) are in neither. A user asserting `ShouldBeConflictError()` on the result of a real duplicate-key or concurrency failure gets a failure; the fix is the same as #1922's (shared constants in `EncinaErrorCodes`, produced by the real errors) or deleting the two methods until a producer exists.
2. **Minor** — The async assertion family takes only `Task<Either<...>>`, while the library's own entry points return `ValueTask<Either<...>>`, so `await encina.Send(request).ShouldBeSuccessAsync()` cannot compile. Evidence: `src/Encina/Abstractions/IEncina.cs:46`, `:77`, `:89`, `:108` and `src/Encina.Testing.Fakes/FakeEncina.cs:150`, `:188`, `:202`, `:227` return `ValueTask<Either<EncinaError, ...>>`; the receivers are `this Task<Either<...>>` at `src/Encina.Testing/Assertions/EitherAssertions.cs:358-467` (ten methods), `src/Encina.Testing.Shouldly/EitherShouldlyExtensions.cs:363-442` (seven) and `src/Encina.Testing.TUnit/TUnitEitherAssertions.cs:280-351`. A search of `src` and `tests` for `.AsTask().ShouldBe` finds nothing, and the only callers of the async family are the packages' own unit tests and `tests/Encina.Testing.Examples/Unit/EitherAssertionExamples.cs:121-128`, which builds a `Task.FromResult` by hand; `EncinaTestFixture.SendAsync` (`EncinaTestFixture.cs:454-461`) awaits the `ValueTask` itself. Fails: the headline use of the assertions (assert the result of `IEncina.Send`) is not reachable by the async variants without `.AsTask()`; a `ValueTask<Either<...>>` receiver (or an awaiting helper) is the fix.
3. **Minor** — `ShouldBeSuccess` and `ShouldBeError` throw `LanguageExt.Common.BottomException` instead of an assertion failure for a default `Either`. Evidence: the failure message is built before the check on every call, `EitherAssertions.cs:26-28` and `:117-119` and `EitherShouldlyExtensions.cs:45-49` and `:155-159`, by `result.Match(...)`, which throws on the bottom state. Replica `bottom.cs` (LanguageExt 4.4.9): `default(Either<string,int>)` has `IsRight=False IsLeft=False` and the same `Match` calls threw `BottomException: In a bottom state and therefore cannot proceed`; a success value whose `ToString` throws also throws inside the eagerly built message of `ShouldBeError` (`:119`) before the check. Fails: the Shouldly twin documents bottom as a reachable result (`ShouldBeBottom` and `ShouldNotBeBottom`, `:104-136`, "testing guard methods that output a default Either"), so a test that asserts success on one gets an infrastructure exception, not "Expected success". Build the message lazily, inside the failing branch, and handle the bottom state explicitly.

## Lessons for the pipeline
- Two assertion twins that share method names are an overload-resolution hazard in both directions: check them with a standalone replica that imports both namespaces (one run settled finding 8), and compare their method-name sets mechanically (a regex over `public static` lines, including `async`) before reading them side by side.
- For an assertion helper that matches a code prefix, grep `src/` for producers of the prefix, case-insensitively, per prefix: validation and not-found were already filed (#1922), conflict and internal were not, and the search takes one command.
- A negative claim about an open issue ("does not list X") must be checked against its comments as well as its body; #1171's scope-update comment named the two packages and #1923's checklist already held the validator null checks. Query the dump with comments joined to the body.
- A sibling-package claim of the form "same overload hazard as #N" needs #N's Environment section and the sibling's parameter list; #2319 states that TUnit is not affected, and `TUnitEitherAssertions.cs:294-296` has no `message` parameter.
- A "dead public type" claim needs the search over `src` and `tests` for the type name with the hit lines listed (here six lines, all in the declaring file).
