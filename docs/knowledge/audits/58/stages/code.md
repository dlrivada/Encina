## Findings
1. **Major** — Nothing in `src/` ever writes the module name into the request context, so `IRequestContext.GetModuleName()` returns `null` for every real request and its two production consumers record no module. `RequestContextModuleExtensions.WithModuleName` (`src/Encina/Modules/RequestContextModuleExtensions.cs:68-74`, `:91-97`) is the only writer of the `"Encina.ModuleName"` key (`:11`); `Grep "WithModuleName|Encina\.ModuleName"` over `src/**/*.cs` returns the definitions, their doc examples and the unused `public const ModuleNameKey` at `ModuleBehaviorAdapter.cs:36`, and no call site. `ModuleBehaviorAdapter.Handle` (`ModuleBehaviorAdapter.cs:94-109`) does not set it, and it could not hand an enriched context on: `RequestHandlerCallback<TResponse>` takes no context (`src/Encina/Abstractions/RequestHandlerDelegate.cs:9`) and `WithMetadata` returns a new instance (`IRequestContext.cs:163`). The reader is nevertheless wired into compliance code: `RetentionValidationPipelineBehavior.cs:299` (`moduleId: context?.GetModuleName()` for the retention record) and `ABACDecisionRecordFactory.cs:57` (`ModuleId = inputs.Context.GetModuleName()` in the ABAC decision audit record), so the `ModuleId` stored in those audit records is always `null`. Their tests hide it by fabricating the metadata by hand (`tests/Encina.ContractTests/Compliance/Retention/RetentionValidationPipelineBehaviorContractTests.cs:240`, `tests/Encina.UnitTests/Security/ABAC/DecisionAudit/ABACPipelineDecisionAuditTests.cs:912`). The behavior contract promises the opposite: `IModulePipelineBehavior.cs:65-67` says the context "contains the module name via `IRequestContext.Metadata` with key `"ModuleName"`" (wrong key and never populated), the issue's own task "Add module context to pipeline" is unchecked in the body, and the closing comment advertises `GetModuleName()`, `WithModuleName()`, `IsInModule()` as delivered. The module identity exists only in the ambient `IModuleExecutionContext`, set by one behavior in `Encina.EntityFrameworkCore` (`ModuleExecutionContextBehavior.cs:93-103`). Checks failed: AGENTS.md §6 function 11 (module isolation) and function 12 (audit trail) for the two consumers; known pattern "API with consumers and no producer" (dead public API, AUD-18). #2442 asks for a `ModuleId` on `IRequestContext` and lists "module as a metadata entry" as Option C for the outbox work; it does not say that the metadata key already exists, that nothing sets it, or that Retention and ABAC read it today. Remediation shape is the maintainer's: the producer has to run where the context is created, before the pipeline (the dispatcher knows the request and response types, so it can ask `IModuleHandlerRegistry`), or `IRequestContext` gets a typed `ModuleId` as #2442 proposes; either way the duplicate constant `ModuleBehaviorAdapter.ModuleNameKey` (`:36`, public const on an internal class, never read) goes away. Unexecuted; verifier reproduction: build a provider with `AddEncina` + `AddEncinaModules` + a module behavior that reads `context.GetModuleName()`, send a request handled in the module and assert the value.

2. **Major** — A module behavior cannot be registered for a module as a whole; every request/response pair needs its own `AddEncinaModuleBehavior` call, which defeats the feature's stated purpose. Both overloads require four closed type arguments, `TModule, TRequest, TResponse, TBehavior` (`src/Encina/Modules/ModuleBehaviorServiceCollectionExtensions.cs:43-47`, `:86-91`) and register one `IPipelineBehavior<TRequest, TResponse>` for that single closed pair (`:59`, `:109`); `ModuleBehaviorAdapter` is excluded from assembly scanning (`MediatorAssemblyScanner.cs:91-93`) and is internal (`ModuleBehaviorAdapter.cs:29`), so there is no open-generic route and nothing that enumerates the module's handlers (`ModuleHandlerRegistry` already knows every request/response pair of the module, `ModuleHandlerRegistry.cs:23`, `:85-93`). The issue's motivation is "an Orders module may need audit logging" and its proposed code is `OrderAuditBehavior<TRequest, TResponse> : IModulePipelineBehavior<OrderModule, TRequest, TResponse>` registered with two type arguments; the interface's own example repeats it (`IModulePipelineBehavior.cs:26-28`, `:49` `AddEncinaModuleBehavior<OrderModule, OrderAuditBehavior<,>>()`), and that call does not compile against any overload (there is no overload with two type parameters, and an open generic cannot be passed as `TBehavior` with a fixed `TRequest`/`TResponse`). The delivered usage in the closing comment registers one behavior for `CreateOrderRequest`/`string`. For a module with N handlers a module-wide concern (audit, authorization) needs N registrations and any handler added later runs without it, silently (see finding 4). Checks failed: issue #58 Proposed Solution and Motivation versus delivered code; AUD docs-versus-code accuracy for the XML example. Unexecuted for the compile claim (derived from the two signatures); verifier: paste the `IModulePipelineBehavior.cs:49` line into a test project.

3. **Minor** — The issue's acceptance item "Override mechanism works" (and task "Create behavior override mechanism", Proposed Solution "Ability to override global behaviors at the module level") has no implementation and no tracker. `Grep "override"` over `src/Encina/Modules/*.cs` finds no member that replaces or suppresses a global `IPipelineBehavior` for a module; `ModuleBehaviorAdapter` only runs an additional behavior (`ModuleBehaviorAdapter.cs:101-108`); the closing comment and the archivist's record (`current: unknown`) do not claim it. The open-issue dump has no issue for it (patterns `override.{0,40}global behavior`, `global behavior.{0,60}override`, `module-level override`: 0 hits; `override mechanism` matches only #1722, an unrelated tooling issue). The related pipeline-order work (#2184) orders module behaviors against global ones but does not let a module replace one. Per AGENTS.md §11 an identified gap must be fixed or recorded; whether it is wanted is a maintainer decision (it may simply be dropped from the 1.0 scope), so the remediation is a decision issue, not an implementation. Also unverified and without a benchmark: "No performance impact on non-module handlers" (no benchmark references `ModuleBehaviorAdapter`; see finding 5 for the cost that does exist).

4. **Minor** — A module behavior that can never run gives no signal, at startup or at run time. `ModuleBehaviorAdapter.Handle` returns `nextStep()` when `IsTargetModule()` is false (`ModuleBehaviorAdapter.cs:101-105`) without a log, metric or activity, and "the handler belongs to another module", "the handler's assembly is not a module assembly", "the registry is the Null registry" (`ModuleHandlerRegistry.cs:202-207`) and "the registry failed to load the handler's type" (finding 6) all produce the same `false`. Nothing validates at startup that the `TRequest`/`TResponse` of an `AddEncinaModuleBehavior` registration is handled by `TModule`: `Grep "BelongsToModule"` over `src/**/*.cs` has callers only in the adapter (`ModuleBehaviorAdapter.cs:125`) and the registry itself, and the ordering validator (`PipelineOrderValidationHostedService`) checks stages, not module ownership. A mis-registered behavior (wrong `TModule`, handler in a different assembly than the module's `HandlerAssembly`) is therefore indistinguishable from a working one until someone notices the missing audit entry. #2752 fixes one cause (registration order) and none of the diagnosability. Checks failed: AGENTS.md §3 "errors are never swallowed", §3 registration completeness ("proven by a DI test"), §6 function 3 (structured logging) and 2 (OpenTelemetry) for a new pipeline behavior; severity Minor because the skip is the documented behavior and the consequence depends on what the behavior is.

5. **Minor** — The per-request ownership test does reflection and allocates on every call. `ModuleBehaviorAdapter.IsTargetModule` (`ModuleBehaviorAdapter.cs:119-126`) builds `typeof(IRequestHandler<TRequest, TResponse>)` and calls `BelongsToModule(type, name)`, which calls `GetModule` (`ModuleHandlerRegistry.cs:158`); `GetModule` runs `IsInterface`, `IsGenericType`, `GetGenericTypeDefinition()` and `GetGenericArguments()` (`:116-122`, the last one allocates a `Type[]` per call) and only then the tuple lookup (`:147`), then `string.Equals(..., OrdinalIgnoreCase)` (`:160`). The adapter is a closed generic, so `(TRequest, TResponse)` and the target module name are known at construction and the answer cannot change after the registry is built; the whole test can be a field computed once (or a direct `GetModuleForRequest(typeof(TRequest), typeof(TResponse))` without the reflection). The same lookup shape is repeated per request in `Encina.EntityFrameworkCore/Modules/ModuleExecutionContextBehavior.cs:90-93`. Known failure pattern: per-request reflection in a pipeline behavior (audit #49); it also bears on the issue's unmeasured acceptance item "no performance impact on non-module handlers". Not measured; verifier: `GC.GetAllocatedBytesForCurrentThread` around 1,000 `Handle` calls on an adapter whose handler belongs to the module.

6. **Minor** — `ModuleHandlerRegistry.GetLoadableTypes` swallows the load failure and the registry then answers "not in a module". The `catch (ReflectionTypeLoadException ex)` at `src/Encina/Modules/ModuleHandlerRegistry.cs:79-82` returns the types that loaded and drops `ex.LoaderExceptions`; the constructor has no logger and throws nothing (`:32-49`). A handler whose type fails to load (a missing optional dependency of the module assembly) is simply absent from `_requestToModuleCache` (`:90`), so every module behavior for that request is skipped (finding 4) and the module's host never learns why. Checks failed: AGENTS.md §3 "errors are never swallowed" (the scan runs at registration time, not in a background service, so Minor); the same swallow-and-continue shape is already filed for `EventUpcasterRegistry` as #2191, which is the only open issue naming `ReflectionTypeLoadException` against this pattern and does not cover this file. Also in the same scan: when two descriptors declare a handler for the same request/response pair the later one silently overwrites the earlier (`:90` indexer assignment), same class as #2755's last-wins for shared assemblies but for distinct assemblies.

7. **Minor** — Stale and wrong XML documentation in the delivered public types. (a) `IModulePipelineBehavior.cs:18-19`: "Phase note (#2184): the stage contract is declared but not yet applied; until the order resolver lands, behaviors still run in registration order". The resolver has landed and is applied: `Core/ServiceCollectionExtensions.cs:65-68` registers `PipelineOrderResolver`, `Pipeline/PipelineBuilder.cs:45` and `Core/Encina.cs:179` use it, and the adapter itself reports `DeclaredStage`/`DeclaredOrder` from `PipelineStageLookup` (`ModuleBehaviorAdapter.cs:78-81`). (b) `IModulePipelineBehavior.cs:67`: metadata key `"ModuleName"`, the real key is `"Encina.ModuleName"` (`RequestContextModuleExtensions.cs:11`). (c) `ModuleBehaviorAdapter.cs:33-36` documents a public key constant that nothing reads (finding 1). (d) `ModuleBehaviorServiceCollectionExtensions.cs:32` says to call the method after `AddEncinaModules`; the factory resolves `TModule` and the registry lazily (`:61-63`), so the order between the two does not matter for this method, while the order of `AddEncina` and `AddEncinaModules` does (#2752), which the remark does not say. Fails AGENTS.md §8 (XML comments on public API must be accurate) and AUD docs-versus-code accuracy; the example problem of the same file is in finding 2.

## Lessons for the pipeline
- An extension class that adds `WithX`/`GetX` for a context key needs a producer search before anything else (`Grep "WithX\("` over `src/` for call sites): here the key had two production readers in compliance code and no writer, and the tests fabricated the value by hand (finding 1).
- When an issue's body shows registration code (`AddEncinaModuleBehavior<OrderModule, OrderAuditBehavior>()`), compare its type-argument shape with the delivered overloads and with the closing comment's usage: the delivered signature quietly narrowed the use case from "module-wide" to "one closed request type" (finding 2).
- A dropped acceptance item ("Override mechanism works") found by the archivist as `current: unknown` needs a one-line open-issue search by its words before it becomes a finding; the search takes one query on the scratch dump (finding 3).
