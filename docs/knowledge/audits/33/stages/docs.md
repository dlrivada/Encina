## Findings
1. **Blocker** — `docs/architecture/adr/001-railway-oriented-programming.md:211-213` ("When Exceptions are NOT Allowed", "API Entry Points") gives the error codes `request.null`, `notification.null`, `request.handler.missing` and `request.handler.type_mismatch`. The real constants in `src/Encina/Errors/EncinaErrorCodes.cs` are `RequestNull = "encina.request.null"` (:12), `NotificationNull = "encina.notification.null"` (:15), `RequestHandlerMissing = "encina.request.handler_missing"` (:30) and `RequestHandlerTypeMismatch = "encina.request.handler_type_mismatch"` (:33). All four identifiers differ (missing `encina.` prefix; `.handler.missing` vs `.handler_missing`; `.handler.type_mismatch` vs `.handler_type_mismatch`), so a caller that matches `GetCode()` against the documented strings never matches. Check that fails: real API (encina-docs SKILL section 6, procedure step 2). The same ADR spells the stream code with a capital E in `Encina.handler.missing` at `:78` (the `Code` property comment) and `:160` (the "Failure Path" example), and the handler-exception code as `Encina.handler.exception` at `:107` ("Safety Net") and `:233` ("Exception Safety Net"); the real constants are lowercase (`EncinaErrorCodes.HandlerMissing = "encina.handler.missing"` at :27, `HandlerException = "encina.handler.exception"` at :42), so none of these strings matches. `:160` is `Encina.Send(new DeleteUserCommand(invalidId))`, and `Send` answers a missing handler with `encina.request.handler_missing` (`src/Encina/Pipeline/EncinaRequestGuards.cs:78`, `src/Encina/Dispatchers/Encina.RequestDispatcher.cs:83`); `encina.handler.missing` is the stream code. The fix for `:160` is therefore the right code, `encina.request.handler_missing`, not only the case. The exception safety net itself (`:107`, `:228-237`: "caught at the dispatcher level") is a separate subject, tracked by open #1800 (reconcile ADR-001 and ADR-006 on the exception safety net); reference it, do not duplicate it. Related open issues: #1177 item 3 covers the ADR-001 `EncinaError` shape (`Code`/`Details` properties) in the same ADR, but not these code strings (search of its body and comments for `request.null`, `notification.null`, `handler_missing`: none). Extend #1177 or open a new one.
2. **Major** — No reader-facing page states the contract that #33 delivered. `docs/architecture/request-pipeline.md:30` (`Send`) and `:65` (`Publish`) describe dispatch but never say that a null request or notification answers `Left` with `encina.request.null` / `encina.notification.null` before any scope, activity or handler resolution (`src/Encina/Core/Encina.cs:87-91`, `:102-106`); `docs/architecture/patterns-guide.md:643-729` ("Guard Clauses") shows only the request guard (`TryValidateRequest`), and its text never mentions `TryValidateNotification` (the `Publish` half of #33; `Select-String` for `TryValidateNotification` in the page: 0 hits). The only statement is the ADR-001 line in finding 1, which is also wrong. The knowledge record lists the destination as a regression test only. Check that fails: rule (a) point 5 (a delivered behaviour needs a page that states it) and the Diátaxis reference quadrant (error codes are reference material). Fix: one row each for the null request and null notification codes in a reference table (the error-code table of the page that documents `EncinaErrorCodes`, or `request-pipeline.md`), plus the notification guard in the patterns-guide section. Related open issues: none names this (searched #1177, #2016, #1955, #1318, #1911 bodies for `TryValidateNotification`, `notification.null`, `Guard Clauses`: #2016 only converts the patterns-guide ASCII flows and the Factory sample, not the Guard Clauses section).
3. **Minor** — `docs/architecture/patterns-guide.md:713-721` ("Guard Clauses", "Usage") shows `Send<TResponse>(IRequest<TResponse> request, CancellationToken ct = default)` calling `RequestDispatcher.ExecuteAsync(this, request, ct)`. The real `Send` delegates to `SendCore` (`src/Encina/Core/Encina.cs:62-63`, `:85-97`), which logs `Log.NullRequest`, resolves the ambient `IRequestContext` through `AmbientRequestContext.Resolve` and calls `ExecuteAsync(this, request, context, cancellationToken)` (`:95`); the sample has no context argument, so it does not compile against the real `ExecuteAsync` and omits the `Publish` twin. The same omission is at `:134` and `:821`. Check that fails: C# samples correct against `src/` (rule (a) point 2). Nearest open issues: #2016 (the Factory sample at `:595-633` and `:825`, a different sample of the same page; the Guard Clauses sample is not named there) and #1177 item 2 ("`docs/architecture/patterns-guide.md` shows API that does not exist"), which covers the page generally and is related, not a duplicate.

5. **Minor** — `docs/architecture/request-pipeline.md:65` (the `Publish` paragraph) says "both parallel strategies run every handler and surface the first `Left` encountered once all of them finish". That is true of neither strategy. `ParallelDispatchStrategy` is fail-fast: its summary says "First error cancels remaining handlers via linked cancellation token" (`src/Encina/Dispatchers/Strategies/ParallelDispatchStrategy.cs:6-9`) and it captures the first error and calls `cts.Cancel()` (`:128-133`), so the remaining handlers do not run to completion. `ParallelWhenAllDispatchStrategy` runs every handler but aggregates all failures into one error: "Errors are aggregated into a single `EncinaError` containing all failure details" (`src/Encina/Dispatchers/Strategies/ParallelWhenAllDispatchStrategy.cs:6-9`, `:66-89`, `CreateAggregateError` at `:128-154`); it returns the single error only when exactly one handler failed (`:85`). Check that fails: accuracy against today's code (encina-docs SKILL section 6, procedure step 2). Fix: describe the two strategies separately in a two-row table (fail-fast with cancellation; run all and aggregate). Related open issues: none names this sentence (searched open issues for `ParallelDispatchStrategy`, `ParallelWhenAll`, `surface the first` and `request-pipeline`; #1911 covers only the behavior-order wording in the same page, #1318 names `SequentialDispatchStrategy.cs:11` (its "backward compatibility" remark, finding 4) but does not cover the `request-pipeline.md:65` sentence about the parallel strategies, #341 is a feature proposal).

## Lessons for the pipeline
- For a core-API refactor audit with no shipped page, search the docs for the error-code strings the change returns (`encina.request.null`): the only hit was an ADR that carried the code without its prefix, which a symbol search for the class names would not have found.
- A page that links a Spanish analysis document from a published index (`docs/architecture/index.md:20`) is easy to miss because the file name is English; check the language of every page the section index links when a delta touches that section.
