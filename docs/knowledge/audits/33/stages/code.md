## Findings
1. **Minor** — `src/Encina.Testing.Fakes/FakeEncina.cs:154` (`Send`), `:232` (`Publish`) and `:250` (`Stream`) call `ArgumentNullException.ThrowIfNull` on a null request or notification, while the real dispatcher returns `Left` with `encina.request.null` / `encina.notification.null` (`Encina.cs:87-91`, `:102-106`, `Encina.Stream.cs:30-35`), which is the behaviour issue #33 asked for and delivered. A test written against `FakeEncina` that expects the `Left` (the ROP contract, AGENTS.md section 3 "Railway Oriented Programming") gets an exception instead, and a test that passes against the fake by catching `ArgumentNullException` fails against the real `Encina`. Fails: provider coherence principle (a double must answer like the implementation) and ADR-001/006. The fake's three null paths can reuse the same guard results (`EncinaRequestGuards` is `internal` to `Encina`, so the fix is to return `EncinaErrors.Create(EncinaErrorCodes.RequestNull, ...)` / `NotificationNull` directly). The same divergence exists in the no-setup answer of `FakeEncina.Send`: with neither a response nor an error configured it returns `EncinaErrorCodes.HandlerMissing` = `encina.handler.missing` (`FakeEncina.cs:178-180`, constant at `EncinaErrorCodes.cs:27`), while the real `Send` with no registered handler answers `encina.request.handler_missing` (`EncinaRequestGuards.cs:78`, `EncinaErrorCodes.cs:30`, `RequestDispatcher.cs:81-83`); `HandlerMissing` is the stream code (`StreamDispatcher.cs:41`). A test that asserts the real code fails against the fake and the reverse. Open issues searched (body and comments, `FakeEncina`, `encina.request.null`, `encina.notification.null`): none covers it.
2. **Minor** — `src/Encina/Dispatchers/Encina.RequestDispatcher.cs:91-98`: when `TryValidateHandlerType` fails (a handler of the wrong type is registered), the dispatcher logs `Log.HandlerMissing` (`:93`, EventId 107, message "No registered IRequestHandler was found for {RequestType} -> {ResponseType}.") although a handler WAS found. The returned error is correct (`RequestHandlerTypeMismatch`, `:95`, `:98`) but the log tells the operator to register a handler that is already registered, so the misconfiguration the guard exists to catch is mis-diagnosed in the logs. Fails: AGENTS.md section 3 structured logging intent (section 6 function 3, "operational visibility"); no dedicated `[LoggerMessage]` exists for the mismatch in `Encina.cs:205-251`. Open issues searched (`HandlerMissing`, `RequestHandlerTypeMismatch`, `TryValidateHandlerType`): none covers it.
3. **Minor** — `src/Encina/Dispatchers/Encina.NotificationDispatcher.cs:215-221` looks the invoker up with the key `(handlerType, desiredNotificationType)`, where `desiredNotificationType` is the notification's runtime type (`:164-167`), but the compiled invoker is stored under `(handlerType, handledType)` with `handledType = method.GetParameters()[0].ParameterType` (`:244-249`). The handlers come from `serviceProvider.GetServices(typeof(INotificationHandler<>).MakeGenericType(notificationType))` with the runtime type (`:63-64`). Microsoft.DependencyInjection does not apply the contravariance of `INotificationHandler<in TNotification>` (`src/Encina/Abstractions/INotificationHandler.cs:36`) when resolving: the verifier ran MS.DI 10.0.12 and a handler registered as `INotificationHandler<IDomainEvent>` gives 0 handlers for `INotificationHandler<Evt>`, so the XML doc claim of polymorphic resolution (`:21`, `:29-30`) holds only for an explicit registration under the derived interface (for example `AddScoped<INotificationHandler<Evt>, BaseHandler>()`, which compiles through the contravariance). Only in that case does a handler of a base type or interface (`Handle(IDomainEvent, ...)`) reach the dispatcher for a derived notification: the two keys differ, the first lookup always misses, and every Publish to such a handler re-runs `ResolveHandleMethod` (`GetMethods` plus LINQ, `:345-373`) and `EncinaNotificationGuards.TryValidateHandleMethod` (`GetParameters`, `typeof(Task<>).MakeGenericType`, `EncinaNotificationGuards.cs:13-29`) before reaching the cache at `:245-249`. The cache comment at `:214` says the lookup is the hot-path optimisation; for handlers registered that way it is not. The miss was reached by reading the keys, and the precondition (explicit registration under the derived interface) by the verifier's MS.DI run; the cost was not measured. The case is narrow, so the priority stays Low. Open issues searched (`NotificationHandlerInvokerCache`, `TryGetNotificationExecutor`, `ResolveHandleMethod`): none covers it (#1998 names `Encina.NotificationDispatcher.cs` for documentation and coverage obligations; #341 and #560 name the class `NotificationDispatcher` for fanout strategies and benchmarks; none mentions the cache-key mismatch).
4. **Minor** — The cancellation-token guard the issue body listed ("Guard clauses for cancellation token validation", "Send ... has proper guard clauses for ... cancellation token validation") was never delivered, and its premise is false: `Send` has no cancellation check either (`Encina.cs:85-97`). `PublishCore` (`Encina.cs:99-112`) creates the scope, the activity and resolves every handler for an already-cancelled token, and the default Sequential strategy never reads the token between handlers (`SequentialDispatchStrategy.cs:30-37`), while the Parallel strategy does (`ParallelDispatchStrategy.cs:110`). Cancellation therefore depends on each handler cooperating (the existing test uses a handler written to do so, `tests/Encina.UnitTests/Core/EncinaTests.cs:796-825`); a handler that ignores the token keeps running and the next handlers are still invoked under the default strategy. The strategies disagree on what a cancelled Publish does. Fails: the issue's own acceptance item, and consistency between the dispatch strategies. The fix is a maintainer decision (a pre-dispatch check in both `SendCore` and `PublishCore`, a per-handler check in the Sequential strategy, or documenting cooperative-only cancellation), so it should not be drafted as a decided change. Open issues searched (`cancellation guard`, `pre-cancelled`, `already cancelled`, `SequentialDispatchStrategy`): #1337 is DataAnnotations cancellation tests and #1724 a skipped pipeline test; neither covers it.
5. **Minor** — `src/Encina/Dispatchers/Encina.RequestDispatcher.cs:201-208` (`DetermineRequestKind`, reached through `GetRequestKind` at `:186-197`) tests `typeof(ICommand).IsAssignableFrom(requestType)` and `typeof(IQuery).IsAssignableFrom(requestType)`, the non-generic interfaces. `ICommand : ICommand<Unit>` (`src/Encina/Abstractions/CqrsContracts.cs:36`) and `IQuery : IQuery<Unit>` (`:67`), so the inheritance runs one way: a request typed only with `ICommand<T>` or `IQuery<T>` is not assignable to `ICommand` / `IQuery`. The verifier confirmed it by reflection against the built `Encina.dll` (`ICommand<Guid>` and `ICommand<Unit>` assignable to `ICommand` = False, `ICommand` to `ICommand<Unit>` = True, `IQuery<string>` to `IQuery` = False). Every request declared with the generic forms, including the documented example `CreateReservation : ICommand<Unit>` (`CqrsContracts.cs:16`) and `GetAgendaById : IQuery<...>` (`:49`), is therefore labelled `"request"` instead of `"command"` / `"query"` in the activity tag (`EncinaDiagnostics.cs:12-16`, called at `Encina.RequestDispatcher.cs:58`) and in `TrackSuccess` / `TrackFailure` (`:83`, `:95`, `:128`, `:132`, `:159`; the `request.kind` dimension at `IEncinaMetrics.cs:58`, `:71`), against the XML doc at `:172-175` and its remarks on metrics segmentation (`:181`). Only requests implementing the non-generic `ICommand` / `IQuery` get the right label. `CommandMetricsPipelineBehavior.cs:35` and `QueryMetricsPipelineBehavior.cs:35` hardcode their kind, so a registered metrics behavior reports correctly while the dispatcher's own series for the same request says `"request"`. Fails: the method's own XML contract and the observability intent of AGENTS.md section 6 function 2. The fix is to test `ICommand<>` / `IQuery<>` as the eight `ReadWriteRoutingPipelineBehavior` copies do (see Siblings audited). Judged Minor (a wrong label, no functional failure); the maintainer may rate it higher because it affects the typical CQRS request. The verifier's duplicate scan over the open issues (term `DetermineRequestKind`) found none; this stage did not search `gh` itself.

## Lessons for the pipeline
- When an issue is "make X consistent with Y", the code stage should also check the test doubles of the abstraction (`FakeEncina` here), not only the real implementation: a fake that throws where the real code returns `Left` is a second implementation of the same guard that nobody audits.
- A claim in an issue body about the reference behaviour ("Send has cancellation token validation") must be checked against the reference code before the unmet half is treated as a gap; here the premise was false, so the finding is about the missing decision, not about a copy that was left behind.
- A claim that a framework resolves something through variance (contravariant `INotificationHandler<in T>`) needs a short check against MS.DI before it is written as fact; the verifier's run showed 0 handlers for a base-typed registration (finding 3).
- When a method classifies a type by a marker interface, check the inheritance direction of the generic and non-generic forms (`ICommand : ICommand<Unit>`) and compare with the sibling copies of the same test (finding 5); the code stage read `DetermineRequestKind` and missed it on the first run.
