## Findings
1. **Major** — `.github/workflows/ci-full.yml:531-541` and `:569-578`: the `pack` job runs with `if: always() && needs.build.result == 'success'`, so it runs after any test job fails, `test-contract` included, and the tag-gated step "Publish to GitHub Packages" (`:569-578`, `if: startsWith(github.ref, 'refs/tags/v')`) then pushes the package. The test jobs are only listed in `needs:` (`:532-538`) to order the jobs; `always()` discards their results and nothing checks them. Evidence in the run history: CI Full run 35652357800 (workflow_dispatch, 2026-09-21) had `test-property`, `test-guard`, `test-unit`, `test-integration` and four `test-ef-providers` shards failed and `pack` concluded `success`; on a `v*` tag push the same wiring publishes. `test-contract` has the identical wiring (`ci-full.yml:197-199`, `:535`), so a red contract suite does not stop a release. Fails AGENTS.md section 8 ("CI enforces: all tests pass") and the known pattern "a MUST rule with no enforcing job" (lesson of audit #19; here the gate that would enforce it exists and ignores the result), and the fail-closed spirit of the SPEC-000 DEC-006 single-gate design that `ci.yml` follows with `ci-result`. Fix direction: drop `always()` or require every `needs.*.result` to be `success` for the publish step; CI Full has no aggregate job like `ci-result`. I found no open or closed issue for it (`gh issue list --state all --search` for "ci-full pack", "pack job needs.build.result", "tag push publish gate tests": no match).
2. **Minor** — `.github/workflows/ci.yml:257-275` (and `:296-314`, `:335-353`, `:122-162`, `:183-236`, `:379-463`; `ci-full.yml:197-215` and siblings): every test job runs `needs: build`, downloads the `build-output` artifact (`ci.yml:267-269`) and then calls `dotnet test <csproj> -c Release` without `--no-build`, so it restores and compiles the test project and its src references again. The artifact only carries dlls, pdbs, deps and `*.assets.json` (`ci.yml:109-119`), not the obj state MSBuild needs for an incremental build. Measured on the last scheduled run (36374317260): the `Run Contract tests` step took 3 min 28 s (03:51:10 to 03:54:38) while the log reports the tests themselves at `Duration: 3 s` for 1860 tests; the `build` job's own `Build` step took 7 min 13 s. Consequences: about 3 minutes of every contract job and the same in each of the other test jobs is a rebuild; the test job compiles without `-warnaserror` (the `build` job compiles with it, `ci.yml:107`), so the artifact the `build` job produced is not the binary under test; the `needs: build` ordering and the artifact download buy nothing but a gate. Fails the cost side of the two-tier design in #1097 (not a duplicate: #1097 is the tier design, this is the missing flag). `--no-build` was searched over `.github/workflows/*.yml`: the only hit is `testing-dogfooding-validation.yml:52`.

## Lessons for the pipeline
- A gate job that lists the test jobs in `needs:` but runs under `always()` is not gated on them. For CI scopes, check every job downstream of the test jobs (pack, publish, coverage), not only the test jobs and `ci-result`, and test the claim against the run history (`gh run view <id> --json jobs`) instead of only reading the YAML.
- A first reading of `needs.build.result` in a job that does not list `build` in `needs:` looked like a dead condition; the run history (`pack` skipped when `build` failed, `success` otherwise) showed it works. Check a suspected dead expression against real runs before reporting it.
