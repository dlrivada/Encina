## Findings

1. **Blocker** — The four SQL Server saga DDL scripts cannot hold a saga written by the stores #38 changed. `src/Encina.ADO.SqlServer/Scripts/003_CreateSagaStatesTable.sql:6-20`, `src/Encina.ADO.SqlServer/Scripts/000_CreateAllTables.sql:69-83`, `src/Encina.Dapper.SqlServer/Scripts/003_CreateSagaStatesTable.sql:6-20` and `src/Encina.Dapper.SqlServer/Scripts/000_CreateAllTables.sql:69-83` define `SagaStates` without a `TimeoutAtUtc` column (a grep for `TimeoutAtUtc` over `*.sql` under `src/` matches only the MySQL and PostgreSQL scripts: `.../ADO.PostgreSQL/Scripts/003_CreateSagaStatesTable.sql:17`, `.../ADO.MySQL/Scripts/003_CreateSagaStatesTable.sql:17`, and the Dapper and `000` counterparts) and with `[Status] INT NOT NULL -- 0=Running, 1=Completed ...` while every store writes the string statuses (`SagaStatus.Running = "Running"`, `SagaOrchestrator.cs:544`). `SagaStoreADO.AddAsync` (`src/Encina.ADO.SqlServer/Sagas/SagaStoreADO.cs:75-79`) and `SagaStoreDapper.AddAsync` (`src/Encina.Dapper.SqlServer/Sagas/SagaStoreDapper.cs:67-73`) insert `TimeoutAtUtc` and a string `Status`, and `MapToSagaState` reads `GetOrdinal("TimeoutAtUtc")` (`SagaStoreADO.cs:250`), so on a table created from the scripts every `AddAsync` fails (invalid column name, and 'Running' cannot convert to int) and the saga store of two of the ten providers is unusable. Both READMEs send the user to these scripts (`src/Encina.ADO.SqlServer/README.md:63-73`, `src/Encina.Dapper.SqlServer/README.md:57-71`). Commit 3cc4d57b changed no script (`git show 3cc4d57b --stat` lists no `Scripts/` file); #1303 (#1261) later rewrote the PostgreSQL and MySQL scripts (both carry `timeoutatutc`/`TimeoutAtUtc`, `correlationid`, `metadata` and a string status) but not SQL Server, so this is the SQL Server copy the later fix did not reach. The tests do not see it: `tests/Encina.TestInfrastructure/Schemas/SqlServerSchema.cs:72-88` creates its own `SagaStates` with `Status NVARCHAR(50)`, `TimeoutAtUtc`, `CorrelationId` and `Metadata`, and no test compares it with the shipped script (#1872 guards `000` against `028` only). Fails AGENTS.md section 5 (all 10 providers; provider coherence) and AUD-07. Fix: align the four scripts with the PostgreSQL ones: the stores need the string `Status NVARCHAR(50)` and `TimeoutAtUtc DATETIME2(7) NULL`. `CorrelationId` and `Metadata` are parity with the EF Core `SagaState` and the test schema, not a store requirement: no ADO.NET or Dapper saga store (SQL Server, PostgreSQL or MySQL) reads or writes either column (a search for `CorrelationId|Metadata` over the six `Sagas/SagaStoreADO.cs` and `Sagas/SagaStoreDapper.cs` files in the worktree returns no match). Add a test that builds the schema from the shipped script.

2. **Major** — `TimedOut` is a dead-end status: the orchestrator marks a saga timed out and then offers no way to compensate it. `SagaOrchestrator.TimeoutAsync` (`SagaOrchestrator.cs:435-469`) sets `Status = TimedOut` (`:458`) and returns `state.CurrentStep`, and its summary says "Marks a saga as timed out and starts compensation" (`:430`) and `SagaStatus.TimedOut` says "is being compensated" (`:566-568`), but nothing starts it: `StartCompensationAsync` accepts only `Running` or `Compensating` (`:258`), and `CompensateStepAsync` requires `Compensating` (`:313`), so a `TimedOut` saga is rejected by both with `saga.invalid_status`; the only call that accepts it is `FailAsync` (`:350-373`, no status check), which ends the saga as `Failed` without any compensation. From `Compensating` the effect is worse: `TimeoutAsync` is allowed there (`:452`) and flips a saga whose compensation is under way to `TimedOut`, so the next `CompensateStepAsync` of `SagaRunner.CompleteCompensationAsync` (`SagaRunner.cs:219-225`) returns a `Left` and the run reports an error with the compensation unfinished; it also overwrites `ErrorMessage` (`:459`), losing the failure code that `StartCompensationAsync` stored (`:264`). The saga then leaves every monitoring query: the seven SQL stores (ADO x3, Dapper x3, EF) filter `Running`/`Compensating` in `GetStuckSagasAsync` and `GetExpiredSagasAsync` (for example `SagaStoreADO.cs:158, :199`, `SagaStoreEF.cs:95, :116`), and `CompletedAtUtc` is not set. The archivist's decision item ("returns the current step from which compensation should start; it does not run compensation itself") is true of the method but the code gives the caller no legal next call. Fails AUD-01 (code does not do what the issue decided: time out, then compensate) and AGENTS.md section 3 (errors never reported as success: the saga stays in a state nobody finds). Fix: decide the transition (let `StartCompensationAsync`/`CompensateStepAsync` accept `TimedOut`, or have `TimeoutAsync` itself move to `Compensating` with `SagaErrorCodes.Timeout`), keep the original error code, and make the monitoring queries and the `Log`/status docs agree. Overlap: #1886 only proposes documenting this difference (its "TimedOut in the Saga States diagram" item); this is the code defect behind it.

3. **Major** — Saga timeouts are recorded and counted but never enforced. `SagaOrchestrator.TimeoutAsync` has no caller in `src/` (a grep for `.TimeoutAsync(` over `src/Encina.Messaging` finds none; the repository-wide grep for `TimeoutAsync\(` over `*.cs` finds `src/` only at `SagaOrchestrator.cs:435`), `GetExpiredSagasAsync` is called only by `SagaHealthCheck.cs:56` and the orchestrator wrapper (`SagaOrchestrator.cs:476-481`), and `RegisterSagas` (`MessagingServiceCollectionExtensions.cs:299-314`) registers no background service, whereas Outbox, Scheduling, DeadLetter and Recoverability each have one (`OutboxProcessorBase.cs:43`, `ScheduledMessageProcessor.cs:48`, `DeadLetterCleanupProcessor.cs:13`, `DelayedRetryProcessor.cs:27`). `AdvanceAsync` (`:145-192`) and `CompleteAsync` (`:200-232`) never compare `TimeoutAtUtc` with the clock, so a saga past its deadline advances and completes normally. Yet the public surface promises enforcement: `SagaDefinition.WithTimeout` ("The maximum duration before the saga times out", `SagaDefinition.cs:98-108`) is passed to `StartAsync` by `SagaRunner.cs:78-82` and then ignored; `SagaOptions.DefaultSagaTimeout` ("all new sagas will have this timeout", `SagaOrchestrator.cs:595-603`); `ISagaState.TimeoutAtUtc` ("the saga will be marked as timed out if it hasn't completed by this time", `ISagaState.cs:77-80`); and `SagaRunner.cs:180-182` justifies leaving a saga `Running` because it is "recoverable by timeout/stuck-saga handling", which does not exist (no caller of `GetStuckSagasAsync` outside the health check either). This is the part of the issue the record calls `pending-work`: the issue asked for `RequestTimeout<T>()`, a timeout handler and scheduler integration (none exists) and the shipped primitives stop at detection. Fails AUD-01 and the cross-cutting check of AGENTS.md section 6 (functions 6 resilience, 7 locks and 12 audit: a processor that times sagas out would need a lock or leader election so two instances do not time out the same saga). Pattern choice is a maintainer decision (an opt-in `SagaTimeoutProcessor` in the style of `ScheduledMessageProcessor`, built on finding 2's fix, versus declaring detection-only and removing the enforcement wording), so the remediation issue should carry `needs-decision`.

4. **Minor** — `TimeoutAsync` persists English prose where the sibling methods persist an error code, and the code constant exists but is unused. `SagaOrchestrator.cs:459` writes `state.ErrorMessage = "Saga exceeded its configured timeout"`, while `StartCompensationAsync` (`:240-242, :264`) and `FailAsync` (`:343-347, :362`) document and persist only an error code in `ISagaState.ErrorMessage`; `SagaErrorCodes.Timeout = "saga.timeout"` (`SagaErrorCodes.cs:51`) has no reference in `src/` (grep for `SagaErrorCodes.Timeout|saga\.timeout` over `src/` matches only the definition). A consumer that groups failures by the stored code sees one literal sentence for timeouts and codes for everything else. The text is a constant, so there is no personal-data leak (AUD-13 holds). Fix: store `SagaErrorCodes.Timeout`, and log it in `Log.SagaTimedOut` (`:672-676`), which today logs only the step.

5. **Minor** — The timeout inputs are not validated and one invalid value makes a store throw instead of returning `Left`. `StartAsync(sagaType, data, TimeSpan? timeout, ...)` (`SagaOrchestrator.cs:95-110`) accepts a zero or negative `timeout`, and `SagaOptions.DefaultSagaTimeout` (`:603`) is unvalidated, so `timeoutAtUtc` equals or precedes `now` and the saga is expired from its first moment; `SagaDefinition.WithTimeout` does reject non-positive values (`SagaDefinition.cs:105`), so the low-ceremony path and the orchestrator disagree. `SagaOptions.ExpiredSagaBatchSize <= 0` reaches `GetExpiredSagasAsync` of the SQL stores, which throw `ArgumentException` outside the `Either` in `GetExpiredSagasAsync`, through `SagaOrchestrator.cs:476-481`. The throw lines, printed per store: ADO SqlServer `SagaStoreADO.cs:189-190`; ADO PostgreSQL and MySQL `SagaStoreADO.cs:190-191`; Dapper SqlServer `SagaStoreDapper.cs:155-156`; Dapper PostgreSQL and MySQL `SagaStoreDapper.cs:156-157` (each under `src/Encina.<ADO|Dapper>.<provider>/Sagas/`). Fix: validate in `StartAsync` and validate `SagaOptions` at registration.

6. **Minor** — `FakeSagaStore` does not match the real stores for expired and stuck sagas. `src/Encina.Testing.Fakes/Stores/FakeSagaStore.cs:143` selects expired sagas with `s.Status == "Running"` and `:125` selects stuck sagas the same way, while the seven SQL stores and MongoDB's expired query include `Compensating` (`SagaStoreEF.cs:116`, `SagaStoreMongoDB.cs:155`), and the fake does not order by `TimeoutAtUtc`. A test of a compensating saga past its timeout passes against the fake and would behave differently in production, the shape of the test-double drift that AUD checks for "make X consistent" issues. Fix: include `Compensating` and order by `TimeoutAtUtc` in the fake, with a contract test run against both.

7. **Minor** — `SagaStoreMongoDB.AddAsync` drops the timeout when it copies a foreign `ISagaState`. `src/Encina.MongoDB/Sagas/SagaStoreMongoDB.cs:72-83` builds a `SagaState` from the interface without `TimeoutAtUtc`, so a saga created by any state factory other than the MongoDB one is stored with no deadline and is never returned by `GetExpiredSagasAsync` (`:154-158`). The MongoDB factory passes the value (`SagaStateFactory.cs:29`), so the production path is unaffected today; the EF store rejects a foreign type outright (`SagaStoreEF.cs:53-57`) and the ADO and Dapper stores map every property. Open issue #1470 does not cover this: it is about `SagaStoreMongoDB.GetStuckSagasAsync` (`:129-132`) having no status filter, a different method and a different defect; it shares only the file, and no open issue mentions the `as SagaState ?? new SagaState` copy in `AddAsync` (searched title, body and comments of all 1155 open issues). Fix: copy `TimeoutAtUtc` (and the other interface members) or reject the foreign type as EF does.

8. **Minor** — `TimeoutAsync` is a read-modify-write with an unconditional update, which becomes a lost-update hazard as soon as finding 3 gives it a caller. It checks the status on the loaded copy (`SagaOrchestrator.cs:452`) and then every store writes with `WHERE SagaId = @SagaId` only (`SagaStoreADO.cs:119`, the same in the Dapper stores `SagaStoreDapper.cs:95`, MongoDB `:97`, and EF has no concurrency token: no `RowVersion`, `IsConcurrencyToken` or `[ConcurrencyCheck]` under `src/Encina.EntityFrameworkCore/Sagas`). A runner that completes the saga between the load and the write has its `Completed` overwritten by `TimedOut`, and the reverse. Static reading, not executed; latent because nothing calls `TimeoutAsync` today. Fix with finding 3: make the update conditional on the expected status (or add a version column) and return a `Left` when no row matched.

## Lessons for the pipeline

- When a commit adds a column to a persisted entity, grep the shipped SQL scripts of every provider (`*.sql` under each package's `Scripts/`) for the column name, not only the store code; the test schema (`tests/Encina.TestInfrastructure/Schemas`) is hand-written and hides a stale shipped script, which is how the SQL Server saga DDL stayed broken for the whole life of #38.
- For a "timeout"/"expiry" feature, trace from the persisted deadline to the first line that acts on it (here: nothing) before reading the stores; the checklist is "who calls the new method, which hosted service runs it, which status transition follows it".
- A state-machine method that moves an entity to a new status needs its outgoing transitions read in the same pass: `TimedOut` is accepted by no other method, which a per-method review of `TimeoutAsync` alone would not show.
- When a finding says "the same line in the other stores", print the line per store: the throw sat at three different line numbers across six files (pass-1 verifier correction 8). When a fix proposes columns, check that the store reads them before calling them required.
- A finding in a file that already has an open issue must say in its own text why that issue does not cover it (finding 7 and #1470 share only `SagaStoreMongoDB.cs`), so the remediation stage does not mark it a duplicate by file.
