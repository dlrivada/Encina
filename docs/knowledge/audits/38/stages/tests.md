## Lessons for the pipeline

- A test infrastructure that hand-writes the schema or the entity model (`SqlServerSchema.cs`, `TestEFDbContext.cs`, `TestPostgreSqlDbContext.cs`) is the common cause of a defect surviving the whole life of an issue (the SQL Server saga DDL and the SQL-Server-only filtered indexes); the test stage should compare each test-owned schema with the shipped scripts and configuration, and look for a test that runs the shipped artefact, before judging a store "covered".
- Line coverage can show a branch as executed when it is not: `SagaStoreMongoDB.cs:72-83` reports 13 hits on every line of a `??` fallback while line 72 has `condition-coverage` 50%. For a fallback or a null-coalescing copy, read the `condition-coverage` attribute of the first line before calling it covered.
- An abstract test base class that no test inherits (`SagaStoreEFTestsBase`) looks like coverage in a name search and runs nothing; a Grep for the class name across `tests\` (declaration only) is the cheap check.
- An orchestrator comment on an umbrella issue is a tracker: the tracker table must search comments (`--json comments`) for every scoped file name, not only issue bodies; finding 11 duplicated the #1887 comment "tests 11" because only the body was read for that file (verifier correction 4).
- Before writing "no X exists" or "all N sites do Y" about test files, list the files with a Glob/Grep and print the lines: the PostgreSQL and MySQL ADO `SagaStateTests` classes existed, no guard test is aimed at `FakeSagaStore`, and the Mongo integration file has two direct `AddAsync` calls, not 15 (verifier correction 7).
- Helper scripts called through a variable path are blocked by `guard-orchestrator-writes`; use the literal absolute path from the first call (the lesson of audit #19, repeated here).
