## Findings

1. **Major** — `Encina.AwsLambda` never binds the caller identity or the correlation/tenant to the Encina request context: "context enrichment" is a stub, so `IEncina.Send` from a Lambda handler runs anonymous. A search of `src/Encina.AwsLambda` for `IRequestContext|RequestIdentity|InboundRequestInfo|RunHostInbound` returns 0 matches; the package has no middleware or scope-opening helper at all. `EnableRequestContextEnrichment` (`EncinaAwsLambdaOptions.cs:34`, doc at `:27-28` "automatically enrich the request context with correlation ID, user ID, and tenant ID") is read only by the health check (`Health/AwsLambdaHealthCheck.cs:42`); README `:11` and `:132` repeat the promise. What exists is three loose extension methods the function must call itself (`LambdaContextExtensions.cs:27`, `:111`, `:250`) and whose results go nowhere. The public API to open the scope exists (`IRequestContextScopeFactory.RunInboundAsync`, `src/Encina/Identity/IRequestContextScopeFactory.cs:139`, with `InboundRequestInfo`) and is the API the Lambda package can use; ASP.NET Core opens the inbound scope on every request through the internal sibling `IInternalRequestContextScopeFactory.RunHostInboundAsync` (`EncinaContextMiddleware.cs:129`, called from the middleware's private method `RunInboundAsync` at `:126`), not through the public `RunInboundAsync`. A call with no scope reads the anonymous identity (`RequestContextAccessor.cs:21-40` documents "reads no context, which is the anonymous identity, which every gate denies"). Same for SQS and EventBridge: nothing opens a service or originating-actor scope around `processMessage`/`processEvent` (`SqsMessageHandler.cs:70`, `EventBridgeHandler.cs:66`). The tenant check (`ResolveTenantId`) therefore runs only when each function remembers to call it and discards the `Left` when it does not. Checks failed: AGENTS.md section 3 (compliance and security gates fail closed, registration completeness), section 6 functions 10 (multi-tenancy) and 12 (audit trail), and the known pattern "host adapters were given the identity-scope API later (SPEC-002) and the serverless ones were never moved over". Lambda counterpart of #2945, #2946 and #2947 (b), all three scoped to `Encina.AzureFunctions`; no open issue covers Lambda (#2947 only says "the AwsLambda package has the same gap in its copy of the mapping").

2. **Major** — Five options, seven log methods and a suppression justification are dead or false. `IncludeExceptionDetailsInResponse` (`EncinaAwsLambdaOptions.cs:98`, with a "Security Warning" in its remarks), `EnableRequestContextEnrichment` (`:34`), `UseApiGatewayV2Format` (`:115`) and `EnableSqsBatchItemFailures` (`:128`) have no reader in `src/` except the health check echoing them (`AwsLambdaHealthCheck.cs:42-44`); `ProviderHealthCheck` (`:106`) has no reader at all (search `ProviderHealthCheck` over the package: declaration, doc and PublicAPI only). `Log.cs:10-70` declares EventIds 4700-4706 (`LambdaExecutionStarting` ... `HealthCheckCompleted`) and none has a caller; only 4707-4710 are used (`LambdaContextExtensions.cs:155,163,173,177`). `GlobalSuppressions.cs:3-6` suppresses CA1848 with the justification "LoggerMessage source generator is used via Log.cs partial class", but `SqsMessageHandler.cs:74,87,142` and `EventBridgeHandler.cs:62,70,81,141` call `logger?.LogError("template", ...)` directly, so the justification is false for the code that raises the warning. README `:138-140` documents the dead options as working. Checks failed: AGENTS.md section 3 ("every line serves a current purpose"), section 8 (a CA warning is suppressed with a true justification), section 7 (EventIds are allocated for use). #2913 plans to "apply the #2649 option and Development guard" to `IncludeExceptionDetailsInResponse` without noting that nothing reads it; #2946 (d) covers only the Azure `HealthCheckCompleted`.

3. **Major** — `SqsMessageHandler.ProcessBatchAsync` breaks ordering on FIFO queues: it keeps processing messages after a failure (`SqsMessageHandler.cs:64-97`: the loop adds the failed `MessageId` to `batchItemFailures` and continues with the next record). For a FIFO queue, AWS's partial-batch-response contract requires stopping at the first failure and returning that message and every later one as failures, otherwise a later message of the same `MessageGroupId` is processed and deleted before the earlier one is retried (AWS documentation, not fetched in this audit). A search of `src/Encina.AwsLambda` and `tests/Encina.UnitTests/AwsLambda` for `FIFO|MessageGroupId|SequenceNumber` (case-insensitive) returns 0 matches; the XML docs (`:44-52`) and README `:216-232` do not mention the limit. The helper is the package's headline SQS API and is presented as safe for any queue. Not executed (needs a FIFO event). Related: `EnableSqsBatchItemFailures = false` (`:128`) cannot be honoured because nothing reads it, and the function-side `ReportBatchItemFailures` setting that the response depends on is undocumented. Checks failed: adversarial-reviewer failure pattern "documented contract narrower than the delivered guarantee"; AGENTS.md section 5 transports "error handling and DLQ".

4. **Major** — The EventBridge and `ProcessAllAsync` adapters turn every failure into a `Left` and the documented usage then reports Lambda success, so the event is neither retried nor dead-lettered. `EventBridgeHandler.cs:79-91` catches `Exception` (including `OperationCanceledException`) and returns `Left`; a `Left` from `processEvent` is only logged (`:68-75`) and returned. The XML example (`EventBridgeHandler.cs:29-33`) and README `:97-103` handle the result with `result.IfLeft(error => ...LogError(...))` and return normally, so the Lambda invocation ends successfully; for an asynchronous (EventBridge) invocation the only retry/DLQ trigger is the function throwing. `SqsMessageHandler.ProcessAllAsync` (`:158-180`) likewise returns the first `Left` with no way to fail the invocation; README `:236-245` shows it printing the error. The package offers no helper that fails the invocation, and `ProcessAsync` has no cancellation token (`:49-52`). Check failed: AGENTS.md section 3 "Errors are NEVER swallowed in background infrastructure: a Left from IEncina.Send/Publish ... inside a processor, adapter ... fails that operation (retry, dead-letter or exception per its semantics), never reports success" (why: #1150-#1153, #1184). Not covered by #727 (OpenTelemetry) or #2699 (emulator tests).

5. **Major** — The "Cold start optimized" acceptance criterion cannot be met with the package's own API: every response is serialized by reflection with a private options instance and no hook for source generation or Native AOT. `ApiGatewayResponseExtensions.cs:106,137,186,211,225` call `JsonSerializer.Serialize(value, JsonOptions)` / `Serialize(problemDetails, JsonOptions)`; `JsonOptions` is `private static readonly` (`:34-38`) and no overload takes `JsonSerializerOptions`, `JsonTypeInfo<T>` or a `JsonSerializerContext`. The private `ProblemDetailsResponse` (`:298-304`) is also serialized by reflection. Under Native AOT (`JsonSerializerIsReflectionEnabledByDefault=false`) these calls throw `InvalidOperationException`. Yet README `:261-268` tells users to "use source generators for serialization" and "consider Native AOT", and the csproj (`Encina.AwsLambda.csproj:1-25`) has no `IsAotCompatible`/trim analyzer property (search of `Directory.Build.props`, `Directory.Build.targets` and the csproj for `IsAotCompatible|PublishAot|EnableTrimAnalyzer|IsTrimmable`: 0 matches), so IL2026/IL3050 never warn. The SQS and EventBridge helpers do accept a `JsonSerializerOptions?` (`SqsMessageHandler.cs:120`, `EventBridgeHandler.cs:124`) but the response side does not. Derived from the code, not executed (an AOT publish was not run). The archivist found cold start is documentation only (`archivist.md`, Destinations); this is the code-side reason it cannot be anything else.

6. **Minor** — Header lookups are case-sensitive, so a lower-case header is missed. `GetCorrelationId` (`LambdaContextExtensions.cs:37-38` for REST, `:65-66` for HTTP API v2) and `ReadHeader` (`:181-184`) use `Headers.TryGetValue(headerName, ...)` on the event's plain dictionary. Executed: `DefaultLambdaJsonSerializer` deserializes `Headers` into a `System.Collections.Generic.Dictionary<string,string>` with the default comparer, and for `{"x-correlation-id":"abc"}` the lookup `"X-Correlation-ID"` returns `False` on both `APIGatewayProxyRequest` and `APIGatewayHttpApiV2ProxyRequest` (replica `hdr.cs`). AWS documents that HTTP API payload 2.0 delivers header names in lower case (not fetched here), so the v2 overload would miss the default header for real requests; HTTP/2 clients send lower case on REST too. Consequences: the caller's correlation id is dropped for the `AwsRequestId`; the claim-versus-header mismatch check (`ResolveWithClaim`, `:148-151`) is bypassed by changing the header's case (the claim still wins, so no identity is gained); a trusted tenant header in another case is ignored (fails closed). ASP.NET Core headers are case-insensitive by type (`HttpContextInboundRequestExtensions.cs:95`); the tests use only the exact default casing (`LambdaContextExtensionsTests.cs:27,76,108`, `LambdaResolveTenantIdTests.cs:34,170,202`).

7. **Minor** — HTTP API (v2) is half-supported, and only for the response and correlation id. Only `GetCorrelationId` (`LambdaContextExtensions.cs:55`) and `ToHttpApiResponse` (`ApiGatewayResponseExtensions.cs:177`) accept the v2 types; `ResolveTenantId` (`:111`) and `GetUserId` (`:250`) take `APIGatewayProxyRequest` only, and there is no v2 `ToCreatedResponse`/`ToNoContentResponse`. Executed (replica `v2.cs`, reflection over the library): the v2 authorizer is `AuthorizerDescription { Jwt, Lambda, IAM }`, a different shape from the `APIGatewayCustomAuthorizerContext` that `ReadAuthorizerValue` reads (`:192-203`), so a v2 function has no supported way to resolve a tenant against a verified claim and must read the tenant header itself, which is the unverified path the package otherwise denies by default. `UseApiGatewayV2Format` (`EncinaAwsLambdaOptions.cs:115`) is dead (finding 2). Checks failed: AGENTS.md section 3 (fail-closed tenant resolution), section 5 (cloud features are complete, not half-supported).

8. **Minor** — The Problem Details body is not RFC 7807 as README `:10` claims and differs from the ASP.NET Core body. `ProblemDetailsResponse.Extensions` (`ApiGatewayResponseExtensions.cs:303`) is a get-only dictionary property, which System.Text.Json writes as a nested `"extensions":{"errorCode":"..."}` member, not the top-level extension members RFC 7807 section 3.2 defines (ASP.NET Core's `ProblemDetails` writes them flat, `ProblemDetailsExtensions.cs:113`); `type` and `instance` are never written; the body carries no `traceId` or `correlationId` (ASP.NET Core `:125,:130`) although the Lambda request id is available through the context the caller already has, and `ToProblemDetailsResponse` takes no context (`:83-85`). The V2 branch duplicates the whole construction (`:192-217` versus `:83-112`). Derived from the serializer's documented behaviour, not executed; the Azure copy has the same class (`HttpResponseDataExtensions.cs:272`). #855 lists this member with a stale line (`:295`) as a mutable-collection exposure, which does not describe the wire-format problem.

9. **Minor** — `GetUserId` throws on valid but non-string claims, while the tenant path was hardened against them. `LambdaContextExtensions.cs:262-267` calls `claims.TryGetProperty(claimType, ...)` on any `JsonElement` (throws `InvalidOperationException` when the `claims` element is not an object) and `userClaim.GetString()` (throws `InvalidOperationException` for a number, object or array claim; executed in replica `hdr.cs`: a numeric `sub` makes `GetString` throw). `ReadStringProperty` (`:213-222`) and `AsNonEmptyString` (`:231-241`) handle exactly these cases for the tenant. The fallback to `principalId` (`:277-281`) returns an authorizer-defined string as a user id with no check that it is a user, and nothing in the package calls `GetUserId` (search of `src/`: declaration only), so an unhandled exception here surfaces in the application's function, not in the package.

10. **Minor** — The SQS and EventBridge callbacks cannot observe cancellation or the remaining invocation time. `ProcessBatchAsync` takes a `CancellationToken` (`SqsMessageHandler.cs:57`) but its callback is `Func<SQSMessage, Task<...>>` (`:55`), so the token reaches no handler; the token is only checked between records (`:66`), and `catch (Exception)` (`:85`) records a cancelled message as an ordinary failure. `GetRemainingTimeMs` exists (`LambdaContextExtensions.cs:313`) but no helper stops before the timeout and reports the unprocessed records as failures, so a timeout kills the invocation after some messages were handled and the whole batch is redelivered (at-least-once duplicates). `EventBridgeHandler.ProcessAsync`/`ProcessRawAsync` have no token at all. AGENTS.md section 6 function 9 (idempotency) is not recorded for the SQS dispatch either.

## Lessons for the pipeline

- A host-adapter package that mirrors one already audited (Lambda after Azure Functions) needs its sibling's open issues read first (#2945-#2949, #2960): four of the ten findings are the Lambda counterparts of Azure bugs that have no Lambda issue, and two of those issues explicitly defer the Lambda copy only in a sentence ("same gap in its copy"), which the remediation stage should not treat as coverage.
- A file-based replica that references only NuGet packages (`#:package`, no `#:project`) written with the Write tool to a literal scratchpad path and run with `dotnet run <literal path>` was not blocked and turned two derived claims (case-sensitive header dictionary, v2 authorizer shape) into executed evidence; the stage text can say so for event-shape questions.
- Hook note: the first `gh issue list ... > $f` redirect through a variable produced a `block-main-checkout-writes` warning (not a block, the scratchpad path was correct); later commands used literal absolute paths and raised none.
- For options classes, a one-line search per property for readers outside the health check found five dead options; make "options read only by the health check or its own tests" a standing check for every `Encina*Options`.
