5. **Major** — `docs/features/cdc.md:605` (table row "Automatic persistence": "Failed events are dead-lettered after `MaxRetries` exhaustion"), `:599` ("When a CDC event fails processing after exhausting all retry attempts") and `:871-873`. Check failed: real behavior. Compared with the literal sentence: a failed event is the case `ICdcDispatcher.DispatchAsync` returns `Left`. `CdcProcessor.cs:151-176` only increments `failureCount` and sets `lastFailedEvent` for a `Left`, and continues; the next successful event saves a later position (`:159-165`); `ProcessChangesAsync` returns normally, so `ExecuteAsync` resets `consecutiveErrors = 0` (`:82-84`) and the dead letter branch (`:94-102`) is reached only after an exception was thrown more than `MaxRetries` times in a row. So a handler failure is neither retried nor dead-lettered, and the page's "after exhausting all retry attempts" describes a path that handler failures never take. `docs/features/cdc.md:244` ("Individual handler failures are tracked but don't stop the stream") is true and is the only line that hints at it. This is the documentation side of code finding 2 (`CdcProcessor` sibling); if the code is fixed to dead-letter a `Left`, the sentences become true and this finding closes with it, so the remediation issue must state which one is chosen. Not covered by #1602 (placeholder only) or by another open issue.
