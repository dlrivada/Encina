## Lessons for the pipeline
- A feature-name filter (`~DeadLetter`) gave 100% for `DeadLetterCleanupProcessor.cs` while the class alone gives 80.85% and the whole unit project 95.74%; async state-machine lines of background services can lose hits depending on which other tests run, so take the whole-project figure (what `coverage-report.cs` reads) as the one a target is judged against and print the other filters beside it.
- A Grep of the sibling's type name over all of `tests\` (`CdcProcessor`) found integration tests that a unit-only search would have missed; the claim became "no test executes lines 174-175" only after running the `Encina.IntegrationTests.Cdc` namespace with coverage.
- Test helpers that nothing calls (`CreateProcessorWithDlq`, `CreateFailingConnector`) are a sign that a test was rewritten around the easy failure (a throwing connector) and the intended one (a Left dispatch) was dropped; Grep each private helper's callers when a test is named after the behavior a code finding says is broken.
- A scratch script in the session scratchpad called through a variable (`& "$s\cov.ps1"`) is blocked by `guard-orchestrator-writes`; use the literal absolute path on every call (the lesson of audits #19 and #38 again), and redirecting `dotnet test` output to `"$s\x.log"` is accepted.
