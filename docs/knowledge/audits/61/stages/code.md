## Findings

1. **Major** — ActivityResult writes the EncinaError message into the Durable history, and the orchestration helpers copy exception and error messages into new errors. `src/Encina.AzureFunctions/Durable/ActivityResult.cs:80-81` sets `ErrorMessage = error.Message` in `Failure(EncinaError)`; that object is what an activity returns (`ActivityResult.cs:18-25`, `README.md:370-379`) and what the Durable runtime persists as the activity output in the task hub history (Azure Storage tables and blobs, or SQL), in plaintext. `ToEither` (`ActivityResult.cs:112-116`) rebuilds an error with the same message, so it travels on. The orchestration side adds the same class of leak: `OrchestrationContextExtensions.cs:69, :124, :157, :192, :251` put the `TaskFailedException` message (which carries the text of the exception thrown inside the activity) into a new error, `FanOutFanInExtensions.cs:113` and `:225-228` concatenate the Message of every failed result into a new message, and `DurableSagaBuilder.cs:330` and `:376` put `ex.Message` into the saga errors. Fails AUD-13 and AGENTS.md section 3 ("EncinaError.Message NEVER reaches logs, activity tags, health-check results or plaintext storage; record only the error code or the exception type"). Same pattern as audit #34 (a validated email travelled in the error). Not covered by an open issue: #2913 covers only the HTTP response `Detail` of this package and AwsLambda, and #2154 is the Marten sibling; a search of the open-issue dump for `ActivityResult`, `ErrorMessage` with Durable and history found none. That the activity output is stored in the history is documented Durable Functions behaviour and was not executed here. Fix direction: carry the error code (and the exception type) across the boundary and rebuild the message from a fixed text per code; an opt-in for the full text, if wanted, is a maintainer decision.

2. **Major** — The saga failure type cannot be returned from an orchestrator, although the README shows exactly that. `DurableSaga<TData>.ExecuteAsync` returns `Either<DurableSagaError, TData>` (`DurableSagaBuilder.cs:276`) and the README returns it as the orchestrator output (`README.md:388-411`). DurableSagaError holds an EncinaError (`DurableSagaBuilder.cs:398`), a `Dictionary<string, EncinaError?>` (`:403`) and no serializable form; every EncinaError built with `EncinaErrors.Create` exposes a non-empty public `Exception` property (`src/Encina/Errors/EncinaError.cs:81-86`: the wrapped inner exception, or the EncinaException itself) and the saga passes a thrown exception into it (`DurableSagaBuilder.cs:328-331`, `:374-377`, and the TaskFailedException wrapped at `OrchestrationContextExtensions.cs:67-70`). Executed on a stand-in with the same public shape (record struct with `string Message` and `Option<Exception> Exception`, the same four members as DurableSagaError, System.Text.Json, a thrown exception inside): `Serialize threw NotSupportedException: Serialization and deserialization of 'System.Reflection.MethodBase' instances is not supported. Path: $.OriginalError.Exception.TargetSite`. The stand-in does not reference the real types, and the worker serializer is assumed to be System.Text.Json (the default); the verifier should run it against the real DurableSagaError. ActivityResult is the only serializable form in the package and it covers `Either<EncinaError, T>`, not the saga error (there is no saga counterpart of `ToActivityResult`). Fails the purpose the issue gave ActivityResult ("Durable Functions JSON state boundary") and AUD-01. #2952 covers only the return-type mismatch of the README sample (`FulfillmentResult` versus `OrderData`); even with that fixed, the failure path cannot leave the orchestrator. Fix direction: a serializable saga result (code, failed step, per-step compensation outcome, no exception) and a conversion from DurableSagaError.

3. **Major** — Four retry defaults, `ContinueCompensationOnError` and `ProviderHealthCheck.Enabled` of DurableFunctionsOptions have no reader, and the README documents them as working. Search over `src/**/*.cs` for `DefaultMaxRetries|DefaultFirstRetryInterval|DefaultBackoffCoefficient|DefaultMaxRetryInterval|ContinueCompensationOnError|DefaultSagaTimeout|DurableFunctionsOptions` returns hits only in the options class, in the XML examples, in the registration (`DurableServiceCollectionExtensions.cs:33`) and in the health check (`DurableFunctionsHealthCheck.cs:41-77`, which only prints and validates them); `SagaOrchestrator.DefaultSagaTimeout` in `Encina.Messaging` is another type. Nothing builds a TaskOptions from the four retry values (`CreateRetryOptions`, `OrchestrationContextExtensions.cs:264-281`, takes explicit arguments and the saga takes `WithDefaultRetryOptions`), so `AddEncinaDurableFunctions(o => o.DefaultMaxRetries = 5)` changes no behaviour. `ContinueCompensationOnError = false` is ignored: `CompensateAsync` (`DurableSagaBuilder.cs:345-379`) always records the error and continues. `ProviderHealthCheck.Enabled = false` is ignored: the health check is registered unconditionally (`DurableServiceCollectionExtensions.cs:41-42`) while the other providers read the flag (for example `src/Encina.AzureFunctions/ServiceCollectionExtensions.cs:86`). `README.md:445-465` presents all of them as configuration. Fails AGENTS.md section 1 (every line serves a current purpose) and the registration rule of section 3 (an option the registration advertises must be honoured). Not covered: #853 asks only for validators, #2949 concerns the other health check registration (`AddEncinaAzureFunctions`), not `AddEncinaDurableFunctions`. Fix direction (pre-1.0, no compatibility): wire them (default `TaskOptions` for the saga and helpers, stop-on-first compensation error, conditional registration) or delete them.

4. **Major** — Saga timeouts are accepted and discarded. `DurableSagaBuilder<TData>.WithTimeout` validates and stores the value (`DurableSagaBuilder.cs:66-71`), `Build` hands it to the saga (`:86`), and the constructor drops it: `// timeout is reserved for future use ... _ = timeout;` (`:261-262`). `DurableFunctionsOptions.DefaultSagaTimeout` (`DurableFunctionsOptions.cs:60`) is never read (finding 3 search). A saga with `WithTimeout(TimeSpan.FromMinutes(5))` runs without bound while its API and the README (`:458`) say it is bounded, and the issue asked for it. Fails AGENTS.md section 1 (no placeholder code) and AUD-01. The core saga has the same defect (#2208, `Encina.Messaging`, timeouts recorded and never enforced), but it does not touch this package, so it is no coverage. Fix direction: enforce it with a Durable timer racing the step activity (`context.CreateTimer` and `Task.WhenAny`, then compensate), or remove both APIs.

5. **Major** — The saga failure report is wrong on the exception path. `DurableSagaBuilder.cs:320-335`: any exception that escapes the loop (anything other than the TaskFailedException that `CallEncinaActivityWithResultAsync` converts, `OrchestrationContextExtensions.cs:120-126`) runs `CompensateAsync` and then reports `WasCompensated = false` (`:333`) even when every compensation succeeded, whereas the Left path computes it from the outcomes (`:306`). The XML says the property means "all compensations completed successfully" (`:405-408`). The same path reports `FailedStep = "Unknown (exception)"` (`:327`) although the failing step is known inside the loop (`step.StepName`, `:287`). A caller deciding whether to alert an operator by `WasCompensated` gets a false alarm for every exception and cannot tell which step to look at. Fails AUD-01 (compensation is the decision the issue recorded). Fix direction: track the current step name and compute `WasCompensated` from `compensationResult` on both paths.

6. **Major** — FanOutAllAsync, FanOutFirstSuccessAsync and FanOutMultipleAsync only call activities that return the plain result type; an activity that follows the documented convention reports success with a default value. `FanOutFanInExtensions.cs:100` (`FanOutAllAsync`), `:217` (`FanOutFirstSuccessAsync`) and `:169-170, :189-191` (`FanOutMultipleAsync`) go through `CallEncinaActivityAsync` (plain `CallActivityAsync<TResult>`, `OrchestrationContextExtensions.cs:62`); only `FanOutWithResultAsync` (`:130-151`) unwraps ActivityResult, and it has no All or FirstSuccess form. The README tells users to write activities that return ActivityResult (`README.md:370-379`, best practice 7 at `:482`) and shows `FanOutAllAsync` and `FanOutFirstSuccessAsync` on `"ProcessItemActivity"` (`:435-442`). Executed on System.Text.Json (stand-in, the Durable default converter is assumed): the JSON of a failed ActivityResult (`{"isSuccess":false,"errorCode":"order.rejected",...}`) read as a `record ProcessedItem(string Id, int Count)` deserializes without any exception to an instance with an empty `Id` (printed as an empty string) and `Count` 0, and the success shape (`{"isSuccess":true,"value":{"Id":"a","Count":2}}`) reads the same way (`Id` empty, `Count` 0, the real value is lost); both would become `Right`. A business failure is therefore reported as success with an empty value. Fails AGENTS.md section 3 (a Left must not be reported as success) and AUD-01. Not covered by #2787 (tests) or #2952/#2953 (README compile errors). Fix direction: WithResult variants for All, FirstSuccess and Multiple (or make the unwrapping the only form) and a README sample that matches.

7. **Minor** — WaitForEncinaExternalEventAsync mishandles its two non-event exits. `OrchestrationContextExtensions.cs:219-232`: the linked CancellationTokenSource is created with the caller's token and cancelled only when the event wins (`:232`); when the timer wins, the external-event waiter stays registered (the `using` disposes the source without cancelling it), and in Durable a later wait for the same event name in the same orchestration is served to the abandoned waiter first (derived from the SDK's event queueing, not executed). If the caller's token is cancelled, both tasks are cancelled and `Task.WhenAny` returns whichever completed first, so `completedTask == timerTask` (`:225`) can report `durable.event_timeout` for a cancellation. Fix: cancel the source in the timeout path and test the caller token before deciding the outcome.

8. **Minor** — FanOutFirstSuccessAsync is not "first success", and FanOutAllAsync drops the codes of multiple failures. `FanOutFanInExtensions.cs:217` awaits `FanOutAsync`, which is `Task.WhenAll` (`:69`), so it waits for every activity and returns the first success in input order; the remarks (`:209-210`: "trying multiple service instances and taking the first response") and `README.md:439-442` promise the first to answer, and a slow or failing instance delays the result by its whole retry policy. `FanOutAllAsync` with two or more failures returns a new error with the code `durable.fanout_failed` and only the first message embedded (`:106-113`), losing the codes of the others; with one failure it returns that error unchanged, so the same call yields different error shapes by count. Decision for the maintainer: rename and document, or implement with `Task.WhenAny`; the aggregate error shape is also open.

9. **Minor** — Error codes are scattered literals with two prefixes and one lossy round trip. Twelve call sites use nine distinct literals with the prefix `durable.` (`OrchestrationContextExtensions.cs:68, :123, :156, :191, :228, :244, :250`, `FanOutFanInExtensions.cs:112, :227`, `DurableSagaBuilder.cs:329, :375`, `ActivityResult.cs:113`) while DurableSagaErrorCodes (`DurableSagaErrorCodes.cs:11, :16`) holds two constants with the prefix `durable_saga.`; a caller that branches on the activity, timeout or compensation codes has no constant to reference. `ActivityResult.Failure(EncinaError)` stores `IfNone(string.Empty)` for an error without a code (`ActivityResult.cs:80`), and `ToEither` falls back to `durable.activity_failed` only for a null code (`:113`), so an error created from a plain string comes back with the code "". Fix: one constants class with one prefix, and `string.IsNullOrEmpty` in the round trip.

10. **Minor** — Several XML examples do not match the API they document. `FanOutFanInExtensions.cs:18-21` calls `context.FanOutAsync("ProcessItem", items, maxConcurrency: 10)`: there is no `maxConcurrency` parameter and the type arguments cannot be inferred. `DurableSagaBuilder.cs:28-30` calls `saga.ExecuteAsync(context, initialData)` on the value that `Build()` returns, which is `Either<EncinaError, DurableSaga<TData>>`. `OrchestrationContextExtensions.cs:27-30` passes a lambda that returns a `Task` to `Bind` (which needs an Either) and returns `Either<EncinaError, OrderResult>` from an orchestrator (not a serializable output, see finding 2); `:23` also contradicts the package's own convention by calling `CallEncinaActivityAsync` for an activity named as an Encina handler. These are the in-code twins of the README samples of #2952 and #2953, which cover the README only. AUD-10 (documentation has to be correct, not only present).

11. **Minor** — The saga builder reports a misconfigured step by throwing. `DurableSagaStepBuilder<TData>.Step` (`DurableSagaBuilder.cs:169-179`) finalizes the current step and throws `InvalidOperationException(error.Message)` when it has no Execute activity, while `Build` returns the same condition as `Either` (`:185-188`, `DurableSagaErrorCodes.StepNotConfigured`); so the same mistake yields an exception or a Left depending on whether another step follows. The documented exception also carries the message of an EncinaError. AGENTS.md section 3 (Railway Oriented Programming; validation returns Either). The chain syntax makes the Left impossible to return from `Step`, so the options (a `Build`-time validation of all steps, or an explicit `Validate` step) are the maintainer's call.

12. **Minor** — The Durable extension is a mandatory dependency of the HTTP package. `Encina.AzureFunctions.csproj:21` references `Microsoft.Azure.Functions.Worker.Extensions.DurableTask` for every consumer, including those that use only the HTTP middleware; the Functions worker SDK discovers referenced extension packages and the transitive Microsoft.DurableTask packages restore for all (the host-side effect of loading the Durable extension in an app that never calls `AddEncinaDurableFunctions` was not verified). Fails AGENTS.md section 1 (pay-for-what-you-use, every feature opt-in); the same rule is applied to the Timer and Storage.Queues references by #2950, which does not mention the DurableTask reference. The issue decided "inside Encina.AzureFunctions" (knowledge record), so the options are a separate `Encina.AzureFunctions.Durable` package or keeping it and recording the decision in an ADR; left to the maintainer.

- DurableFunctionsHealthCheck (`DurableFunctionsHealthCheck.cs:88-90`) reports "configured and ready" with the tag `ready` (`DurableFunctionsOptions.cs:68`) without touching the task hub storage, and can only be Degraded for invalid numbers. ## Lessons for the pipeline

- A serializable wrapper for an error that crosses a persisted boundary (Durable history, outbox payloads, queue messages) is an AUD-13 check by construction: search the wrapper's factory for `.Message` before reading anything else; #2913 and #2154 each cover one carrier of the same rule and neither covered this one.
- When the issue's deliverable is a type meant to cross a serialization boundary, check the failure type of the same feature, not only the success wrapper: ActivityResult handled Either, but the saga's own error type has no serializable form (finding 2). A stand-in replica of the public shape, run by literal scratchpad path with only NuGet packages, settled it in one run; the stage text should say the verifier must repeat it against the real types.
- A GraphQL-free dump of the open issues works with `gh api --paginate "repos/<owner>/<repo>/issues?state=open&per_page=100" --jq '.[] | select(.pull_request==null) | {n:.number,t:.title,b:.body}'` redirected to a literal scratchpad path (1777 issues, one call); it does not include comments, which the stage should state beside every "no open issue" claim.
- For an options class, the dead-option search (one pattern over `src/**/*.cs` listing every property) found six dead settings in one call; keep it as the first check for any `*Options` in a feature package.
