## Lessons for the pipeline

- `coverage-report.cs` classifies result folders by substring, so a diagnostic run folder such as `GuardTestsClausesOnly` under `artifacts\audit\coverage` would be read as a second guard run; name diagnostic folders without the flag word, or feed the report a copy of the folders it should read (done here).
- Splitting the guard project's classes into "null-check classes" and "behaviour classes" and running them as two filtered runs took under a minute and exposed that a package guard target of 15 is met only by behaviour tests (5.01% vs 47.61%); this is the cheapest standing check for the guard flag and the stage text could ask for it for every package.
- A generator's tests that all pass forward-slash paths and pre-created folders mask the very inputs a user types on Windows; for any generator or scaffolder, check the test data for backslash paths, hyphenated names, existing target files and missing output folders before reading the pass count as evidence.
- The earlier theory-row lesson (a test named for a mapping can execute none of it) recurred as 43 `Parse_*` rows over an unvalidated `Argument<string>`; when a command argument has no validator, a parse-only test cannot fail, and the unexecuted switch arms in the missed-line list are the quickest way to see it.
- Hooks: no command was blocked. The `block-main-checkout-writes` hook printed a warning (not a block) for `New-Item`/`Copy-Item` into `$s\a47input` because the path used a variable; the commands ran, but the stage should use literal absolute paths for the scratchpad copies as well.
