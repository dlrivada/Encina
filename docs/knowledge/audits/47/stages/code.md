## Findings

1. **Major** — The `api` template emits a `Program.cs` that does not compile. `src/Encina.Cli/Services/ProjectScaffolder.cs:203` writes `encina.Send<SampleCommand, SampleResponse>(command)`; `IEncina` declares only `Send<TResponse>(IRequest<TResponse> request, ...)` (`src/Encina/Abstractions/IEncina.cs:46` and `:77`), and a search of `src/**/*.cs` for ` Send<\w+, ?\w+>\(` returns 0 matches, so there is no two-type-argument overload or extension. Fails: AUD-01 (the issue's acceptance "scaffolds a working project"; `encina new api` is the primary path), and nothing catches it because the tests only assert substrings of the generated text (`tests/Encina.UnitTests/Cli/Services/ProjectScaffolderTests.cs:57` asserts `ShouldContain("AddEncinaAspNetCore")`) and no test builds a scaffolded project (derived from the grep and the interface; the build of a scaffolded project was not run). The other generated pieces were checked against the core API and match: `ICommand`, `ICommandHandler<,>`, `Task<Either<EncinaError, T>> Handle(...)`, `AddEncina(params Assembly[])`, `AddEncinaAspNetCore()`.

2. **Major** — `encina generate ...` silently overwrites existing files. `src/Encina.Cli/Services/CodeGenerator.cs:95, :100, :120, :125, :149, :154, :173, :178` call `File.WriteAllText` with no existence check and `GenerateCommand` has no `--force` option, so `encina generate handler CreateOrder` in a folder that already holds a hand-written `CreateOrder.cs` or `CreateOrderHandler.cs` replaces it without a warning and prints "Created:". The sibling command has the guard: `ProjectScaffolder.cs:53-60` refuses a non-empty directory unless `--force`. A scaffolder that destroys user code on a name collision is a data-loss defect (known failure pattern: operation reports success while losing data). Derived from the code, not run. Contrast the partial-write case: if the second `WriteAllText` of a pair throws, the first file stays and the command exits 1 (`GenerateCommand.cs:243-247`).

3. **Major** — Names are never validated, so common inputs produce code or paths that do not compile or escape the output folder. `encina new api my-app` writes `using my-app.Handlers;` (`ProjectScaffolder.cs:188`) and `namespace my-app.Handlers;` (`:256`) because the project name is used verbatim as a namespace, and, when `--output` is not given, `NewCommand.cs:89` builds the output path from it (`output ?? Path.Combine(Directory.GetCurrentDirectory(), name)`, so `..\x` or an absolute path also escapes the working folder; with `--output` the name is not used for the path). The generators have the same hole: `CodeGenerator.cs:386, :411, :434, :501, :544, :563` put `options.Name` into `record`/`class` declarations (`encina generate handler create-order` yields `public sealed record create-order`), `:94, :99, :119, :124, :148, :153, :172, :177` put it into file names, and `DetectNamespace` returns the `.csproj` file name as the namespace (`CodeGenerator.cs:356` and `:367`, so `My-App.csproj` gives `namespace My-App;`) instead of reading `RootNamespace`. Only `ArgumentException.ThrowIfNullOrWhiteSpace` is applied (`:84, :109, :134, :163`). Fails the "generated code compiles" expectation of the issue (AUD-01). Derived from the code, not run; a verifier can confirm with `new api my-app` followed by `dotnet build`.

4. **Major** — The Stryker generator writes invalid JSON for Windows paths and for any value containing a quote. `CodeGenerator.cs:260` and `:301` interpolate `options.ProjectPath` raw into `"project": "..."`, and `:220` wraps each `--test-projects` value in quotes without escaping. Executed replica: `{ "project": "src\MyApp\MyApp.csproj" }` fails `JsonDocument.Parse` with `'M' is an invalid escapable character within a JSON string`. The command prints "Generated Stryker configuration" and exits 0 (`GenerateCommand.cs:467-478`), so the failure shows up later inside `dotnet stryker`. `BuildTestProjectsJson` normalises separators only on the derived-test-project branch (`:224`, `:248`), never for `project`. Added by #437 (successor of this issue's scope, same file), but the file is in scope and the defect is in the code today. Fix is to build the document with `System.Text.Json` (`Utf8JsonWriter` or a typed object) instead of string templates.

5. **Major** — User-controlled text is interpolated into Spectre.Console markup unescaped, so brackets in a path, a name or `dotnet` output turn the error report into a different error. `AddCommand.cs:165, :195, :220, :240, :259` print the provider name outside any `try`; `AddCommand.cs:286, :292, :298`, `GenerateCommand.cs:230, :233, :239, :245, :270, :273, :279, :285, :312, :315, :321, :327, :350, :353, :359, :365, :470, :482, :488` and `NewCommand.cs:102, :103, :106, :113, :119` print names, paths and `result.ErrorMessage` (which for `add` is the full stdout/stderr of `dotnet add package`, `PackageManager.cs:80-81`) inside `[red]...[/]` with no `Markup.Escape`. Executed replica (Spectre.Console 0.55.0, the version in `Directory.Packages.props`): `MarkupLine($"[red]Error: Failed to add package: ... [C:\x\proj.csproj][/]")` throws `InvalidOperationException: Could not find color or style 'C:\x\proj.csproj'`, and `my[name` throws `Encountered malformed markup tag`. Consequences: inside a `try` the `catch (Exception ex)` prints that style error instead of the real NuGet/MSBuild message (NuGet's NU1102/NU1103 text and MSBuild errors end in bracketed text such as `[ Nearest version: ... ]` or `[C:\...\proj.csproj]`; that exact `dotnet` output was not reproduced), so the failure of `encina add` loses its cause; outside a `try` (`AddCommand.cs:165` and siblings) the process dies with an unhandled exception and a stack trace. Fails: the known failure pattern "the error path itself fails" (the real cause is replaced by a formatting exception); AGENTS.md section 3 scopes "errors are never swallowed" to background infrastructure, so it is an analogy here, not the rule. Fix: `Markup.Escape` for every interpolated value or `MarkupLineInterpolated`.

6. **Minor** — `encina generate` fails with "Could not find a part of the path" when `--output` points at a folder that does not exist yet and `--namespace` is not given. `CodeGenerator.cs:87` (and `:113, :142, :166`) calls `DetectNamespace(options.OutputDirectory)` before `Directory.CreateDirectory` (`:90, :116, :145, :169`), and `DetectNamespace` starts with `Directory.GetFiles(directory, "*.csproj", ...)` (`:353`), which throws `DirectoryNotFoundException` for a missing directory; `GenerateCommand.cs:243-247` reports it as a plain error. Related: `DetectNamespace` looks one level up only (`:359-369`) and otherwise falls back silently to `"MyApp"` (`:371`), so `-o src/MyApp/Features/Orders` yields `namespace MyApp;` for a project named something else.

## Lessons for the pipeline

- A scaffolder's generated text is code under review: the tests assert `ShouldContain` on substrings of it, so the generated `Program.cs` carried a two-type-argument `Send<,>` that no overload of `IEncina` has for the whole life of the tool. For any generator, check each generated API call against the declaring interface by grepping its signature in `src/` (zero hits for the call shape is the signal), and treat "no test compiles the output" as a standing check, not only for the saga template.
- Running a file-based replica by its literal scratchpad path worked for `issue-auditor` (Spectre.Console and System.Text.Json only, no `#:project` to `src/`); it turned two "probably" findings (markup exceptions, invalid JSON on backslash paths) into executed evidence in one run. Worth a line in the stage text.
- A tool with `PackAsTool` is a library nobody references: check `public` types against the PublicAPI/XML-doc setup of the csproj, not only the files; here the missing analyzer reference is why AUD-09 and AUD-10 reported nothing.
- Before filing "the packages the CLI adds do not exist", check the publication state in `ci-full.yml` and the open INFRA issues (#100, #101, #893): the gap is real but already tracked, which moved it to Informational.
