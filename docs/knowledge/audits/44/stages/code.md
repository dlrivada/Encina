## Findings
1. **Major** — `ShouldBeSuccess(expectedValue)` silently turns into a message-only check when the success type is `string`: `src/Encina.Testing/Assertions/EitherAssertions.cs:22-26` declares `ShouldBeSuccess<TLeft,TRight>(this Either<TLeft,TRight>, string? message = null)` and `:79-83` declares `ShouldBeSuccess<TLeft,TRight>(this Either<TLeft,TRight>, TRight expectedValue, string? message = null)`. For `Either<EncinaError,string>`, `result.ShouldBeSuccess("order-123")` has two applicable candidates with identical parameter types for the argument; the C# tie-break prefers the candidate that needs no substituted default argument, which is the `message` overload. The call then asserts only `IsRight` and uses `"order-123"` as a failure message; the value is never compared. A standalone replica of the two signatures (generic `Box<T>` instead of `Either`, run with `dotnet run` from the scratchpad, not the real types) printed `message-overload` for `Box<string>.ShouldBeSuccess("expected")` and `value-overload` for `Box<int>.ShouldBeSuccess(7)`. The identical pair exists in the sibling `src/Encina.Testing.Shouldly/EitherShouldlyExtensions.cs:41-44` and `:65-69`, and the repository's own tests hit it: `tests/Encina.UnitTests/AwsLambda/EventBridgeHandlerTests.cs:32` and `:128` call `result.ShouldBeSuccess("order-123")` on an `Either<EncinaError,string>` and would pass for any right value. The only tests of the overload use `int` (`tests/Encina.UnitTests/Testing/EitherAssertionsTests.cs:43`, `tests/Encina.UnitTests/Testing/Shouldly/EitherShouldlyExtensionsTests.cs:64`), where overload resolution picks the value overload, so no test can see it. Fails the known failure pattern "an assertion that cannot fail" (adversarial-reviewer) and AGENTS.md §9 (test quality). No open issue covers it (#1922, #2121, #2122 and #1923 are about codes, branches and manifests). Fix direction for the drafter: the two overloads must not be callable ambiguously for `string` (rename one, make the message keyword-only by dropping it from the value overload, or add a string-specific overload), in both packages, plus a test with a `string` success type that fails when the value differs, and a re-check of the call sites of `ShouldBeSuccess(<string literal>)` in `tests/` (EventBridgeHandlerTests `:32`, `:128`; the other string-literal callers found, `tests/Encina.IntegrationTests/Observability/Polly/EndToEndIntegrationTests.cs:120`, `:292` and `tests/Encina.PropertyTests/Infrastructure/EntityFrameworkCore/InboxStoreEFPropertyTests.cs:79`, pass a message on purpose). `Encina.Testing.TUnit` is not affected (`TUnitEitherAssertions.cs:51-79` has no message parameter).
2. **Major** — `FakeInboxStore` takes a `TimeProvider` ("controlling time in tests", `src/Encina.Testing.Fakes/Stores/FakeInboxStore.cs:32-35`) but decides expiry with the system clock: `GetExpiredMessagesAsync` filters with `m.IsExpired()` (`FakeInboxStore.cs:175`), and `FakeInboxMessage.IsExpired()` is `TimeProvider.System.GetUtcNow().UtcDateTime > ExpiresAtUtc` (`src/Encina.Testing.Fakes/Models/FakeInboxMessage.cs:41`); the property defaults `ReceivedAtUtc` and `ExpiresAtUtc` (`:23`, `:29`) also read `TimeProvider.System`. Advancing a `FakeTimeProvider` never expires a message, and a message added with an `ExpiresAtUtc` computed from a fake clock is compared against the wall clock. The other store methods in the same file use the injected `_timeProvider` (`:116`, `:134`), so the store is half-wired. `FakeScheduledMessage.IsDue()` (`src/Encina.Testing.Fakes/Models/FakeScheduledMessage.cs:55`) and the defaults at `:20`, `:23` have the same shape (no in-package caller of `IsDue`; the store uses its own `_timeProvider` at `FakeScheduledMessageStore.cs:122`, so this part is a public method that ignores the clock rather than a wrong store result). Fails AGENTS.md §3 "Every store and repository supports it [TimeProvider]" (why #543, #667) and AUD-14. Not covered by an open issue (a search of the open issues for `FakeInboxStore`, `FakeInboxMessage`, `FakeScheduledMessage` and `IsExpired` returns only #2267, #212, #141 and #126, none about this). Fix direction: the expiry/due decision takes the time from the caller (a `TimeProvider` or a `now` argument), not from a model property; add a test that advances a `FakeTimeProvider` past `ExpiresAtUtc` and expects the message in `GetExpiredMessagesAsync`.
3. **Minor** — the fake clock never reaches the fake stores in the two ways a test normally creates them. `AddFakeOutboxStore`, `AddFakeInboxStore`, `AddFakeSagaStore` and `AddFakeScheduledMessageStore` construct `new Fake...Store()` with no argument (`src/Encina.Testing.Fakes/ServiceCollectionExtensions.cs:81`, `:94`, `:107`, `:120`), although every store constructor accepts a `TimeProvider` (`FakeOutboxStore.cs:40`, `FakeInboxStore.cs:33`, `FakeSagaStore.cs:31`, `FakeScheduledMessageStore.cs:34`); only `AddFakeDeadLetterStore` reads the container's provider (`:137`, with a remarks paragraph saying so at `:131-134`). `EncinaTestFixture.WithMockedOutbox/Inbox/Saga/Scheduling/DeadLetter` do the same (`src/Encina.Testing/EncinaTestFixture.cs:232`, `:245`, `:257`, `:269`, `:281`) even after `WithFakeTimeProvider(...)` registers a `TimeProvider` (`:323-325`), so a test that advances `fixture.TimeProvider` does not move the retry, saga or schedule decisions of its own stores. The inconsistency inside one file (dead letter fixed, four others not) shows the rule was applied to one store only. Fails AGENTS.md §3 (TimeProvider in every store) and AGENTS.md §3 registration completeness. Not covered by an open issue (searched `FakeTimeProvider`, `AddFake`, `WithMockedOutbox`; #2148 and #2265 are about other tests). Fix direction: resolve `TimeProvider` from the container in the four registrations the way `AddFakeDeadLetterStore` does, and pass the fixture's fake provider in `EncinaTestFixture`; DI test that builds the provider and advances a registered `FakeTimeProvider`.
4. **Minor** — `ShouldBeValidationErrorForProperty` and four copies accept almost any validation error because the property name is matched as a case-insensitive substring of the whole message. `src/Encina.Testing/Assertions/EitherAssertions.cs:328` is `error.Message.Contains(propertyName, StringComparison.OrdinalIgnoreCase)`, and the real validation message is `"Validation failed for {RequestType} with {n} error(s): ..."` (`src/Encina/Validation/ValidationResult.cs:88`, produced at `src/Encina/Validation/ValidationOrchestrator.cs:70-71`). `propertyName` "Id" is a substring of "Validation", "Valid", "Order" of any `CreateOrder` request type, and "error" of "error(s)", so the assertion passes for a validation error on a different property. The same predicate is at `src/Encina.Testing/Assertions/EitherCollectionAssertions.cs:344`, `src/Encina.Testing/Handlers/ScenarioResult.cs:238`, `src/Encina.Testing/Handlers/HandlerSpecification.cs:459` and `src/Encina.Testing.Shouldly/StreamingShouldlyExtensions.cs:328`. This is an "assertion that cannot fail" in a library whose purpose is assertions. It is independent of #1922 (which is about the code prefix and would leave this open once fixed) and of #2121 (which asks for tests of the `PropertyName` details branch; the substring branch is the one that makes it vacuous). Fix direction: match the structured `PropertyName` detail, or the `"{PropertyName}: "` token the message format uses, not a bare substring; keep the message fallback only with a word-boundary match.
5. **Minor** — the custom `message` argument is silently dropped on the second assertion of the helpers that have one. In `src/Encina.Testing/Assertions/EitherAssertions.cs` the `message` reaches only the first check (`ShouldBeSuccess`/`ShouldBeError`), and the value or code comparison that follows is called without it: `:85` (`Assert.Equal(expectedValue, actualValue)`), `:195` (`Assert.Equal(expectedCode, actualCode)`), `:208` (`Assert.Contains`), `:222`, `:236`, `:250` (`Assert.StartsWith`). The same drop is in `src/Encina.Testing/Assertions/EitherCollectionAssertions.cs:450`. `src/Encina.Testing/Handlers/ScenarioResult.cs:262` (`ShouldBeErrorWithCode(string expectedCode)`) has no `message` parameter at all, so nothing is dropped there and it is not part of this finding. The documented parameter is "Optional custom failure message" (`EitherAssertions.cs:20`, `:41`, `:111`, `:141`, `:317`), and the Shouldly sibling passes it (`EitherShouldlyExtensions.cs:71`, `:214`, `:232`), so the two packages give different failure output for the same call. Fix: the `message` cannot be handed to the underlying calls as they are, because `xunit.v3.assert` 3.2.2 has no message overload for `Assert.Equal`, `Assert.Contains` or `Assert.StartsWith` (reflection over `xunit.v3.assert.dll` by the verifier: only `Assert.True(bool, string)` and `Assert.Fail(string)` take one). Compare first and fail through `Assert.True(condition, message)` or `Assert.Fail`, composing the custom message with the expected and actual values, and test one failing call per helper with a custom message.
6. **Minor** — `EncinaFixture` disposes its provider synchronously only and replaces it silently. `src/Encina.Testing/EncinaFixture.cs:42` declares `IDisposable` only, `:96` calls `_serviceProvider?.Dispose()` before building the next provider and `:212` does the same in `Dispose`. `ServiceProvider.Dispose()` throws `InvalidOperationException` for a registered service that implements only `IAsyncDisposable` (a replica with one such singleton, run with `dotnet run` in the scratchpad, printed `InvalidOperationException: 'AsyncOnly' type only implements IAsyncDisposable. The newer fixture in the same package already implements both (`src/Encina.Testing/EncinaTestFixture.cs:56`, `:544-573`), and `ModuleTestFixture.cs:59` too. In addition, a second `CreateEncina` call on the same fixture disposes the provider behind the `IEncina` it returned earlier (`:96`), so two instances from one fixture cannot coexist and the first fails with `ObjectDisposedException` on use; the class summary and example (`:6-41`) present the fixture as a way to "share configuration across tests" with `IClassFixture` although it keeps no configuration. Fix: implement `IAsyncDisposable` and dispose with `DisposeAsync`, and either make `CreateEncina` throw/guard on a second call or document the single-instance contract; test with an `IAsyncDisposable`-only singleton.

## Lessons for the pipeline
- The archivist wrote "no in-memory transport" after grepping only `src/Encina.Testing`; the transport lives in `src/Encina.InMemory`. For a pending-work item, search the whole `src/` tree by concept (transport, InMemory) before recording it as not delivered.
- When an issue's headline type is a test helper, check the overload set with a standalone replica: C# prefers the overload that needs no default argument, so a `(T value, string? message = null)` overload next to a `(string? message = null)` overload breaks for `T = string`. A hook-safe replica (no `src/` reference, literal path) settles overload resolution in one run.
- A MUST rule that names "every store" (TimeProvider) needs a grep over the places stores are constructed (DI extension methods and fixtures), not only the store classes; the store constructors were correct and every construction site was not.
