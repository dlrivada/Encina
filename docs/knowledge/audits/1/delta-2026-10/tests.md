## Findings
1. **Minor** — `.github/coverage-manifest/Encina.json:200-207` (`Core/ServiceCollectionExtensions.cs`) and `:313-320` (`Dispatchers/MediatorAssemblyScanner.cs`): both files have entries with `defaultTests: [unit, guard]`, so they are not untargeted, but the effective targets are the package aggregates (unit 70, guard 20) and are clearly below what the files already deliver and what is demanding and realistic for them. Measured today: `ServiceCollectionExtensions.cs` unit 94.1% / guard 85.3% (68 coverable lines, 17 branching constructs, every `AddEncina` registration path); `MediatorAssemblyScanner.cs` unit 98.6% / guard 91.9% (74 coverable lines, 14 branching constructs, a pure reflection scan). A guard target of 20 for a file whose guard tests already reach 85-92% protects nothing. Proposed targets and justification, for the manifest once #1762 adds the field. `Core/ServiceCollectionExtensions.cs`: unit 90, guard 80, contract 15, because `AddEncina` is a small registration method whose branches (assembly scan, behavior and handler registration, context accessor, metrics) are all exercised by `AddEncinaServiceGraphTests`, and a guard run reaches 85%. `Dispatchers/MediatorAssemblyScanner.cs`: unit 90, guard 85, because the scanner is a single reflection pass with no I/O whose request, notification, stream and open-generic branches are all hit by the existing tests (unit 98.6%, guard 91.9%).
2. **Minor** — `.github/coverage-manifest/Encina.json:313-320` (`Dispatchers/MediatorAssemblyScanner.cs`): the entry's only justification is the generic default `"reason": "Default: assume testable with mocks"` with `"defaultRule": "*.cs"`, which says nothing about this file's code. Proposed justification, one sentence: "Internal reflection scanner that classifies handler and behavior types (request, notification, stream, open generic) for `AddEncina`; deterministic, no I/O, fully unit-testable with in-memory types, and its null guards belong to the guard flag." The same generic reason sits on most `Dispatchers/*` entries (`Encina.RequestDispatcher.cs:305-312`) and should be replaced where those files are reviewed.
3. **Minor** — `.github/coverage-manifest/Encina.json:200-207` (`Core/ServiceCollectionExtensions.cs`): `defaultTests` lists unit and guard only, while the package has a `contract` target (15) and `AddEncina` is public API (AGENTS.md section 9: contract is required "if public API"). Contract tests of this entry point already exist and run (`tests\Encina.ContractTests\ServiceRegistrationContracts.cs`, `HandlerRegistrationContracts.cs`, both calling `AddEncina`), so the contract flag applies in practice but is not in the file's obligations. Proposed: add `contract` to `defaultTests` with target 15, justification "`AddEncina` is the public registration contract (which services a consumer can resolve), kept stable by the registration contracts". `MediatorAssemblyScanner` is `internal`, so contract does not apply to it; property, integration, load and benchmark do not apply to either file (no persistence, no concurrency, no hot path).
