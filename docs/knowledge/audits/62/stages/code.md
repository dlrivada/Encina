## Findings

1. **Major** — With `RoutingSlipOptions.ContinueCompensationOnFailure = false` a failing compensation makes `RunAsync` throw instead of returning a Left, and it first re-runs the compensations a second time. `RoutingSlipRunner.cs:230` (step-failure path, `FailStepAsync`) calls `CompensateAsync`; when a compensation throws, `CompensateAsync` rethrows (`:318-321`). That exception leaves `FailStepAsync`, `ExecuteNextStepAsync` and `ExecuteStepsAsync` and lands in the `catch (Exception ex)` of `RunAsync` (`:141-149`), which calls `CompensateAsync` again over the same, untrimmed activity log (`:146`, log read at `:284`). The compensation that just threw runs a second time; if it throws again, the rethrow at `:320` escapes the catch block and `RunAsync` faults with the compensation's exception. The step's own Left is lost either way. If the second pass succeeds (transient fault), the caller gets `HandlerFailed` built from the compensation exception's message (`:148`), not the error of the step that failed. The compensations of earlier steps (steps before the one that threw) are never reached in the throwing case. This breaks the option's own doc ("stop immediately and mark the routing slip as failed", `RoutingSlipOptions.cs:35-39`), the Railway Oriented Programming rule (operations return `Either`, AGENTS.md section 3) and the unused code `RoutingSlipErrorCodes.CompensationFailed` (`RoutingSlipErrorCodes.cs:31`) is the code this path should return. The existing test `RunAsync_CompensationThrows_WithoutContinueOnFailure_Throws` (`tests/Encina.UnitTests/Messaging/RoutingSlip/RoutingSlipRunnerTests.cs:513-533`) pins the exception escape on purpose and does not count compensation calls, so it hides the double invocation. Derived from reading, not run; a verifier reproduction: steps S1 (compensation counts calls), S2 (compensation throws), S3 returns Left, option false; assert one Left comes back and each compensation ran at most once. Check failed: ROP rule; AUD-01 (code does not do what the option promises); known pattern "errors escape a catch block that is itself a failure handler".

2. **Major** — With the default `ContinueCompensationOnFailure = true` a failed compensation is invisible to the caller: the run reports the original step error as if the undo had worked. The catch at `RoutingSlipRunner.cs:314-323` only logs `CompensationFailed` (EventId 2886) and continues; `RunAsync` then returns the step's Left (`:107`, `:232`) and `RoutingSlipResult` carries no compensation outcome (`RoutingSlipResult.cs:10-44`, only `ActivityLog` of executed steps). A compensation is a `Func<..., Task>` (`RoutingSlipStepDefinition.cs:25`), so it cannot return an error either. The code `RoutingSlipErrorCodes.CompensationFailed` and the status text "The routing slip failed (step or compensation failed)" (`RoutingSlipStatus.cs:29-31`) show the intent; nothing produces them. A caller that retries or alerts on the result cannot tell "rolled back" from "left half-done". Check failed: AGENTS.md section 3, a failure that is only logged is reported as handled (errors never swallowed; the sibling low-ceremony saga has the same shape, filed as #2304, which does not mention routing slips). Derived from reading.

3. **Major** — Routing slip timeouts are accepted and discarded: nothing enforces `RoutingSlipBuilder.WithTimeout` or `RoutingSlipOptions.DefaultTimeout`. `RoutingSlipBuilder.cs:132-137` stores `_timeout`, `BuiltRoutingSlipDefinition.Timeout` exposes it (`:197`), `RoutingSlipOptions.DefaultTimeout` defaults to 30 minutes (`RoutingSlipOptions.cs:12`), and the XML example teaches `.WithTimeout(TimeSpan.FromMinutes(5))` (`RoutingSlipBuilder.cs:57`). A search of `src/Encina.Messaging/RoutingSlip` for `\.Timeout\b|DefaultTimeout` finds only the declarations and the builder assignment; `RoutingSlipRunner` never reads either, never links a timeout token and never returns `RoutingSlipErrorCodes.Timeout` (`:36`, referenced nowhere else in `src/`). A slip with a hanging step runs forever. Same defect as the saga (#2208) and Durable saga (#3212) timeouts, which are filed for those components only. Check failed: AUD-01 (the builder API and its doc example promise a bound the runner does not apply); fail-closed principle for resource bounds.

4. **Major** — On the step-failure path the compensations run under the caller's cancellation token, so a cancellation during or just before the undo cancels the undo. `RoutingSlipRunner.cs:230` passes `cancellationToken` to `CompensateAsync`, while both catch paths pass `CancellationToken.None` (`:137`, `:146`). When the token is cancelled while the compensations run (or a step returns a Left because it observed the cancellation), each remaining compensation receives a cancelled token, throws `OperationCanceledException`, and is swallowed by `catch (Exception ex)` at `:314-323` with the default option, so the remaining steps are not undone and only a log line remains. The inconsistency inside one class is the evidence; #2303 files the same defect for SagaRunner and cites `RoutingSlipRunner.cs:137` and `:146` as the correct precedent, so the step-failure path here is the copy that issue does not cover. Derived from reading, not run.

5. **Minor** — `catch (OperationCanceledException)` at `RoutingSlipRunner.cs:132` has no `when (cancellationToken.IsCancellationRequested)` filter, so a step that throws `TaskCanceledException` from its own timeout (an `HttpClient` timeout, a linked token) while the caller's token is live is logged as "cancelled" (`:134`, EventId 2877), compensated and returned as `HandlerCancelled` (`:139`) instead of as a step failure. The sibling ScatterGatherRunner separates the two (`ScatterGatherRunner.cs:104` filters on the caller's token and treats other cancellations as timeouts, per #2307), and SagaNotFoundDispatcher uses the same filter (`SagaNotFoundDispatcher.cs:103`). #2307 covers SagaRunner only. Derived from reading.

6. **Minor** — `RoutingSlipStepBuilder` silently drops a step that is never closed and adds a step twice when it is closed twice. `Execute`, `Compensate` and `WithMetadata` only assign fields (`RoutingSlipStepBuilder.cs:29-117`); the step reaches the parent only in `Complete()` (`:163-175`), which `Step`, `OnCompletion`, `WithTimeout` and `Build` call (`:124-161`) and which records nothing that the step was already added. `builder.Step("a").Execute(f);` as a statement of its own, followed by `builder.Step("b")....Build()`, builds a slip that contains only "b" and runs without error; `stepBuilder.Build()` called twice adds the step twice. The default step name `Step {_steps.Count + 1}` (`RoutingSlipBuilder.cs:99`) is computed at open time, so two builders opened before either is closed are both "Step 1". Identical shape to #2306 (saga step builder, a [BUG]); that issue names `SagaStepBuilder` only. Derived from reading.

7. **Minor** — Result bookkeeping misreports dynamic itinerary changes that net to zero or remove steps. `RecordStepSuccess` counts a step's additions as `remainingSteps.Count - stepCountBefore` and ignores a negative difference (`RoutingSlipRunner.cs:198`, `:250-255`), and `StepsRemoved` is derived as `initialStepCount + StepsAdded - StepsExecuted` (`:119`, `:128`). A step that adds one step and removes another (net 0) reports `StepsAdded = 0` and `StepsRemoved = 0`; a step on a 3-step slip that adds one step and removes two reports `StepsRemoved = 1` while 2 were removed and 1 was added. `RoutingSlipResult.StepsAdded` and `StepsRemoved` are public figures documented as "dynamically added" and "skipped or removed" (`RoutingSlipResult.cs:25-33`). The dynamic route is the pattern's defining feature (the archivist's decision 2). Derived by hand from the arithmetic, not run.

## Lessons for the pipeline

- A `catch` block that is itself the failure handler (here a second compensation pass inside `catch (Exception)`) must be read together with every path that can throw into it; the double run only shows when the step-failure path and the catch path are read as one flow, not method by method.
- An option documented as "stop immediately and mark failed" is worth tracing to its failing branch: the test that pins `Throws` for the `false` value looked like coverage and was the pointer to the ROP violation (a test named `..._Throws` for a business failure is a finding candidate).
- For a runner copied in a family (Saga, RoutingSlip, ScatterGather, ContentRouter), the open issues of the family cover the sibling that was audited first; compare each issue's cited file list with the other runners (here #2303, #2307, #2306 and #2208 each covered only the saga copy).
- Brace globs in the Grep tool (`{A,B}/*.cs`) silently returned no matches inside the worktree; use one Grep call per folder.
