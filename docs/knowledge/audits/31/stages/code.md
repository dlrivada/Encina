## Findings
1. **Major** — `.github/workflows/load-tests.yml:256, 265, 274, 345, 353, 358, 444, 449, 548, 553, 667, 672`: every scenario step and every threshold-validation step of the five sub-jobs (database, messaging, caching, locking, broker) has `continue-on-error: true`, with no comment explaining it, so a crashed harness, a failed container or a threshold breach cannot fail a job. Evidence: scheduled run 37089511733 (2026-10-03) concluded `success` for all six jobs; GitHub reports a continue-on-error step as `success` whatever its outcome, so even the step list cannot show a failure. Only `run-load-tests` (the Windows job, no `continue-on-error`) can turn the run red, and the failure I verified in the weekly history is its `Restore` step (run 35415291678, 2026-09-19; the 12 latest weekly runs are 10 red from 2026-07-18 to 2026-09-19 and 2 green, the failing step of the other nine was not inspected), not a measurement. Fails the known pattern "a gate that cannot fail" (lesson of audits #19 and #29) and the stated intent of `ci.yml` ("Test failures MUST fail the CI — no continue-on-error", `ci.yml:194, :268, :307, :346, :385, :495`). Not covered: #1760 asks only that an unknown scenario name fails and that the `tests/Encina.LoadTests` projects run; #930 and its comment (2026-09-26) question the numbers, not the masking. No open issue names `continue-on-error` in `load-tests.yml`. Fix direction: remove the 12 keys (or restrict them to the summary and upload steps) in the same change that makes #1760's scenarios real, since removing them first would turn the run red on the first dispatch that does not exist.
2. **Major** — `.github/workflows/load-tests.yml:357, 448, 552, 671` and `.github/scripts/check-load-metrics.cs:226-235, 246-291`: the four "Validate X thresholds" steps run `check-load-metrics.cs --config .github/ci/nbomber-{messaging,caching,locking,brokers}-thresholds.json`, but that script reads exactly nine keys (`metricsDirectory`, `maxMeanCpuPercent`, `maxPeakWorkingSetMb`, `minSend*Ops`, `minPublish*Ops`, `LoadMetricsCheckConfig`), and those files contain none of them (their keys are `global`, `featureThresholds`, `providerThresholds`, `scenarioThresholds`, e.g. `.github/ci/nbomber-caching-thresholds.json`). Evidence: the caching job log of run 37089511733 prints `Mean CPU: NaN% (max 1.00%) | Peak Working Set: NaN MB (max 100.00 MB) | Send: 240000.00 ops/sec ... ## Lessons for the pipeline
- When the sibling of a workflow review (audit #29 here) already covered the CI test jobs, the new effort belongs in the workflows nobody confirmed (SBOM, benchmarks, load tests, mutation tests); read their latest real runs, not only the YAML, because a green conclusion on a `continue-on-error` step proves nothing.
- For a load or benchmark workflow, follow each script it calls to its input: three of the four load-test defects here (threshold files read by a script with a different schema, a stale script path, summaries reading a directory nothing writes) are invisible in the YAML and show up only by reading the step log and the called script side by side.
- A workflow check that passes with "NaN", "N/A" or "No reports found" in its log is a finding candidate: grep the job log of the latest run for those tokens before writing "green".
