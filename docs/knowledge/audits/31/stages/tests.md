## Lessons for the pipeline
- For a CI-workflow scope the useful test-stage work is a synthetic-input run of each gate script that the workflow calls, with one input that must fail and one control input in the script's own schema: four runs (R1 to R4) reproduced two Major code-stage findings in minutes without Docker, and the control (R2) is what proves the script can fail at all.
- A gate script that ignores unknown configuration keys and falls back to defaults on a missing file (`check-load-metrics.cs`, `summarize-nbomber-run.cs`) is a fail-open pattern worth a repository search for `Falling back to defaults`; the stage definition could ask for the search whenever a workflow passes `--config` to a script.
- The workflows of a scheduled or dispatch-only tier (load, mutation, SBOM, benchmarks) have no pull-request run, so nothing but a static check or a script self-test guards a change to them; the delta brief for a CI-workflow scope can say so up front and ask for the static-check proposal.
