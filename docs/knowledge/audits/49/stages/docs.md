## Findings
1. **Major** — `docs/testing/benchmarks/benchmark-results.md:326-327` (section "8. Cache Optimization Analysis", generated table `bench:cache/*`) contradicts the claim the same issue's records make. The table shows `Cache_GetOrAdd_Direct` 3.41 ns / 0 B and `Cache_TryGetValue_ThenGetOrAdd` 3.65 ns / 0 B (ratio 1.07), so the TryGetValue-first pattern is not faster and the "always allocates" baseline allocates nothing. The page never says so; the same claim, that TryGetValue-before-GetOrAdd "avoids delegate allocation on cache hits", stays as fact at `CHANGELOG.md:9612`, `docs/releases/v0.11.0/CHANGELOG-DETAILS.md:4155`, `docs/releases/pre-v0.10.0/README.md:853` and, as a lesson, `docs/engineering/PROJECT-HISTORY.md:264` ("GetOrAlloc always allocates the factory delegate even on cache hits, so TryGetValue should be checked first"; note the typo `GetOrAlloc`). The code stage (finding 1, executed replica: 0 bytes/op for a `static` lambda with and without the guard) shows the premise is false for the request dispatcher. Check that fails: accuracy against today's code and measurements. Release-history lines are dated records and only need a correction note if the maintainer wants one; `PROJECT-HISTORY.md:264` and the benchmark page are current-facing. Related: #927 covers qualitative claims in ADR-003 only, not these pages.
2. **Minor** — `docs/testing/benchmarks/benchmark-results.md:337-340` (same section, "### Analysis") hand-types performance figures: "sub-5ns", "~1 μs for commands, ~460 ns for notifications", "TypeCheck caching adds ~1.7 ns overhead", "~3 ns". The table above them is a `docref-table` citation, the bullets are literals. They already drifted: the table gives 1,036 ns and 461 ns (rounded, acceptable) but "~1.7 ns" is a hand subtraction of 2.10 ns and 0.38 ns, and "Direct method calls are ~3 ns" matches no row of that table (the 3.41 ns row is a dictionary lookup). Check that fails: figures cited, never hand-typed (rule (a) point 3). Also, the bullet "TypeCheck caching ... avoids repeated type inspection" hides that `TypeCheck_Cached` (2.10 ns) is 5.5 times slower than `TypeCheck_Direct` (0.38 ns) in this run, so the page presents a regression as a benefit.

## Lessons for the pipeline
- For a performance issue, read the project's own benchmark results page for the issue's benchmark rows before trusting the claim: here the published table (3.41 ns vs 3.65 ns, both 0 B) already disproved "avoids allocation" and nobody had read it against the changelog.
- The Analysis bullets under a generated `docref-table` are a typical place for hand-typed figures; check bullets next to a citation table, not only prose.
