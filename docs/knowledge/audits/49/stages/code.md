## Findings
1. **Minor** — The "TryGetValue before GetOrAdd avoids delegate allocation" premise is false for the request dispatcher, and the benchmark pair that is meant to prove it cannot show it. `src/Encina/Dispatchers/Encina.RequestDispatcher.cs:63-70` guards `GetOrAdd(cacheKey, static key => CreateRequestHandlerWrapper(...))` with `TryGetValue` and comments that this avoids the delegate allocation. A `static` lambda is cached by the compiler, so `GetOrAdd` with it allocates nothing on a hit. Executed (`alloc.cs`, 1,000,000 calls each, `GC.GetAllocatedBytesForCurrentThread`): `GetOrAdd(static lambda)` 0 bytes/op, `TryGetValue` then `GetOrAdd(static lambda)` 0 bytes/op, `GetOrAdd(capturing lambda)` 88 bytes/op. The sibling `src/Encina/Core/StreamDispatcher.cs:31-33` uses the plain `GetOrAdd` with the same `static` lambda, so the two dispatchers disagree for no reason and the extra lookup on a miss is pure overhead. The notification path is different (`Encina.NotificationDispatcher.cs:247-250` captures `method`, `handlerType`, `handledType`, so the guard is real there). The benchmark has the same flaw: `CacheOptimizationBenchmarks.cs:25` makes `Factory` a `static readonly` delegate and `:62` passes it, so `Cache_GetOrAdd_Direct` (the "always allocates" baseline) allocates nothing either; and both cache benchmarks (`:60-77`) and `TypeCheck_Cached` (`:137-149`) run on a private `ConcurrentDictionary` and a copy of the algorithm, not on the dispatcher, so a regression in the production caches (see finding 3 and #2089) cannot show in them. The CI gate misdescribes what it gates: `.github/ci/benchmark-thresholds.json:59-63` attaches `maxAllocatedBytes: 0` and the description "ConcurrentDictionary TryGetValue hot path" to `Cache_GetOrAdd_Direct`, which is the GetOrAdd baseline, while the optimized `Cache_TryGetValue_ThenGetOrAdd` has `docRef: null` and no threshold (`.github/perf-manifest/Encina.Benchmarks.json:99-102`). The claim is repeated in `CHANGELOG.md:9612` and `docs/releases/v0.11.0/CHANGELOG-DETAILS.md:4155`. Fails AUD "measurable improvement is evidenced" (the acceptance criterion the archivist found unevidenced) and the known failure pattern "comment/claim not matching the code". Fix direction: drop the redundant `TryGetValue` in `RequestDispatcher` (or keep it and correct the comment), benchmark the real dispatcher caches, and point the threshold at the variant it names. Not covered by an open issue: searched the dump for "delegate allocation", "allocates the delegate", `get-or-add-direct`, `Cache_GetOrAdd_Direct` (no match).
2. **Minor** — The notification path re-resolves its handler type and rebuilds the handler list on every publish, the reflection and allocation work the request path moved into a cached wrapper. `src/Encina/Dispatchers/Encina.NotificationDispatcher.cs:63-64` calls `typeof(INotificationHandler<>).MakeGenericType(notificationType)` and then `GetServices(handlerType).Where(...).Cast<object>().ToList()` per `Publish`; nothing caches the closed handler type per notification type, whereas `RequestHandlerWrapper<,>` keeps `HandlerType` in a static field (`src/Encina/Core/Encina.cs:168`) and is cached per type pair (`Encina.RequestDispatcher.cs:64-70`). Issue #49 was about minimizing reflection in these delegate caches; the notification side only got the invoker cache (`NotificationHandlerInvokerCache`, `Encina.cs:44`). Derived from reading, not measured (the runtime caches `MakeGenericType` results internally, so the cost is a lookup plus the LINQ allocations, not a type build). Distinct from open #2089, which is about the invoker-cache probe key at `:215-216`, and from #2101 (coverage obligations). Fails the issue's own "minimize reflection/boxing" goal and AUD "optimization applied consistently across the paired code paths".
3. **Minor** — `ResolveHandleMethod` does not prefer the exact-match `Handle` overload, contradicting its documented behaviour, and can pick an overload that throws `InvalidCastException`. `src/Encina/Dispatchers/Encina.NotificationDispatcher.cs:357-373` takes `FirstOrDefault` of the candidates satisfying `HasCompatibleFirstParameter`, and `:384-386` accepts the match in both directions (`parameterType.IsAssignableFrom(candidateType) || candidateType.IsAssignableFrom(parameterType)`). Executed on a copy of the two methods (`resolve.cs`): handler declaring `Handle(Base)` then `Handle(Derived)`: publish `Derived` -> `Handle(Base)`, publish `Base` -> `Handle(Base)`; handler declaring `Handle(Derived)` then `Handle(Base)`: publish `Derived` -> `Handle(Derived)`, publish `Base` -> `Handle(Derived)`. The last case compiles an invoker that does `Expression.Convert(notification, Derived)` on a `Base` instance (`:297`, `:304`); read, not run end to end: the cast throws inside the delegate and `ExecuteHandlerAsync` turns it into a `NotificationException` Left (`:194-208`), so the handler body never runs. The class remark claims "preferring the more specific (runtime) type" (`:29-30`), which the `FirstOrDefault` does not implement. The invoker cache stores each entry under the chosen method's own parameter type (`handledType = method.GetParameters()[0].ParameterType`, `:244-245`, `GetOrAdd` at `:249`), so every cached entry is correct for its key; the wrong dispatch recurs because `TryGetNotificationExecutor` probes the cache with `(handlerType, desiredNotificationType)` at `:215-216` and, on a miss, re-runs `ResolveHandleMethod` at `:223` (the miss pattern of #2089), not because a wrong invoker is cached. ## Lessons for the pipeline
- When an issue claims "avoids delegate allocation", check the lambda's capture state before accepting it: `static` lambdas and cached delegate fields do not allocate, and a 20-line replica with `GC.GetAllocatedBytesForCurrentThread` settles it in one run (finding 1).
- For a performance issue, read how the CI threshold file names the benchmark it gates; here the gate carried the optimized variant's description on the unoptimized baseline.
- The archivist's destination sweep marked the three optimizations `current: yes` on the strength of a benchmark file; the benchmarks measure copies of the algorithm, not the production caches, so "benchmark present" is not evidence the optimization is proven.
- Before saying a cache holds a wrong value, read the line that stores it and the key it uses: here the entry is stored under the chosen method's own parameter type and is correct; the defect is the repeated selection on a lookup miss. When costing a branching method per request, count each call per branch (command, query, unclassified) instead of summing every call in the file.
- For a "cache in the dispatcher" issue, grep the repository for the same per-request reflection shape (`GetInterfaces()` inside a pipeline behavior) in the provider packages; the eight read/write routing copies were one hop outside the scope list.
