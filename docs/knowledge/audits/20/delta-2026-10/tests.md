## Lessons for the pipeline

- A package-level guard figure for a shared registration file can come mostly from other packages' guard classes; before accepting a guard target, run the file's own guard namespace alone and then the project-wide filter and say which one the proposal rests on (`MessagingServiceCollectionExtensions.cs`: 8.04% own, 66.96% project-wide, and the open issue attributed the whole figure to the file's own guard class).
- Before agreeing with a remediation that deletes "redundant" test files (#1340), measure the flag with only the surviving tests; the six duplicate guard files were the only source of the guard coverage of the shared class (7/39 with them, 0/39 without).
- A knowledge-record scope that names "N call sites" of a helper makes rule (b) cover every one of them (90 files here); the delta brief should say whether call-site files owned by other issues' audits are in scope, because the stage otherwise has to group them by theme and the findings overlap later delta audits of the same stores.
- A validation regex checked in a shell (`[regex]::IsMatch`) is a cheap, product-free way to derive a validator defect when the scratch-app route is blocked; `$` accepts a trailing newline unless the pattern uses `\z` or `RegexOptions` change it.
- The coverage helper must be called with a literal absolute path: `& "$sp\cov.ps1"` is blocked by `guard-orchestrator-writes`, `& 'C:\...\cov.ps1'` runs.
