The live data agrees: `latest.json` lists 95 files for package `Encina`, all inside the simulated covered set (128 files; 33 of them have no tested mutant or a missing shard), and none outside it. This is the AUD "who fails when the intent is violated" check: `methodology.md:119` and the workflow comment at `mutation-tests.yml:84-89` promise that "a file added to the folder later always lands in some shard", which holds only for the folders that have a shard; `methodology.md:34` and `056-mutation-testing-scope.md:9` describe the shards as slices of `src/Encina` without saying that most folders are not sliced, and ADR-056's own criterion (fail-closed gates, security, state machines, concurrency, high complexity) selects `Identity/`, `Authorization/`, `Recoverability/` and the dispatchers. The per-file score that #67's decision made the only target therefore does not exist for these files, and nothing says so: no step of `select-matrix` (`:300-334` only checks SHARDS/TIMEOUTS length and span twins) compares the shard globs with the file tree. Open issues #2829 (more packages), #2897 (a decision per package), #2830 (a package-level scope panel) and #2914 (re-open the scope at rc.1) all work at package level; none covers the folders inside `Encina`. Evidence is a static simulation (not Stryker's own matcher); it was cross-checked against the live file list as stated. Fix direction: add to `select-matrix` a check that every non-excluded file of the project matches a shard or an explicit, reasoned exclusion list, then add the missing folders (or record them as deferred) and state the real coverage in the methodology page.
2. **Major** — The reusable template `encina-full-ci.yml` offers a project-wide mutation threshold that cannot enforce a real score. `.github/workflows/templates/encina-full-ci.yml:70-74` declares `mutation-score-threshold` and `:561-579` enforces it by reading `"mutationScore"` with `grep -oP` from each `mutation-report.json`. A Stryker JSON report has no such key: the only report available in the main checkout (`artifacts\mutation\StrykerOutput\2025-12-07.01-17-30\reports\mutation-report.json`, 566 KB) has the top-level keys `files, projectRoot, schemaVersion, testFiles, thresholds` and 0 occurrences of `mutationScore`. What the step then does is derived from the script text, not run (no bash was run). The step sets `shell: bash` (`:563`), which GitHub runs as `bash --noprofile --norc -eo pipefail`. If a report path matched, `score=$(grep -oP ... | head -1)` (`:572`) would return 1 because grep finds no `mutationScore` (pipefail), an assignment takes the status of its command substitution, and `-e` would end the step with exit 1 before `:573`: it would fail for every threshold other than the default `0`, not pass, whatever the real score is. But the loop `for report in artifacts/mutation/**/mutation-report.json` (`:568`) has no `globstar`, so `**` behaves as `*` and probably cannot match Stryker's `reports/mutation-report.json` layout under `--output "artifacts/mutation/$proj_name"` (`:549`); the pattern then stays literal, `[[ ! -f "$report" ]] && continue` skips it, and the loop body never runs, so the step passes. Which of the two branches applies depends on the layout (the glob branch is the likelier one); either way the input cannot enforce a real project-wide threshold. It is also the single-percentage model that #67 rejected: `docs/ci-cd-templates.md:211` documents the input and `:259` recommends `mutation-score-threshold: '80'`. It also installs Stryker unpinned (`:526`, `dotnet tool install --global dotnet-stryker`) and runs the VsTest-era `--test-project` form (`:546-550`) that the repository's own methodology replaced. Open issue #1660 covers only the `coverage-threshold` input of the same templates; its body has no mutation input (0 hits for `mutation-score-threshold` in the dump of open issues). Fix direction: delete the input and its step (the per-file model has no threshold to enforce), or replace it with a per-file report and no pass/fail.

## Lessons for the pipeline
- For an issue closed as "rejected by policy" with an empty diff, the code stage still has work: apply the policy to the tooling that implements the rejected model (templates, dashboard thresholds, helper scripts). Searching `threshold|target` over `.github/` and the dashboard front end found two of the five findings.
- A shard or matrix partition is checkable mechanically: translate the globs to regexes, list the files of the project that match none, and cross-check the result against the live dashboard's file list. That turned a documented "every file lands in some shard" into a measured 220-file gap in one script, and the same check belongs in the workflow.
- Compare every helper that recomputes a score with the documented formula and with a real report; the status name `Timeout` versus `TimedOut` was visible only against a real Stryker JSON (the main checkout keeps old ones under `artifacts\mutation\StrykerOutput`).
- A bash gate claim ("passes", "fails open") must account for the step's `shell:` (GitHub's bash adds `-eo pipefail`, so a grep with no match ends the step with exit 1) and for whether a `**` in a `for` glob can match without `globstar`; state which branch applies and label the other as derived (verifier correction 7 of #67).
- Quote a line number from a fresh Grep of the exact text (the Spanish messages of `list_survivors.cs` are at `:15`, `:47`, `:136`, `:140`), and check how often a helper such as `statusLabel` is called before saying a label appears on every row.
- When a template or script reads a key from a third-party report (`mutationScore`), open a real report and count the key before accepting the gate; a missing key plus `bc` and `(( ))` makes a bash gate fail open.
