## Findings
1. **Blocker** — `docs/en/guides/REQUIREMENTS.md:26`, `:35`, `:53` and `docs/en/guides/REQUIREMENTS_MAPPING.md:23` state a project-wide mutation gate ("Mutation score remains ≥93.74% on the main branch", "CI enforces the 93.74% baseline", row "Mutation | run-stryker.cs | ≥93.74% mutation score", "Maintain ≥93.74% mutation score") that does not exist and that #67's decision rejected. The checks that fail are house rule 2 (a hand-typed figure, not a `mutref` citation) and the real-behaviour check: `.github/stryker-config.json:17` sets `"break": 0`, so Stryker never fails on a score, and no workflow step compares a score with a threshold (code stage informational item; `run-stryker.cs` exit branch unreachable). The figure does not match the dashboard either: the code stage fetched an overall 68.54 % from the live `latest.json` on 2026-11-07. `REQUIREMENTS.md:35` and `:53` also say a CI step enforces it, and `REQUIREMENTS_MAPPING.md:23` names `run-stryker.cs` as the "CI step", which only measures. Related open issues leave this out: #2072 touches `REQUIREMENTS.md:35` only for the "refresh the badge" clause and explicitly keeps the 93.74 sentence out; #2003 covers `:27` and `:54` (benchmark percentages). Search `93.74` over open issue bodies hits only #2003, #2072 and #3323, none of which asks to remove it. The earlier audit #32 (`docs/knowledge/audits/32/stages/docs.md:18`) reported the same line as a Blocker. Fix direction: drop the percentage and the "CI enforces" sentence, say the score is tracked per file on the dashboard and cite per-file figures with `<!-- mutref -->` markers.
2. **Major** — `docs/en/guides/REQUIREMENTS.md:34` and `:52` give "≥90% line coverage" as a project-wide gate, and `:34` says "Coverage results must stay ≥90% line coverage". `AGENTS.md` section 9 states there is no project-wide percentage; coverage is per flag against `.github/coverage-manifest/{Package}.json`. This is the single-percentage model that #67's close comment retired, stated on the page that lists the quality gates (`REQUIREMENTS.md:50-53` table). The figure is hand-typed (house rule 2) and cites no `covref`. Same family as finding 1; kept separate because the rejected model is coverage, not mutation, and the fix points to the coverage methodology page.
3. **Major** — `docs/ci-cd-templates.md:211` documents the input `mutation-score-threshold` ("Minimum mutation score %") and `:259` recommends `mutation-score-threshold: '80'`, as a reference-table row and a copy-paste example. Per the code stage (finding 2, re-read) the template step (`.github/workflows/templates/encina-full-ci.yml:561-579`) cannot enforce a real score: Stryker reports have no `mutationScore` key; the step runs under `bash -eo pipefail` (`:563`); and the loop `for report in artifacts/mutation/**/mutation-report.json` (`:568`) has no `globstar`, so `**` acts as `*` and probably never matches the `reports/` layout. The loop body then never runs and the step passes; if a report did match, the step would end with exit 1 for every non-default threshold whatever the score. Either way the page documents a project-wide threshold that is both the model #67 rejected and unable to enforce a real score. Open issue #1660 covers only the `coverage-threshold` input of the same templates (its body has no mutation input). Fix direction depends on the code fix: delete the input row and the example line when the template drops the input.

## Lessons for the pipeline
- For an issue whose decision rejects a single-percentage model, search the whole of `docs/` for the rejected figure's literal (`93.74`) and for the sibling single-percentage gates on the same table (`≥90% line coverage`): the page that lists the quality gates carried both, and a search for the issue's own number (95 %) found neither.
- Check a "CI enforces X" sentence against the tool's own break/fail setting (`"break": 0`) before classifying it; here one config line decides whether the page is true.
- An earlier audit's blocker on the same line (#32) did not produce an open issue that covers the 93.74 sentence; before marking a docs finding new, search open issue bodies for the literal and read what each hit actually asks to change (#2072 names the line for a different clause).
- Before writing a rule (a) finding on a page, search open issues for the page name: #1900 (job-graph diagram), #1901 (navigation) and #3323/#3324 already covered the diagram, navigation and figure parts, so each finding must say what is new beyond them. Also check `docs/_config.yml` `exclude:` before proposing a link from a published page to a page under an excluded folder.
