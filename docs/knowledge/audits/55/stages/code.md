## Findings

1. **Major** — SQL Server waits longer than 30 seconds fail instead of waiting. `src/Encina.DistributedLock.SqlServer/SqlServerDistributedLockProvider.cs:170-185` builds the `sp_getapplock` command and never sets `CommandTimeout`, so ADO.NET's default of 30 seconds applies to the client call. `AcquireAsync` passes `-1` (infinite wait, `:107`) and the interface promises "waiting indefinitely" (`src/Encina.DistributedLock/IDistributedLockProvider.cs:85`); the client call times out at about 30 seconds and the exception becomes `LockAcquisitionException` (`:121-125`). `TryAcquireAsync` with `wait` above 30 seconds (the README's own example uses exactly 30 seconds, `src/Encina.DistributedLock/README.md:119-124`) throws a raw `SqlException` out of the `catch { ... throw; }` at `:82-86` instead of returning `null` after the wait. The cast `(int)wait.TotalMilliseconds` at `:60` also overflows for waits above about 24.8 days (`TimeSpan.MaxValue` gives an undefined value). Checks failed: the interface contract (`IDistributedLockProvider.cs:63-66, :85`) and AGENTS.md section 5, "TryAcquire with timeout" for every lock provider. Derived from the ADO.NET default, not executed; reproduction for the verifier: hold the lock on connection A, call `AcquireAsync` for the same resource on provider B, and time the failure. Not covered by #2405 (expiry and ownership) or #1799 (exceptions or Either).

2. **Major** — The SQL Server provider reports a lock as extended when nobody holds it, and a lost session is never detected. `SqlServerDistributedLockProvider.cs:154-162` (`ExtendAsync(resource, ...)`) logs and returns `Task.FromResult(true)` without a single SQL call, so it returns true for a resource that is not locked at all; the interface says `false` "if the lock was not held" (`IDistributedLockProvider.cs:116`). The handle (`:276-286`) returns true whenever it has not been disposed, and `IsReleased` (`:274`) is only the local `_disposed` flag, so a lock lost because the pooled connection broke or was reset still reads as held and extendable. A caller using `ExtendAsync` as a lease renewal (leader election, #216/#717) is told it still holds the lock forever. Checks failed: the interface contract and the "auto-release on timeout" capability of AGENTS.md section 5. Why #2405 does not cover it: #2405's SQL Server half is "the expiry argument is ignored" and calls the handle-level extension "cosmetic"; this finding is that the provider-level call succeeds for an unheld resource and that no liveness check exists at all. The remediation of #2405 (enforce or document expiry) would not fix either. Static reading; nothing run.

3. **Major** — Two more lock provider copies are registered by the cache packages and win or lose by registration order. `src/Encina.Caching.Redis/ServiceCollectionExtensions.cs:160` (`AddEncinaRedisCache`) and `src/Encina.Caching.Memory/ServiceCollectionExtensions.cs:67` (`AddEncinaMemoryCache`) both call `TryAddSingleton<IDistributedLockProvider, ...>` with their own copy of the provider (`src/Encina.Caching.Redis/RedisDistributedLockProvider.cs:17`, `src/Encina.Caching.Memory/MemoryDistributedLockProvider.cs:21`), as do the three `AddEncinaDistributedLock*` methods (`Redis/ServiceCollectionExtensions.cs:130`, `InMemory/ServiceCollectionExtensions.cs:70`, `SqlServer/ServiceCollectionExtensions.cs:88`). Because every one is `TryAdd`, the first call decides: an application that calls `AddEncinaMemoryCache` (development default) before `AddEncinaDistributedLockRedis` or `AddEncinaDistributedLockSqlServer` silently gets in-process locks in a multi-instance deployment; one that calls `AddEncinaRedisCache` before `AddEncinaDistributedLockSqlServer` gets Redis locks it never asked for, and registering a cache brings a lock provider with it (pay-for-what-you-use, AGENTS.md section 1). Checks failed: AGENTS.md section 3 registration completeness ("a database store MUST win over an in-memory default in any registration order"), provider coherence (section 3), and the AUD-18 spirit of "no re-duplication" for an issue whose commit moved the abstraction out of Encina.Caching. The copies have diverged: neither cache copy returns an `ILockHandle` (`Caching.Redis/RedisDistributedLockProvider.cs:208`, `Caching.Memory/MemoryDistributedLockProvider.cs:222` implement only `IAsyncDisposable`), `MemoryDistributedLockProvider` has no key prefix, there are two public `RedisLockOptions` types (`Encina.DistributedLock.Redis/RedisLockOptions.cs:6` and `Encina.Caching.Redis/RedisDistributedLockProvider.cs:266`), and the #531 retry fix and the Redis ExtendAsync defect of #2405 exist in four copies each (`Caching.Redis/RedisDistributedLockProvider.cs:161`, `Caching.Memory/MemoryDistributedLockProvider.cs:166-175`). Why open issues do not cover it: #2405 names only the `Encina.DistributedLock.*` packages and #2430 covers log sites. The fix design (one implementation, the cache packages stop registering a lock provider) is left to the maintainer.

4. **Major** — The documented base lock configuration does nothing. `src/Encina.DistributedLock/ServiceCollectionExtensions.cs:47-57` registers `Configure<DistributedLockOptions>`, but every provider reads its own derived options type (`InMemoryDistributedLockProvider.cs:21`, `RedisDistributedLockProvider.cs:20`, `SqlServerDistributedLockProvider.cs:22`), so nothing ever resolves the base options. The README shows exactly this call to set `KeyPrefix`, `DefaultExpiry`, `DefaultWait` and `DefaultRetry` (`README.md:161-167`); the prefix that namespaces lock keys in a shared Redis is silently not applied. `DefaultExpiry`, `DefaultWait` and `DefaultRetry` (`DistributedLockOptions.cs:26, :35, :44`) are read by no code in `src/` (search `DefaultExpiry|DefaultWait|DefaultRetry` over `src` `*.cs`: only the declarations, the SQL Server options copy at `SqlServer/ServiceCollectionExtensions.cs:81-83` and a `ToString()`), although their docs say they are "used when no explicit ... is provided" and every interface method requires the values. `AcquireAsync` hard-codes a 100 ms retry (`InMemory...Provider.cs:96`, `Redis...Provider.cs:101`) instead of `DefaultRetry`. `AddEncinaDistributedLock()` (`:31-39`) is an empty method whose comment calls it "a marker for documentation purposes". Checks failed: AGENTS.md section 3 registration completeness (an option type the registration configures must be the one the service resolves) and section 1 ("every line serves a current purpose"). Not covered by an open issue (search for `DefaultExpiry` hits only #908 and #482, and #908 documents the page).

5. **Minor** — The interface and the README promise Redlock, which was never built. `src/Encina.DistributedLock/IDistributedLockProvider.cs:20` ("Redis (Redlock algorithm)") and `:73-74` ("typically uses the Redlock algorithm for high availability across multiple Redis instances") describe the Redis provider, but `RedisDistributedLockProvider.cs:127-131` is a single-database `SET NX PX` and its own remarks (`:10-11`) say Redlock is only something to "consider". `MemoryDistributedLockProvider.cs:18` repeats the claim. This answers the archivist's `current: unknown` for the Redlock gotcha: the Redlock decision has no record in an ADR (the archivist found none) and is tracked only as the open feature #226, so the XML docs (public API, AGENTS.md section 8) state behavior the code does not have. AUD-01 drift without a record; severity Minor because #226 is open and the Redis remarks are honest.

6. **Minor** — `SqlServerDistributedLockProvider.AcquireAsync` turns cancellation into a lock failure. `SqlServerDistributedLockProvider.cs:121-125` wraps every exception except `LockAcquisitionException`, including the `OperationCanceledException` thrown by `ExecuteNonQueryAsync(cancellationToken)` at `:185`, so a cancelled caller sees `LockAcquisitionException` with the cancellation as inner exception. The interface documents `OperationCanceledException` for a triggered token (`IDistributedLockProvider.cs:91`), and the other providers throw it (`InMemory...Provider.cs:100`, `Redis...Provider.cs:105`). A cancellation before the connection opens (`:102`) still throws the raw exception, so the same cancelled token produces two different exception types depending on timing. Check failed: the provider-coherence rule (same contract in every provider, AGENTS.md section 5). Static reading.

7. **Minor** — SQL Server return codes are collapsed and `IsLockedAsync` can report errors as a lock. `sp_getapplock` returns -1 (timeout), -2 (cancelled), -3 (deadlock victim) and -999 (parameter or call error). `TryAcquireAsync` treats every negative value as "not acquired" and returns `null` with only a Debug "Failed to acquire" log that omits the code (`SqlServerDistributedLockProvider.cs:70-80`, `:164-188`); `IsLockedAsync` returns true for every negative value (`:143-150`), so a deadlock-victim or error result is reported as "the resource is locked". `IsLockedAsync` also acquires the lock for a moment to test it (`:140-146`), so a concurrent `TryAcquireAsync` with a zero wait on the same resource can fail while nobody holds the lock. Checks failed: errors are not swallowed (AGENTS.md section 3) and the interface remark that the check is point-in-time (`IDistributedLockProvider.cs:104-107`) does not cover a probe that changes the state. Static reading; the -999 case depends on the server's reply to an oversized or invalid resource name and was not run.

8. **Minor** — `ExtendAsync` replaces the expiry in every provider instead of adding to it, and the in-memory provider has no owner or expiry check. The interface and handle describe "the additional time to add to the lock expiry" (`IDistributedLockProvider.cs:113`) and "extends the lock expiry by the specified duration" (`ILockHandle.cs:46-48`). The code sets the expiry to now plus the argument: `InMemoryDistributedLockProvider.cs:161`, `:215`; `RedisDistributedLockProvider.cs:163` (`KeyExpireAsync(lockKey, extension)`) and the handle script `:239-245` with `:267-272` (`pexpire` of the extension); `SqlServer...Provider.cs:284`. A holder with 25 seconds left that extends by 5 seconds loses 20 seconds. Separately, the in-memory provider-level `ExtendAsync(resource, ...)` (`InMemory...Provider.cs:152-172`) neither compares the owner (the Redis half of this is #2405, the in-memory half is not named there) nor checks that the entry has expired, so it can revive an expired entry that `CleanupExpiredLocks` has not yet removed, unlike `MemoryDistributedLockProvider.ExtendAsync` (`Caching.Memory:166`) which checks `entry.ExpiresAt > now`. Checks failed: the interface contract, and the "false if the lock was not held" return. The semantic mismatch is not part of #2405.

9. **Minor** — No argument validation beyond null. All providers check only `resource` for null (`InMemory...Provider.cs:52`, `Redis...Provider.cs:57`, `SqlServer...Provider.cs:55`). An empty resource yields the shared key `lock:`; a non-positive `expiry` in the in-memory provider creates an entry that is already expired (`TryAddLock`, `InMemory...Provider.cs:125-134`), which the next caller's `CleanupExpiredLocks` (`:181-194`) removes while the first holds a handle, so two callers hold the lock; a negative `wait` simply behaves as zero. AGENTS.md section 6, function 5 (Validation: "Receives input?"), is not integrated nor deferred in any record. Outcome of the remediation is a decision on which values are rejected (exception per #1799 or `Left`).

## Lessons for the pipeline

- The archivist's scope stopped at the four `Encina.DistributedLock*` packages; the closing commit also touched `Encina.Caching`, and the two cache packages implement the same interface. For a feature that moved an abstraction out of a package, the scope list should include every remaining implementer of the interface (search `: IInterfaceName` over `src`).
- Run the open-issue dump first: #2405 and #1799 already owned the most obvious defects (Redis owner check, SQL Server expiry, exceptions versus Either), so the effort went to the SQL Server command timeout, the provider-level `ExtendAsync` contract, the cache-package duplicates and the dead configuration path.
- A configuration example in a README is the cheapest pointer to a dead option: check that the options type the registration configures is the type the service resolves (finding 4).
- A `?? default` on a property that is non-nullable with a default is dead code; check the declaring options class before trusting a fallback list (finding 10).
