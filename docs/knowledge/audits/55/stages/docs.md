2. **Major** — `src/Encina.DistributedLock/README.md:158-168` ("Base Options") shows `services.AddEncinaDistributedLock(options => { KeyPrefix, DefaultExpiry, DefaultWait, DefaultRetry })`. The overload exists (`src/Encina.DistributedLock/ServiceCollectionExtensions.cs:47`) and the properties exist, but per the code stage (finding 4) no provider resolves the base options, so the sample compiles and does nothing, and the section also promises defaults that no code reads. Check failed: README sample correct against `src/` in behavior (rule (a) point 2). The code remediation (code finding 4) decides whether to fix or delete the section; the README must change with it. Related: code finding 4.

3. **Major** — `src/Encina.DistributedLock/README.md:62` and the Usage sample (`:50-67`) throw `LockAcquisitionException` when `TryAcquireAsync` returns null, with a 30 second wait (`:56`). For SQL Server the code stage (finding 1) shows a wait above 30 seconds fails with a raw `SqlException`, so the README's own recommended example does not behave as written on that provider. ## Lessons for the pipeline

- A README written for a C# feature can use a language keyword as a variable name (`lock`); an identifier-existence check passes it, so the docs stage should scan sample variable names against the C# keyword list.
- When the code stage reports a dead option path, the docs stage should map it to the README section that advertises it (here "Base Options") and write it as a README finding tied to the code finding.
