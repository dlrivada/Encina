## Findings

1. **Blocker** — `docs/architecture/adr/027-marten-as-the-event-sourcing-provider.md:30`, Consequences section: "`Encina.EventStoreDB` remains in the repository as deprecated code until a removal decision; it is not part of SPEC-000's 1.0 list." Per SKILL.md §6 "Decisions linked": the ADR is the canonical decision link for #17, and it states something the repository contradicts, which is exactly the "blocker" case in §4 ("Link to a document that says something different: blocker") applied to the ADR's own text against the filesystem it describes.

2. **Blocker** — `AGENTS.md:70`, the "Other categories" sentence: "Event sourcing (Marten primary, EventStoreDB future; applies to aggregate repositories, projections, snapshots, crypto-shredding)." This directly contradicts ADR-027 and #17's own decision comment ("deprecate Encina.EventStoreDB and keep only Encina.Marten for Event Sourcing"): EventStoreDB is deprecated, not a future/planned provider, and `AGENTS.md` §12 itself names "a design decision already taken" as governed by `docs/architecture/adr/index.md`, which this line does not follow. `AGENTS.md` is the binding rules file every session and subagent reads first (`CLAUDE.md`: "The engineering rules are in AGENTS.md … and bind every session and subagent"); a wrong "future provider" claim here is more consequential than the same error in a secondary page, because it is the file every future agent trusts as the current source of truth before touching event sourcing.

3. **Blocker** — `docs/INVENTORY.md:89`: `| **Event Sourcing** (1+) | Marten, EventStoreDB (future) | Aggregate persistence |`. Same false "(future)" framing as finding 2, on the repository's own package inventory reference page (Reference quadrant, `docs/`). A reader consulting this table to plan event-sourcing work would conclude EventStoreDB support is coming, which #17/ADR-027 explicitly rules out.

## Lessons for the pipeline

- A stale cross-reference to a deprecated decision is not confined to the files the closing commit touched or the files an archivist's `docs/`-only destination sweep finds: it recurs independently in the project's most-read binding-rules file (`AGENTS.md`), its package inventory (`docs/INVENTORY.md`), a pre-decision architecture analysis page (`docs/architecture/extensibility-analysis.md`), and a later, unrelated ADR's comparison table (`ADR-019`). A docs-stage review of a deprecation SPIKE should grep every `docs/*.md` and root-level `.md` hit for the deprecated name, not just the files an earlier stage already named as "destinations," and should check the file's own frozen/historical status (an explicit "snapshot, not maintained" banner, or `nav_exclude` plus a dated changelog-entry style) before deciding whether staleness is a defect or an accurate historical record.
- The same "the ADR restates a fact the filesystem contradicts" defect appears twice with the same root cause (`.backup/deprecated-packages/` does not exist in this checkout) in two independent files — `docs/architecture/adr/027-marten-as-the-event-sourcing-provider.md:30` and `ROADMAP.md:805` — both apparently copied from the original 2025-12-23 commit message's "moved to `.backup/`" claim without anyone verifying it against the checkout. A single unverified claim in a commit message can propagate into multiple "current" docs; checking `Test-Path` once and then grepping every doc for the same claim is cheaper than checking each doc for it independently.
- A citation must be re-verified against the *cited file*, not just confirmed to exist somewhere in the repository: the previous draft of finding 5 quoted a real, verbatim line but attributed it to `extensibility-analysis.md:332` when it actually lives in `ENGINEERING-HANDBOOK.md:332` (a different, frozen file this stage's own scope excludes). Before citing a file:line + quote, grep the specific cited file for the exact quoted string and confirm a hit there, not just a hit somewhere in the tree — and check the finding against every open issue whose title or body names the same file/table row before treating it as new, since a near-identical claim may already be tracked (here, correctly, for a different file: #1347 covers `CLAUDE.md`/`ENGINEERING-HANDBOOK.md` only, not `extensibility-analysis.md`).
