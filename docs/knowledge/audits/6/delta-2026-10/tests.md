## Lessons for the pipeline

- A package with a `Log.cs` of `[LoggerMessage]` declarations and a constants-only file such as `EncinaJobFailureData.cs` has no coverable line, yet a generic manifest entry may still list `unit` and `guard` for it; the delta brief should say that rule (b) judges such entries by whether the listed flags can ever be measured, and the generator's classifier could emit empty `defaultTests` for const-only static classes.
- The original audit's coverable-line counts (82 and 66) and today's (45 and 33) differ for the same files; a delta stage should re-measure rather than reuse the original figures, and every stage should say how it counts coverable lines (unique line numbers per file, or summed class entries) and the build configuration, so figures from two audits can be compared.
- A justification sentence for a per-file target must be checked against the uncovered-line list line by line, not against the percentage: the first version listed lines 85 and 87 as uncovered and still wrote that the missing-request path was reached. Read the source at each uncovered line, name the branch behind it, and confirm the claim against the test class's method list (the request job's property class has no missing-request test; the notification job's has).
- An internal helper (`JobFailure`) can be fully executed by other types' tests while no test names it; a "zero test references" claim (as in #1544) is a name search, not a coverage measurement, and should be closed or kept based on the measured lines.
