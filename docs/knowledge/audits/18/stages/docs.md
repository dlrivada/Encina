## Findings

1. **Blocker** — `docs/messaging/transports.md:293` (`services.AddEncinaNatsCore(options => ...)`) and `:305` (`services.AddEncinaNatsJetStream(options => ...)`) document two extension methods that do not exist. `src/Encina.NATS/ServiceCollectionExtensions.cs:21` exposes only `public static IServiceCollection AddEncinaNATS(...)`, with JetStream selected through a `UseJetStream` boolean (`:34`, `:51`). Following either NATS sample verbatim fails to compile.

2. **Blocker** — `docs/messaging/transports.md:224-229` shows `options.ConnectionString = "amqp://localhost"`, `options.Exchange = "my-exchange"` and `options.ExchangeType = ExchangeType.Topic`. None of these members exist: `src/Encina.RabbitMQ/EncinaRabbitMQOptions.cs` has `HostName`, `Port`, `VirtualHost`, `UserName`, `Password`, `ExchangeName` (not `ConnectionString`/`Exchange`), and there is no `ExchangeType` property or type anywhere in `src/Encina.RabbitMQ` (grepped, zero matches). Line 235 (`public class OrderCreatedHandler : IMessageHandler<OrderCreated>`) references `IMessageHandler<T>`, which does not exist anywhere under `src/` (repo-wide grep for `IMessageHandler` returns zero matches) — RabbitMQ has no consume/subscribe API at all, confirming the code stage's finding 3.

3. **Blocker** — `docs/messaging/transports.md:257-262` documents `options.ConsumerGroup = "my-service"` and `options.DefaultTopic = "events"` on Kafka options; `src/Encina.Kafka/EncinaKafkaOptions.cs` has `GroupId` and `DefaultCommandTopic`/`DefaultEventTopic` instead — neither documented name exists. Lines 270-273 (`consumer.ConsumeFromAsync(topic: "events", offset: 12345, ct)`) reference a consumer type/method that does not exist anywhere in `Encina.Kafka` (the package's only files are `EncinaKafkaOptions.cs`, `IKafkaMessagePublisher.cs`, `KafkaMessagePublisher.cs`, `Log.cs`, `ServiceCollectionExtensions.cs` — publisher only, no consumer).

4. **Blocker** — `docs/messaging/transports.md:334` (`options.QueueName = "orders";`) does not match `src/Encina.AzureServiceBus`'s options class, which exposes `DefaultQueueName` (also `DefaultTopicName`, `SubscriptionName`), never `QueueName`.

5. **Blocker** — `docs/messaging/transports.md:358` (`options.QueueUrl = "https://sqs..."`) does not match `src/Encina.AmazonSQS/EncinaAmazonSQSOptions.cs`, which exposes `DefaultQueueUrl` (also `DefaultTopicArn`), never `QueueUrl`. Line 365 (`await consumer.StartAsync(ct);`) references a consumer type that does not exist anywhere in `Encina.AmazonSQS` (the package's files are `AmazonSQSMessagePublisher.cs`, `EncinaAmazonSQSOptions.cs`, `IAmazonSQSMessagePublisher.cs`, `Log.cs`, `ServiceCollectionExtensions.cs`, `GlobalSuppressions.cs` — publisher only, no `StartAsync`, no `IHostedService`/`BackgroundService` match anywhere in the package).

6. **Blocker** — `docs/messaging/transports.md:389` (`await subscriber.SubscribeAsync("cache-*", async (channel, message) => {...});`) misuses the real API. `src/Encina.Redis.PubSub/IRedisPubSubMessagePublisher.cs:32` declares `SubscribeAsync<TMessage>(Func<TMessage, ValueTask> handler, string? channel = null, CancellationToken cancellationToken = default)` — a single-channel subscription whose first parameter is the handler, not a pattern string, and whose handler takes only the message, not `(channel, message)`. Pattern subscription with a `(channel, message)` handler is a *different* method, `SubscribePatternAsync<TMessage>(string pattern, Func<string, TMessage, ValueTask> handler, ...)` (`:46`). The documented call compiles to neither overload.

7. **Blocker** — `docs/messaging/transports.md:410` (`options.BrokerAddress = "localhost";`) does not match `src/Encina.MQTT/EncinaMQTTOptions.cs`, which exposes `Host` (also `Port`, `ClientId`, `TopicPrefix`, `Username`, `Password`, `QualityOfService`, `UseTls`, `CleanSession`, `KeepAliveSeconds`), never `BrokerAddress`.

8. **Blocker** — `docs/messaging/transports.md:441-447` documents `services.AddEncinaGrpc(options => { options.ServerAddress = "https://localhost:5001"; });` and `var result = await grpcClient.SendAsync(new CreateOrder(items));`. `src/Encina.gRPC/EncinaGrpcOptions.cs` has no `ServerAddress` property at all — its members are `EnableReflection`, `EnableHealthChecks`, `MaxReceiveMessageSize`, `MaxSendMessageSize`, `EnableLoggingInterceptor`, `DefaultDeadline`, `EnableCompression`. And the only `SendAsync` in the package, `src/Encina.gRPC/IGrpcMediatorService.cs:17`, is `ValueTask<Either<EncinaError, byte[]>> SendAsync(...)` on a server-side mediator bridge, not a typed client returning a typed `result` from a `CreateOrder` call — this is not how the package is used at all; `Encina.gRPC` is a server-side bridge like `Encina.GraphQL`, not an outbound RPC client.

9. **Blocker** — `docs/messaging/transports.md:462-464` documents `services.AddEncinaGraphQL().AddQueryType<QueryRoot>().AddMutationType<MutationRoot>();`. `src/Encina.GraphQL/ServiceCollectionExtensions.cs:17` shows `AddEncinaGraphQL` returns `IServiceCollection`, which has no `AddQueryType`/`AddMutationType` members (those belong to HotChocolate's `IRequestExecutorBuilder`, obtained from `services.AddGraphQLServer()`, a call this page never shows). The sample as written does not compile.

10. **Blocker** — `docs/messaging/transports.md:498-506` (the "Testing with InMemory" example) calls `bus.GetPublishedMessages<OrderCreatedEvent>()`. `src/Encina.InMemory/IInMemoryMessageBus.cs` has no such method; its full surface is `PublishAsync`, `EnqueueAsync`, `Subscribe<TMessage>(Func<TMessage, ValueTask>)`, `PendingCount`, `SubscriberCount` (confirmed by reading the whole 52-line interface). The page's flagship testing pattern for `Encina.InMemory` cannot be written against the real API.

11. **Blocker** — `docs/messaging/transports.md:545-549` (FAQ, "How do I handle transport failures?") documents `services.AddEncinaPolly(options => { options.RetryCount = 3; options.CircuitBreakerThreshold = 5; });`. `src/Encina.Polly/ServiceCollectionExtensions.cs:185-212` shows `EncinaPollyOptions` has exactly two members, `EnableTelemetry` and `EnableLogging` ("Reserved for future extensibility. Currently, all configuration is done via attributes." per its own XML doc) — `RetryCount` and `CircuitBreakerThreshold` do not exist on this or any other type in the package (real retry/circuit-breaker configuration is per-request via `[Retry(MaxAttempts = ...)]`/`[CircuitBreaker(FailureThreshold = ...)]` attributes, shown in the package's own XML doc example, not through this options class).

12. **Blocker** — `docs/messaging/index.md:45` lists `Encina.Dapper.Oracle` as a live persistence-provider package ("Enterprise, Oracle DB"). `Test-Path src/Encina.Dapper.Oracle` is `False`, and `git ls-files | Select-String Oracle` returns only `docs/architecture/adr/009-remove-oracle-provider-pre-1.0.md` and `changelog.d/1262-bulk-ef-remove-oracle-sqlite.removed.md` — Oracle was removed pre-1.0 by ADR-009 and no `.backup/` directory exists anywhere in this checkout. This row documents a package that does not exist and directly contradicts the standing decision the page itself sits one directory away from.

13. **Major** — `docs/messaging/transports.md:520-528` (FAQ, "Should I use a unified messaging interface? No.") restates issue #18's whole design decision as settled fact with no ADR or SPEC link anywhere on the page. No ADR records this decision (a messaging-transport strategy of native per-transport APIs instead of a unified interface): `docs/architecture/adr/index.md` lists none, and a case-insensitive search of `docs/architecture/adr` for "unified messaging", "unified transport", "transport strategy", "transport abstraction" and "IMessageTransport" finds no ADR on the subject (the only hit, ADR-023, is about coverage strategy). Several ADRs (014, 018, 021, 023, 025, 028, 029, 030) do mention the word "transport" in other contexts; none decides this question. Per the docs skill's house rule 4 ("Decisions are linked, not restated... If no ADR exists for a decision the page needs, say so in the report; do not invent a rationale"), this FAQ answer needs either an ADR or an explicit statement that none exists; it has neither.

14. **Major** — `docs/messaging/transports.md` mixes all four Diátaxis quadrants under one title with no split into separate pages. The "Design Philosophy" callout (`:35`) and the whole "FAQ" section (`:518-565`, headings "Should I use a unified messaging interface?", "When should I use gRPC vs a message broker?") are Explanation ("why", discussion, trade-offs); the "Decision Flowchart" section (`:39-96`) is How-to ("how do I choose a transport"); "Detailed Transport Guides" (`:211-479`) mixes Reference (option tables, comparison table) with How-to (task-oriented code samples). `docs/messaging/transports.md` is not one of the `docs/features/*.md` pages the docs skill exempts from the one-quadrant rule ("Mixed today" row, SKILL.md §1) — it is a page created fresh by this issue and should have been split from the start.

15. **Major** — The page asserts full API parity per transport ("Each transport exposes its native API… Kafka users get offsets and partitions", `:35`) and shows fabricated subscribe/consume samples for RabbitMQ, Kafka, AzureServiceBus and AmazonSQS (findings 2, 3, 4, 5 above) instead of stating the real gap: none of those four packages implements subscription, consumption or DLQ handling in `src/` today (confirmed independently in this stage and by the code stage's finding 3 — a repo-wide grep of all five broker/streaming packages for `SubscribeAsync|ConsumeAsync|Subscribe\(` and `DeadLetter|DLQ` returns zero matches outside MQTT, Redis.PubSub and InMemory). AGENTS.md §5's Transports row requires "subscription management" and "error handling and DLQ" from every transport in this category; the page does not disclose the five-package gap and instead invents code that implies the gap is closed.

## Lessons for the pipeline

- A documentation-only SPIKE with no linked PR (lesson already recorded from #16) reproduces at a larger scale here: of the ~11 per-transport code samples plus the InMemory testing sample and the Polly FAQ sample in `docs/messaging/transports.md`, all but two (`AzureServiceBus.ScheduleAsync`'s parameter list and `RabbitMQ.PublishAsync`'s `routingKey` parameter) name an option property, method or type that does not exist in `src/`. When a docs page's only gate was a single unreviewed commit nine months ago, checking "does this identifier exist" symbol-by-symbol for *every* code block — not spot-checking a sample per package — is the only way to catch this; a spot-check of one or two blocks per package would have missed most of these.
- The same fabrication pattern recurs in a specific shape across packages: the option class in the doc example almost always has the *right general idea* (a connection setting, a topic/queue setting) but the *wrong property name* (`ConnectionString`/`Exchange`/`ExchangeType` vs real `HostName`/`ExchangeName`; `ConsumerGroup`/`DefaultTopic` vs real `GroupId`/`DefaultCommandTopic`; `QueueName` vs `DefaultQueueName`; `QueueUrl` vs `DefaultQueueUrl`; `BrokerAddress` vs `Host`; `ServerAddress` vs no such property; `RetryCount`/`CircuitBreakerThreshold` vs no such properties). This is consistent with the doc having been written from the issue's own aspirational code samples or from memory of a similar library's API (e.g. `ExchangeType.Topic` reads like raw `RabbitMQ.Client`, not `Encina.RabbitMQ`), never copied from the actual `*Options.cs` file as SKILL.md §3 requires ("find the method in `src/`, copy its exact name"). Future docs review of any page from this era should default to reading the real options class file in full before trusting a single property name in the sample.
- A stale persistence-provider row (`Encina.Dapper.Oracle` in `docs/messaging/index.md:45`) survived an ADR (009) that removed the package entirely — the same "a decision reaching one destination doesn't mean it reached all of them" lesson recorded for #17 recurs here in a page that was edited by a *later*, unrelated commit (this issue's own #18 commit, 2025-12-23) after the removal; the removal predates this page's edit, so the drift was introduced fresh, not merely left unfixed. Worth a standing check: when editing any page that lists persistence providers, grep `docs/architecture/adr/index.md` for a removal ADR of any named provider before publishing.
- A "no ADR records X" claim must name the exact decision and the patterns searched, not "no match for transport/strategy": ADR-014, 018, 021, 023, 025, 028, 029 and 030 mention "transport" and many ADR titles contain "strategy", so a bare keyword claim is false even when the conclusion (no ADR decides this) is true. State the decision, the index check and the specific phrases searched.
