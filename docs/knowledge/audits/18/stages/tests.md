## Findings

1. **Blocker** — Five transport packages (NATS, RabbitMQ, MQTT, AzureServiceBus, Kafka) have no test that could catch code.md finding 1 (the scope-vs-singleton lifetime bug: the scoped publisher's `Dispose`/`DisposeAsync` closes or disposes the DI-singleton connection, channel, client or producer when the scope ends), and in four of them the existing tests encode the buggy behaviour as the expected, passing outcome. Two independent gaps compound this. (a) No `ServiceCollectionExtensions*Tests.cs` of any of the five packages ever creates a scope or resolves the publisher (verified by a search of every `.cs` under `tests/` in the five package folders for `CreateScope`: zero matches). `tests/Encina.UnitTests/RabbitMQ/ServiceCollectionExtensionsTests.cs:89` (`AddEncinaRabbitMQ_RegistersPublisher`) checks only the `ServiceDescriptor` metadata, with its own comment reading "will fail at resolution without real connection"; the singleton factory delegates are 0% exercised in RabbitMQ (`ServiceCollectionExtensions.cs:44-51,53,58-59`), NATS (`:44-48`), MQTT (`:45-69`) and Kafka (`:44-58`); AzureServiceBus's registration lines are 100% covered but only at descriptor level, with no scope created or disposed. (b) The existing disposal tests assert that the shared object IS disposed, so fixing code.md finding 1 would make them fail: `tests/Encina.UnitTests/RabbitMQ/Publishing/RabbitMQMessagePublisherTests.cs:313` `DisposeAsync_ShouldCloseChannelAndConnection`; `tests/Encina.UnitTests/NATS/Publishing/NATSMessagePublisherTests.cs:366` `DisposeAsync_ShouldDisposeConnection` and `NATSMessagePublisherRequestAsyncTests.cs:82` `DisposeAsync_DisposesConnection` (the class is named `NATSMessagePublisherAdditionalTests`); `tests/Encina.UnitTests/MQTT/Publishing/MQTTMessagePublisherTests.cs:264,281` `DisposeAsync_WhenConnected_ShouldDisconnectAndDispose` / `DisposeAsync_WhenNotConnected_ShouldOnlyDispose` (`_client.Received(1).Dispose()`); `tests/Encina.UnitTests/Kafka/Publishing/KafkaMessagePublisherTests.cs:354` `Dispose_ShouldFlushAndDisposeProducer` (`_producer.Received(1).Flush(...)` and `.Dispose()`). AzureServiceBus has no disposal test at all: `AzureServiceBusMessagePublisher.cs:203-204` (`DisposeAsync`) is uncovered by the unit run and no file under `tests/Encina.UnitTests/AzureServiceBus` mentions `Dispose`. These are not a safety net, they are the opposite. A regression test is buildable today without a live broker, one per package: register a substitute (NSubstitute) `IConnection`/`IChannel` (RabbitMQ), `INatsConnection` (NATS), `IMqttClient` (MQTT), `ServiceBusClient` (AzureServiceBus) or `IProducer<string, byte[]>` (Kafka) as a DI singleton, `services.AddScoped<I*MessagePublisher, *MessagePublisher>()`, build the provider, `using (var scope = provider.CreateScope()) { scope.ServiceProvider.GetRequiredService<I*MessagePublisher>(); }`, then assert the singleton substitute was NOT disposed or closed (and, for Kafka, not flushed) after the `using` block ends, and that the existing disposal tests above are rewritten to the fixed contract. None of the five packages has this test.

2. **Major** — `Encina.InMemory` (the `InMemoryMessageBus` implementation) has **zero tests of any test type** anywhere in `tests/`: coverage measured 0/110 unit and 0/110 guard on `InMemoryMessageBus.cs` itself, and 0% on `EncinaInMemoryOptions.cs`/`ServiceCollectionExtensions.cs` too (confirmed by search: no `new InMemoryMessageBus(` construction anywhere in `tests/`; the only references are `Encina.NBomber`'s load-scenario factories, which build a real host for throughput measurement, not correctness, and an unrelated `EncinaEventIdAllocationTests.cs` architecture check that only verifies EventId-range ownership). This is the same package the issue's own decision names as the "purpose-built," "sufficient" substitute for testing every one of the other 9 transports ("Runtime switching for testing? NO — Use Encina.InMemory for tests"), so the one package this decision leans on hardest for the whole ecosystem's test story is itself untested. Root cause traced to the manifest: `.github/coverage-manifest/Encina.InMemory.json:27-30`, the `"InMemoryMessageBus.cs"` entry reads `"defaultTests": [], "reason": "Interface — no implementation"`, a copy of the actual interface file's entry (`"IInMemoryMessageBus.cs"`, `:22-25`, five lines above it in the same file); `InMemoryMessageBus.cs` is a 252-line concrete `sealed class` (`Channel<object>`-backed publish/enqueue/subscribe with background worker tasks, `ConcurrentDictionary` subscriber registry, `IDisposable`), not an interface. The manifest is actively telling tooling this file needs no tests when unit and guard both clearly apply per its own `defaultRule: "*.cs"` sibling pattern. Both a manifest correction and real unit/guard tests (publish delivers to subscribers, enqueue increments/decrements `PendingCount`, bounded-channel `FullMode` behavior, concurrent subscribe/unsubscribe, `Dispose` cancels workers) are needed.

3. **Major** — `Encina.MQTT/MQTTMessagePublisher.cs` is only 33.6% unit-line-covered (49/146); every uncovered line (verified from the cobertura report: 107-162, 184-313) is exactly the `SubscribeAsync`/topic-pattern-subscribe method and the internal `MqttSubscription<TMessage>`/`MqttPatternSubscription<TMessage>` classes' own `Dispose`/unsubscribe logic (`MQTTMessagePublisherTests.cs:299-342` has only null-argument tests for `SubscribeAsync`/`SubscribePatternAsync`). Per code.md's sibling audit, MQTT is one of only 3 of the 10 transports (with `Redis.PubSub` and `InMemory`) that actually implements subscribe — the one capability code.md's finding 3 says the other 5 (RabbitMQ, Kafka, NATS, AzureServiceBus, AmazonSQS) are missing entirely, and that AGENTS.md §5's Transports row requires every provider to support ("subscription management"). The capability that is supposed to be MQTT's point of difference from the 5 non-compliant siblings is itself the one thing no test in `MQTTMessagePublisherTests.cs`/`MQTTMessagePublisherExtendedTests.cs` exercises — a subscribe-then-receive-a-message-then-dispose path is untested, so a regression in unsubscribe cleanup or double-dispose would pass CI silently.

4. **Minor** — `Encina.RabbitMQ/ServiceCollectionExtensions.cs:53,59` and `Encina.MQTT/ServiceCollectionExtensions.cs:67` (code.md finding 4, the sync-over-async `factory.CreateConnectionAsync().GetAwaiter().GetResult()` / `client.ConnectAsync(...).GetAwaiter().GetResult()` calls inside the `TryAddSingleton` factory delegates) measured 0% executed in the Release unit run: no existing test resolves `IConnection`/`IChannel`/`IMqttClient` from the built `ServiceProvider`, so the delegate bodies containing the blocking calls never run. A regression test needs a fake `IConnectionFactory`/`IMqttClient` double substituted before resolution (the real RabbitMQ.Client/MQTTnet types are not natively mockable without wrapping), which none of the current `ServiceCollectionExtensionsTests.cs` files provide.

5. **Minor** — `src/Encina.NATS/NATSMessagePublisher.cs:93-141` (`RequestAsync<TRequest, TResponse>`, everything after the `ArgumentNullException.ThrowIfNull` at :91) is 0% unit-covered and 0% guard-covered in the Release run (31 uncovered lines, 35% of the file's 89 coverable lines). The only test of the method is `NATSMessagePublisherRequestAsyncTests.cs:71` `RequestAsync_WithNullRequest_ThrowsArgumentNullException`, which stops at the null guard, despite the file name promising `RequestAsync` coverage (the class inside is named `NATSMessagePublisherAdditionalTests`, and its remaining tests are about `PublishAsync`, `JetStreamPublishAsync` and `DisposeAsync`). The method's four outcomes (success with a deserialized response, `NATS_DESERIALIZE_FAILED` when the reply deserializes to null, `NATS_REQUEST_TIMEOUT` on a timeout-triggered cancellation, `NATS_REQUEST_FAILED` on any other exception) have no test, so the timeout-versus-caller-cancellation distinction at `:124` (`catch (OperationCanceledException) when (!cancellationToken.IsCancellationRequested)`) could be inverted without a test failing. The earlier version of this stage wrongly noted "DisposeAsync/RequestAsync covered" for this file; only `DisposeAsync` is.

## Lessons for the pipeline

- Record the build configuration next to every coverage figure and command. Debug and Release builds produce different sequence points and therefore different covered/valid line counts, so a faithful re-run under the other configuration looks like a mismatch. Use `-c Release` (the configuration CI and `AGENTS.md` §9's workflow use) and say so in the stage.
- A `FullyQualifiedName~<namespace>` filter that includes a dot-separated *suffix* after the package namespace (e.g. `Encina.UnitTests.Kafka.Publishing`) silently drops sibling test classes that sit directly in the parent namespace (`Encina.UnitTests.Kafka.ServiceCollectionExtensionsTests`, namespace `Encina.UnitTests.Kafka`) without any error: the run reports "N passed, 0 failed" for whatever it did match. Use the bare package namespace (`Encina.UnitTests.{Package}`) and, if suffixed sub-filters are preferred for speed, verify the total pass count against the sub-filters' union (here 384 became 398).
- A test file's name is not evidence of what it covers: `NATSMessagePublisherRequestAsyncTests.cs` contains a class named `NATSMessagePublisherAdditionalTests` whose only `RequestAsync` test stops at the null guard, and the first version of this stage inferred "RequestAsync covered" from the file name. Read the per-line uncovered list for the method's line range before writing that a method is covered.
- A "this package has no disposal test" claim needs the same all-variants search a sibling-bug claim needs (`DisposeAsync`, `\.Dispose\(`, `CreateScope`, over every `.cs` of the package's test folders in every test project); this stage's first version generalized from the NATS/MQTT/RabbitMQ tests and missed that Kafka's test asserts the buggy behaviour and that AzureServiceBus has none.
- The `enforce-path-ownership.ps1` hook (#1345) denies this stage writing anywhere under `artifacts/audit/coverage/`, even though the SPEC-003 pipeline brief and skill instructions say to write `--results-directory <wt>\artifacts\audit\coverage\<flag>`; the stage's actual write allowlist is only its own `artifacts/knowledge/stages/tests.md`. Coverage results were instead written to the session scratch directory (outside the project tree) and read from there for this report, which is not a hook workaround since no repository-tracked artifact was the target. Worth flagging to the orchestrator: either the brief's instructed results-directory needs an allowlist exception in the hook, or the brief text should stop naming a path this stage cannot write to.
