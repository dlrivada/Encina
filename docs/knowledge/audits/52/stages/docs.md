3. **Major** — Rule (a) point 2 and the code stage's finding 1, `src/Encina.Marten/Snapshots/ISnapshotable.cs:18-21` and `:26-31`. The XML documentation, which is the only reference text for the opt-in contract, tells users to write the aggregate with `private set` properties (`CustomerName`, `Total`, `Status`, all `{ get; private set; }`) and says "Marten handles serialization automatically, so no special snapshot creation logic is required." The code stage's finding 1, as restated after verification, says `AggregateBase.Id` carries `[JsonInclude]` and `Version` has a public setter, so those two members restore; the defect is the state the derived aggregate declares with `private set`, which the default `System.Text.Json` serializer does not restore, so that state is lost on load. That conclusion is derived from the serializer's rules and was not run. The integration test helper uses public setters "to allow JSON deserialization by Marten" (`tests/Encina.IntegrationTests/Infrastructure/Marten/Snapshots/TestSnapshotableAggregate.cs:11-15`), which is consistent with it. Whatever fix the code finding chooses (configure the serializer, require public setters, capture state differently), the documented example and the "handled automatically" sentence are likely wrong today and must be checked and changed with it. The same release-record sample (`docs/releases/pre-v0.10.0/README.md:1594-1597`, `class Order : AggregateBase, ISnapshotable<Order>` with `// ... standard aggregate implementation`) omits the two constraints the registration imposes: `class`, `IAggregate`, `ISnapshotable<TAggregate>` and `new()` (`src/Encina.Marten/ServiceCollectionExtensions.cs:363-364`), so an aggregate without a public parameterless constructor does not satisfy `AddSnapshotableAggregate<Order>()`. Both snippets use real identifiers and are otherwise correct against `src/` (`AddEncinaMarten(Action<EncinaMartenOptions>)` at `ServiceCollectionExtensions.cs:35-37`, `ConfigureAggregate<T>(int snapshotEvery, int? keepSnapshots = null)` at `SnapshotOptions.cs:69-72`, defaults 100, 3 and `true` at `:23`, `:33`, `:44`).

## Lessons for the pipeline

- When an issue was already audited under a sibling closed-in-error issue (#25 here), read that issue's published docs stage first and map findings to it; the new value in this stage was the three code-linked defects the earlier stage could not have seen (the XML docs sample versus the serializer finding, the EventIds and error-code drift in the record).
- The XML-documentation example on a public type is a reference page for rule (a) point 2 and must be compared with the code stage's defects: here the documented `private set` aggregate shape is the shape whose derived state is lost on restore (derived, unrun), while the test helper was altered to public setters to pass.
- A `gh` rate-limit error (GraphQL) can occur during a docs stage that maps findings to open umbrella issues; read the sibling stage's mapping and state the date of the mapping instead of leaving the claim unqualified.
- When a code-stage finding is restated after verification, re-read every docs finding that repeats it and copy the restated claim, not the original wording (audit #52 verifier correction 4: "restores with an empty `Id`" was dropped upstream).
- Count the constants of a class by reading its declarations and say which ones are not codes (here `Prefix` at `SnapshotErrorCodes.cs:11` is a constant, not an error code: eight codes, not nine; audit #52 verifier correction 2).
