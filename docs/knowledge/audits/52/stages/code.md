## Findings
1. **Blocker** — A snapshot restore very likely returns an aggregate whose derived `private set` state is lost under Marten's default serializer; the real-type round trip has not been run. `MartenSnapshotStore.cs:62` and `:104` rebuild the state through `SnapshotEnvelope<TAggregate>.State` (`SnapshotEnvelope.cs:70`), a document Marten serializes with its default `System.Text.Json` serializer (no serializer is configured anywhere in `src/Encina.Marten`; searched case-insensitively, recursively, `Serializer|UseSystemTextJson|UseNewtonsoft|NonPublic` over `src/Encina.Marten/**/*.cs`: four hits, none configuring a serializer: the comments at `EncinaStoreOptionsConfigurator.cs:14` and `EventReadScope.cs:4-5`, and `Projections/InlineProjectionDispatcher.cs:61`, a `BindingFlags.NonPublic` reflection constant). The documented aggregate shape uses `private set` for its own state (`ISnapshotable.cs:26-31`: `CustomerName`, `Total`, `Status`). The base type carries the two inherited members in a way that restores: `AggregateBase.Id` has `[JsonInclude]` (`src/Encina.DomainModeling/AggregateBase.cs:72`, with the remark at `:70-71` that it exists "so a serialized snapshot keeps its id") on `{ get; protected set; }` (`:73`), and `Version` has a public setter (`:76`); open #1976 states the same. So `Id` and `Version` very likely restore on the real type (derived from the attributes, unrun); the derived `private set` properties are the surviving defect. Replica result, which does NOT describe the real type and was not run on it: a file-based app with `Marten` 9.38.0 (the version of `Directory.Packages.props`), `new StoreOptions().Serializer()` = `Marten.Services.SystemTextJsonSerializer`, and a stand-in base class with `Guid Id { get; protected set; }` and no `[JsonInclude]`, plus a derived class with `private set` properties: `ToJson` wrote `Id`, `Name`, `Total`, `Version`; `FromJson` returned `Id empty: True; Version: 100; Name: ''; Total: 0` and kept the public-setter property. What the replica shows for the real type is only the derived part: `System.Text.Json` does not restore a `private set` property that carries no `[JsonInclude]`; its `Id` result is an artifact of the stand-in lacking `[JsonInclude]` and must not be read as the real behaviour. Consequence, derived and unrun: `LoadWithSnapshotAsync` (`SnapshotAwareAggregateRepository.cs:373-374`) replays only the events after the snapshot onto an aggregate whose pre-snapshot derived state is lost (default values for every `private set` property) and returns `Right`, so the loaded aggregate differs from a full replay; whether a later `SaveAsync` then appends to the right stream follows from `Id` restoring, so no `Guid.Empty` consequence is claimed. The no-snapshot path rejects a foreign or empty identity (`:337-346`); the snapshot path has no such check, which matters only if `Id` does not restore. The only round-trip test helper declares public setters "to allow JSON deserialization by Marten" (`TestSnapshotableAggregate.cs:11-15`), so the fixture is shaped to pass and masks the defect (known failure pattern: test fixture hides the production shape). Fails the feature's own contract (load from snapshot plus remaining events gives the same aggregate as a full replay) and AUD correctness. #1976 item 6 only asks for a round-trip test and says "whether Marten's default serializer restores the `private set` properties ... is not established"; the replica supports the derived-state half of that question for a type without `[JsonInclude]` and is the defect behind that test. The verifier or implementer should run the real round trip through `MartenSnapshotStore` on PostgreSQL (`GetLatestAsync`, then `State.Id`, `State.Version` and each `private set` property) with an aggregate deriving the real `AggregateBase` before the fix is designed (options: configure the serializer, require public setters and say so, or capture state without the aggregate type).
2. **Major** — The default snapshot creation (`AsyncSnapshotCreation = true`, `SnapshotOptions.cs:44`) runs `_snapshotStore.SaveAsync` and `PruneAsync` on a `Task.Run` thread (`SnapshotAwareAggregateRepository.cs:427-448`) that uses the same scoped `IDocumentSession` as the caller (the repository takes it at `:44` and `MartenSnapshotStore` takes the same scoped instance at `MartenSnapshotStore.cs:26`; both are registered scoped, `ServiceCollectionExtensions.cs:248`, `:369`, `:372`). Three consequences, read from the code and not run: (a) a Marten session is not safe for concurrent use, and the background `Store`, `Query` and `SaveChangesAsync` can race with the caller's next use of the same session or flush the caller's pending changes; (b) after the request scope ends the session is disposed, so the snapshot fails with an object-disposed error that `:440-447` only logs, and the caller never learns the snapshot was lost; (c) `Snapshot<TAggregate>` holds the live aggregate (`:418-422`, `Snapshot` stores `State` by reference, `ISnapshot.cs:48`, `SnapshotEnvelope.cs:26`), while `Version` is copied as an int at creation and the state is serialized later inside `SaveChangesAsync`; if the handler raises more events on the same instance before that runs, the persisted `State` is ahead of the envelope `Version` and `LoadWithSnapshotAsync` (`:357-374`) replays events the state already contains. It also passes `CancellationToken.None` to the store calls and the `Task.Run` at `:431`, `:438`, `:448`, so the background database work is not cancellable and no comment says why. AGENTS.md has no text on `CancellationToken.None` (searched `CancellationToken\.None` over `AGENTS.md`: 0 matches); the rule in section 3 says only that database calls take a `CancellationToken` ("Database calls MUST be asynchronous with a `CancellationToken`"), so this is a design observation, not a rule breach. Fails the intent of the async database rule (a cancellable, scoped unit of work) and the section 3 rule "errors never swallowed in background infrastructure" (the `catch` at `:440-447` logs and drops the failure). The tests set `AsyncSnapshotCreation = false` for every repository test (`SnapshotAwareAggregateRepositoryTests.cs:37`), so the default path never runs; #1894 and #1976 ask for a test of this path and call the race "not established", they do not file it as a defect. Mark (a)-(c) as unexecuted; the verifier should run a save across the threshold with the default option, then continue to use the session and the aggregate, and read the logs and the stored `State.Version`.
3. **Major** — A snapshot is created only when the aggregate version is an exact multiple of `SnapshotEvery` after a save: `SnapshotAwareAggregateRepository.cs:398` (`aggregate.Version % snapshotEvery != 0` then return), while the method's own summary says "has crossed the snapshot threshold" (`:388`) and the option is documented as "number of events after which a snapshot should be created" (`SnapshotOptions.cs:17-23`). A save appends a batch (`:173`), so a command that raises 3 events per save with `SnapshotEvery = 100` reaches versions 99, 102, ... and snapshots only at 300, 600; a command raising 7 events snapshots only at 700. A stream that grows by a fixed batch size that does not divide `SnapshotEvery` is never or rarely snapshotted and keeps paying the full replay the feature exists to avoid. `CreateAsync` (`:240-281`) never calls `TryCreateSnapshotAsync`, so an aggregate created with `SnapshotEvery` or more events in one save gets none either. Fails the feature's acceptance (load performance for long streams). The unit test names the behaviour (`SaveAsync_VersionMultipleOfSnapshotEvery_CreatesSnapshot`, `SnapshotAwareAggregateRepositoryTests.cs:292`), so the modulo is pinned, not designed. Derived from the code, not run; `versionBeforeAppend` is already computed at `:172`, so crossing is `versionBefore / every != versionAfter / every`.
4. **Minor** — `SnapshotOptions.Enabled` ("whether snapshotting is enabled", default false, `SnapshotOptions.cs:10-14`) does not control snapshotting. Its only reader is the registration of the open-generic store (`ServiceCollectionExtensions.cs:90-93`, `:243-251`); `AddSnapshotableAggregate<T>` registers its own store and the snapshot-aware repository whatever `Enabled` is (`:363-375`), and the repository never reads it (searched `Snapshots\.Enabled|\.Snapshots\b` over `src/**/*.cs`: the repository reads only `GetConfigFor` at `:64` and `AsyncSnapshotCreation` at `:424`). An application that calls `AddSnapshotableAggregate<Order>()` and leaves `Enabled` false still creates and prunes snapshots. Fails the pay-for-what-you-use principle of AGENTS.md section 1 (`AGENTS.md:9`, "every feature opt-in": a feature that is off must not run) and the XML contract of the option; either the flag gates the repository or it is removed.

## Lessons for the pipeline
- (pass 2 correction) A stand-in replica of a framework behavior must derive from the real base type or copy its attributes line by line: the first run's "empty `Id`" came from a stand-in without the `[JsonInclude]` that `AggregateBase.cs:72` carries. State what the replica does and does not describe, and read the real type's attributes before stating a replica result as the defect.
- A serializer-defaults question that an earlier audit left "not established" (here #25's tests stage, item 6) is settled in one run by a file-based replica that instantiates the library's own `StoreOptions().Serializer()`; file-based apps default to `PublishAot` and disabled reflection, so the replica needs `#:property PublishAot=false` and `#:property JsonSerializerIsReflectionEnabledByDefault=true` or `System.Text.Json` throws before reaching the question.
- When a test helper's comment says a property shape was changed "to allow JSON deserialization" (`TestSnapshotableAggregate.cs:11-15`), that comment is the cheapest pointer to a production-shape defect: compare the helper's shape with the shape the XML docs tell users to write.
- When an earlier audit of a sibling issue (#25 here) already audited the same code, read its remediation list first and spend the effort on what it classed as a test gap: two of the four findings here (the serializer round trip and the shared-session background task) were written there as "tests to add" but are code defects.
