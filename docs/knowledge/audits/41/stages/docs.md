## Findings

1. **Major** — `CHANGELOG.md:9424-9439` (also `docs/releases/v0.11.0/CHANGELOG-DETAILS.md:3967-3982`): the sample for the delivered API reads members that do not exist. The comment says "`SagaResult<TData>` contains IsSuccess, Data (final state), Error (if failed), SagaId, and StepsExecuted", and the code uses `result.IsSuccess`, `result.Error?.Message` and `result.Error` on the value returned by `sagaRunner.RunAsync`. In `src` `SagaResult<TData>` has only `SagaId`, `Data` and `StepsExecuted` (`src/Encina.Messaging/Sagas/LowCeremony/ISagaRunner.cs:61-65`), and `RunAsync` returns `ValueTask<Either<EncinaError, SagaResult<TData>>>` (`ISagaRunner.cs:32-36`), so the caller must `Match` the `Either`; `Either` has no `IsSuccess`. This is a missing-identifier defect (a blocker on a live page); I rank it Major only because both files are dated release records and not guides, but they are the only description of the result handling in `docs/`. The Features list at `CHANGELOG.md:9396-9410` also says "Full test coverage: unit, property-based, and contract tests", a literal claim with no citation; the hand-typed counts at `docs/releases/pre-v0.10.0/README.md:1127-1131` (45, 11, 8) are the same kind and are dated history. No open issue names these lines (search of all open issue bodies for `result\.IsSuccess|SagaResult|low-ceremony` returned only code and test issues: #2221, #2216, #2210, #2208, #2207, #2200, #2199, #1886, #1581, #1343).

2. **Major** — `docs/sharding/cross-shard-operations.md:105`: "Each step is persisted to `ISagaStore` (all 10 database providers)" is false for the three EF Core providers (SqlServer, PostgreSQL, MySQL): the runner persists nothing through `SagaStoreEF`, which only tracks changes (#2199, code stage informational). The same persistence claim is repeated at `:485` ("`SagaRunner` persists state after each step") and `:939` ("Saga state is persisted to `ISagaStore` after each step"), and is equally false for those three providers. This is the only claim of this finding that is false. The other sentences cited by the first draft are literally true as written and are not findings (audit #38 read them so): `:107` ("Timeout management — Optional per-saga timeout via `WithTimeout`"), `:108` ("Crash recovery — `SagaOrchestrator.GetStuckSagasAsync` detects incomplete sagas after a process restart"), `:488` ("so stuck sagas are detected by `SagaOrchestrator.GetExpiredSagasAsync`") and the detection sentences of `:939` (`GetStuckSagasAsync`, `SagaOptions.StuckSagaThreshold`, `GetExpiredSagasAsync` for sagas that used `WithTimeout`); the methods exist (`src/Encina.Messaging/Sagas/ISagaStore.cs:56`, `:67`, `SagaOrchestrator.cs:461-464`, `:516`). The labels "Timeout management" and "Crash recovery" at `:107-108` can mislead a reader into expecting enforcement or resumption, but the page promises no retries and no automatic recovery. Related open issues: #2199 (the persistence defect; the page should say what holds per provider or be corrected after the fix) and #2208 (timeout recorded, never enforced; informational context for the labels only), #2216 (timeouts missing from `docs/messaging/sagas.md`, a different page).

3. **Major** — `docs/sharding/cross-shard-operations.md:170-177`, `:186-199`, `:262-274`, `:289-301`, `:366-378`, `:421`, `:463-477`: every compensation example discards the `Either` of the repository call (`await _repo.DeleteAsync(...)` at `:174`, `await _repo.AddAsync(original, ct)` at `:196`, `await _accountRepo.UpdateAsync(...)` at `:271`, `:298`, `:475`, `await _inventoryRepo.UpdateAsync(...)` at `:375`, `:421`), and `Compensate` is `Func<TData, IRequestContext, CancellationToken, Task>` (`SagaDefinition.cs:197`), so a failed refund or re-insert returns `Left` and the saga still ends `Compensated`. The FAQ at `:941-943` then tells the reader "If a compensation persistently fails, the saga enters `Failed` status": that happens only when a compensation throws (code stage finding 2, `SagaRunner.cs:320-331`). The guidelines at `:486` ("`SagaRunner` logs compensation failures but continues") repeat it. The page teaches the pattern the library cannot detect and promises the outcome it does not deliver. The fix depends on the signature change proposed by the code stage (a compensation that returns `Either`); until then the page should show the compensation checking the result and throwing, and state the rule. Not tracked: #1581 and #2200 are about the orchestrator results, not the page.

4. **Minor** — `docs/sharding/cross-shard-operations.md:430-456` (Idempotency patterns 2 and 3): two samples do not compile against the page's own types. `:437` and `:441` read `data.TransactionRef`, but `OrderFulfillmentData` (`:323-331`) has no `TransactionRef` (only `FundsTransferData` has, `:228`). `:455` uses `sagaId.ToString()` and the comment at `:453-454` says the runner generates a `SagaId` that "you can store in saga data"; a step receives `(data, IRequestContext, CancellationToken)` (`SagaStepBuilder.cs:35`, `SagaRunner.cs:126`) and no saga id, which `SagaRunner` creates at `:89` and returns only in `SagaResult` after the run, so no step can read it. The idempotency key has to come from the caller (a value placed in the initial data).

## Lessons for the pipeline

- When the only page that teaches a feature belongs to another feature's section (here sagas inside the sharding guide), find it by searching the type names across all of `docs/`, not by the feature's own section; `docs/messaging/sagas.md` had 0 hits.
- A page that lists runner guarantees (persistence, timeout, crash recovery, compensation failure) must be compared claim by claim, but a claim is a finding only when its literal text is false: of the five bullets in the first draft only the persistence claim (:105, :485, :939, EF Core providers) is; labels that merely mislead are not findings (audit #38 / verifier Correction 3).
- A release-record sample that reads members of a returned `Either` (`IsSuccess`, `Error`) passes a name search because those names exist on other types; check the receiver's real type.
