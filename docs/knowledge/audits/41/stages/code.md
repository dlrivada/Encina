## Findings
1. **Major** — Compensation runs under the caller's cancellation token on two of the three failure paths, so a cancelled run cannot undo anything. `SagaRunner.cs:245` (`HandleCancelledAsync`) passes the already-cancelled `cancellationToken` to `CompensateAsync`, which hands it to every compensation at `:323`; `SagaRunner.cs:191` (`HandleStepFailedAsync`) passes the caller's token too, so a cancel that arrives while compensating makes every remaining compensation start with a cancelled token. The exception path uses `CancellationToken.None` (`:271`) and the terminal persistence uses `CancellationToken.None` (`:198`, `:250`) with the comment at `:194-195` ("persisted even when the caller's token is cancelled"), so the class already knows compensation must outlive the token and applies it to three of five sites. A compensation that calls `encina.Send(..., ct)` (the shape of the documented example, `SagaDefinition.cs:23-27`) gets a dispatch that cannot do its work and, because `Compensate` returns `Task` (finding 3), nothing reports it; one that calls `ct.ThrowIfCancellationRequested()` or an async store call throws, lands in the `catch` at `:326`, and is logged as `CompensationFailed` while the cancel path discards the returned failure code (`:245-246`, tracked by #2200 only as "ignores the outcome", not as the token). The unit test that pins this path (`SagaRunnerTests.cs:676-708`) uses a compensation that ignores `ct` (`:687`), so it passes. The sibling `RoutingSlipRunner.cs:137` and `:146` already compensate with `CancellationToken.None` on cancel and exception, which is the precedent in the same package. Fails AGENTS.md section 3 ("Errors are NEVER swallowed in background infrastructure") and the compensation guarantee in `ISagaRunner.cs:10-16`. Static reading, not run: the verifier can run a two-step saga whose first compensation does `ct.ThrowIfCancellationRequested()`, cancel the token inside step 2, and assert the compensation never completes.

2. **Major** — A compensation has no way to report a `Left`, and the XML example that documents the API discards it, so a failed undo ends the saga `Compensated`. `SagaStepDefinition<TData>.Compensate` is `Func<TData, IRequestContext, CancellationToken, Task>` (`SagaDefinition.cs:197`, `SagaStepBuilder.cs:83-104`, `PublicAPI.Unshipped.txt:445`); `SagaRunner.CompensateAsync` counts a compensation as failed only when it throws (`SagaRunner.cs:320-331`). The example in `SagaDefinition.cs:23-27` and `:34-38` (repeated in `SagaStepBuilder.cs:23-27`) is `await encina.Send(new CancelReservation(...), ct);` with the `Either` dropped, and `encina.Send` returns `Left` for failures instead of throwing. Result: a refund that returns `Left` is "compensated" (`CompleteCompensationAsync` at `:213-232` records every step done, `RunAsync` ends `Compensated` without a DLQ capture), the customer keeps the charge, and no log, state or error shows it. This is the case the Failed end state and `DeadLetter` capture added by #2185 and #2202 exist for, and it is unreachable for any compensation written the documented way. Fails ADR-001/ADR-006 (operations return `Either`, no exceptions for business outcomes) and AGENTS.md section 3 (a `Left` never reports success). Sibling contrast: `DurableSagaBuilder.cs:369` handles a compensation `Either` (`compensateResult.Match(...)`) and records `CompensationErrors`; the low-ceremony API is the one that cannot. This is a signature change (`Task<Either<EncinaError, Unit>>` or similar), correct to make pre-1.0 (AGENTS.md section 1); not tracked by #1581 or #2200, which are about the orchestrator results.

3. **Major** — `encina saga` generates code that does not compile. `src/Encina.Cli/Services/CodeGenerator.cs:491-494` emits `using Encina.Messaging.Sagas;` and then `SagaDefinition.Create<...>` and `BuiltSagaDefinition<...>` (`:503-505`); both types are in `Encina.Messaging.Sagas.LowCeremony` (`SagaDefinition.cs:3`, `PublicAPI.Unshipped.txt:414,422`) and no type of that name is in `Encina.Messaging.Sagas` (searched `class SagaDefinition` over `src/Encina.Messaging/Sagas/**`: the only matches are the LowCeremony file). The template also emits `async (data, ct) => { return Right<...>(data); }` and `async (data, ct) => { }` with no `await` (`:513-521`), which is CS1998 in the generated project, and writes the step name raw into a C# string literal (`:512`, `.Step("{{step}}")`), so a name with a quote breaks the file. The test only asserts the substring `.Step("ValidateOrder")` (`tests/Encina.UnitTests/Cli/Services/CodeGeneratorTests.cs:146-148`), so nothing compiles the output. Fails the known pattern "generated or documented example never compiled against the real API". Derived from reading the namespaces, not compiled: the verifier can generate `OrderProcessing` with three steps into a scratch project that references `Encina.Messaging` and build it.

4. **Minor** — A step defined with the fluent builder is lost, or duplicated, unless the exact closing call is made. `SagaStepBuilder<TData>.Execute` only stores the delegate (`SagaStepBuilder.cs:52-58`); the step reaches the definition only when `Compensate`, `Step`, `WithTimeout` or `Build` is called on that builder (`:83-89`, `:111-115`, `:122-126`, `:132-136`, through `AddStepToParent` `:138-146`). So `def.Step("a").Execute(f);` followed by `def.Step("b").Execute(g).Build()` builds a one-step saga without "a" and without an error; and `Build()` on the same step builder twice calls `AddStepToParent` twice, adding the step twice (nothing guards re-entry). `SagaDefinition<TData>.Step()` also computes the default name from `_steps.Count` at call time (`SagaDefinition.cs:93-96`), so two un-closed builders are both named "Step 1". Static reading; unit tests pin the happy chains only. Fails the fail-fast expectation for a builder that throws on `Execute == null` (`:140-143`) but accepts the more common mistake silently.

5. **Minor** — Cancellation is classified by exception type only, and the first store call can escape as an exception. `RunAsync` catches `OperationCanceledException` without a `when (cancellationToken.IsCancellationRequested)` filter (`SagaRunner.cs:100`), so a step whose own `HttpClient` timeout or linked token throws `TaskCanceledException` is logged as "cancelled" (`:242`), compensated with a still-live token, ended `Failed` (DLQ capture) with `HandlerCancelled` (`:250-255`), while the same step returning `Left` ends `Compensated` through `HandleStepFailedAsync`. The sibling decision in this package was the opposite (`when (!token.IsCancellationRequested)`, audit lesson #39). Separately `StartAsync` runs outside the `try` (`:78-82`): a cancelled token makes the store throw and `RunAsync` throws instead of returning `Left`, although the same cancel one line later returns `Left(HandlerCancelled)`. Static reading, not run.

6. **Minor** — The issue's undelivered scope has no tracked successor. The body asks for the `[Saga]` attribute, a `SagaStep` builder (`SagaStep.Do(...).OnSuccess(...).OnFailure(...).Timeout(...)`), convention-based routing, inline state, documentation, and lists "Convention-based routing works" as an acceptance criterion; the closing comment lists none of them and the issue closed COMPLETED. Searches over the open-issue dump for `convention-based|Wolverine`, `\[Saga\]` and `inline state|SagaStep\.` returned no issue about this (the Wolverine hits are unrelated features); `src/` has no `[Saga]` attribute (the only `Saga` attribute types searched: none under `src/Encina.Messaging/Sagas`). AGENTS.md section 11 ("NEVER leave an identified problem unresolved or unrecorded") needs either an issue for the dropped scope or an explicit decision that the fluent API replaces it; the options stay for the maintainer (needs-decision), they are not picked here.

## Informational (not findings)
- Nothing resumes a low-ceremony saga: the steps are lambdas that are not persisted, so a process that dies mid-run leaves a `Running` row (reported by `GetStuckSagasAsync`) that no code can continue or compensate. `ISagaRunner.cs:10-16` promises "complete saga lifecycle" without saying so. Together with #2208 this is the real durability limit of the API; a decision, not a defect.
- A step that throws is not compensated itself (`HandleExceptionAsync` compensates from `StepsExecuted - 1`, `SagaRunner.cs:271`; the failing step is index `StepsExecuted`), and the caller gets the original step error whether compensation succeeded or failed (`:205-206`); the difference is visible only in the saga row and the DLQ. Deliberate as written; worth one sentence in the docs.
- Every compensation receives the final saga data, not the data as of its own step (`SagaRunner.cs:191`, `:245`, `:271` pass `progress.Data`).
- Registration is complete for the runner: `IRequestContextAccessor`, `IMessageSerializer` and `TimeProvider` are `TryAdd`-ed by the same method (`MessagingServiceCollectionExtensions.cs:234-243`) before `RegisterSagas` adds `SagaOrchestrator` and `ISagaRunner` (`:306-313`); EventIds 2888-2898 are inside `Messaging` (2800-2999, `EventIdRanges.cs:126`) with 2899-2914 used by the sibling files, no overlap. Whether a `ValidateOnBuild` test exists is the test stage's.
- The runner has no `Activity`, meter or tenant/module on the saga row (cross-cutting functions 2, 10, 11 in AGENTS.md section 6); `InstrumentedSagaStore` wraps only the store. No PR record exists for a Defer decision (no PR), so this is noted, not a finding.
- The sharding page (`docs/sharding/cross-shard-operations.md:170-177`, `:262-274`) repeats the discard-the-`Either` compensation shape of finding 2; docs stage.

## Lessons for the pipeline
- Walk one hop from a "new API" issue to its generators and scaffolds (`Encina.Cli` here): the only consumer of the API outside its folder was a text template that nothing compiles, and its tests assert substrings.
- When the closing comment of a FEATURE issue omits body tasks and acceptance criteria, search the open issues for each dropped item before the code stage ends; the archivist records `current: no`, but only the code stage can say whether anything tracks it.
- Run the open-issue dump first: 7 of the 12 candidates in this scope were already filed (#1581, #2200, #2199, #2208, #2210, #2207, #2216), so new effort went to cancellation-token flow, the compensation signature and the generator.
- For a compensation or rollback path, read which token reaches the user's delegate on every failure path, not only the persistence calls; the class applied `CancellationToken.None` consistently to the store and inconsistently to the delegates.
