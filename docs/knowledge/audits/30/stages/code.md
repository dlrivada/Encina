## Findings
1. **Major** — `.github/workflows/sonarcloud.yml:133-134` (listed in `multicriteria` at `:68` as `e33`): the SonarCloud rule `csharpsquid:S6966` is ignored for `src/**/*.cs`, i.e. for the whole product. AGENTS.md section 3 ("Database calls MUST be asynchronous with a `CancellationToken` ... NEVER the synchronous overloads such as `IDbConnection.Open()`") names S6966 as the reason for the rule (`(why: Sonar S6966 ...; #794, #897)`), and `docs/engineering/agents-md-traceability.md:24` maps the rule to "S6966; #794, #897". The suppression was added by commit `5a2ca97d` (2026-03-24, "exclude S6966 (LeftAsync/RightAsync) as architectural false positive", `Closes #897`) on the claim that all 2,242 issues were "Await LeftAsync/RightAsync" on `Either` returns, but issue #897's own body lists the patterns it covers as `connection.Open()`, `command.ExecuteNonQuery()`, `command.ExecuteScalar()`, `reader.Read()` and `.ToList()` in EF Core, so the same rule that was dismissed was the one that detected sync database calls. The comment block of the workflow gives no rationale (`grep S6966` in the file shows only the two ignore lines), and the suppression is rule-wide with no file or folder scope. Synchronous database calls remain in the product today and are being found one by one by audits instead of by the analyzer: `src/Encina.Messaging/TransactionPipelineBehavior.cs:77,83` (tracked as open #2031) and, as conditional fallbacks, `src/Encina.Messaging/Services/ConnectionWarmupHostedService.cs:90`, `src/Encina.ADO.SqlServer/ABAC/PolicyStoreADO.cs:441`, `src/Encina.Dapper.PostgreSQL/BulkOperations/BulkOperationsDapper.cs:396` and `src/Encina.ADO.SqlServer/Sharding/Migrations/AdoMigrationExecutor.cs:53`; open #1418 and #1419 are for the same family (#1610 is not: it is about RabbitMQ and MQTT connect blocking, not a database call, and is left out of this list). Those four cited sites are `else` branches taken only when the connection or command is not the provider's concrete type (`DbConnection` at `ConnectionWarmupHostedService.cs:84`, `SqlConnection` at `PolicyStoreADO.cs:438`, `NpgsqlConnection` at `BulkOperationsDapper.cs:390`, `DbCommand` at `AdoMigrationExecutor.cs:47`); the async overload (`OpenAsync` or `ExecuteNonQueryAsync`) is used otherwise, so they are fallbacks, not the primary path, and `AdoMigrationExecutor.cs:53` is a synchronous `ExecuteNonQuery()`, not an `Open()`. Counts in `src` (searched `\.Open\(\)` over `src/**/*.cs` in the audit worktree): 26 lines, of which 6 are the `SchemaValidatingConnection.cs:81` overrides (ADO and Dapper times SqlServer, PostgreSQL, MySQL) and 20 are call sites. The same false positive is already suppressed line by line elsewhere: 240 inline `// NOSONAR S6966` comments in 39 files under `src` (searched `NOSONAR S6966` over `src/**/*.cs`), which bears on the fix direction (the rule-wide ignore duplicates what those comments already do for the known sites). Not every site would be flagged (the interface-typed `IDbConnection.Open()` has no async twin, so S6966 itself does not fire on it), which is why the fix is not "remove the line and fix 2,242 issues" but "decide what enforces the MUST". Fails the known pattern "a MUST rule with no enforcing job" (lesson of audit #19: ask who fails when the rule is violated; here the one detector named by the rule is switched off, `.editorconfig` has no `dotnet_diagnostic.S6966` or `CA1849` entry, and no architecture test under `tests/Encina.UnitTests/Testing/Architecture` mentions `OpenAsync` or `Open()`: searched `OpenAsync|\.Open\(\)|synchronous` in that folder, 0 files) and AUD-16 of SPEC-003 ("database calls use `OpenAsync`, `BeginTransactionAsync`, ... never the synchronous overloads"). Related, not a duplicate: #1341 (open) is the same defect for the S2077 suppression at `:69-72` and `:135-136` and does not mention S6966; I found no issue about S6966 (`gh issue list --state all --search "S6966"`: #897 closed, #1325 closed, #1418, #1419, #1610, #2031 open, none about the suppression; #1610 only mentions S6966 and is RabbitMQ and MQTT connect blocking). Fix direction: remove the rule-wide ignore and scope it to the verified `LeftAsync/RightAsync` false positives (or, if SonarCloud cannot express that, scope by folder), and add a deterministic check for the sync database overloads (a `BannedSymbols.txt` entry for `System.Data.IDbConnection.Open` and siblings, or an architecture test) so the rule has an enforcing job that does not depend on SonarCloud.

## Lessons for the pipeline
- For a CI-workflow scope whose commit also closed a sibling issue already audited (#29 here), read the sibling's code stage first, re-verify each of its findings against the current files, and spend the new effort on the part of the file the sibling did not review (here the SonarCloud rule exclusions in `sonarcloud.yml`, which the #29 stage listed as read in full but did not assess).
- A rule suppression in an analyzer config (SonarCloud `multicriteria` entry) deserves the same "who enforces the MUST" check as a deleted test: compare each ignored rule key with the rules AGENTS.md section 3 cites as its reason (`S6966` is cited by the async-database rule) and with the issue the suppression commit closed (#897's body described sync database calls, the commit message called them LeftAsync/RightAsync false positives).
