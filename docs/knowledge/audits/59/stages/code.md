## Findings

1. **Major** — The middleware never binds the caller identity to Encina's request context, so `IEncina.Send` from a function runs anonymous. `src/Encina.AzureFunctions/EncinaFunctionMiddleware.cs:63-85` (`Invoke`) only writes a `FunctionContext.Items` entry (`:91`) and calls `next`. The public inbound-scope API exists (`src/Encina/Identity/IRequestContextScopeFactory.cs:134` `RunInboundAsync`, with `InboundRequestInfo` at `src/Encina/Identity/InboundRequestInfo.cs:52`) and the ASP.NET Core adapter binds the identity for every request, though through the internal `IInternalRequestContextScopeFactory.RunHostInboundAsync` (`src/Encina.AspNetCore/EncinaContextMiddleware.cs:129`; `src/Encina/Identity/RequestContextScopeFactory.cs:149-153`; response correlation header at `:136`), which `Encina.AzureFunctions` cannot reach (`src/Encina/Encina.csproj:84-94` grants `InternalsVisibleTo` to `Encina.Security.ABAC`, `Encina.AspNetCore` and `Encina.AspNetCore.Blazor`, none to `Encina.AzureFunctions`). The public `RunInboundAsync` (the "application binding path") remains the right API for Azure Functions. Search, run in the worktree: pattern `IRequestContext|RequestContextScope|RunInboundAsync|InboundRequestInfo|ClaimsPrincipal` over `src/Encina.AzureFunctions/*.cs` and `Durable/*.cs` returns 0 matches. By `src/Encina/Core/RequestContextAccessor.cs:25` a call with no scope reads the anonymous identity, which every identity gate denies; so the correlation id, user and tenant the package claims to propagate (`README.md:13` "Middleware for request context propagation", `EncinaAzureFunctionsOptions.cs:28-29`) never reach handlers, pipeline behaviors, audit or tenancy (AGENTS.md section 6 functions 10 and 12). The application can open a scope itself by injecting the factory, but the package offers no helper and the README never says so. Read from the code, not run; the verifier can register a handler that reads `IRequestContextAccessor` and call it through the middleware to confirm. Check failed: AGENTS.md section 6 (cross-cutting integration), known pattern "claimed propagation with no producer".

2. **Major** — The request-context enrichment is a stub and several documented behaviours are not implemented. (a) `EncinaFunctionMiddleware.cs:90` always generates `Guid.NewGuid().ToString("N")`; the middleware never reads `CorrelationIdHeader` (`EncinaAzureFunctionsOptions.cs:38`), and `ToProblemDetailsResponse` returns the context value only (`HttpResponseDataExtensions.cs:117`, via `FunctionContextExtensions.cs:37-48`), so the `correlationId` in an error body is the generated GUID, never the caller's `X-Correlation-ID`. (b) `EncinaFunctionMiddleware.UserIdKey` (`:37`) is read at `FunctionContextExtensions.cs:232` and written nowhere (search `UserIdKey` over `src/`: the declaration plus that one read), so `GetUserId(FunctionContext)` (`:228-239`) always returns null and the HTTP overload's fallback at `:269` is dead. (c) `EncinaFunctionMiddleware.cs:93-98` logs `UserId` and `TenantId` as the literal `"(pending)"`. (d) `Log.HealthCheckCompleted` (EventId 4754, `Log.cs:49-55`) has no caller (search `HealthCheckCompleted` over `src/Encina.AzureFunctions`: the declaration only). (e) The docs promise more than the code: `FunctionsWorkerApplicationBuilderExtensions.cs:19-22` ("User ID extraction from claims", "Tenant ID extraction from headers or claims"), `EncinaAzureFunctionsOptions.cs:28-29` (enrich with "correlation ID, user ID, and tenant ID") and `README.md:247-248`. Checks failed: AGENTS.md section 3 ("every line serves a current purpose"), section 8 (accurate XML docs), known pattern "options/keys with a reader and no writer".

3. **Major** — The tenant-denial codes the package defines are answered as 500, and the tenant gate is opt-in per function. `FunctionContextExtensions.cs:91` and `:97` define `tenancy.tenant_mismatch` and `tenancy.invalid_tenant_claim`; `HttpResponseDataExtensions.cs:201-237` (`MapErrorCodeToStatusCode`) has no branch for them (validation, `encina.authorization.*`, `.not_found`/`.missing`, `.conflict`/`.already_exists`/`.duplicate`, otherwise 500), so passing the `Left` of `ResolveTenantId` to `ToProblemDetailsResponse`, the rail the package documents, yields `500 Internal Server Error`, indistinguishable from a server fault. The equivalent ASP.NET Core refusal is a 403 (`src/Encina.AspNetCore/EncinaContextMiddleware.cs:155-162`). Second part: `ResolveTenantId` (`FunctionContextExtensions.cs:123`) has no production caller (search `ResolveTenantId` over `src/Encina.AzureFunctions`: the definition and doc references only); the middleware does not call it (`EncinaFunctionMiddleware.cs:15-16` says the tenant is resolved per request by the function), so a function that forgets the call runs with no tenant check at all, which is the opposite of the fail-closed rule when context is missing. The `AwsLambda` copy has the same gap (see Siblings audited). Checks failed: AGENTS.md section 3 (compliance and security gates fail closed), section 6 function 10.

4. **Major** — `IncludeExceptionDetailsInResponse` is a dead option and the client always receives `EncinaError.Message`. `EncinaAzureFunctionsOptions.cs:91` declares the option ("Default: false (production-safe)", "Including exception details in production responses can expose sensitive information"); the only occurrences in `src/` are the declaration and doc examples (`ServiceCollectionExtensions.cs:63`, `EncinaAzureFunctionsOptions.cs:21`), no reader. `HttpResponseDataExtensions.cs:100` sets `Detail = error.Message` unconditionally, and for errors built from exceptions that text is the exception message (`src/Encina/Results/EncinaErrors.cs:77`, `message ?? exception.Message`). ASP.NET Core honours its analogue (`IncludeExceptionDetails`) only for the `exception` member it adds (`src/Encina.AspNetCore/ProblemDetailsExtensions.cs:101-115`) and sets `Detail = error.Message` unconditionally (`:75`), so no adapter sanitises `Detail`. Open issue #2913 ("Cloud helpers and docs still return EncinaError.Message to HTTP clients", follow-up of #2649) already tracks the `EncinaError.Message` exposure in the cloud helpers, including `HttpResponseDataExtensions.cs` and this option; this finding is a duplicate of #2913. The README shows the option set to false (`README.md:158-159`) and tells users to "Disable exception details in production" (`:479`), so a user who follows it believes the response is sanitised. This is the same text the AGENTS.md section 3 rule keeps out of logs and health results; the HTTP body is not a listed sink, so the policy decision (always send the message, or send a code and a fixed text unless the option is on) belongs to the maintainer. Checks failed: AGENTS.md section 3 (no dead options), known pattern "EncinaError.Message leaked".

5. **Minor** — The Problem Details body is probably not RFC 7807 shaped. `HttpResponseDataExtensions.cs:266-273` serialises a private class whose `Extensions` is a get-only `Dictionary<string, object?>` with no `[JsonExtensionData]` (search `JsonExtensionData` over the package: 0 matches), so `errorCode`, `traceId` and `correlationId` (`:108`, `:114`, `:120`) most likely come out nested under an `"extensions"` member, while RFC 7807 section 3.2 puts extension members at the top level (ASP.NET Core's `ProblemDetails` flattens them, `ProblemDetailsExtensions.cs:85-98`); there is also no `type` member. `tests/Encina.UnitTests/AzureFunctions/HttpResponseDataExtensionsTests.cs` has no assertion on the body shape (search `extensions` over the file: 0 matches). Unexecuted, static reading: hand the verifier a standalone replica that serialises that class with the same options and prints the JSON. Check failed: the decision the issue recorded ("RFC 7807 Problem Details", `README.md:11`).

The check itself (`Health/AzureFunctionsHealthCheck.cs:44-70`) never reports Unhealthy and its doc (`:13-16`) says it verifies "Middleware is registered", which the code does not test. Checks failed: AGENTS.md section 3 (registration completeness, a registration must not depend on order), section 6 function 4.

## Lessons for the pipeline

- The Glob tool returned "No files found" for a valid `src/<package>/**/*.cs` pattern inside a worktree under `.claude\worktrees`; use `Get-ChildItem -Recurse` for file lists and say so in the scope section.
- For an adapter-package issue (Azure Functions, Lambda), compare its middleware with the ASP.NET Core adapter's `EncinaContextMiddleware` line by line: the host adapters were given the identity-scope API later (SPEC-002) and the serverless ones were never moved over, which no per-file review of the serverless package shows.
- A context key with a reader and no writer (`UserIdKey`) is found by one search of the constant name; run it for every `*Key` constant of a context-enrichment class.
- Dump the open issues once and query by the specific symbols of each candidate finding: seven candidates here had no open issue, five concerns were already tracked and moved to Informational.
