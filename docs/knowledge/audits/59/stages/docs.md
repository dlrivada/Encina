The names (`Create`, `Step`, `Execute`, `Compensate`, `WithDefaultRetryOptions`, `Build`) all exist (`DurableSagaBuilder.cs:44`, `:55`, `:77`, `:121`, `:133`, `:421`), which is why a symbol-existence check passes. 3. **Major** — The orchestrator sample's final `Match` has no common return type. `src/Encina.AzureFunctions/README.md:360-362` calls `paymentResult.Match(Right: payment => new OrderResult(orderId, payment.TransactionId), Left: error => error)`: `Right` yields `OrderResult` and `Left` yields `EncinaError`, and LanguageExt 4.4.9 (`Directory.Packages.props:11`) `Match<B>` needs both lambdas to return the same `B`, so the call does not compile: the compiler falls to the `Action`-returning `Match` overload and rejects `e => e` as a statement (CS0201, reproduced by compiling the same shape against LanguageExt.Core 4.4.9 in the verification stage) even though the method returns `Either<EncinaError, OrderResult>`. The fix is `Right: p => Right<EncinaError, OrderResult>(...)`-style lambdas or `Map` on the `Either`. Check failed: rule (a) point 2. Neighbouring lines `:350` and `:353` are fine (both branches return the same type).

## Lessons for the pipeline

- For an issue whose only destination is a package README, the rule (a) point 5 check still needs a search of `docs/tutorials/`, `docs/features/` and `docs/index.md` for the feature name; here the whole docs site mentions the feature only as a row count and in decision text.
- A sample's `Match(Right: ..., Left: ...)` with a different type in each branch passes every symbol-existence check; compare the types the two lambdas return, and compare a method's declared return type with what the final `return` actually yields (the saga sample returns `Either<DurableSagaError, OrderData>` for a declared `FulfillmentResult`).
- When a repo-wide README defect is already an open issue (#2280 lists nine READMEs), search the issue body for the package name before writing the finding, and move it to Informational.
- Glob returned no files for `artifacts/knowledge/**` in a worktree under `.claude\worktrees` on the first call; use `Get-ChildItem` there.
