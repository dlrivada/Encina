## Findings
1. **Major** — The dispatcher is never called by the saga infrastructure, and the public XML docs say it is. `src/Encina.Messaging/Sagas/ISagaNotFoundDispatcher.cs:10-12` states "This dispatcher is used internally by the saga infrastructure to invoke registered `IHandleSagaNotFound<TMessage>` handlers when a saga cannot be found for a given message"; `IHandleSagaNotFound.cs:12-17` lists "Starting a new saga for late-arriving events" as a common scenario. A search of `src/` (pattern `ISagaNotFoundDispatcher|IHandleSagaNotFound|SagaNotFoundContext`, `*.cs`) finds the dispatcher only in its own files, the registration `MessagingServiceCollectionExtensions.cs:310`, and doc comments; there is no caller of `DispatchAsync` in `SagaOrchestrator.cs`, `LowCeremony/SagaRunner.cs`, any transport, inbox or choreography code. `SagaOrchestrator` returns `Left(saga.not_found)` at lines 168, 220, 294, 317 and 487 without dispatching (it also receives no message to hand over), so the registered feature only runs when application code builds the context and calls the dispatcher by hand, as `docs/features/dead-letter-queue.md:263-267` shows. The issue's task "Integrate with saga pipeline" and acceptance criterion "Handler executes on saga not found" are therefore unmet, the `StartNewSaga` strategy the interface docs advertise does not exist (`SagaNotFoundAction` has only `None`, `Ignored`, `MovedToDeadLetter`), and the XML docs describe behaviour the code does not have (known failure pattern: documented but unwired; AUD code/docs consistency). Fix by either wiring the dispatcher at the point where a message fails correlation (and defining that point) or correcting the XML docs and removing the unsupported scenarios; no open issue tracks the wiring (#1480 covers only tests).
2. **Minor** — A message with no registered handler, or whose handler takes no action, is acknowledged as success and leaves almost no trace. `SagaNotFoundDispatcher.cs:84-89` returns `unit` after a `Debug`-level log (`:126-130`, EventId 2899) when `GetService<IHandleSagaNotFound<TMessage>>()` is null, and `:101` returns `unit` when the handler neither calls `Ignore()` nor `MoveToDeadLetterAsync` (`Action` stays `None`). The caller's documented rule is "acknowledge only when Right" (`docs/features/dead-letter-queue.md:267`), so an orphan message of a type nobody wrote a handler for is silently dropped; there is no Warning log, no counter and no `Activity` tag (AGENTS.md §6 functions 2 and 3, observability of a dropped message). The lookup is on the compile-time `TMessage` (`:82`), so a caller that dispatches a message typed as `object` or a base class finds no handler for the runtime type and gets the same silent success. Only the last registered handler is resolved, other registrations are ignored without a log. At minimum raise the no-handler and `Action == None` cases to `Warning` and count them; consider returning a `Left` or requiring an explicit opt-in to drop.
3. **Minor** — The two error codes added for this issue are reused with a different meaning by `SagaRunner`. `SagaErrorCodes.cs:53-61` defines `saga.handler.cancelled` and `saga.handler.failed`, which `SagaNotFoundDispatcher.cs:107,114` return when an `IHandleSagaNotFound` handler is cancelled or throws (original commit: "Saga not found handler was cancelled"). `LowCeremony/SagaRunner.cs:250,255,275,280` returns the same two codes, and persists them in the saga state through `FailAsync`, when a saga step is cancelled or throws. A consumer matching on `saga.handler.failed` cannot tell a failed not-found handler (no saga exists) from a failed saga step (a saga row stores the code), and the XML summary ("Saga handler failed with an exception") hides the split. Give the not-found handler its own codes (for example `saga.not_found_handler.failed`) or document the shared meaning; changing the constants touches `PublicAPI.Unshipped.txt:138-139`.
4. **Minor** — `SagaNotFoundContext` can report that a message was ignored although it was stored in the dead letter queue. `SagaNotFoundContext.cs:126-136` sets `_action = MovedToDeadLetter` after a successful move; a later `Ignore()` (`:101-105`) overwrites it with `Ignored` and clears `FailedMove`, so `WasIgnored` is true, `WasMovedToDeadLetter` false, the dispatcher's completion log (`SagaNotFoundDispatcher.cs:97`, `Action: Ignored`) is wrong, and `DeadLetterReason` stays set. The reverse order (Ignore, then a successful move) ends as `MovedToDeadLetter`, so the outcome depends on call order without being documented. Make the action terminal once a move succeeded (or reject the second call) and document the rule on `Ignore()` and `MoveToDeadLetterAsync`.

## Lessons for the pipeline
- When a closed feature's deliverable is a dispatcher or handler abstraction, grep for the callers of its single entry method (`DispatchAsync`) before reading the implementation; a registered, documented, tested service with zero callers is the main defect and the XML remarks may claim otherwise.
- Check each public error-code constant added by an issue against every other use of the same string in `src/` (here `SagaRunner` reused the codes); a code introduced for one meaning and later reused is invisible to a file-by-file read of the scoped files.
