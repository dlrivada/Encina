## Lessons for the pipeline

- A copied manifest `reason` ("Interface — no implementation") on a class that has real logic (`InboxOrchestrator.cs`, the six ADO and Dapper `InboxMessageFactory.cs`) silently removes every obligation for that file; the manifest check that lesson #103 asks for (`defaultTests: []` on a file with a non-interface type) would have caught eight entries in this one unit.
- A knowledge record whose audit says "coverage not run" and whose scope spans 63 manifest entries across nine packages is a rule (b) job of this size (11 findings here); the delta brief should say whether sibling providers' `ServiceCollectionExtensions.cs` and factories are in scope up front, and whether to group by package or by theme (this stage grouped by theme to keep one numbered finding per remediation issue).
- Reading the guard report against the `ThrowIfNull` lines of each source (a three-line script) exposed an asymmetry the aggregate hides: the ADO guard classes execute every argument check of their registration file and the Dapper and MongoDB guard classes miss 7-12 of 15-17. A per-provider table of missed null-check lines is a cheap standard output for provider-coherent registration files.
- A namespace-filtered measurement can miss a test class of the scope that sits in another namespace (`Encina.UnitTests.Core.NestedDispatchContextTests` executes `InboxPipelineBehavior.cs:59`); before listing a line as missed, search `tests\Encina.UnitTests` for the type name across all namespaces and include the extra class in the run.
- `Select-String -Pattern <class name>` over `tests\` overstates coverage: `ScheduledMessageProcessor` appears in the integration scenarios only in a doc comment, and in one unit test file only because that test happens to run its hosted loop; always open the match before counting it as a test of the type.
