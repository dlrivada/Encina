## Findings

1. **Major** — A route condition that throws is swallowed and the message falls through to the next route, the default route or an empty success. `src/Encina.Messaging/ContentRouter/ContentRouter.cs:203-207` catches every `Exception` from `route.Matches(message)`, logs a Warning (`ConditionEvaluationFailed`, EventId 2811, `:476-480`) and goes on; the comment says "Skip this route on condition evaluation failure". The skipped route is then indistinguishable from a route that did not match: with `AllowMultipleMatches = false` the next lower-priority route that matches handles the message (`:187-201`), and when none does, `RouteWithoutMatchAsync` runs the default route (`:121-127`) or, with `ThrowOnNoMatch = false`, returns `Right(ContentRouterResult.Empty)` (`:138-140`, a success that processed nothing). A predicate such as `o => o.Customer.Risk > 5 → manual review` that throws a `NullReferenceException` therefore sends the message to the default or a less specific route instead of failing. The code was designed to return an error here: `ContentRouterErrorCodes.ConditionEvaluationFailed` (`ContentRouterErrorCodes.cs:36`) exists and is produced nowhere (see finding 5). The behaviour is pinned as intended by `ContentRouterTests.cs:300-322` (`RouteAsync_WhenConditionThrowsException_SkipsRoute`), so the fix must change that test. Fails: AGENTS.md section 3 "Errors are NEVER swallowed" and "gates fail closed" (a content route is often an approval or compliance branch), section 3 ROP (a failure returned as success), known failure pattern "error swallowed, reported as success". Open issues #3723 (categories), #1580 (`ex.Message`) and #3412 (unread options) do not cover it. Proposed direction for the drafter, not a decision: return `Left` with `ConditionEvaluationFailed` (category per ADR-062) and stop routing, or make the skip an explicit option that defaults to failing. Read from the code and the test; not executed.

2. **Minor** — Cancellation is handled three different ways and any `OperationCanceledException` is reported as a cancellation of the router. `ContentRouter.cs:90-94` and `:361-367` turn every `OperationCanceledException` (including a handler's own `TaskCanceledException`, for example an `HttpClient` timeout, with `cancellationToken.IsCancellationRequested == false`) into `content_router.cancelled` and a Warning "was cancelled"; the default route has no such catch, so the same exception there falls into `catch (Exception)` at `:254-260` and becomes `content_router.route_execution_failed` with the exception's message. The same handler therefore returns a different code depending on whether it is the matched route or the default route. Same defect shape as the scatter-gather copy filed as #3700 (its catches treat any `OperationCanceledException` as a cancellation of the run); there is no content-router counterpart. Fails: AGENTS.md section 3 (errors keep their real cause), consistency of the code per path. Read from the code; not executed.

3. **Minor** — With `AllowMultipleMatches` and `EvaluateInParallel`, the result order and the reported error are nondeterministic. `ContentRouter.cs:319-328` collects handler results in a `ConcurrentBag` and returns `[.. results]`; `BuildRoutingResult` then returns `results.FirstOrDefault(r => r.HasError)` (`:150`) and builds `RouteResults` in bag order (`:161-168`). `ConcurrentBag` enumeration order is unspecified, so `RouteResults` is not in priority order (the sequential path is, `:288-301`), although `ContentRouterOptions.cs:57` documents "all matching routes are executed in order", and when two handlers fail the caller gets an arbitrary one of the two errors. In the parallel path every handler also runs even after one fails, while the sequential path stops at the first error (`:296-300`), and the caller of a failed run gets no information about which handlers already ran. Fails: determinism of a public result contract. Hand-off to the verifier: build a definition with 6 routes, `AllowMultipleMatches = true`, `EvaluateInParallel = true`, handlers that delay `(7 - index) * 5` ms, and compare `RouteResults[*].RouteName` with the route order over 20 runs. My stand-in replica (a `ConcurrentBag` filled by `Parallel.ForEachAsync`) was blocked by `block-main-checkout-writes` (see Informational), so this finding is unexecuted.

4. **Minor** — `ContentRouterOptions.MaxDegreeOfParallelism` is not validated and a bad value fails per call with an exception message in the `Left`. `ContentRouterOptions.cs:77` accepts any `int`; `ContentRouter.cs:313-317` assigns it to `ParallelOptions.MaxDegreeOfParallelism`, whose setter throws `ArgumentOutOfRangeException` for 0 and for values below -1 (documented BCL behaviour, not executed here). The exception is thrown only when `AllowMultipleMatches` and `EvaluateInParallel` are both true, is caught by `ContentRouter.cs:95-99` and returned as `content_router.route_execution_failed` with `ex.Message`, on every call, after the router has already evaluated the conditions. `RegisterContentRouter` (`MessagingServiceCollectionExtensions.cs:154`) registers the options instance with no validation, so the application learns of it at the first routed message. Same shape as #3701 (`ScatterGatherOptions` not validated); no content-router issue. Fails: AGENTS.md section 3 registration completeness (options validated when the provider is built is the house expectation in the family) and the fail-fast principle.

5. **Minor** — Three public error codes are produced nowhere. `ContentRouterErrorCodes.cs:16` (`MultipleRoutesMatched`), `:21` (`NoRoutesConfigured`) and `:36` (`ConditionEvaluationFailed`) have zero producers: `Grep "NoRoutesConfigured|MultipleRoutesMatched|ConditionEvaluationFailed"` over `src/` returns the three declarations, `ContentRouter.cs:205` (which is the log method `ContentRouterLog.ConditionEvaluationFailed`, not the constant) and `ContentRouter.cs:480` (its declaration). `NoRoutesConfigured` is unreachable by construction because `ContentRouterBuilder.Build()` throws `InvalidOperationException` when no route and no default exist (`ContentRouterBuilder.cs:139-143`), and `BuiltContentRouterDefinition`'s constructor is `internal` (`:308`). The sibling families have the same defect filed (#3310 routing slip codes, #3699 scatter-gather codes); #3412 lists only the two caching options of the content router, not the codes. Fails: "every line serves a current purpose" (AGENTS.md section 3, no dead code), and the public API promises errors that never come. Direction depends on finding 1 (`ConditionEvaluationFailed` becomes live if that finding is fixed with a `Left`).

6. **Minor** — The content router emits no trace span and no metric. `Grep "ActivitySource|new Meter|StartActivity"` over `src/Encina.Messaging/ContentRouter/*.cs`, `RoutingSlip/*.cs` and `ScatterGather/*.cs` returns 0 matches; the only instrumentation is the 12 `[LoggerMessage]` definitions (`ContentRouter.cs:410-480`). A routing decision (which route matched, default used, duration, failure) is exactly what ADR-018 function 2 (OpenTelemetry) asks to trace. The routing slip (#3311) and scatter-gather (#3693) copies of this gap are filed; the content router is not mentioned in either. Fails: AGENTS.md section 6, function 2. A per-route outcome counter and a span around `RouteAsync` would carry the same data the Debug logs hold today.

7. **Minor** — A handler exception is logged without its stack trace and under the wrong field. `ContentRouter.cs:258` and `:371` call `ContentRouterLog.RouteExecutionFailed(_logger, routingId, route.Name, ex.GetType().Name)`, whose last parameter is `{ErrorCode}` (`:434-438`); the exception type name is passed as an error code, and the exception itself (`ex.ForLogging()`, the pattern used at `:97` and `:205`) is not logged at all, so a handler that throws leaves only its type name in the logs while the run returns `route_execution_failed` (with `ex.Message` in the `Left`, tracked by #1580). Operators cannot find the failing frame. Fails: AGENTS.md section 3 ("an exception passed to a logger goes through `ForLogging()`") by omission, and the structured-logging field contract of `RouteExecutionFailed` (`{ErrorCode}` is also filled with a real code at `:155` and `:357`).

8. **Minor** — The builder drops a route silently. `ContentRouterBuilder.When(...)` returns a `ContentRouteBuilder` and nothing is added to the parent until `RouteTo(...)` runs (`ContentRouterBuilder.cs:70-74`, `:82-87`, `:224-232`); `builder.When(o => o.Total > 10000).WithPriority(1);` followed by `.Build()` compiles, passes the "at least one route" check if any other route exists, and the high-value route is missing from the definition with no error. The same builder lets `Default(...)` be called twice and the second silently replaces the first (`:99-104`). Fails: fluent-API design (a terminal step that cannot be forgotten without a signal); no analyzer attribute (`[MustUseReturnValue]`) and no `Build()` check detects a pending `When`. Read from the code; not executed.

9. **Minor** — The `IContentRouter` XML example does not compile. `IContentRouter.cs:23-26` shows `.RouteTo<HighValueOrderHandler>()`, `.RouteTo<InternationalOrderHandler>()` and `.Default<StandardOrderHandler>()`; `ContentRouterBuilder.cs` defines only the four non-generic `RouteTo` overloads (`:219`, `:241`, `:254`, `:271`) and two non-generic `Default` overloads (`:94`, `:114`), and `Grep "RouteTo<|Default<"` over `src/Encina.Messaging/ContentRouter/` returns only those three comment lines (as `RouteTo&lt;...&gt;`). The example is the leftover of the aspirational API the issue body described (handler types resolved from DI; see the archivist's `AddEncinaContentRouter` gotcha) and misleads IntelliSense readers. Fails: AGENTS.md section 8 (XML comments on every public API, with examples when helpful: a wrong example is worse than none).

## Lessons for the pipeline

- A try/catch that "skips" an item (`// Skip this route on condition evaluation failure`) is the cheapest pointer to a swallowed-error finding: read what the skipped item falls through to (next route, default, empty success) before sizing it, and check whether the module already declares an error code meant for that case (`ConditionEvaluationFailed` was declared and never produced).
- A family audit (routing slip, scatter-gather, content router) produces sibling issues that each name one runner: for every defect shape in the family's issues, grep the third runner for the same shape and write the finding even when the sibling issue says nothing about it; four of the nine findings here are copies of #3310/#3311/#3693/#3699/#3700/#3701.
- `block-main-checkout-writes` blocks a NuGet-free file-based replica when the shell's cwd is the main checkout, even though the file lives in the scratchpad and writes nothing; the stage text should say whether replicas must be run with the worktree as cwd, or that the verifier runs them. I stopped at the hook, as instructed, and marked the dependent claims as derived.
