## Findings
1. **Major** — The classifier registered in DI is never used by the recoverability behavior or processor, although ADR-029 and the Hangfire/Quartz docs say it is. `RecoverabilityPipelineBehavior.cs:70` builds `_errorClassifier = options.ErrorClassifier ?? new DefaultErrorClassifier()`; its constructor (`:59-64`) takes no `IErrorClassifier`, and `grep IErrorClassifier src` finds no other resolution inside `Encina.Messaging`. So `AddEncinaRecoverability<TClassifier>` (`RecoverabilityServiceCollectionExtensions.cs:90-97`, which does `services.AddSingleton<IErrorClassifier, TClassifier>()`) registers a type that the behavior never calls: with the generic overload and no `options.ErrorClassifier`, every failure is classified by `DefaultErrorClassifier`. The same applies to any application that registers its own `IErrorClassifier` before `UseRecoverability` or `AddEncinaRecoverability`: `TryAddSingleton` (`:65`, `MessagingServiceCollectionExtensions.cs:118`) keeps the application's registration, but the behavior still ignores it. Meanwhile `HangfireRequestJobAdapter.cs:38,:52`, `HangfireNotificationJobAdapter.cs:26,:40`, `QuartzRequestJob.cs:40,:59` and `QuartzNotificationJob.cs:27,:41` do resolve the DI classifier, so one application gets two different classifications for the same error. Fails the contract in ADR-029 line 13 ("applications extend or replace it through DI") and `src/Encina.Hangfire/README.md:263` ("the registered implementation"), and AGENTS.md §3 registration completeness (a registered dependency that nothing resolves). Reproduction for the verifier: `AddEncinaRecoverability<AlwaysPermanentClassifier>()`, send a request whose handler returns a transient-looking `Left`, assert the classifier was called (it is not). Not covered by an open issue (#1182 is about the central code lists inside `DefaultErrorClassifier`).
2. **Major** — A handler timeout that surfaces as `TaskCanceledException` bypasses recoverability entirely. `RecoverabilityPipelineBehavior.cs:269` catches `Exception ex when (ex is not OperationCanceledException)`; `TaskCanceledException` derives from `OperationCanceledException`, so it is excluded whether or not the caller's token was cancelled. An `HttpClient` timeout throws exactly `TaskCanceledException` with the caller's token not cancelled. The core dispatcher only converts an `OperationCanceledException` to a `Left` when `cancellationToken.IsCancellationRequested` (`src/Encina/Dispatchers/Encina.RequestDispatcher.cs:146`), and its comment at `:163-165` says every other exception propagates and crashes the process. Result: no immediate retry, no delayed retry, no dead letter. The classifier documents the case the behavior cannot deliver: `IErrorClassifier.cs:57` ("TaskCanceledException (usually timeout)") and `:244` (`TaskCanceledException => Transient`) are unreachable through the behavior's exception path. The sibling filters use the correct form: `DelayedRetryProcessor.cs:330` (`ex is not OperationCanceledException || !cancellationToken.IsCancellationRequested`) and the behavior's own `:187`. No test throws `TaskCanceledException` or `OperationCanceledException` through the behavior (grep over `tests/Encina.UnitTests/Messaging/**/*ecoverab*.cs` returned no match). Known failure pattern: exception filter that equates "OperationCanceledException" with "cancelled". Reproduction: handler throws `new TaskCanceledException(new TimeoutException())` with `CancellationToken.None`; expect retries, observe the exception escaping `Handle`.
3. **Major** — The default registration cannot be built or resolved: `AddEncinaRecoverability()` and `UseRecoverability = true` register `DelayedRetryScheduler` and `DelayedRetryProcessor` (default `EnableDelayedRetries = true`, `RecoverabilityOptions.cs:108`) but not the store and factory the scheduler needs. `RecoverabilityServiceCollectionExtensions.cs:71-78` and `MessagingServiceCollectionExtensions.cs:131-137` register the scheduler; `DelayedRetryScheduler.cs:43-48` requires non-optional `IDelayedRetryStore` and `IDelayedRetryMessageFactory`; `grep "IDelayedRetryStore|IDelayedRetryMessageFactory|AddEncinaDelayedRetryStore" --include=*.cs` over the worktree finds the interfaces, the registration helper, the processor, the scheduler and tests only, so no class in `src/` implements either (the archivist's record says the same, and #594 is the open Post-1.0 issue). With default options a provider built with `ValidateOnBuild` should fail, and without validation the first request through `RecoverabilityPipelineBehavior` (parameter `IDelayedRetryScheduler? delayedRetryScheduler = null`, `:62`) should throw while the container builds the registered scheduler. Every test that proves registration supplies a store stub (`MessageSerializerRegistrationTests.cs:130` `ProbeDelayedRetryStore`; `DeadLetterSourceCaptureRegistrationTests.cs:57` `Substitute.For<IDelayedRetryStore>()`), so the default path is not exercised. The processor's graceful path (`DelayedRetryProcessor.cs:121-126`, `StoreNotConfigured`, log text "delayed retries disabled") contradicts the registration: it is reachable only for an application that never sends a request. Fails AGENTS.md §3 registration completeness ("MUST also register every option type and dependency it resolves, proven by a DI test that builds the provider with `ValidateOnBuild`") and the opt-in principle (a delayed phase that is on by default but has no storage). The fix is a decision (default `EnableDelayedRetries` to `false` until a store is registered, or register the delayed phase only from `AddEncinaDelayedRetryStore`); it is not the persistent stores of #594. Static reading, unexecuted: the verifier should build `new ServiceCollection().AddEncinaRecoverability()` with `ValidateOnBuild = true`.
4. **Major** — Recoverability cannot be enabled through the EF Core and MongoDB registrations (4 of the 10 database providers), unlike ADO.NET and Dapper. `UseRecoverability` and `RecoverabilityOptions` are read only in `MessagingServiceCollectionExtensions.cs:72` and `:113-123`, inside `AddMessagingServices`, which the ADO.NET and Dapper registrations call. EF Core: `AddEncinaEntityFrameworkCore<TDbContext>(Action<MessagingConfiguration>)` (`src/Encina.EntityFrameworkCore/ServiceCollectionExtensions.cs:132-203`) accepts the same `MessagingConfiguration` but registers Outbox, Inbox, Saga, Scheduling and the dead letter queue (`:173-188`) and never reads `UseRecoverability`, so setting the flag compiles, throws nothing and registers nothing. MongoDB: `EncinaMongoDbOptions` has no recoverability flag at all (`EncinaMongoDbOptions.cs:42-75` lists `UseOutbox`, `UseInbox`, `UseSagas`, `UseScheduling`, `UseDeadLetterQueue`; `grep "Recoverab"` over `src/Encina.MongoDB` returns 0 matches) and `RegisterMessagingPatterns` passes the pattern flags individually (`src/Encina.MongoDB/ServiceCollectionExtensions.cs:595-613`), so there is no flag to set and the capability is simply absent from that registration. The remarks at `MessagingServiceCollectionExtensions.cs:193-199` acknowledge that EF Core "does not (yet) support those other patterns", but no registration-time error says so and no open issue tracks it (`grep UseRecoverability` over the open issues matches only #117). Fails AGENTS.md §3 provider coherence ("switching provider means changing the DI registration") and §5. Applications on those providers must know to call `AddEncinaRecoverability()` directly, which the README (`:191-222`) does not say.
5. **Minor** — The jitter source is a shared, non-thread-safe `Random`. `RecoverabilityPipelineBehavior.cs:45` declares `private static readonly Random Jitter = new();` and `:398` calls `Jitter.NextDouble()` from every concurrent request of the same closed generic type. `Random` instances (other than `Random.Shared`) are not thread-safe; concurrent use can corrupt the generator state and return a constant, which removes the jitter the option promises (`RecoverabilityOptions.cs:114-115`). It is the only static `Random` in `src/` (`grep "static (readonly )?Random \w+ = new"` returns this one line); `OutboxBatchProcessor.cs:79` and `RandomReplicaSelector.cs:64` use `Random.Shared`. Use `Random.Shared`, or take the jitter source as a constructor parameter as the outbox does, which also lets a test pin it.
6. **Minor** — Cancellation is handled three different ways in one pipeline method. (a) A token already cancelled at an attempt boundary returns `Left` with `recoverability.cancelled` (`RecoverabilityPipelineBehavior.cs:215-219`); the classification is `Unknown` when no attempt was recorded (a token cancelled before the first attempt, `RecoverabilityContext.cs:79`) and `Transient` after a failed attempt (set at `:132`), and neither is `Permanent`, so `HandleFailureAsync` (`:128-142`) goes on to call `ScheduleFirstDelayedRetryAsync` with the cancelled token, which either throws `OperationCanceledException` out of `Handle` (the filter at `:187` rethrows when the token is cancelled) or, with a scheduler that ignores the token, persists a delayed retry for a request the caller abandoned. (b) A cancellation during the back-off wait `Task.Delay(delay, cancellationToken)` (`:237`) throws `TaskCanceledException` out of `Handle` instead of returning the `Left` of (a). Through `IEncina.Send` that escaping exception does not crash the host: when the caller's token is cancelled the dispatcher converts it into a `Left` with `EncinaErrorCodes.RequestCancelled` (`Encina.RequestDispatcher.cs:146-161`), so the visible defect through `Send` is two different error codes for the same cancellation (`recoverability.cancelled` for (a), `RequestCancelled` for (b) and for the throwing-scheduler case of (a)), while a direct caller of `Handle` (a test, an outer behavior) sees the exception. (c) `HandlePermanentFailureAsync` skips the dead letter capture on cancellation (`:417`) but still runs `OnPermanentFailure` (`:423`). The only cancellation test (`RecoverabilityPipelineBehaviorTests.cs:291-311`) pre-cancels the token on a behavior without a scheduler and asserts only the `Left` of (a). Same family as #2090 (Send/Publish and a cancelled token), which covers the core dispatcher, not this behavior. Static reading, unexecuted.
7. **Minor** — `RecoverabilityOptions` is never validated and one public doc line is wrong. Nothing checks `ImmediateRetries >= 0`, `ImmediateRetryDelay >= 0`, `DelayedRetries` elements or `MaxJitterPercent` (`RecoverabilityOptions.cs:43-124`; the options are a plain singleton built in `RecoverabilityServiceCollectionExtensions.cs:59-62`, not `IOptions` with `ValidateOnStart`). A negative `ImmediateRetryDelay` makes `Task.Delay` throw `ArgumentOutOfRangeException` out of `Handle` (`RecoverabilityPipelineBehavior.cs:237`) only when jitter is off or `MaxJitterPercent <= 0`, because then `GetDelayWithJitter` returns the base delay unchanged (`:392-395`); with the defaults (jitter on) it clamps the jittered value with `Math.Max(0, jitteredTicks)` (`:399-400`), so a negative delay silently becomes a zero wait. Either way the invalid value is accepted without a message, in a pipeline that is otherwise `Either`-based; `UseExponentialBackoffForImmediateRetries` multiplies by `Math.Pow(2, attempt - 1)` and casts to `long` (`:383-384`), so a large `ImmediateRetries` produces multi-day waits or an overflowed cast. The XML doc says the delay is `ImmediateRetryDelay * 2^attempt` (`RecoverabilityOptions.cs:55`) but the code uses `2^(attempt - 1)` (`:383`), so the first retry waits the base delay, not twice it.
8. **Minor** — `DelayedRetryProcessor` exposes `ProcessingInterval` (default 30 s) and `BatchSize` (default 100) only as public settable properties on a hosted service the container constructs (`DelayedRetryProcessor.cs:43,:48`). `RecoverabilityOptions` has no corresponding property and `AddHostedService<DelayedRetryProcessor>()` (`RecoverabilityServiceCollectionExtensions.cs:77`, `MessagingServiceCollectionExtensions.cs:136`) sets none, so an application cannot change either without replacing the registration; the 30 s poll is also the floor of the first delayed retry's accuracy. The processor's other waits use the wall clock (`Task.Delay(ProcessingInterval, stoppingToken)` at `:106`) instead of a `TimeProvider`, and a zero or negative `ProcessingInterval` busy-loops or makes `Task.Delay` throw outside the loop's `try` (`:104-111` only catches `OperationCanceledException`), which faults the `BackgroundService` and stops the host. Compare the outbox, whose interval is an option (`OutboxOptions.cs:16`, `ProcessingInterval`).
9. **Minor** — Recoverability has no OpenTelemetry instrumentation and no health check, although the sibling patterns do (AGENTS.md §6 functions 2 and 4). `grep "class .*(Metrics|ActivitySource|HealthCheck)" src/Encina.Messaging` lists `OutboxActivitySource`, `InboxActivitySource`, `SagaActivitySource`, `SchedulingActivitySource`, `OutboxProcessorMetrics`, `SchedulingProcessorMetrics`, `DeadLetterMetrics`, and health checks for outbox, inbox, saga, scheduling and dead letters; none for recoverability. The behavior and processor only log (`RecoverabilityLog`, `DelayedRetryProcessorLog`, EventIds 2845-2871 and 5450-5452), so retry rates, permanent failures and a stuck delayed-retry backlog cannot be alarmed on. No Integrate/Defer/Not-applicable record exists for the 12 functions, and no open issue tracks it (`grep` over the open issues for Recoverability with metric, health, OpenTelemetry or ActivitySource: none).
10. **Minor** — Dead public API on the scheduler and store. `IDelayedRetryScheduler.CancelScheduledRetryAsync` (`IDelayedRetryScheduler.cs:48-50`, implemented at `DelayedRetryScheduler.cs:110-122`) has no caller in `src/` (`grep CancelScheduledRetryAsync src` finds the interface and the implementation only); it therefore also makes `IDelayedRetryStore.DeleteByContextIdAsync` (`:193`) a method that every persistent store of #594 must implement for no consumer, and it always returns `Unit` even when nothing was deleted. Likewise `RecoverabilityContext.TransitionToDelayedPhase` (`RecoverabilityContext.cs:167-170`), `RecoverabilityErrorCodes.CancelRetryFailed` and `RecoverabilityErrorCodes.Unknown` (`RecoverabilityPipelineBehavior.cs:491,:501`) have no use in `src/`. AGENTS.md §3: "Every line serves a current purpose". Remove them, or give the cancel path a real caller (a chain whose message succeeded elsewhere) before #594 multiplies the store surface by 13.

## Lessons for the pipeline
- When a decision record says a component is "replaceable through DI", grep the consumer's constructor for the interface before accepting it; here the interface was registered in two places and resolved in none inside its own package (finding 1).
- An exception filter `ex is not OperationCanceledException` equates "cancelled" with "the caller cancelled"; check every such filter against the sibling filter in the same package (`when (!token.IsCancellationRequested)`), and against what the classifier documents for `TaskCanceledException` (finding 2).
- For a feature that depends on a store with no implementation, read the tests that prove registration: every one supplied a stub, so the default registration was never built. Ask "what happens with the defaults and nothing else registered" (finding 3).
- A flag on a shared configuration class (`MessagingConfiguration`) is only honoured by the registration that reads it; grep each provider's `AddEncina*` for the flag, not only the shared helper (finding 4).
- Search the open issues once into a scratch file and query by file, type and symbol: #2105, #2204 and #2205 already covered three defects in this folder, and #1580 turned out to be stale against the current code.
