## Findings
1. **Blocker** — `src/Encina.Messaging/README.md:194`, section "5. Recoverability Pipeline", the configuration sample assigns `config.RecoverabilityOptions = new RecoverabilityOptions {...}`, but the property is get-only (`src/Encina.Messaging/MessagingConfiguration.cs:734`, `public RecoverabilityOptions RecoverabilityOptions { get; } = new();`), so the assignment does not compile; the settings must be set on the existing instance (`config.RecoverabilityOptions.ErrorClassifier = ...` at `:258` compiles because that property has a setter, `RecoverabilityOptions.cs:97`). Fix: set properties on `config.RecoverabilityOptions`. Related open issues, not repeated here: #1886 (OPEN) already tracks the non-existent `services.AddEncinaMessaging(...)` calls at `:18`, `:24`, `:191` and `:316`; #1990 (OPEN) already tracks the non-existent `_deadLetterQueue.SendAsync(failedMessage, ct)` at `:217` and the missing flow diagram of the section. The rest of the section matches the code: property names and types at `RecoverabilityOptions.cs:43-124` and `IErrorClassifier.Classify(EncinaError, Exception?)` at `IErrorClassifier.cs:24`.
2. **Major** — `src/Encina.Messaging/README.md:182-259` documents a default setup that cannot run and a flag two providers ignore, and says neither. Rule (a) point 2 against the code stage's findings 3 and 4. The sample at `:202` sets `EnableDelayedRetries = true` (also the default, `RecoverabilityOptions.cs:108`) and lists four delayed intervals, but no class in `src/` implements `IDelayedRetryStore`, and `DelayedRetryScheduler` requires one (code stage finding 3, `DelayedRetryScheduler.cs:43-48`); the section never tells the reader to supply a store or to call `AddEncinaDelayedRetryStore`. `:193` shows `config.UseRecoverability = true`, which is read only by `AddMessagingServices` (ADO.NET and Dapper); the EF Core and MongoDB registrations ignore it (code stage finding 4). A reader on those providers follows the page and gets no recoverability. Add a short "Requirements and provider support" paragraph or table (provider by flag) beside the sample. No open issue names this paragraph (#1886 and #1990 cover other lines of the section, see finding 1); related tracking: #594 (persistent store), not the README.
3. **Major** — `docs/architecture/adr/029-recoverability-error-classification.md:9` and `:13` state behavior the code does not have. `:9` says the behavior "had to be uniform across the Outbox, Inbox and transport consumers"; the code stage (Siblings audited) found that Outbox, Inbox and the transport consumers do not use `IErrorClassifier` at all (only `RecoverabilityPipelineBehavior`, the registration code and the Hangfire and Quartz adapters; the delayed-retry processor takes no `IErrorClassifier` either and only reads `marker.Classification`, `src/Encina.Messaging/Recoverability/DelayedRetryProcessor.cs:323`). `:13` says "applications extend or replace it through DI"; the behavior builds `options.ErrorClassifier ?? new DefaultErrorClassifier()` (`RecoverabilityPipelineBehavior.cs:70`) and never resolves the DI registration (code stage finding 1), so the replacement route that works is `RecoverabilityOptions.ErrorClassifier`. `:30` ("New exception types ... must be mapped in the classifier") is accurate. The ADR is "Accepted", so the fix is a superseding or amending note, not a silent edit (lesson #19). `docs/engineering/PROJECT-HISTORY.md:97` repeats the sentence as a history entry, and the "A3" row is `docs/engineering/PROJECT-HISTORY.md:721` (not the ADR index, which has 68 lines); that line only restates the three-category decision (transient, permanent or unknown; permanent to the dead-letter queue) and makes no claim about Outbox, Inbox or DI replacement, so neither history line needs a change unless the ADR is amended.
