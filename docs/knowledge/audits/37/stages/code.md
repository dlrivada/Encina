## Findings
1. **Major** — `src/Encina.Marten/Versioning/LambdaEventUpcaster.cs:45, :60` set `EventTypeName` to `typeof(TFrom).Name` (for example `OrderV1`), while Marten matches stored events by its own alias, `order_v1` for `OrderV1` (probe: the default `EventTypeName` of `EventUpcaster<OrderV1,OrderV2>` printed `order_v1`). With the override, the probe read the stored `OrderV1` back unchanged (`[EventTypeName overridden to 'OrderV1'] -> OrderV1`), and with Marten's default it returned `OrderV2`. So the inline form `options.EventVersioning.AddUpcaster<TFrom, TTo>(func)` (`EventVersioningOptions.cs:122-133`), the documented example at `EventVersioningOptions.cs:24-26` and `LambdaEventUpcaster.cs:18-19`, never upcasts unless the caller passes the alias as `eventTypeName`, and nothing says so. `EventUpcasterBase.cs:43` has the same two-name split: `SourceEventTypeName` (`typeof(TFrom).Name`) is the registry key, but Marten matches on the unoverridden `EventTypeName`; the doc at `IEventUpcaster.cs:21-24` ("should match the event type name stored in the database") is false for the default. The failure is silent: old events deserialize as the old type or are dropped by the aggregate's `Apply`. Fails: the issue's acceptance goal (events upcast transparently), known pattern "documented example that cannot work". Confirms the hypothesis #1914 left open ("likely, not proven"); the fix is a separate defect from the dead failure policy (use Marten's `EventTypeName` for both properties, or drop the override), and its regression test is an end-to-end read of an old stored event through the lambda registration (verifier: append `OrderV1` with a store without upcasters, read it back through `AddEncinaMarten` with `EventVersioning.Enabled = true` and `AddUpcaster<OrderV1, OrderV2>(...)`). Unexecuted through Encina's classes (hook block above); executed at the Marten level.
2. **Major** — `src/Encina.Marten/Versioning/ConfigureMartenEventVersioning.cs:75` hands an upcaster to Marten only `if (upcaster is MartenIEventUpcaster martenUpcaster)`; any other `IEventUpcaster` is dropped with no log, no exception and no error. `IEventUpcaster` and `IEventUpcaster<TFrom, TTo>` are public (`IEventUpcaster.cs:16, :59`), `IEventUpcaster<TFrom,TTo>`'s own remarks say "Implement this interface to define how old events should be transformed" (`:45-46`), and `EventVersioningOptions.AddUpcaster(IEventUpcaster)` (`:75-81`) and `AddUpcaster<TUpcaster>()` (`:60-65`) accept any implementation. A direct implementation is registered, counted in `VersioningLog.EventVersioningEnabled(_logger, upcasters.Count)` (`ConfigureMartenEventVersioning.cs:82`, "enabled with N upcasters") and never runs. Fails: fail-open silent skip (AGENTS.md section 3 spirit of "errors never swallowed"), public API that promises behavior it does not have. Fix direction (pre-1.0, no compatibility): either narrow the public contract to the Marten-backed types (make the interface non-implementable, or constrain `AddUpcaster` to `EventUpcaster`-derived types) or throw at `Configure` for an upcaster that cannot be wired. Static reading; the verifier can confirm with a 10-line implementer of `IEventUpcaster<OrderV1, OrderV2>` that does not derive from `EventUpcasterBase`.
3. **Major** — Chained upcasting (V1 to V2 to V3) does not work, and the code documents it as working. Probe (Marten 9.38.0): a stored `OrderV1` with `Upcast(V1ToV2)` and `Upcast(V2ToV3)` both registered was read back as `OrderV2`, not `OrderV3` (`[chain default 1->2 and 2->3] -> OrderV2`). Encina passes every upcaster straight to `options.Events.Upcast(martenUpcaster)` (`ConfigureMartenEventVersioning.cs:78`) and adds no chaining. Yet the `AddEventUpcaster` example registers exactly that shape (`ServiceCollectionExtensions.cs:292-293`: `OrderCreatedV1ToV2Upcaster` then `OrderCreatedV2ToV3Upcaster`), the issue asked for "upcasting (v1 to v2 to v3)" (record `Asked`), and the property tests for upcasting chains named in the commit message no longer exist (archivist scope). An application following the example applies `OrderV2` handlers to events stored as V1 while its aggregate expects V3. Fails: the issue's chain requirement, known pattern "documented example that cannot work". Remediation either composes chains in Encina (resolve V1 to the final type before calling `Upcast`, with a cycle and ambiguity check) or documents and enforces "one upcaster per stored type, direct to the latest" and corrects the example; decision for the maintainer, not pre-decided here. Executed at the Marten level; the verifier should confirm through `AddEncinaMarten`.
4. **Major** — `AddEventUpcaster<TUpcaster>()` is not registration-complete (AGENTS.md section 3, "Registration completeness"). `ServiceCollectionExtensions.cs:296-306` only does `services.AddSingleton<IEventUpcasterRegistrar>(new EventUpcasterRegistrar<TUpcaster>())`; the registry and `ConfigureMartenEventVersioning` that consume the registrar are registered only when `options.EventVersioning.Enabled` is true (`:73-77`, `:239-250`). Called without `Enabled = true` (or on its own, which the XML doc `:277-283` only hints at), it is accepted and never takes effect, with no error. It is also not idempotent: it uses `AddSingleton`, not `TryAddEnumerable`, so two calls for the same type register two registrars and the second `registry.Register<TUpcaster>()` throws `InvalidOperationException` ("An upcaster for event type ... is already registered", `EventUpcasterRegistry.cs:53-57`) from inside Marten's store construction, far from the cause; the same exception follows when the type is also added through `options.EventVersioning.AddUpcaster<T>()` or found by `ScanAssembly`. Sibling comparison: `AddProjection<,>` in the same file was fixed for exactly this (`:194-215`, "Registering a projection is opting in", `AddProjectionInfrastructure` is idempotent, `TryAddEnumerable`); the upcaster path was left behind. No DI test builds this with `ValidateOnBuild` and an upcaster registered without `Enabled`. Static reading.
5. **Minor** — `EventUpcasterRegistry.cs:201-211` `GetLoadableTypes` catches `ReflectionTypeLoadException` and returns the types that did load, with no log and no record of `ex.LoaderExceptions`. An upcaster class whose type failed to load is silently missing from `ScanAndRegister` (`:162-184`), so its old events are never upcast; `VersioningLog.ScanningAssemblyForUpcasters` and `FoundUpcastersInAssembly` (`VersioningLog.cs:30-40`) exist for this and are never called (#1914 counts them among the 9 dead messages, but does not mention this catch). The same method treats duplicates inconsistently: `Register` throws (`:53-57`) while `ScanAndRegister` uses `TryRegister` (`:177`) and silently drops a second upcaster for the same source type name, although `VersioningLog.DuplicateUpcasterRegistration` says "Existing upcaster will be used" (`VersioningLog.cs:24-28`) and is not called. Fails: errors swallowed (AGENTS.md section 3), known pattern "caught and ignored".
6. **Minor** — The registry's public lookup surface has no production reader: `GetUpcasterForEventType` (`EventUpcasterRegistry.cs:117`), `HasUpcasterFor` (`:141`) and `Count` (`:151`) are called nowhere in `src/` (Grep for `GetUpcasterForEventType|HasUpcasterFor` over `src` matches only their own definitions; `TryRegister` is called only at `:177`). The class remarks claim the registry "enables fast lookup during event deserialization" (`:11-12`); deserialization never consults it, Marten does the matching. The registry is used only for duplicate detection and enumeration. Fails: AGENTS.md section 3 ("every line serves a current purpose"), misleading XML doc (section 8). Also `Register(Type, factory)` and `AddUpcaster(Type)` (`EventUpcasterRegistry.cs:74-89`, `EventVersioningOptions.cs:94-107`) check only `IsAssignableFrom`; an abstract type or one without a public parameterless constructor passes validation and fails later with `MemberAccessException` or `MissingMethodException` from `Activator.CreateInstance(...)!` (`:85-86`) when Marten's store is built, while the XML doc promises only `ArgumentException` for the non-`IEventUpcaster` case.

## Lessons for the pipeline
- When an audit worktree forbids `#:project` references to `src/` for an `issue-auditor` (`guard-orchestrator-writes`), a Marten-only replica run by literal path still settles library-behavior questions (alias matching, chaining); the stage text should say so, and say that the end-to-end run through Encina's own classes goes to the verifier.
- For a wrapper over a library feature (Marten upcasters), probe the library with the wrapper's exact overrides before accepting an open "likely, not proven" hypothesis from an earlier issue; here it settled #1914's open question and also exposed that chaining does not exist.
- A document example in `ServiceCollectionExtensions.cs` XML docs (V1ToV2 then V2ToV3) was the cheapest pointer to a missing capability; read registration examples against the library's semantics, not only the types.
