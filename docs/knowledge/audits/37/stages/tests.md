## Findings
1. **Major** — Chained upcasting (V1 to V2 to V3) has no test in any flag, and the tests that once looked like chain proof were deleted. `src/Encina.Marten/ServiceCollectionExtensions.cs:292-293` documents registering `OrderCreatedV1ToV2Upcaster` and `OrderCreatedV2ToV3Upcaster` together, and the issue asked for "upcasting (v1 to v2 to v3)", but a Grep of `tests\` for `V2ToV3|ChainedUpcast|Chained` over the Marten folders finds nothing. Commit `957093c2` added `EventUpcasterBaseTests.ChainedUpcasting_WorksCorrectly` and `VersioningPropertyTests.ChainedUpcast_PreservesIdentity`; both only called the two typed `Upcast` methods by hand (`typedV2ToV3.Upcast(v2Event)`), never the registry or Marten, and consolidation commit `65826302` deleted them with no successor (`EventUpcasterBaseTests` and `VersioningPropertyTests` do not exist today; no `tests\Encina.PropertyTests` file mentions `Upcast`). The code stage (finding 3) showed with Marten 9.38.0 that a stored V1 event is read back as V2 when both upcasters are registered, so a test through the real path would fail today. The open umbrella #1915 holds an end-to-end test with five scenarios (item "End-to-end integration test for event upcasting on read") and none of them is a chain; its property flag is not proposed at all. Needed after the maintainer picks the chain decision recorded in the code stage: (a) an integration test in `tests\Encina.IntegrationTests\Infrastructure\Marten\Versioning\` (collection `Marten`) that appends a V1 event to a store built through `AddEncinaMarten` with `EventVersioning.Enabled = true` and both upcasters, reads it with `FetchStreamAsync` and asserts the V3 shape, or asserts the enforced "one direct upcaster per stored type" rule if that is the decision; (b) property tests (`Encina.PropertyTests`, FsCheck) for the chain invariant (identity fields preserved across any chain length) that instantiate the real registry, which also restores the property coverage the issue's commit introduced and gives the package a `property` key to gate (it has none). The test is derived from the code stage's probe and has not been run through Encina's classes.

## Lessons for the pipeline
- When an earlier delta audit of the same code (here #22 re-created as #37's subject) already filed a consolidated issue with measured per-file proposals (#1915), the useful tests-stage work is a tracker table that confirms each figure, followed by findings only for what no tracker holds: here the test-side counterparts of the code stage's defects, where the tracker's own test plan either skips the defect (no chain scenario) or would pin it as expected (skipped non-Marten upcaster, duplicate-registration throw).
- A green test that asserts the same wrong value as the code (`EventTypeName_MatchesSourceEventTypeName`) is the pattern to search first after a code-stage finding of "property X does not match the library's X": grep the test class for the property name and read each assertion against the library value the code stage measured.
- Search test doubles by base type, not by name: all eight upcaster doubles in the unit, guard and contract projects implement the interface directly, which is exactly the shape the production wiring ignores; one Grep for `: IEventUpcaster`, its fully qualified spelling `global::...IEventUpcaster` (`MartenServiceCollectionExtensionsGuardTests.cs:82`) and `EventUpcasterBase<` over `tests\` showed that no test of those flags builds a Marten-wired upcaster. Count a family of doubles with a pattern that matches both spellings and list each file once (the first version of this stage counted nine by counting the two contract lines under the wrong file).
- Tests deleted by a consolidation commit can be the only tests of a capability the code does not have (the hand-called `ChainedUpcasting_WorksCorrectly` never used the registry): for a deleted-test list in the archivist stage, read what each deleted test actually exercised before reading its absence as a regression gap.
