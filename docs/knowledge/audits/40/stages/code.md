## Findings

1. **Blocker** — `src/Encina.Polly/RateLimiting/AdaptiveRateLimiter.cs:181-197`, `:206-207`, `:235-236`, `:214-215`: the success and failure counters that drive the adaptive state machine are reset on every `TryAcquire` once the first window has elapsed, so the headline feature of #40 (detect an outage and auto-throttle) stops working 60 seconds (the default window) after the bucket is created. `CleanupExpiredTimestamps` computes `windowStart = now - WindowSizeSeconds` and, when `_windowStart < windowStart`, sets `_windowStart = windowStart` and zeroes `_successCount` and `_failureCount` (`:191-196`). `_windowStart` is then always exactly one window behind the last call, so on the next call (`now' > now`) the condition `_windowStart < now' - W` is true again, and the counters are zeroed on every acquire. `TryAcquire` runs the cleanup (`:127`) before `UpdateState` (`:128`), so `UpdateState` reads `totalRequests == 0` (`:206`) and the `Normal` branch (`:214-215`) and the `Recovering` re-throttle branch (`:235-236`) can never fire from sequential traffic. Only outcomes recorded between two consecutive acquires survive (in-flight completions under concurrency), and the error rate is computed over that tiny sample; with the default `MinimumThroughputForThrottling = 10` that needs at least 10 completions between two acquires. The counters are also not a sliding window (the class remarks at `:10` and the attribute remarks at `RateLimitAttribute.cs:9` promise one): they are a window that is re-anchored on each call. A second symptom of the same counters: when `CooldownSeconds < WindowSizeSeconds` (the tests use 30 against 60), the failures that caused the throttle are still counted when the state moves to `Recovering`, so the next acquire re-throttles at once (`:235-241`) and the limiter cannot ramp up until the window passes. Checks failed: the issue's own acceptance (outage detection and auto-throttle); known failure pattern "the test passes only because of how the fixture drives time". Why the tests do not see it: every transition test (`AdaptiveRateLimiterTests.cs:131-163`, `:260-292`, `:334-371`) either stays inside the first window or advances `FakeTimeProvider` by one big jump, and `FakeTimeProvider` does not move between the consecutive acquires of the loop, so `now' > now` is never true. Reproduction for the verifier (unexecuted): create the limiter with a `FakeTimeProvider`, advance 61 s, then run 20 iterations of `AcquireAsync("k", config)` + `RecordFailure("k")` with `Advance(1 ms)` between iterations and assert that `GetState("k")` becomes `Throttled` (expected by the documentation, fails by this reading). No open issue covers it (searched `AdaptiveRateLimiter`, `RateLimitingPipelineBehavior`, `RateLimitAttribute`, `IRateLimiter`: #704 distributed state, #740 tenants, #565 benchmarks, #728 telemetry; none mentions the counters). #197 (open, "Rate Limiting Pipeline Behavior") is partially related by name only: its body proposes a different, never-built design (`PermitLimit`, `services.AddEncinaRateLimiting(config => ...)`, ASP.NET Core rate limiting middleware) and says nothing about the adaptive counters, so it does not cover this finding.

## Lessons for the pipeline

- A state machine driven by counters needs the counter reset rule read next to the update order: here the reset sat in a helper called before the state update and re-anchored on every call, and the tests (one big `Advance` or no advance between calls) could never expose it. For adaptive or windowed logic, hand the verifier a reproduction with small time steps after the first window.
- A constant defined in `EncinaErrorCodes` and consumed by classifiers and adapters is worth a search for its producers; here the constant had three consumers and no producer.
- When the archivist records "nothing tracks it", search the open issues by every feature named in the claim (metrics, `AddEncinaRateLimiting`, circuit breaker), not only by the file names; and compare each hit with the issue's own body before presenting it as a tracker: #728 tracks metrics, #197 is a partially related different design, and #704 and #740 are adjacent items #40 never asked for.
- A boundary-value effect ("every request is denied") must be traced to the comparison that produces it: the denial at `AdaptiveRateLimiter.cs:134` needs a counted request, and a non-positive window empties the queue, so the real effect was the opposite.
