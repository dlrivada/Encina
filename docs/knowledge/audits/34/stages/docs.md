## Lessons for the pipeline

- A type-narrowing issue should have the docs stage search every page for the members used to read the changed type (`.Details`, `.Code`, `.Metadata`, `LeftValue`), not only the two READMEs the archivist named: the archivist's two `GetDetails()` snippets were correct, while the defects were in six other pages that use a member that does not exist.
- For an API read through extension methods on a record struct, a symbol search for `Details` passes because `ABACErrors` and many `*Errors` classes mention it in prose and comments; read `EncinaError.cs` for the public instance members first and compare each `error.<member>` in the docs against that short list.
- A sample that reads a dictionary key must be compared with the overload that the package actually calls (`RepositoryErrors.BulkInsertFailed` has two overloads with different keys); the key `Reason` exists in the codebase, which is why a key-name search passes.
- When an open issue describes a snippet by its first defect (#1416: a missing store method), search the issue body for each other member in the same snippet before calling the rest new; here the same snippet also carries `error.Code`/`error.Details`, and the right action is to extend the issue.
