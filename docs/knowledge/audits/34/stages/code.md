## Findings

1. **Major** — `src/Encina.GuardClauses/Guards.cs:362` (`TryValidateEmail`), `:501` (`TryValidatePattern`) and `:397` (`TryValidateUrl`) copy the rejected input itself into the error details (`["value"] = value`), and `:255, :287, :326` do the same for the numeric guards. The XML example at `Guards.cs:484` validates a phone number. The details bag is `IReadOnlyDictionary<string, object?>`, so it carries any object, which is the freedom #34 narrowed from `object?` to a dictionary without bounding what a value may be. The result is that a failed email or phone-number validation returns an `EncinaError` whose metadata holds the data subject's email address or phone number. This fails AUD-13 ("No `EncinaError` (its `Message`, its metadata or the exception it wraps) ... carries ... a direct identifier of a data subject"; #856; SPEC-002 REQ-034, REQ-062). The message text of the same errors does not carry the value (`Guards.cs:358, 497`), so the leak is only in the details, and nothing in production reads `GetDetails()` (see Informational), which is why it went unnoticed; any consumer that serializes details (the Verify converter already does, `EncinaErrorConverter.cs:42-46`) prints it. Fix: drop `value` from the email, URL and pattern details (keep `parameter`, `guard`, `stage`, `pattern`); for the numeric guards keep the value only if the maintainers decide numbers are never identifying, and record that decision.

2. **Minor** — `src/Encina/Results/EncinaErrors.cs:30` and `:96`: `EncinaErrors.Create` passes the caller's dictionary to `EncinaException`, which stores the same reference (`Details { get; } = details ?? Empty`) with no snapshot. `EncinaError` is documented as "Minimal immutable Encina error representation" (`src/Encina/Errors/EncinaError.cs:7`) and #34's title promised an `ImmutableDictionary`, but what ships is a type-level promise only: the producers pass mutable `Dictionary<string, object?>` instances (`Guards.cs:117`, `RequestIdentityErrors.cs:35`, `Encina.NotificationDispatcher.cs:186`), and a producer that keeps the reference can change an error after it was returned or while it is read from another thread. Nested values are worse: `ParallelWhenAllDispatchStrategy.cs:135-147` stores `List<Dictionary<string, object?>>` under `errors` and `List<string>` under `failed_handlers`, mutable through the "read-only" API. The same codebase snapshots its other bag: `RequestContext.cs:216-217, 243, 269-271` copies to `ImmutableDictionary` on the way in. Check failed: Class B drift from the decision's intent (immutable details) with no record that the shallow reference is accepted. Fix: `ToImmutableDictionary()` in the `EncinaException` constructor (or a documented, tested "the dictionary is not copied" contract), and `ImmutableList`/arrays for the nested values.

3. **Minor** — `src/Encina/Results/EncinaErrors.cs:158-165, 167-188` (and `PublicAPI.Unshipped.txt:209`): `GetMetadata()` is a public alias of `GetDetails()` ("`GetMetadata()` is now an alias for `GetDetails()`", issue #34 body), and `GetEncinaDetails()` / `GetEncinaMetadata()` are two more internal aliases, each commented "Internal method for compatibility" (`:167, :182, :186`). Neither internal alias has a caller in `src/`; all 12 call sites are in two unit-test files (search `GetEncinaDetails|GetEncinaMetadata` over `*.cs` in the worktree, excluding `artifacts/`: 14 matches, 2 of them the definitions): `GetEncinaDetails` is called 8 times, 7 in `tests/Encina.UnitTests/Core/EncinaTests.cs` (`:612, :613, :642, :652, :666, :680, :693`) and 1 in `tests/Encina.UnitTests/Dispatchers/Strategies/ParallelWhenAllDispatchStrategyTests.cs:291`, and `GetEncinaMetadata` is called 4 times, all in `EncinaTests.cs` (`:907, :948, :1031, :1052`). Four names for one operation, three of them aliases kept "for compatibility" in a pre-1.0 library. This fails AUD-18 and AGENTS.md §3 ("NEVER add ... compatibility aliases"). Fix: keep `GetDetails`, delete the other three, and move their five `src/Encina.Testing*` callers (`EitherAssertions.cs:325`, `EitherCollectionAssertions.cs:343`, `ScenarioResult.cs:232`, `HandlerSpecification.cs:464`, `StreamingShouldlyExtensions.cs:327`) and the 12 test call sites listed above to `GetDetails`. Also drop the dead `details ?? ImmutableDictionary...Empty` at `:155`: `Details` is never null (`:96`) and both match arms already return `Empty`.

4. **Minor** — `src/Encina/Sharding/Resharding/ReshardingOrchestrator.cs:222`, `Phases/CleaningUpPhase.cs:71`, `Phases/CopyingPhase.cs:71`, `Phases/ReplicatingPhase.cs:71`, `Phases/VerifyingPhase.cs:62`: each re-wraps a failed phase with `EncinaErrors.Create(code, message, error.MetadataException.MatchUnsafe(e => e, () => null!))`. `MetadataException` is the internal `EncinaException` carrier, whose `Message` is the inner error's `Message`. Passing it as the inner exception makes the new error's `Exception` property return that carrier (`EncinaError.cs:83-85`), so the inner error's message sits in the exception chain that callers may inspect or log. `EncinaErrorExtensions.GetCause` exists for exactly this (`EncinaErrors.cs:120-138`: "passing `EncinaError.Exception` ... would copy `EncinaError.Message` ... into the exception chain") and `Encina.cs:131` and `Encina.NotificationDispatcher.cs:132-135` use it. The wrapper also drops the inner error's code and details (the outer carrier gets no details, `EncinaErrors.cs:30`), so the resharding error cannot say which inner code failed. Checks failed: AGENTS.md §3 `EncinaError.Message` never reaches logs or plaintext (as an exception-chain leak) and the #1319 pattern the code already fixed elsewhere. Whether a resharding inner message can hold personal data is not shown by the code (these are shard-copy errors), hence Minor. Fix: pass `error.GetCause()` (and put the inner code in the new error's details).

5. **Minor** — `src/Encina.Compliance.GDPR/GDPRErrors.cs:107`, `src/Encina.Compliance.AIAct/AIActErrors.cs:215` and `src/Encina/Dispatchers/Strategies/ParallelWhenAllDispatchStrategy.cs:139` copy `innerError.Message` / `e.Error.Message` into the details bag (`["innerError"]`, `["message"]`), and the first two also interpolate it into the new error's own message (`GDPRErrors.cs:101`, `AIActErrors.cs:210`). The details already hold the inner code in the third site (`:138`), so the message is redundant there. This widens where `EncinaError.Message` can surface: any consumer that serializes details (Verify snapshots, a future ProblemDetails mapper) emits inner messages from registry lookups and compliance validators, which AGENTS.md §3 and AUD-13 say must not reach plaintext. Fix: store the inner code (`GetEncinaCode()`) instead of the message in all three details bags and build the outer message without the inner one.

## Informational (not findings)

- Nothing in production code reads `GetDetails()`/`GetMetadata()`: the search `GetDetails\(\)|GetMetadata\(\)|GetEncinaDetails|GetEncinaMetadata` over `src/**/*.cs` matches only the Testing packages and the definitions. The details bag is write-only outside test tooling today, so findings 1 and 5 are latent leaks, not live ones; an ASP.NET `ProblemDetails` or Azure Functions mapper that adds details later would activate them. Whether details should reach HTTP responses at all is a design question for the maintainer, not decided by #34.
- The shipped type is `IReadOnlyDictionary<string, object?>`, not the `ImmutableDictionary` of the title (already in the archivist's record); `object?` values remain by design.
- `GetCode()` returns `None` for errors not built by `EncinaErrors.Create` (`EncinaErrors.cs:109-118`) while the internal `GetEncinaCode()` returns the exception type name or `"Encina.unknown"` (`:168-180`); the two disagree on the same error. Harmless for tags (both are code-or-type, never the message) but a trap for callers choosing between them.
- `userId` / `tenantId` values in details (`src/Encina.Security/SecurityErrors.cs:55, 80, 108, 131`, `Encina.Compliance.NIS2/NIS2Errors.cs:146`, `Encina.Security.Audit/ReadAuditErrors.cs:118`, `Encina.Messaging.Encryption/MessageEncryptionErrors.cs:151`) are opaque identifiers by convention; if an application uses an email as `userId`, they become direct identifiers. Not raised as a finding because the code does not decide the identifier format.
- Duplicate check: one `gh issue list --state open --limit 1000 --json number,title,labels` into the scratchpad (`scratchpad\open34.json`) returned exactly 1000 issues, so the list may have been truncated at the cap. Title search for Guards, GuardClauses, GetMetadata, GetDetails, details, EncinaError, Resharding, innerError and Metadata found no issue on the details bag of `EncinaError`, on `Guards` putting the validated value into details, or on the resharding re-wrap. Related but different: #1797 and #1134 (Left-to-throw and `ex.Message` into `EncinaError.Message`), #1788/#1591 (`EncinaError.Message` into Activity tags), #2043 (Guards property-flag coverage).

## Lessons for the pipeline

- A type-narrowing issue ("object? to a dictionary") is not finished at the signature: the code stage should walk the producers of the narrowed bag and ask what may enter it, because the real defect here (the validated email stored in details) was in a package the diff never touched.
- When the archivist records that an issue created an alias ("`GetMetadata()` is now an alias for `GetDetails()`"), run AUD-18 against it directly: the alias was the decision, and it is still there.
- "No production reader" is a useful severity input: it shows a leak is latent. State it beside the finding instead of silently downgrading, so the remediation drafter knows the trigger (a future ProblemDetails mapper).
- A search with `--limit 1000` that returns exactly 1000 rows is truncated; say so beside every "no duplicate" claim.
