## Summary

Today the coverage report can say whether a file's flag meets its justified target (`IsBelowTarget`, `.github/scripts/coverage-report.cs:356-357`) but nothing says **how far** it is, and nothing aggregates the distance. The headline number, "obligations met / obligations" (`coverage-report.cs:926-928`), counts covered (line, applicable flag) pairs and never looks at a target; per-file targets are printed as a table of `met`/`below` (`:987-998`) and stop there. `docs/testing/coverage-measurement-methodology.md:187` states it: "Per-file targets are not yet shown on the coverage dashboard or in the docref index."

The maintainer's wording in the issue is the requirement: "Guard at 20% says nothing by itself; Guard at 20% against a target of 21% or of 50% says exactly how close we are to the demanding and realistic goal we set."

**What this plan implements** (the issue's main proposal; every fork is a Design Choice below, decided by the maintainer on 2026-10-21, see Maintainer Decisions):

1. **Per-(file, flag) attainment** for every pair that has a per-file target in `.github/coverage-manifest/*.json`: measured %, target %, gap in percentage points (`max(0, target - measured)`), capped attainment (`min(measured / target, 1)`), and the line counts behind them. Emitted in the "Per-file targets" table of `encina-coverage-report.md`, in `encina-coverage-summary.json` (which `publish-coverage.yml` publishes verbatim as `latest.json`), and rendered on the Pages dashboard, sortable by gap.
2. **Aggregates** next to the unchanged obligations figure: the targets-met ratio, the line-weighted attainment (`sum(min(covered, target x total)) / sum(target x total)`), the mean gap, and the number of pairs the aggregates leave out (no data, zero target).
3. **History**: the aggregates are appended to each `history.json` entry so the dashboard can draw the trend.
4. **Methodology**: `coverage-measurement-methodology.md` explains obligations versus attainment (and loses the "not yet shown" sentence).

**Code facts the plan rests on** (all at `origin/main`):

- The per-pair row already exists: `BuildFileTargetRows` (`coverage-report.cs:334-352`) produces `FileTargetRow(Package, File, Flag, Target, Measured)` (`:1501`), with `Measured` unrounded and `null` without data (`MeasureFileFlag`, `:323-330`). The new work adds the line counts to that row and a pure summary over a list of rows.
- A flag is measured **straight from its own Cobertura data, whatever the file's `defaultTests` say** (`:332-333`); a line covered under one flag never counts for another (AGENTS.md section 9). The attainment view keeps that.
- `encina-coverage-summary.json` (`:1025-1078`) has `overall`, `packages[]` and `untrackedPackages`. `publish-coverage.yml:109` copies it to `overlay/coverage/data/latest.json` unchanged and `:127-128` only adds `runId`; so anything written into the summary reaches `latest.json` **without a workflow change**.
- `coverage-history.cs:42-49` builds each history entry from `latest.json`'s `overall` (`coverage`, `obligations`, `met`, `runId`, `perFlag`) and keeps the last 100 (`:85-86`); `coverage-recalculate.cs:170-203` updates only named keys of an existing entry, so an extra key survives a recalculation.
- The dashboard (`docs/coverage/app.js`) fetches `data/latest.json` (`:5`, `:141`), `data/cited-by.json` (`:158`) and `data/history.json` (`:729`). It never reads `docref-index.json`. Its "File Detail" panel (`:478-505`) reads `pkg.files`, which the summary does not emit (`packages[]` has no `files`, `coverage-report.cs:1036-1066`): that panel cannot open against live data. Follow-up issue file written (see the report).
- `docref-index.json` (`BuildDocRefIndex`, `:1125-1208`) already carries `perFlag[flag].target`, but it is the **package-level** target (`:1136`, `:1158`), not the per-file one. SPEC-001 REQ-002 fixes that schema, and `cov-docs-render.cs:81-82` validates citation fields against it.
- The script has **no test project**: `git grep` finds no reference to `.github/scripts` under `tests/`. Its test path is the in-script `--self-test` (`RunSelfTest`, `coverage-report.cs:364-445`), run in `ci.yml:619-622` (step "Check coverage-report self-test and per-file justifications"). Design Choice 5 decides how the new computation is tested.
- `artifacts/board/refresh-dash.ps1` (named in the issue) is **not tracked**: `artifacts/` is git-ignored (`.gitignore:26`) and `git ls-files` finds no such script. The implementation PR cannot change it; the plan fixes the `latest.json` contract it will read and lists the board update as an orchestrator task (Next Steps).
- Size of the problem at `origin/main` on 2026-10-21 (counts of manifest entries, not coverage figures): 56 manifests carry per-file targets, 441 files, 967 (file, flag) pairs, 173 of them with target 0. Re-count before coding with the snippet in Phase 1 task 1.

**Affected paths**: `.github/scripts/coverage-report.cs`, `.github/scripts/coverage-history.cs`, `.github/scripts/coverage-recalculate.cs` (only if Design Choice 8 picks backfill), `docs/coverage/index.html`, `docs/coverage/app.js`, `docs/coverage/app.css`, `docs/testing/coverage-measurement-methodology.md`. **No `src/` file, no package, no manifest**; the only workflow edit under the recommended options is the added `ci.yml` command.

**Provider category**: none (build tooling).

**Hot spots**: the publish path needs no change to `.github/workflows/*`, but the recommended options need **one added command in `ci.yml`** (the history self-test, see "Workflow and script changes"). Changes that **would** be needed under a non-recommended option are listed in "Workflow and script changes" under Prerequisites & Dependencies, so the orchestrator can decide before a brief is written.

## Design Choices

Nine forks were found in the code; each has at least two valid options with a concrete winning scenario. Every Chosen Option was decided by the maintainer on 2026-10-21 (see Maintainer Decisions at the end of this file); the issue's `needs-decision` label predates that decision. Options eliminated by a rule are named in the rationale of the choice they would belong to.

<details>
<summary><strong>1. Scope of the attainment view — per-file plus aggregates, or something smaller</strong></summary>

**Class**: Dilemma

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A — The issue's main proposal: per-(file, flag) metrics in the report, `latest.json` and the dashboard, plus aggregates, plus history** | Answers "how close, and where" at every level; the 967 pairs are already computed by `BuildFileTargetRows`, so the per-pair data is nearly free; the report, the dashboard and the history agree | Largest change (script, three JSON shapes, dashboard card, history); `latest.json` grows by the per-file rows |
| **B — Alternative A of the issue: keep only the obligations percentage and colour it** | No new data, no new schema, no dashboard work | Does not tell how close a file is to its target (a 52% obligations rate is good or bad depending on targets); the existing headline colours use fixed cut-offs that the methodology calls historical (`coverage-measurement-methodology.md`, "Known limitations", item 8) |
| **C — Alternative B of the issue: aggregates only, no per-file breakdown** | Smallest payload; one tile and one trend line | Hides which files are far from target, so it cannot prioritise work; the per-file table already exists in the report, so dropping it from the dashboard loses information the team already has |
| **D — Aggregates and a per-package roll-up in `latest.json` and the dashboard; per-file rows only in the Markdown report** | Keeps `latest.json` small (no 967-row array); package rows can show their own attainment; files stay visible in the CI job summary | The dashboard cannot sort files by gap, which is the issue's acceptance criterion; two places show different granularity |

### Chosen Option: **A — Per-file and aggregate attainment everywhere** (decided by the maintainer, 2026-10-21)

### Rationale

- A wins when the goal is prioritisation: "which file/flag is furthest from its justified target" is only answerable per file and sortable on the dashboard (acceptance: "Pages dashboard displays per-file metrics (sortable by gap) and aggregates").
- B wins only if the maintainer wants no new surface at all (for example while #1651 is expected to change what the dashboard shows); it fails the issue's own motivation.
- C wins when payload size matters more than actionability; the size cost of A is small (see Design Choice 7).
- D wins if the 967-row array is judged too heavy for `latest.json` and the sort-by-gap criterion is relaxed; it is the fallback if Design Choice 7 is answered "separate file" and the extra file is refused.
- The Markdown report keeps the per-file table in every option.

<summary><strong>2. Aggregate headline metric — pair-count ratio, line-weighted attainment, or both</strong></summary>

**Class**: Dilemma

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A — Pair-count "targets met" ratio only (`met pairs / pairs`)** | Trivially explained and reproducible by hand; one number agrees with the existing "below target: N" console line (`coverage-report.cs:960`); each (file, flag) obligation weighs the same, which matches "every file has a justified target" | A 5-line file weighs as much as a 2,000-line one; a pair at 99% of its target counts as fully unmet |
| **B — Line-weighted attainment only (`sum(min(covered, t x total)) / sum(t x total)`)** | Large files weigh more; partial progress counts, so it moves smoothly as tests are added | Harder to explain; saturates per pair (surplus coverage in one file cannot offset a deficit in another, by the `min`); needs a line count for every pair (see Design Choice 3) |
| **C — Both, with the pair-count ratio as the headline and the line-weighted value beside it, plus the mean gap in points and the total lines still to cover** | The ratio answers "how many of our commitments are met", the weighted value answers "how much of the work is done", the gap numbers answer "how far"; matches the issue's list (ratio, gap statistics, line-weighted) | Four numbers on a tile can read as noise; more fields to keep stable in `latest.json` and `history.json` |
| **D — Exactly the issue's set: ratio, total gap (sum of positive gaps in points), mean gap, line-weighted** | Literal to the issue | The sum of percentage-point gaps across files of different sizes has no unit anyone can act on ("1,240 points"); lines still to cover is the actionable total |

Eliminated by rule: a project-wide attainment **target** or a fixed colour threshold for the new headline (for example "green at 80%"): AGENTS.md section 9 states "There is no project-wide percentage" (`AGENTS.md:124`), and #1656 tracks the one project-wide line the dashboard still hard-codes (`docs/coverage/app.js:817-830`). The new tiles show numbers and trends, with no colour derived from a project-wide cut-off.

### Chosen Option: **C — Ratio headline, line-weighted beside it, mean gap in points and lines still to cover** (decided by the maintainer, 2026-10-21)

### Rationale

- A alone wins when the audience is people who want a checklist ("how many commitments are met"); B alone wins for a progress bar over the whole effort; D is the issue's literal text and wins if the maintainer wants the exact set it listed.
- C keeps the issue's ratio, line-weighted value and mean gap, and replaces the total gap in points by the total **lines to cover** (`max(0, ceil(t x total) - covered)` per pair) because points do not add up across files. This is the only deviation from the issue's text; D restores it.
- All four values are derived from the same row list, so the cost of C over A is a few lines of arithmetic and four JSON fields.
- The obligations figure stays as it is and is shown next to the new tiles; the methodology explains the difference (Phase 7).

</details>

<summary><strong>3. How a flag with no data counts in the aggregates</strong></summary>

**Class**: Dilemma

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A — Count it as 0% measured: the pair stays in every denominator, with attainment 0 and gap = target; its line count comes from the file's line set under the other flags (as `allLineNumbers` does, `coverage-report.cs:869-875`); when no flag has any data for the file, the pair counts in the pair-count aggregates and is listed as unweighted** | Same reading as `IsBelowTarget` (no data is below any target above 0, `:354-357`, AGENTS.md section 9); denominators stay the manifest's pairs, so history is comparable run to run; a partial CI run (a whole flag's reports missing) shows up as a drop instead of a flattering silence | A broken or partial run lowers the headline sharply and temporarily; the borrowed line count is an assumption (Cobertura lists every instrumented line, so line counts normally match across flags) |
| **B — Exclude it from every aggregate and report "N pairs without data" beside them** | Aggregates describe only what was measured; a run missing the integration reports does not crater the ratio | The headline can rise when data disappears (a flag that failed to upload stops hurting); denominators move run to run, so the trend is not comparable; contradicts the "below target" status of the same pair in the table |
| **C — Count it as unmet in the pair-count ratio, exclude it from the line-weighted value (no reliable line count)** | No assumption about line counts; the ratio is stable | Two aggregates use different pair sets, which is hard to explain |

Eliminated by rule: filling a no-data flag with the **covered lines of another flag** (so that the file looks tested): AGENTS.md section 9 ("a line covered by one flag does not count for another"). Option A borrows only the **number of lines**, never their coverage.

### Chosen Option: **A — Count as 0% measured; borrow the line count, never the coverage** (decided by the maintainer, 2026-10-21)

### Rationale

- A wins when a partial run must be visible and the trend must be comparable (the weekly CI Full on `main` is the source, `publish-coverage.yml`); B wins when someone wants to read the attainment of one special run in isolation (for example a local run of a single flag, `AGENTS.md` section 9 measurement recipe), where most flags are legitimately absent.
- That B scenario is covered under A by the per-flag filter in the dashboard table and by the `noData` count shown beside the tiles (it is a separate field, not hidden in the ratio).
- `ci-full.yml` already fails the job when every entry of `docref-index.json` has `noData` (`ci-full.yml:493-496`), so a total collection failure never reaches the dashboard; A only has to behave sensibly for partial ones.
- Orchestrator rule check (2026-10-21): option B is eliminated by rule, because AGENTS.md section 9 and `IsBelowTarget` (`coverage-report.cs:354-357`) read a flag with no data as below any target above 0. Option C is no better than A in any scenario, because A already lists the pairs that have no line count as unweighted. A is not a dilemma for the maintainer; it is recorded as decided by rule.

</details>

<summary><strong>4. Pairs whose target is 0 — inside or outside the aggregates</strong></summary>

**Class**: Dilemma

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A — Include them: a target of 0 is met (as `IsBelowTarget` says, `:356-357`), attainment 1, weight 0 in the line-weighted value** | Consistent with the table and with the console line "Per-file targets: N" which counts every row (`:960`); denominators stay stable when someone raises a 0 to a real target | 173 of 967 pairs at the time of writing are zero targets (each justified, "a 0 only with a reason", AGENTS.md section 9), so the pair-count ratio is inflated by pairs that carry no demand |
| **B — Exclude them from the aggregates and show "of which zero-target: N" beside the tiles** | The ratio and the mean gap describe only the demanding targets; raising a 0 to 30 visibly adds a pair to the denominator | Denominator jumps when a 0 becomes a target (history needs the `pairs` field to explain the jump); a zero target stops being counted anywhere in the headline |

### Chosen Option: **B — Exclude from aggregates, show the count beside them** (decided by the maintainer, 2026-10-21)

### Rationale

- B wins when the question is "how close are we to the targets that ask something of us"; A wins when the question is "what fraction of all recorded commitments is met", for example if a reviewer wants zero targets to be a visible cost.
- The pair stays in the per-file table with status `met` and target `0%` (its justification explains why), so nothing is hidden; only the headline arithmetic skips it.
- The weighted value is unaffected either way (weight `t x total` is 0 for `t = 0`); only the pair-count ratio and the mean gap differ.

- A wins when the change must reuse the existing test path (the `ci.yml:621` command already exists) in the same style as the code it extends; C wins when the maintainer wants the end-to-end reproducibility criterion proven by a run of the real script, accepting one `ci.yml` step (listed under "Workflow and script changes"); B wins only if the script is ever turned into a project.

- Orchestrator rule check (2026-10-21): option B is eliminated by rule (AGENTS.md section 2: scripts are file-based apps with no `.csproj`). The dilemma left for the maintainer is A versus C.

<details>
<summary><strong>9. How the dashboard presents the per-file rows</strong></summary>

**Class**: Dilemma

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A — A new "Target attainment" card under the overall card: four tiles (ratio, weighted, mean gap, lines to cover), a trend toggle, and one flat table of all pairs with package, flag and status filters, a text search and column sorting (default: gap descending)** | Answers "which file is furthest" in one view; sorting by gap is the acceptance criterion; reuses the card/table styling of `index.html` | A 967-row table needs a simple page size or a "top N" default to stay light; one more block in a 906-line `app.js` |
| **B — Only a per-package drill-down: clicking a package row opens its `fileTargets` (replacing the File Detail panel that cannot open today, `app.js:478-505`)** | Small; reuses an existing interaction and its place in the page | No cross-package sorting by gap, so "the worst 20 files" is not answerable; the existing click handler is currently dead code, so its behaviour is untested |
| **C — Both: the card of A, and the drill-down of B** | Overview and drill-down | Most code; two ways to reach the same rows |

### Chosen Option: **A — One card with tiles, trend toggle and a filterable, sortable table** (decided by the maintainer, 2026-10-21)

### Rationale
