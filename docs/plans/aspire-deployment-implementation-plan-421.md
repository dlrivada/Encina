# Implementation Plan: `Encina.Aspire.Deployment` — processor settings for the Docker Compose and Kubernetes publishers

> **Issue**: [#421](https://github.com/dlrivada/Encina/issues/421)
> **Type**: Feature
> **Complexity**: High (7 phases, 4 pull requests of 13, 10, 15 and 7 files)
> **Estimated Scope**: ~600 lines of production code + ~1,300 lines of tests
> **Family**: Aspire (aspire-1): #416 hosting package (not referenced by this package), #417 service defaults, #419 dashboard commands, #440 umbrella; the Azure Container Apps half of the issue is #2698 (outside 1.0, SPEC-000 section 6) and reuses the processor model defined here; the family continues in #424, #425, #382, #387 and #391. **This plan owns the processor model (`EncinaProcessorOptions`, `EncinaProcessorAnnotation`, `WithEncinaProcessor`) and the Compose and Kubernetes customizations.**

---

## Summary

The issue asks for deployment publishers that generate Kubernetes and Docker Compose manifests for the Encina processors, with ConfigMaps, Secrets, Helm, HPA and KEDA. State of `origin/main` (`ec129cae5`), verified by reading and by reading the Aspire 13.6.5 packages:

| Item of the issue | Today | Owner of what remains |
|-------------------|-------|-----------------------|
| `Encina.Aspire.Deployment` | Missing | **This plan** |
| Docker Compose publisher | `Aspire.Hosting.Docker` 13.6.5 is stable and ships `AddDockerComposeEnvironment`, `PublishAsDockerComposeService(Action<DockerComposeServiceResource, Service>)`; its `Service` node has `Deploy`, `Restart`, `StopGracePeriod`, `Healthcheck`, `Volumes`, `Environment`, `Labels` | **This plan** customizes it for processors |
| Kubernetes publisher | `Aspire.Hosting.Kubernetes` exists on NuGet only as `13.6.5-preview.1.26559.7` (no stable release); it ships `AddKubernetesEnvironment`, `WithHelm`, `PublishAsKubernetesService(Action<KubernetesResource>)`; `KubernetesResource` exposes `Workload`, `ConfigMap`, `Secret`, `Service`, `AdditionalResources`; typed `Deployment`, `HorizontalPodAutoscaler`, `ConfigMap`, `Secret` and probes exist | **This plan** customizes it (Design Choice 1 for the layout) |
| ConfigMaps and Secrets for configuration and connection strings | Generated by Aspire's publishers from the environment, parameters and references | Nothing to build; Encina writes no secret (Design Choice 6) |
| Helm chart generation | `WithHelm` of the Kubernetes package | Aspire's |
| "Aspir8" | A third-party tool that predates the publishers above | Not used (Design Choice 6) |
| HPA | `HorizontalPodAutoscaler` type exists (`MinReplicas`, `MaxReplicas`, `TargetCPUUtilizationPercentage`) | **This plan**, gated (Design Choice 3) |
| KEDA `ScaledObject` | No type in the Kubernetes package; the custom resource would have to be written as raw YAML | Design Choice 2 (not delivered; spike issue file) |
| Azure Container Apps | Out of 1.0 | #2698 |
| Separate processor deployments (`outbox-processor` image) | There is no standalone processor executable: processors are `BackgroundService` instances hosted in the application (`OutboxProcessorBase` in `src/Encina.Messaging/Outbox/OutboxProcessorBase.cs`, `ScheduledMessageProcessor`, the provider `OutboxProcessor` classes); `src/Encina.Cli` is a tool, not a host | Design Choice 4 |

Differences from the issue text: the sketched `WithEncinaManifests(...)`, `GenerateOutboxProcessorDeployment()` and `WithEncinaServices(...)` assume Encina generates manifests for processor images. What a solution actually has is its own project (or projects) that run the processors, and the Aspire publisher already turns each project into a Deployment or a Compose service; what Encina adds is what the publisher cannot know: that this resource runs background processors and must therefore not be scaled out or killed abruptly by default.

**Delivered**: `EncinaProcessorOptions` (`Replicas` = 1, `AllowHorizontalScaling` = false, `ShutdownGracePeriod`, `Autoscaling` min, max and CPU target); `WithEncinaProcessor<T>(this IResourceBuilder<T>, Action<EncinaProcessorOptions>? configure = null)` for a compute resource, which records an `EncinaProcessorAnnotation`; the Docker Compose customization (restart policy, stop grace period, replica count) in `Encina.Aspire.Deployment`; the Kubernetes customization (replicas, `Recreate` strategy, termination grace period, probes on the probe paths of #454, a gated HPA) in `Encina.Aspire.Deployment.Kubernetes`.

**Not in scope**: KEDA (Design Choice 2), Azure Container Apps (#2698), Terraform and Pulumi, generating images, secrets and connection strings (Aspire's), the application-side probes (#454).

**Affected packages**: `Encina.Aspire.Deployment` (new), `Encina.Aspire.Deployment.Kubernetes` (new). They reference no Encina application package: the AppHost does not load application code.

**Provider category**: none (Cloud category of AGENTS.md section 5: the local, emulator-free targets Docker Compose and Kubernetes; the Azure leg is #2698 and the GCP leg is post-1.0 by SPEC-000 section 6).

## Design Choices

<details>
<summary><strong>1. Package layout and the preview Kubernetes dependency (Dilemma D1)</strong></summary>

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A) `Encina.Aspire.Deployment` (model and Docker Compose, stable dependency) plus `Encina.Aspire.Deployment.Kubernetes` (preview dependency)** | The stable package never depends on a preview; Compose users do not pull Kubernetes types; the Kubernetes package can be dropped or stabilized on its own | Two packages; the issue names one |
| **B) One package with both, referencing `Aspire.Hosting.Kubernetes` 13.6.5-preview.1** | The issue's layout | A stable package may not have a prerelease dependency (NuGet NU5104, an error here with `TreatWarningsAsErrors`); it packs today only because `Directory.Build.props` gives every package the `dev` version suffix, and breaks at the first stable version |
| **C) Docker Compose only until the Kubernetes package is stable** | No preview dependency at all | The issue's headline target is missing |

### Chosen Option: **A — two packages** (recommended, pending the maintainer)

### Rationale

A wins because it keeps the stable surface clean and lets the Kubernetes half follow Aspire's preview on its own schedule. C wins if the maintainer prefers to wait for a stable `Aspire.Hosting.Kubernetes` before any Encina code depends on it (for example if the preview API changes before the 1.0 release). B wins only while every Encina package is a prerelease. The processor model lives in the stable package, so the Kubernetes package and #2698 both reuse it.

**Class:** Dilemma

</details>

<details>
<summary><strong>2. Backlog-driven scaling with KEDA (Dilemma D2)</strong></summary>

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A) Not delivered: CPU-based HPA only (Design Choice 3); a `[SPIKE]` issue file investigates KEDA** | No raw custom-resource YAML; no scaler per database provider; ships with typed Aspire resources | The issue's "KEDA scaling rule configuration" acceptance item is not met |
| **B) A KEDA `ScaledObject` written as an additional resource, with one scaler query per database family on the pending outbox count (SQL Server, PostgreSQL, MySQL, MongoDB)** | Scales on what matters: the backlog | The Kubernetes package has no KEDA type (raw YAML, no schema check); a scaler needs the connection string and a provider-specific query for each of the 10 providers; scaling out before #713 and #715 land (distributed locks) risks double processing |

### Chosen Option: **A — HPA only, KEDA as a spike** (recommended, pending the maintainer)

### Rationale

A wins because scaling processors out is unsafe until the lock integration (#713, #715, open and planned) exists, and backlog-driven scaling needs the provider matrix. B wins when backlog-driven scaling is the reason the maintainer wants this feature and accepts a second plan. The spike issue file (`artifacts/issues/aspire-keda-processor-scaling-spike.md`) frames it.

**Class:** Dilemma

</details>

<details>
<summary><strong>3. Whether a processor may be scaled out by default (Dilemma D3)</strong></summary>

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A) Safe by default: `Replicas = 1`, Kubernetes strategy `Recreate`, no HPA unless `AllowHorizontalScaling = true` is set explicitly (the option documents that the processors must take distributed locks first)** | Two pods can never process the same outbox rows during a rollout or a scale-out; the operator opts in knowingly | A rollout has a short gap with no processor running |
| **B) Scale by default (`RollingUpdate`, HPA on CPU)** | No gap; matches generic Aspire output | Until #713 and #715 land, two replicas can process the same rows; a failure mode that only shows under load |

### Chosen Option: **A — safe by default** (recommended, pending the maintainer)

### Rationale

A wins today because the lock integration is open and planned (#713, #715) and `OutboxProcessorBase` has no cross-instance guard in `src/`. B wins once those land and processors are safe to run in several replicas; the default is then one constant. A processor annotation on a resource that also serves HTTP traffic keeps scaling off unless the operator sets the option, which is documented.

**Class:** Dilemma

</details>

<details>
<summary><strong>4. A processor is a resource of the solution, not an image Encina ships</strong></summary>

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A) `WithEncinaProcessor` marks the solution's own project or container as the one running the processors, and the publishers customize its output** | Matches how Encina works: processors are hosted services of the application | A solution that wants a dedicated worker writes a worker project (one line of host code) |
| **B) Encina ships a generic processor host executable and image** | A ready-made `outbox-processor` image as in the issue sketch | A new product: the host would need the application's stores, options and handlers, which only the application can supply |

### Chosen Option: **A — mark the solution's resource**

### Rationale

The processors are `BackgroundService` classes registered by the application's own `AddEncina*` calls (`OutboxProcessorBase : BackgroundService`, `ScheduledMessageProcessor : BackgroundService`, the per-provider `OutboxProcessor`); there is no host project among the packages of `src/` (`Encina.Cli` is a tool).

**Class:** Settled
**Settled by:** `src/Encina.Messaging/Outbox/OutboxProcessorBase.cs` and `src/Encina.Messaging/Scheduling/ScheduledMessageProcessor.cs` (both `BackgroundService`); the package list of `src/` (no worker host).

</details>

<details>
<summary><strong>5. Default shutdown grace period (Dilemma D5)</strong></summary>

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A) 60 seconds, twice the .NET host default `HostOptions.ShutdownTimeout` of 30 seconds, so a processor can finish its batch and release its work before the platform kills it** | Room for a batch in flight; one named default | A slow rollout |
| **B) The platform defaults (Kubernetes `terminationGracePeriodSeconds` is 30 seconds and Compose `stop_grace_period` is 10 seconds when unset)** | No change to the platform | A batch that takes longer than the host's own timeout is cut, sooner in Compose |
| **C) No default; the operator must set it** | Nothing hidden | Every resource needs a line |

### Chosen Option: **A — 60 seconds** (recommended, pending the maintainer)

### Rationale

A wins because a killed processor leaves rows claimed and delays them until the retry. B wins when rollout speed matters more. The value is a property of `EncinaProcessorOptions` and the same in Compose and Kubernetes.

**Class:** Dilemma

</details>

<details>
<summary><strong>6. Use Aspire's publishers; write no secrets and no YAML of our own</strong></summary>

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A) Customize the output of `Aspire.Hosting.Docker` and `Aspire.Hosting.Kubernetes` through `PublishAsDockerComposeService` and `PublishAsKubernetesService`; Aspire's publishers keep producing the ConfigMap, Secret, Helm chart and connection strings** | Follows the platform; typed model; one source of truth | Bound to the publishers' API (a preview for Kubernetes) |
| **B) Generate our own YAML (or use Aspir8) and add it next to the publisher's output** | Independent of the preview | Two writers of the same files; our YAML would hold connection strings, so Encina would handle secrets |

### Chosen Option: **A — customize Aspire's publishers**

### Rationale

The issue's technical considerations say to "follow Aspire publisher extension patterns" and that the manifests are verified locally; the extension points above exist. Encina adds no ConfigMap or Secret: options with a connection string are not part of this feature, and nothing in the processor options holds a secret.

**Class:** Settled
**Settled by:** issue #421 Technical Considerations (follow Aspire publisher extension patterns; no cloud deployment); `Aspire.Hosting.Docker.xml` and `Aspire.Hosting.Kubernetes.xml` 13.6.5 (`PublishAsDockerComposeService`, `PublishAsKubernetesService`, `WithHelm`).

</details>

## Implementation Phases

### Phase 1: Package and processor model (pull request 1)

> **Goal**: A solution can mark a resource as an Encina processor host with validated settings.

<details>
<summary>Tasks</summary>

1. `src/Encina.Aspire.Deployment/Encina.Aspire.Deployment.csproj` (`PackageId`, XML docs, `PackageReference Aspire.Hosting.Docker`, no reference to any Encina package, `InternalsVisibleTo` for the unit, guard and contract test projects, PublicAPI files), the pin `Aspire.Hosting.Docker` 13.6.5 next to the other Aspire pins of `Directory.Packages.props` (the `Aspire.Hosting` pin is added by #416), and the project entry in `Encina.slnx`.
2. `EncinaProcessorOptions.cs` (public sealed): `Replicas` (default 1, 1 to 100), `AllowHorizontalScaling` (default false), `ShutdownGracePeriod` (default 60 seconds, 1 second to 1 hour), `Autoscaling` (`int MinReplicas`, `int MaxReplicas`, `int TargetCpuUtilizationPercentage`, null by default); an internal `Validate()` that rejects a `Replicas` above 1 or any `Autoscaling` when `AllowHorizontalScaling` is false, `MaxReplicas < MinReplicas`, and out-of-range values, with an `InvalidOperationException` naming the property.
3. `EncinaProcessorAnnotation.cs` (public sealed, `IResourceAnnotation`) carrying the validated options; `EncinaProcessorBuilderExtensions.WithEncinaProcessor<T>(this IResourceBuilder<T> builder, Action<EncinaProcessorOptions>? configure = null) where T : IComputeResource` runs the action, validates, adds the annotation; a second call on the same resource throws `InvalidOperationException` (the precedent of `WithEncinaTestSupport`).
4. Tests: unit (defaults, every validation rule, annotation present, second call throws), guard, the project references of `Encina.UnitTests.csproj` and `Encina.GuardTests.csproj`, `PublicAPI.Unshipped.txt` and `.github/coverage-manifest/Encina.Aspire.Deployment.json` through `mechanical-fixer`.
