## Findings
1. **Blocker** — Hand-typed contract-test counts on six feature pages: `docs/features/cdc-debezium.md:372` ("Contract Tests | ~24"), `docs/features/cdc-sharding.md:389` ("Contract Tests | 14"), `docs/features/cdc.md:781` ("~47 contract tests"), `docs/features/gdpr-compliance.md:300` ("ContractTests | 16"), `docs/features/id-generation.md:279` ("Contract Tests | 43"), `docs/features/lawful-basis-validation.md:489` ("Contract Tests | 26"). The check that fails is encina-docs section 3 rule 2 ("Counts that no dashboard measures (number of packages, providers, tests) go in a sentence with the date and the command that produced them, or are left out"): none of the six lines carries a date, a command or a citation. Evidence that they drift: `id-generation.md:279` says 43 while `Select-String '^\s*\[(Fact|Theory)'` over `tests/Encina.ContractTests/IdGeneration` finds 19 attributes in the one file `IdGeneratorContractTests.cs` (theory expansion and tests elsewhere were not measured, so the true count is not established here); `cdc-sharding.md:389` says 14 and the same search over `tests/Encina.ContractTests/Cdc/Sharding` finds 14 today, so that one is right now but equally unsourced. The `~` figures (`cdc-debezium.md:372`, `cdc.md:781`) were not measured.
2. **Major** — `docs/releases/RELEASE-PROCESS.md:17-23` (checklist item 1, "`main` is green") and `:151-157` (Step 3 verification): the release how-to does not stop a release with failing tests. Item 1 checks only the latest `ci.yml` runs (`--workflow ci.yml`), which is the PR-tier workflow that runs contract tests only when path filters select them (#1721) and never runs the full suite; it does not ask for a successful `ci-full.yml` run on the commit to tag. Step 3 then verifies the package only after the tag push (`:151-155`, "confirm the package was pushed"), by when `pack` has already published. Because `pack` runs under `always() && needs.build.result == 'success'` (`.github/workflows/ci-full.yml`, code stage finding 1, which `RELEASE-PROCESS.md:142` itself quotes), a red contract suite on the tag run still publishes; the page's only mitigation is the trailing clause "check every job of the run, not only the push" (`:142`), a check performed after the publish. The reader is never told to confirm a green `CI Full` for the commit before `git tag` (Step 2, `:115-127`). Fix direction for the page: add a pre-tag item "the latest `ci-full.yml` run on the commit to tag is `success` for every `test-*` job" with its `gh run list --workflow ci-full.yml` command, until the workflow itself is gated (code stage finding 1).
3. **Minor** — `docs/releases/RELEASE-PROCESS.md:142`: "by its condition it is not skipped when a test job fails; that was never exercised". It was exercised: `gh run view 35652357800` (CI Full, `workflow_dispatch`, 2026-09-21) reports 17 failed test jobs (`test-property`, `test-guard`, `test-unit`, `test-integration`, four `test-ef-providers` shards) while `pack` concluded `success` (`test-contract` was `success`). That run was not a tag push, so the publish step was skipped, but the condition is proven to let `pack` run on red tests. The sentence understates the risk and sends the reader to check a hypothetical; it should cite the run.

## Lessons for the pipeline
- When the code stage finds a CI gate bug, the docs stage should read the release or runbook page that tells a human how to rely on that gate, and check whether the page's pre-conditions cover the hole (here, a green `ci.yml` is not a green `ci-full.yml`).
- Feature pages carry per-test-type count tables (`Contract Tests | N`); a docs stage about a test project should grep all of `docs/features/` for them, since each is a hand-typed count with no date or command.
