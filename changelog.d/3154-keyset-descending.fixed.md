- Keyset pagination follows the sort direction of the keyset property in every provider's query builder (the ADO.NET and Dapper `SpecificationSqlBuilder` for SqlServer, PostgreSQL and MySQL, the EF Core `SpecificationEvaluator` and the MongoDB `SpecificationFilterBuilder`): when the specification orders the keyset property descending, the next page is filtered with `<` instead of `>`, so it holds the smaller keys instead of the wrong rows or none. The direction comes from the new `IsKeysetDescending` extension property on `IQuerySpecification<T>`. `ListAsync` on the ADO.NET, Dapper and MongoDB repositories does not apply a query specification's keyset yet (#3151) (#3154).
- Those builders and the EF Core evaluator now require the keyset to be a property access and the primary ordering (`ApplyOrderBy` or `ApplyOrderByDescending`). A computed keyset, a specification ordered by another property first, or a keyset property only in a `ThenBy`/`ThenByDescending` is rejected with `NotSupportedException` on every page, the first one included, instead of silently skipping or repeating rows; EF Core's `ListAsync` returns it as an error. A specification with no ordering keeps the ascending filter (#3154).
