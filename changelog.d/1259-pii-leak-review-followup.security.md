- **Shared health checks now omit the exception message and object from unhandled-exception results** (#1259). `Encina.Messaging.Health.EncinaHealthCheck` is the base class for every Encina health check (including third-party provider packages like Kafka, MQTT, RabbitMQ, Marten); when an unhandled exception occurs, it now returns only the exception's type name in the unhealthy result text, never the `Exception.Message` (which could carry personal data) or the exception object itself (which would be propagated unchanged by `Encina.AspNetCore`'s `EncinaHealthCheckAdapter` into `Microsoft.Extensions.Diagnostics.HealthChecks.HealthCheckResult`, outside this library's control).

- **Hangfire job failure exceptions no longer leak personal data through their cause chain** (#1259). When `EncinaJobFailedException` or `EncinaJobPermanentFailureException` is built from an `EncinaError` that carries a cause, the `InnerException` is now a sanitized `InvalidOperationException` whose message contains only the cause's type name (e.g. "Cause type: System.Argument­NullException"), never the cause's own `Exception.Message` (which may carry data-subject identifiers). Hangfire persists the full exception chain in its storage; the sanitization prevents personal data from leaking into Hangfire's job history.

- **Dead letter orchestrator now agrees on request type between storage and content serialization** (#1259). `DeadLetterOrchestrator.AddAsync<TRequest>` previously computed `RequestType` from the compile-time generic parameter `typeof(TRequest)` while serializing the `RequestContent` using the actual request's runtime type; when a caller passed a derived type through a base type or interface parameter, the two disagreed and `IDeadLetterManager.ReplayAsync` could fail to resolve the type or deserialize into the wrong type. Both now use the runtime type via `request.GetType()`.

- **Dead letter manager replay results and logs now omit the error message** (#1259). When `IDeadLetterManager.ReplayRequestAsync` completes a replay (whether success or failure), the returned `ReplayResult.ErrorMessage` and the logged failure message now contain only the error code and outcome, never `EncinaError.Message`, which for compliance modules (Consent, DSR) can embed a data-subject id. This matches the rule already applied elsewhere in dead-letter handling.
