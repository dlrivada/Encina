- **`Encina.Hangfire` job adapters now fail the job on a handler `Left` result, separating cancellation, permanent and transient failures** (#1152). `HangfireRequestJobAdapter.ExecuteAsync` and `HangfireNotificationJobAdapter.PublishAsync` used to log a handler failure and return normally, so Hangfire recorded the job as succeeded and never retried it. They now throw: `OperationCanceledException` when the error is an Encina `*.cancelled` code and the job's token is cancelled (Hangfire treats the job as interrupted, not failed); the new `EncinaJobPermanentFailureException` when `Encina.Messaging.Recoverability.IErrorClassifier` (the registered one, or `DefaultErrorClassifier`) classifies the error as permanent — validation, not found, missing handler, missing or withdrawn consent, an active processing restriction, and so on; and the new `EncinaJobFailedException` for transient or unclassified failures. Both exceptions carry only the error code in their `Message` and `Data` (never `EncinaError.Message`, which may contain data-subject ids that Hangfire persists), and the causing exception as `InnerException`. The new `EncinaAutomaticRetry.Create` / `JobFilterCollection.UseEncinaAutomaticRetry` configure Hangfire's `AutomaticRetryAttribute` with `ExceptOn = [EncinaJobPermanentFailureException]`, so permanent failures go straight to Failed while transient ones are retried. Breaking: `ExecuteAsync` now returns `Task<TResponse>` instead of `Task<Either<EncinaError, TResponse>>`, and both adapters take an optional `IErrorClassifier`.

- **`Encina.Quartz.QuartzNotificationJob` no longer discards a failed publish** (#1152). It ignored the `Either` returned by `IEncina.Publish`, so a failed notification was recorded as a successful run. Both Quartz jobs now throw `OperationCanceledException` for a cancelled job and otherwise a `JobExecutionException` with `RefireImmediately = false`, whose message carries only the error code and whose `Data` carries the error code and the `IErrorClassifier` classification under the new `EncinaJobFailureData.ErrorCodeKey` / `ErrorClassificationKey` keys, for job listeners that reschedule transient failures. `QuartzRequestJob` no longer copies `EncinaError.Message` into the exception message.

- **`DefaultErrorClassifier` now classifies by error code as well as by exception and message** (#1152). Codes such as `encina.handler.missing`, `consent.missing`, `consent.withdrawn` or `dsr.restriction_active` are permanent and `encina.timeout` or `encina.ratelimit.exceeded` are transient, instead of falling through to `Unknown` (treated as transient) because their messages carry none of the known words. The new `EncinaErrorExtensions.GetCause` returns the exception that caused an error without the internal carrier whose message is the error message itself.
