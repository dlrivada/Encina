- Request and stream pipelines are now built from a cached per-pipeline order: steps run by `PipelineStage`, then `Order`, and registration order only breaks ties between behaviors that declare the same stage and order (a behavior that declares no stage runs in `Application`, in registration order; built-in behaviors declare their stages in a later phase of #2184). Pre-, post-, error- and post-commit processors are now steps of the pipeline: they are placed by stage and order (default `Application`, ordered by type name, never by registration order), a pre-processor `Left` aborts before the inner steps, a post-processor runs only when the inner pipeline succeeded and post-processors of one stage run in the reverse of their order because each wraps the inner steps, and a step type registered twice is collapsed to one (#2184, phase 2). At equal stage and order the processor kinds nest pre-processor (outermost), error processor, post-processor, post-commit processor, then behaviors; the type name only breaks ties inside one kind, so an error processor also observes a post-processor's `Left`. A module behavior class registered for two modules keeps both adapters. A stage override recorded after the first pipeline was built is rejected with an `InvalidOperationException`. A cancelled post-commit processor returns the new error code `EncinaErrorCodes.PostCommitProcessorCancelled`.
