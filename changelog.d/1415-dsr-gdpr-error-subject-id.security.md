- **DSR and Crypto-Shredding error messages no longer leak data subject identifiers** (#1415). Fixes the same data-exposure pattern as #1350/#1417, this time in `Encina.Compliance.DataSubjectRights` (`DSRErrors`: RestrictionActive, ErasureFailed, ExportFailed, ExemptionApplies, SubjectNotFound, LocatorFailed, RectificationFailed, ObjectionRejected) and `Encina.Marten.GDPR` (`CryptoShreddingErrors`: SubjectForgotten, EncryptionFailed, DecryptionFailed, KeyRotationFailed, InvalidSubjectId, KeyAlreadyExists).

  These factories used to interpolate the raw data subject id directly into both `EncinaError.Message` and the error's structured `details` dictionary (worse than the Consent case, which only leaked through Message). The fix replaces the subject id in Message with the non-identifying text "the specified data subject" (preserving reason/field/purpose/format context that was already present), and removes the subject id entirely from `details` (no `subjectId` key remains).

  Factory signatures and error codes are unchanged. The `IDataPortabilityExporter` and `IDataErasureExecutor` XML doc examples in `Encina.Compliance.DataSubjectRights`, and the `Encina.Marten.GDPR` README examples, were also corrected to read `GetCode()` instead of `Message`, so the copy-pasteable examples don't reintroduce the leak.
