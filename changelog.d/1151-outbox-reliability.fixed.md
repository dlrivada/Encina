- **Outbox processors no longer mark failed deliveries as processed** (#1151). `IEncina.Publish` reports a failing handler as a `Left` and never throws, but every outbox processor discarded that result and marked the message processed, so a failed delivery was never retried. A `Left` now follows the same failure path as a thrown exception, and the delivery rules live in one place for the seven ADO.NET, Dapper and EF Core processors.
- **Outbox retries back off instead of retrying at a fixed delay** (#1150). The next retry was always `BaseRetryDelay` after the failure; it is now `min(BaseRetryDelay * 2^RetryCount, MaxRetryDelay)`, reduced by up to `RetryJitterRatio`. A very large `MaxRetryDelay` no longer overflows: the next retry time saturates at `DateTime.MaxValue`.
- **Exhausted outbox messages are no longer dropped silently** (#1150). The failure that uses up `MaxRetries` is logged at Error level with EventId 2958 and the `outbox.max_retries_exceeded` code, and the message stays in the outbox, unprocessed, where it can be counted and requeued. The MongoDB, Bogus (`OutboxMessageFaker`) and FsCheck (`ArbitraryOutboxMessage`) `IsDeadLettered` implementations no longer report processed messages as dead-lettered.
- **Outbox store results are checked** (#1151). The processor ignored the result of `IOutboxStore.SaveChangesAsync`, so an EF Core batch whose save failed was still reported as processed; it now logs EventId 2960, skips the batch summary and counts the batch as `outcome="unsaved"`. A `Left` from `MarkAsProcessedAsync` or `MarkAsFailedAsync` is logged with EventId 2961 and counted as `outcome="store_error"`, never as delivered or exhausted, and EventId 2958 is written only when the exhausted state was actually recorded.
- **Stopping the host no longer consumes outbox retries** (#1151). A delivery interrupted by cancellation (the processor's token, or `encina.notification.cancelled` from the dispatcher) stops the batch without marking the message failed (EventId 2962). The Dapper outbox stores for SQL Server, PostgreSQL and MySQL now pass the `CancellationToken` to every query.
- **Requeueing outbox messages by id is all-or-nothing on SQL Server and MySQL** (#1150). The ADO.NET and Dapper stores send the identifiers in chunks of 1,000; the chunks now run in one transaction, so a failure part-way leaves no message requeued.
- **The outbox health check reports the real backlog** (#1150). It sampled one message, so it could never reach the 100 and 1000 pending thresholds; it now uses an exact pending count, and `OutboxOrchestrator.GetPendingCountAsync` no longer loads every pending message to count them.
