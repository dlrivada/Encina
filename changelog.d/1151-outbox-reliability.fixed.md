- **Outbox processors no longer mark failed deliveries as processed** (#1151). `IEncina.Publish` reports a failing handler as a `Left` and never throws, but every outbox processor discarded that result and marked the message processed, so a failed delivery was never retried. A `Left` now follows the same failure path as a thrown exception. `OutboxOrchestrator.ProcessPendingMessagesAsync` takes a callback returning `ValueTask<Either<EncinaError, Unit>>`, and the seven ADO.NET, Dapper and EF Core processors now derive from the new `OutboxProcessorBase` in `Encina.Messaging`, so the delivery rules live in one place. The EF Core processor now honours `OutboxOptions.EnableProcessor` and logs with the shared `MessagingLog` EventIds; its own EventIds 3026-3034 are retired.
- **Outbox retries use capped exponential backoff with jitter, and exhausted messages are observable** (#1150). The next retry was always `BaseRetryDelay` after the failure; it is now `min(BaseRetryDelay * 2^RetryCount, MaxRetryDelay)`, reduced by up to `RetryJitterRatio` (new options, defaults 10 minutes and 0.2), computed by the new `OutboxRetryBackoff`. The failure that uses up `MaxRetries` is logged at Error level with EventId 2958 and the `outbox.max_retries_exceeded` code, and counted in `encina.outbox.processor.messages_total{outcome="exhausted"}`; before, the message was dropped from processing silently.
