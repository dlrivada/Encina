- Fixed about 30 call sites that resolved an unregistered `IRequestContext` from DI and always got `null`. They now read the ambient context through `IRequestContextAccessor` (registered by `AddEncina()` and by every messaging/repository provider package), matching the pattern introduced by #1147. Affected: repository and sharding registrations in `Encina.ADO.*`, `Encina.Dapper.*` and `Encina.MongoDB`; `Encina.Security.ABAC`'s `PersistentPolicyAdministrationPoint`; `Encina.Security.Secrets`'s `AuditedSecretReaderDecorator`, `AuditedSecretWriterDecorator` and `AuditedSecretRotatorDecorator`; and `Encina.Compliance.NIS2`'s `DefaultNIS2ComplianceValidator`.
- Fixed `SagaRunner` and `RoutingSlipRunner` (`Encina.Messaging`), which failed to build from DI in every ADO.NET and Dapper package whenever `UseSagas`/`UseRoutingSlips` was enabled because they required an unregistered `IRequestContext`; both now depend on `IRequestContextAccessor` and resolve the current context (or a fresh, tenant-less one) at the start of each run.
- `IRequestContextAccessor` is now also registered by `Encina.MongoDB`, `Encina.EntityFrameworkCore` (both the pattern-configuring overload and the no-pattern `AddEncinaEntityFrameworkCore<TDbContext>()` overload used by the repository-only setup) and every ADO.NET/Dapper/MongoDB sharding extension package, so a host that wires only one of these provider packages (without the core `AddEncina()`) still resolves the accessor instead of silently getting a null request context.
