- **Non-string data subject ids (`Guid`, integer ids, strongly-typed ids) are now resolved correctly instead of falling back to the authenticated caller, and a missing subject fails closed** (#1149). `Encina.Compliance.DataSubjectRights.DefaultDataSubjectIdExtractor`, the explicit `[RestrictProcessing(SubjectIdProperty = ...)]` path of `ProcessingRestrictionPipelineBehavior`, and `Encina.Compliance.Consent.ConsentRequiredPipelineBehavior` only recognized `string`-typed subject-id properties; a matching property of any other type (e.g. a `Guid PatientId`) was silently ignored and the subject fell back to `IRequestContext.UserId` — the authenticated caller — instead of the real data subject. All three now share one conversion: `string`, `Guid` (`"D"` format), integer types, strongly-typed ids implementing `IFormattable`, and wrappers (record struct, record class or struct) exposing a public `Value` property of one of those types, which is unwrapped first even when the wrapper also implements `IFormattable` (so a `PatientId(Guid.Empty)` is a missing subject; an `IFormattable` id that formats as an all-zero Guid is missing too); the compiler-generated record `ToString()` and `ValueType.ToString()` are never used. `null`, `Guid.Empty` and an empty string mean "subject missing" (numeric `0` is a valid id); any other type is a configuration error and throws `InvalidOperationException`. The fallback to the caller only happens when no `SubjectIdProperty` is configured and the request has no matching property. Breaking: an explicitly configured `[RestrictProcessing(SubjectIdProperty = ...)]` or `[RequireConsent(SubjectIdProperty = ...)]` that names no public instance property of the request now throws `InvalidOperationException` (configuration error) in `ProcessingRestrictionPipelineBehavior`, `DefaultDataSubjectIdExtractor` and `ConsentRequiredPipelineBehavior`, instead of falling back to other properties, the registered extractor or `IRequestContext.UserId`.

  A `[RestrictProcessing]` request whose subject cannot be resolved now fails closed with the new `DSRErrors.SubjectIdMissingCode` (`dsr.subject_id_missing`) in `Block` mode (a warning in `Warn` mode) instead of silently skipping the restriction check, consistent with consent enforcement; set the new `DataSubjectRightsOptions.FailClosedOnMissingSubjectId` to `false` to keep skipping. Requests that only carry `[ProcessesPersonalData]` or `[ProcessingActivity]` still skip the check when no subject is found. `Encina.Compliance.GDPR`'s `DefaultLawfulBasisSubjectIdExtractor` never inspects request properties and needed no change.
