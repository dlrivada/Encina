- **Retention enforcement now completes the record lifecycle** (#1142). Each expired record moves `Active → Expired` before erasure and `→ Deleted` only after a successful erasure. The results of `EraseAsync`, `MarkExpiredAsync` and `MarkDeletedAsync` are checked: a failure (including an erasure that reports failed fields) is logged and counted in `RecordsFailedTotal`, never as a deletion. `GetExpiredRecordsAsync` also returns `Expired` records, so a record whose erasure or deletion failed is retried on the next cycle, while `Deleted` records are never selected again and their entities are not erased twice. Without a registered `IDataErasureExecutor` nothing is erased and no `DataDeleted` event is recorded: the record stays `Expired`, is counted as failed and a warning (EventId 8519) is logged once per cycle. A cancellation that does not come from the service's stopping token (for example an HTTP timeout inside erasure) fails only the record being processed and the cycle continues.
- **Retention enforcement fails closed when the legal-hold lookup fails** (#1143). If `ILegalHoldService.HasActiveHoldsAsync` returns an error, the record is skipped without erasure, logged (EventId 8586) and counted as failed, and the next cycle retries it. An exception from the lookup is treated the same way, and holds are re-checked right before erasure, so a hold placed after the first check still prevents erasure and moves the record to `UnderLegalHold`.
- **Encina.Compliance.Retention takes time from `TimeProvider`** (#1146). `RetentionRecordAggregate` decides between `Active` and `Expired` after a hold release from the release event's `OccurredAtUtc`, so replaying the stream is deterministic; `RetentionEnforcementService` and `RetentionValidationPipelineBehavior` accept an optional `TimeProvider` (defaulting to `TimeProvider.System`) for the expiry alert window and the logged expiry.
