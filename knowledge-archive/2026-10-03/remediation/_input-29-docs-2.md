`docs/releases/RELEASE-PROCESS.md:17-23` (checklist item 1, "`main` is green") and `:151-157` (Step 3 verification): the release how-to does not stop a release with failing tests. Item 1 checks only `--workflow ci.yml`. `ci.yml` does run on push to `main` and `workflow_dispatch` (`ci.yml:3-8`) with the same test projects and shards as `ci-full.yml`, but each test job is gated by a path filter (`ci.yml:124`, `:185`, `:259`; `|| github.event_name == 'workflow_dispatch'` is the only bypass), so a green `ci.yml` on `main` can mean the test jobs were skipped (#1721). The page never asks for a successful `ci-full.yml` run on the commit to tag (Step 2, `:115-127`), and Step 3 verifies the package only after the tag push (`:151-155`), by when `pack` has already published. `pack` runs under `always() && needs.build.result == 'success'` (`ci-full.yml` lines 532-541, code stage finding 1, which `RELEASE-PROCESS.md:142` itself quotes), so a red suite on the tag run still publishes; the page's only mitigation is the clause "check every job of the run, not only the push" (`:142`), performed after the publish. Fix direction for the page: add a pre-tag item requiring the latest `ci-full.yml` run on the commit to tag to be `success` for every `test-*` job, with its `gh run list --workflow ci-full.yml` command, until the workflow is gated (code stage finding 1).
