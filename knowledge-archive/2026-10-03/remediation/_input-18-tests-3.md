`Encina.MQTT/MQTTMessagePublisher.cs` is only 33.6% unit-line-covered (49/146); every uncovered line (verified from the cobertura report: 107-162, 184-313) is exactly the `SubscribeAsync`/topic-pattern-subscribe method and the internal `MqttSubscription<TMessage>`/`MqttPatternSubscription<TMessage>` classes' own `Dispose`/unsubscribe logic (`MQTTMessagePublisherTests.cs:299-342` has only null-argument tests for `SubscribeAsync`/`SubscribePatternAsync`). Per code.md's sibling audit, MQTT is one of only 3 of the 10 transports (with `Redis.PubSub` and `InMemory`) that actually implements subscribe — the one capability code.md's finding 3 says the other 5 (RabbitMQ, Kafka, NATS, AzureServiceBus, AmazonSQS) are missing entirely, and that AGENTS.md §5's Transports row requires every provider to support ("subscription management"). The capability that is supposed to be MQTT's point of difference from the 5 non-compliant siblings is itself the one thing no test in `MQTTMessagePublisherTests.cs`/`MQTTMessagePublisherExtendedTests.cs` exercises — a subscribe-then-receive-a-message-then-dispose path is untested, so a regression in unsubscribe cleanup or double-dispose would pass CI silently.
