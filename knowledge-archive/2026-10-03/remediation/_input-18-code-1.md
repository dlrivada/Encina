Five transport packages dispose their DI-singleton client from a scoped publisher: `src/Encina.NATS/NATSMessagePublisher.cs:14,191-194` (`DisposeAsync` awaits `_connection.DisposeAsync()`), `src/Encina.RabbitMQ/RabbitMQMessagePublisher.cs:13,158-162` (closes `_channel` and `_connection`), `src/Encina.MQTT/MQTTMessagePublisher.cs:14,165-173` (`_client.Dispose()` at :172), `src/Encina.AzureServiceBus/AzureServiceBusMessagePublisher.cs:13,201-204` (`DisposeAsync` awaits `_client.DisposeAsync()`; `_client` is the constructor-injected `ServiceBusClient`, :15,26,34) and `src/Encina.Kafka/KafkaMessagePublisher.cs:13,196-200` (`Dispose()` calls `_producer.Flush(TimeSpan.FromSeconds(10))` then `_producer.Dispose()`; `_producer` is the constructor-injected `IProducer<string, byte[]>`, :15,26,34). In every case the disposed object is a DI singleton (`src/Encina.NATS/ServiceCollectionExtensions.cs:42` `TryAddSingleton<INatsConnection>`; `src/Encina.RabbitMQ/ServiceCollectionExtensions.cs:42,56` `TryAddSingleton` for `IConnection` and `IChannel`; `src/Encina.MQTT/ServiceCollectionExtensions.cs:43` `TryAddSingleton<IMqttClient>`; `src/Encina.AzureServiceBus/ServiceCollectionExtensions.cs:47-48` `TryAddSingleton` of `ServiceBusClient`; `src/Encina.Kafka/ServiceCollectionExtensions.cs:42-59` `TryAddSingleton` of the `ProducerBuilder<string, byte[]>(...).Build()` producer) while the publisher that wraps and disposes it is registered `TryAddScoped` (NATS `:61`, RabbitMQ `:62`, MQTT `:72`, AzureServiceBus `:50`, Kafka `:61`). The .NET DI container disposes every disposable service it created when the owning scope ends, so the first time a consumer resolves the publisher inside a scope that later ends (an ASP.NET Core request scope, `IServiceScopeFactory.CreateScope()` in a handler, a background-job scope) the shared singleton connection/channel/client/producer is closed for the rest of the application's lifetime, and every later publish on that transport fails until the app restarts. This is a scope-vs-singleton lifetime defect that `ValidateOnBuild`/`ValidateScopes` do not catch (they catch captive dependencies, not premature disposal of a longer-lived dependency by a shorter-lived owner) and it fails the AGENTS.md §3 registration-completeness expectation that an `AddEncina*` registration is safe to build and use in any composition. Kafka additionally blocks the disposing thread for up to 10 seconds in a synchronous `Flush` inside a container-invoked `Dispose()`. Fix per package: register the publisher as a singleton (none of the five holds per-request state) or remove the publisher's `Dispose`/`DisposeAsync` so only the container's singleton-disposal path owns the connection. Only `Encina.AmazonSQS` (and the non-broker transports listed under Siblings audited) is unaffected.
