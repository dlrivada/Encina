## Outcome (audited, from today's code — verified, not from the pre-draft)

Issue #11 was delivered exactly as scoped: the Dec 23, 2025 fix correctly adopted the `Option<Exception>` pattern and the two named property tests passed afterward. That specific test file no longer exists, however, and the underlying behavior it protected has since drifted:

1. **2025-12-29**, commit `d7b7b8ac` ("Add unit tests for domain modeling components") deleted the entire file `ValidationPipelineBehaviorPropertyTests.cs` (462 lines) as an incidental side effect unrelated to its own stated purpose. No replacement was added in that commit.
2. **2026-01-09**, commit `20038395` (issue #507) added a new file with the same package-relative role, `ValidationInvariantProperties.cs`, but it tests `IValidationProvider` invariants (null args, idempotency, DI registration) — it does **not** exercise `error.Exception` / `ValidationException` aggregation at all.
3. **2026-01-16**, test consolidation (`65826302`) moved that file to today's location, `tests/Encina.PropertyTests/Validation/FluentValidation/ValidationInvariantProperties.cs`. Confirmed by reading it: still no `error.Exception` assertion anywhere.
4. **2026-01-13**, commit `fc36f4df` ("refactor: apply Orchestrator pattern to validation packages (#14)") changed the production code the deleted tests protected: `src/Encina/Validation/ValidationOrchestrator.cs` (lines 63-81, today) now builds the failure as `EncinaError.New(errorMessage)` — a flat string from `ValidationResult.ToErrorMessage` — so `Exception` is always `None` for a validation failure routed through the orchestrator. It no longer builds `EncinaError.New(new ValidationException(...))`. Note that `src/Encina.FluentValidation/FluentValidationProvider.cs` still produces the structured `ValidationError(PropertyName, ErrorMessage)` list correctly; the orchestrator is the point where that structure is discarded down to a string.
5. `src/Encina.FluentValidation/README.md` (lines ~91-257, today) still documents the pre-#14 behavior: `error.Exception.IfSome(ex => ex is ValidationException ...)` with an ASP.NET Core minimal-API example that groups `Results.ValidationProblem` by `PropertyName` from `error.Exception`. That example no longer works against today's code.

So issue #11's fix was correct and is not itself broken; the *invariant it verified* was later invalidated by an unrelated refactor (#14), and no test was added to catch the regression when the invariant changed. That gap is real, but it is not net-new: it is **already tracked as open issue #1330** ("[BUG] Encina.DataAnnotations and Encina.FluentValidation READMEs document EncinaError.Exception behaviour the code does not implement", milestone v0.14.0 — Hardening), filed 2026-09-25 by another audit thread. No new remediation issue is drafted here; see `remediation/11-notes.md`.
