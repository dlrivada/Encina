## Decisions

- Centralized `InboxPipelineBehavior` (`src/Encina.Messaging/Inbox/InboxPipelineBehavior.cs`),
  `OutboxPostProcessor` (`src/Encina.Messaging/Outbox/OutboxPostProcessor.cs`), and
  `IHasNotifications` into `Encina.Messaging`, removing 11 provider-local duplicates
  (source: issue comments 2025-12-23; confirmed present in today's code).
- Introduced factory interfaces in `Encina.Messaging` — `IInboxMessageFactory`,
  `IOutboxMessageFactory`, `ISagaStateFactory`, `IScheduledMessageFactory` — implemented once
  per provider package (ADO ×3, Dapper ×3, EntityFrameworkCore, MongoDB = 8 implementations)
  so provider-specific entity construction stays local while the behavior around it is shared
  (source: issue comments; confirmed present today, e.g.
  `src/Encina.ADO.SqlServer/Inbox/InboxMessageFactory.cs`).
- Centralized saga and scheduling orchestration into `SagaOrchestrator`
  (`src/Encina.Messaging/Sagas/SagaOrchestrator.cs`) and `SchedulerOrchestrator`
  (`src/Encina.Messaging/Scheduling/SchedulerOrchestrator.cs`) (source: issue comments;
  confirmed present today).
- All of the above are wired through two single DI entry points in
  `src/Encina.Messaging/MessagingServiceCollectionExtensions.cs`:
  `AddMessagingServices<...>` (9 generic parameters: Outbox/Inbox/Saga/Scheduling stores and
  factories + the outbox processor) and `AddMessagingServicesCore<...>` (Outbox/Inbox only,
  for standalone registrations). Every provider's `ServiceCollectionExtensions.cs` calls one
  of these instead of hand-rolling registration (verified: all 6 Dapper/ADO packages call
  `AddMessagingServices<...>`, e.g. `src/Encina.Dapper.SqlServer/ServiceCollectionExtensions.cs:69-78`).
- Accepted **intentional** duplication in the Store implementations (`OutboxStore*`,
  `InboxStore*`, `SagaStore*`, `ScheduledMessageStore*` per provider) because SQL dialects
  differ (`TOP` vs `LIMIT` vs `FETCH FIRST`, UTC timestamp functions, etc.) and excluded them
  from SonarCloud CPD analysis (source: comment by dlrivada, commit `c66625f5`).

## Rejected alternatives

- **Abstract base classes for Store implementations**: rejected — adds coupling between
  providers, against the project's provider-independence goal (source: issue body).
- **SQL template approach**: not implemented for Store classes; centralization stopped at the
  behavioral layer, and the remaining SQL-level duplication was excluded from analysis rather
  than templated (source: issue body, comment by dlrivada).
- **Full duplication acceptance** (do nothing beyond exclusion): partially adopted only for
  the Store SQL layer — active refactoring was done first for every non-SQL-specific
  behavior (source: issue body, comment by dlrivada).

## Rules and lessons

- Providers must stay independent and self-contained; centralize only the SQL-dialect-free
  behavior, never store SQL, in the shared `Encina.Messaging` package (source: issue body,
  comment by dlrivada). This lesson generalizes the "Provider Coherence" principle already in
  `CLAUDE.md` (same interfaces, different implementations) but does not appear there in this
  more specific SQL-duplication form.
- When SQL dialects differ meaningfully, prefer separate Store implementations over
  abstraction, for clarity and performance (source: comment by dlrivada). Not currently
  written into `CLAUDE.md`; only lives in this issue's comment thread and in the SonarCloud
  workflow's exclusion comment.
- A provider-specific factory (`I*Factory`) is the seam that lets shared orchestration logic
  construct provider-specific entities without the shared code knowing the concrete type
  (source: comment by dlrivada; confirmed as the live pattern in
  `MessagingServiceCollectionExtensions.cs`).

## Outcome revised by this audit (2026-09-25)

The audit's adversarial-reviewer pass found the centralization is **incomplete**, not fully
delivered as the closing comments claimed: EF Core and MongoDB register their factories/stores
by hand instead of through the shared `MessagingServiceCollectionExtensions` helper, and that
hand registration silently dropped two things the helper provides for every ADO/Dapper provider
— `InboxPipelineBehavior<,>` (MongoDB `UseInbox`, both overloads) and `ISagaRunner`/
`ISagaNotFoundDispatcher` (EF Core and MongoDB `UseSagas`). See `audits/issue-12.md` for full
evidence and the remediation drafts this produced. Outcome changed from `delivered` to `partial`
to reflect that the intended provider-coherence guarantee (same behavior across all 8 providers)
does not hold today.
