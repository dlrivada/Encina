## Decisions

- `Log.cs` and `TransactionPipelineBehavior.cs`, duplicated across all 8 Dapper/ADO provider packages (including the since-removed Oracle and SQLite providers, ADR-009/ADR-024), were centralized into `Encina.Messaging` as `MessagingLog.cs` and `TransactionPipelineBehavior.cs` (source: issue body; commit 760e27c). Verified today: both files exist at `src/Encina.Messaging/MessagingLog.cs` and `src/Encina.Messaging/TransactionPipelineBehavior.cs`.
- `MessagingServiceCollectionExtensions` was created as a DI helper so the 8 providers register the shared behavior consistently (source: issue body; verified in commit diff, `src/Encina.Messaging/MessagingServiceCollectionExtensions.cs` referenced from provider `ServiceCollectionExtensions.cs` files).
- 20 duplicated files (10× `Log.cs` + 10× `TransactionPipelineBehavior.cs`, one pair per then-existing provider including Oracle/SQLite) were deleted (source: closing comment; verified via `git show --stat 760e27c`, which lists exactly this file-deletion pattern across `Encina.ADO.MySQL`, `.Oracle`, `.PostgreSQL`, `.SqlServer`, `.Sqlite` and the Dapper equivalents).
- A SonarCloud suppression for rule `csharpsquid:S2077` (SQL injection) was added for Dapper/ADO store files, justified by `SqlIdentifierValidator.ValidateTableName()` validating table names and all data values being parameterized (source: commit e1c68db). Verified today: `SqlIdentifierValidator` still exists (`src/Encina.Messaging/SqlIdentifierValidator.cs`) and is used across 91 files in the Dapper/ADO packages.
- Commit 19f2402 (S6444 ReDoS fix) is unrelated to issue #20's stated scope — it fixed regex timeouts in `Encina.Caching.Hybrid`, `Encina.Caching.Memory`, `Encina.GuardClauses`, and `Encina.SignalR`, none of which are Dapper/ADO packages. It rode along in the same closing comment but did not touch code in scope for this issue.
- Reported result "duplication reduced from ~11% to 1.7%" (closing comment) could not be independently re-measured (no archived SonarCloud report from that date); the commit message on 760e27c itself claims a more modest "~11% to ~8%". Treat the 1.7% figure as unverified, consistent with the pattern already flagged for issue #12 in #1335.

## Rejected alternatives

- Consolidating SQL scripts and Store implementations across providers was explicitly rejected as "intentional duplication" due to dialect-specific requirements (TOP vs LIMIT, GETUTCDATE vs NOW, backticks vs brackets) (source: issue body). Still true today: provider-specific store files remain separate.
- `ServiceCollectionExtensions.cs` full consolidation was scoped down: the issue body proposed a `MessagingServiceCollectionExtensions` helper, and providers kept their own `ServiceCollectionExtensions.cs` calling into it, rather than being deleted outright (source: commit 760e27c diff, which shows `ServiceCollectionExtensions.cs` shrinking, not disappearing, in every provider).

## Rules and lessons

- Shared behavioral logic (logging, transaction pipeline) belongs in `Encina.Messaging`; provider-specific SQL dialects and entity mappings stay in their own packages (source: issue body). This is the origin of the pattern CLAUDE.md now documents under "Provider Coherence".
- A centralization refactor that moves a class does not automatically move its logging/tracing/DI-test obligations with it — the deep audit found the moved `TransactionPipelineBehavior` lost logging and tracing relative to its EF Core sibling, and gained no DI completeness test for its new shared registration path (see audit file). This is a lesson for future consolidations: verify cross-cutting integration (CLAUDE.md's 12 functions) is preserved, not just compiled, after a move.
- A percentage claim (duplication ratio) in a closing comment is not evidence unless the report artifact is attached or archived; this is the second time this pattern surfaced (first in #12/#1335).
