## Summary

Issue #15 proposed applying the Orchestrator pattern to Event Sourcing packages (Encina.EventSourcing, Encina.EventStoreDB, Encina.Marten) as part of a broader pattern unification effort across Caching, Validation, and other subsystems.

**Status**: Superseded by deeper architectural analysis (dlrivada's comment, 2025-12-23).

## Architectural Decision

The investigation concluded that Event Sourcing requires a **Strategy pattern** instead of simple Orchestrator + Provider, because:

- **EventStoreDB**: catch-up subscriptions, server-side projections, dedicated event store semantics
- **Marten**: inline projections, async daemon, PostgreSQL-native features, document store hybrid

These represent fundamentally different architectural approaches, not interchangeable implementations like caching backends or validation libraries.

**Result**: Three replacement spike issues created:
- #17: Implement Strategy pattern for Event Sourcing (EventStoreDB vs Marten)
- #16: Implement Strategy pattern for Sagas (Choreography vs Orchestration)  
- #18: Implement Strategy pattern for Messaging Transports (RabbitMQ, Kafka, NATS)

## Current Implementation Status (Audit: 2026-09-25)

### Existing Packages
- **Encina.Marten**: Fully implemented
  - `IAggregateRepository<TAggregate>` interface
  - `MartenAggregateRepository` implementation
  - `AddEncinaMarten()` registration with options
  - Projections, Snapshots, Versioning, Health sub-modules
  - Encina.Marten.GDPR compliance module

- **Encina.EventStoreDB**: Marked "future" in CLAUDE.md § 6 Event Sourcing; not implemented

- **Encina.EventSourcing**: Not created (proposed in #15 but not realized)

### Pattern Used
Marten uses a **provider-specific repository pattern**, not a general orchestrator:
- Direct `IAggregateRepository<TAggregate>` interface in Encina.Marten
- No abstract strategy layer above it
- Consistent with decision to defer EventStoreDB integration

## Lessons

1. **Heterogeneous strategies differ from interchangeable providers**: Caching backends (Redis/Memory) are swappable; EventStoreDB (server-side projections) and Marten (inline projections) are not.

2. **Deferred designs preserve correctness**: Skipping EventStoreDB (pre-1.0 scope, ADR-024/ADR-025) until both strategies exist avoids premature abstraction over a single provider.

3. **Spike issues validate architecture before implementation**: Proposal → Spike → Replacement issues flow allowed design refinement without wasted refactoring.
