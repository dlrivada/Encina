## Decisions
- Centralize validation logic into `Encina.Validation` (core) via `IValidationProvider`, `ValidationResult`/`ValidationError`, `ValidationOrchestrator`, and a shared `ValidationPipelineBehavior<TRequest, TResponse>` — verified present today at `src/Encina/Validation/{IValidationProvider,ValidationResult,ValidationOrchestrator,ValidationPipelineBehavior}.cs`. (Source: issue body)
- `FluentValidationProvider`, `DataAnnotationsValidationProvider`, `MiniValidationProvider` each implement `IValidationProvider` — verified present at `src/Encina.FluentValidation/FluentValidationProvider.cs`, `src/Encina.DataAnnotations/DataAnnotationsValidationProvider.cs`, `src/Encina.MiniValidator/MiniValidationProvider.cs`. (Source: comment by dlrivada)
- Each provider package's `ServiceCollectionExtensions` registers the provider, `ValidationOrchestrator` and the open-generic `ValidationPipelineBehavior<,>` — verified present in all three `ServiceCollectionExtensions.cs`. (Source: comment by dlrivada)
- The per-package duplicated `ValidationPipelineBehavior` files were removed — no such files exist under `src/Encina.FluentValidation`, `src/Encina.DataAnnotations`, or `src/Encina.MiniValidator` today; only the shared core one remains. (Source: issue body)

## Rejected alternatives
- none recorded

## Rules and lessons
- Centralizing behavior logic into one generic class with a domain orchestrator gives uniform behavior across the three validation libraries — confirmed structurally: all three providers return the same `ValidationResult` shape and the pipeline behavior never branches on provider type. (Source: issue body)
- Refactors like this must keep the full test suite green; today's suite for the three provider packages (unit, guard-adjacent, property, contract) exists and passes, but see audit findings below for gaps left by later work. (Source: issue body; comment by dlrivada)
