## Decisions
- The feature to create a new package `Encina.OpenApi` for auto-generating OpenAPI specifications from Encina handlers was rejected.
- The decision was based on the analysis of new OpenAPI capabilities in .NET 10 (OpenAPI 3.1, JSON Schema 2020-12, document transformers, native YAML support), which provided native functionality that `Encina.OpenApi` would have merely wrapped without adding significant value. (Source: comment by dlrivada)
- Users are advised to use `Microsoft.AspNetCore.OpenApi` directly with native transformers for customization. (Source: comment by dlrivada)
- Maintaining a wrapper package around native functionality was deemed not to justify the maintenance cost. (Source: comment by dlrivada)

## Rejected alternatives
- Manual OpenAPI YAML/JSON files (risk of drift). (Source: issue body)
- Swashbuckle-only approach (does not natively understand Encina's handler/mediator pattern without custom integration). (Source: issue body)
- NSwag code-first (similar limitations to Swashbuckle for non-controller-based architectures). (Source: issue body)
- The proposed `Encina.OpenApi` package itself (rejected due to lack of value over native .NET 10 features). (Source: comment by dlrivada)

## Rules and lessons
- Avoid creating wrapper packages for functionality that is natively provided by the underlying framework (e.g., .NET 10 `Microsoft.AspNetCore.OpenApi`) if the wrapper does not add significant value. (Source: comment by dlrivada)
- Maintenance costs for packages that simply expose or wrap native capabilities are not justified. (Source: comment by dlrivada)

## Candidate destinations
- adr: The rejection rationale based on .NET 10 native capabilities serves as a permanent architectural decision record for why `Encina.OpenApi` does not exist.
- roadmap: Mark the "Encina.OpenApi" package as dropped/rejected to prevent future re-submission without a new value proposition.
- none: The specific technical details of the proposed API are not needed elsewhere as the feature is dead.
