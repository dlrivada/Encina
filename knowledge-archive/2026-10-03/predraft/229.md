## Decisions
- Consolidate `ValidationPipelineBehavior<,>`, `IValidationProvider`, and `ValidationOrchestrator` into the core Encina package (`Encina.Validation` namespace implied) to eliminate duplication across satellite packages (source: issue body / comment by dlrivada).
- Remove duplicate behavior classes from satellite packages: `Encina.FluentValidation.ValidationPipelineBehavior<TRequest, TResponse>`, `Encina.DataAnnotations.DataAnnotationsValidationBehavior<TRequest, TResponse>`, and `Encina.MiniValidator.MiniValidationBehavior<TRequest, TResponse>` (source: comment by dlrivada).
- Mark the v0.10.0 DDD Foundations milestone as complete upon this delivery (source: comment by dlrivada).
- No user migration action is required if using standard extension methods like `AddEncinaFluentValidation()`, `AddDataAnnotationsValidation()`, or `AddMiniValidation()` (source: comment by dlrivada).

## Rejected alternatives
- **Keep duplicate behaviors**: Rejected due to code duplication and potential inconsistencies between providers (source: issue body).
- **Shared package dependency**: Creating a new `Encina.Validation.Core` package was rejected because it adds another package to the dependency graph (source: issue body).
- **Abstract base class approach**: Sharing logic via inheritance was rejected because it couples implementations and makes testing harder (source: issue body).

## Rules and lessons
- Core validation orchestration logic (`ValidationPipelineBehavior`, `ValidationOrchestrator`, `IValidationProvider`) must reside in the core Encina package to be provider-agnostic, while satellite packages provide only the specific `IValidationProvider` implementation (source: issue body).
- Removal of public API types (`ValidationPipelineBehavior`) in satellite packages is considered a BREAKING CHANGE, but can be mitigated if internal registration extensions handle the new core types transparently for the user (source: comment by dlrivada).

## Candidate destinations
- **spec-invariant**: The validation architecture mandates that only one `ValidationPipelineBehavior<,>` exists in the core package, and satellite packages must implement `IValidationProvider` rather than define their own behaviors.
- **docs**: Migration guide for the breaking change in v0.10.0 regarding removed satellite validation behaviors.
- **roadmap**: Confirmation of the completion of the v0.10.0 DDD Foundations milestone.
