## Summary

Optimize the delegate caching mechanism to minimize reflection overhead and boxing.

## Motivation

The current delegate cache implementation uses ConcurrentDictionary, expression tree compilation, and some reflection for type resolution. In high-throughput scenarios, reflection overhead and value-type boxing on hot paths can degrade performance. Optimizing these paths is foundational for future source generator work and ensures Encina's mediator dispatch remains competitive with hand-written code.

## Proposed Solution

### Optimization Goals

- Reduce memory allocations in hot paths
- Minimize boxing of value types
- Use `CollectionsMarshal.AsSpan` where applicable
- Cache compiled expressions aggressively

### Current State

Current implementation uses:
- ConcurrentDictionary for handler caches
- Expression tree compilation
- Some reflection for type resolution

### Approach

1. Profile current delegate cache performance to establish baseline
2. Identify boxing hotspots via allocation profiling
3. Apply `CollectionsMarshal.AsSpan` for dictionary value access
4. Optimize ConcurrentDictionary access patterns (e.g., `GetOrAdd` with factory caching)
5. Add micro-benchmarks for before/after comparison
6. Verify no regressions in functionality

## Alternatives Considered

1. **Source generators instead of runtime reflection**: Would eliminate reflection entirely but is a larger effort; this optimization is a stepping stone toward that goal.
2. **Frozen collections (.NET 8+)**: Using `FrozenDictionary` for handler registrations that don't change after startup could reduce lookup overhead, but requires validating that all registrations are truly immutable.
3. **No optimization (status quo)**: Acceptable for low-throughput scenarios but leaves performance on the table for demanding workloads.

COMMENT by dlrivada:
Issue resolved in commit bcd86ef.

## Summary of Optimizations

### 1. TryGetValue-before-GetOrAdd Pattern
Applied to both RequestDispatcher and NotificationDispatcher caches. This avoids delegate allocation for the factory function on cache hits (hot path), since `GetOrAdd` always allocates the delegate even when the key exists.

**Before:**
```csharp
var dispatcher = RequestHandlerCache.GetOrAdd(
    (requestType, typeof(TResponse)),
    static key => CreateRequestHandlerWrapper(key.Request, key.Response));
```

**After:**
```csharp
var cacheKey = (requestType, typeof(TResponse));
if (!RequestHandlerCache.TryGetValue(cacheKey, out var dispatcher))
{
    dispatcher = RequestHandlerCache.GetOrAdd(
        cacheKey,
        static key => CreateRequestHandlerWrapper(key.Request, key.Response));
}
```

### 2. RequestKind Type Check Caching
Added a static cache for `GetRequestKind` results to avoid repeated `IsAssignableFrom` calls on every request dispatch.

### 3. New Benchmarks
Added `CacheOptimizationBenchmarks.cs` with:
- Raw cache access comparison (GetOrAdd vs TryGetValue+GetOrAdd)
- Full pipeline cache hit scenarios (Send_Command, Send_Query, Publish_Notification)
- Type check caching comparison

All tests pass. Ready for Source Generators (#50) as the next optimization step.
