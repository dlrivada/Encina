## Summary

Add **transparent message encryption/decryption support** for sensitive data in Outbox/Inbox patterns to meet regulatory compliance requirements.

## Motivation

- **Regulatory compliance** requirements (GDPR, HIPAA, PCI-DSS)
- Protection of PII, payment info, health records in message queues
- Defense against insider threats and message broker compromises
- **Audit logging requirements** for sensitive data access
- Multi-tenant environments with tenant-specific keys

## Proposed Solution

### Core Interfaces

```csharp
public interface IMessageEncryptionProvider
{
    Task<EncryptedPayload> EncryptAsync(
        byte[] plaintext,
        EncryptionContext context,
        CancellationToken ct);

    Task<byte[]> DecryptAsync(
        EncryptedPayload ciphertext,
        EncryptionContext context,
        CancellationToken ct);
}

public record EncryptionContext(
    string? KeyId,
    string? TenantId,
    Dictionary<string, string>? Metadata);

public record EncryptedPayload(
    byte[] Ciphertext,
    string KeyId,
    string Algorithm,
    byte[]? Iv,
    byte[]? Tag);
```

### Attribute-Based Encryption

```csharp
// Encrypt entire message
[Encrypted]
public record SensitiveCommand(string CreditCardNumber) : ICommand<Result>;

// Encrypt with specific key
[Encrypted(KeyId = "payment-key")]
public record PaymentCommand(decimal Amount) : ICommand<PaymentResult>;

// Tenant-specific encryption
[Encrypted(UseTenantKey = true)]
public record TenantDataCommand(string Data) : ICommand<Result>;

// Selective field encryption
public record MixedCommand(
    string PublicData,
    [property: EncryptedField] string SecretData
) : ICommand<Result>;
```

### Configuration

```csharp
config.Encryption.Enabled = true;
config.Encryption.DefaultProvider = "AzureKeyVault";
config.Encryption.KeyRotationEnabled = true;
config.Encryption.AuditDecryption = true;
config.Encryption.TenantKeyResolver = tenantId => $"tenant-{tenantId}-key";
```

## Alternatives Considered

1. **Transport encryption only**: Rely on TLS for message broker connections. Doesn't protect data at rest, vulnerable to insider threats.

2. **Application-level encryption**: Encrypt manually in handlers. Inconsistent, error-prone, no centralized key management.

3. **Database encryption only**: Use database TDE. Doesn't protect data in transit through message brokers.

## Summary

Implement **transparent message encryption/decryption** for Outbox/Inbox message payloads, enabling regulatory compliance (GDPR, HIPAA, PCI-DSS) by encrypting the serialized `Content` field before persistence. This complements the existing `Encina.Security.Encryption` field-level encryption (which operates on request/response properties in the CQRS pipeline) by adding **payload-level encryption** at the messaging storage layer.

The feature introduces:

1. **`Encina.Messaging.Encryption`** ÔÇö Core abstractions for message payload encryption (`IMessageEncryptionProvider`, `[EncryptedMessage]` attribute, `MessageEncryptionPipelineBehavior`)
2. **`Encina.Messaging.Encryption.AzureKeyVault`** ÔÇö Azure Key Vault KMS integration for message encryption keys
3. **`Encina.Messaging.Encryption.AwsKms`** ÔÇö AWS KMS integration for message encryption keys
4. **`Encina.Messaging.Encryption.DataProtection`** ÔÇö ASP.NET Core Data Protection integration (simplest option for single-deployment scenarios)

**Provider category**: None (provider-independent). Message encryption wraps the serialized `Content` string *before* it reaches any database provider's `IOutboxStore.AddAsync()`, so all 13 database providers benefit automatically without per-provider implementations.

**Affected packages**: `Encina.Messaging` (minor: new hook in `OutboxOrchestrator` / `InboxOrchestrator`), plus 4 new satellite packages.

### Key Architectural Insight

Encina already has **field-level encryption** (`Encina.Security.Encryption`) that encrypts individual properties decorated with `[Encrypt]` before/after handler execution. Issue #129 requests a *different* layer: encrypting the **entire serialized message payload** (`OutboxMessage.Content`) at rest in the database and in transit through message brokers. These two layers are complementary:

| Layer | Package | Scope | When |
|-------|---------|-------|------|
| **Field-level** | `Encina.Security.Encryption` | Individual properties with `[Encrypt]` | Before/after handler execution |
| **Payload-level** | `Encina.Messaging.Encryption` (this feature) | Entire `OutboxMessage.Content` / `InboxMessage.Response` | Before/after database persistence |

- **Multi-tenant isolation** ÔÇö per-tenant key derivation via `ITenantKeyResolver`
- **Railway Oriented Programming** ÔÇö all operations return `Either<EncinaError, T>`
- **Compact format** ÔÇö `ENC:v1:{KeyId}:{Algorithm}:{Nonce}:{Tag}:{Ciphertext}`
- **Observability** ÔÇö OpenTelemetry tracing (2 activities) and metrics (4 instruments)
- **Health check** ÔÇö roundtrip verification of the encryption pipeline
- **9 domain error codes** under `msg_encryption.*`
