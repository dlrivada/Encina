## Summary

Create fluent assertion extensions for Railway Oriented Programming results.

## Motivation

- **Phase**: 2 - Functionality
- **Priority**: Critical
- **Complexity**: Low

Testing `Either<EncinaError, T>` results requires verbose `Match` calls and manual assertions. Fluent assertion extensions like `ShouldBeSuccess()` and `ShouldBeError()` make tests more readable and provide better failure messages.

## Proposed Solution

### Features

- Success/Error assertions
- Value extraction with assertions
- Error code/message assertions
- Chained assertions

### Proposed API

```csharp
// Success assertions
result.ShouldBeSuccess();
result.ShouldBeSuccess(value => value.Should().Be(expected));
result.ShouldHaveValue<OrderId>(id => id.Value.Should().NotBeEmpty());

// Error assertions
result.ShouldBeError();
result.ShouldBeError(e => e.Code == "validation.failed");
result.ShouldHaveErrorCode("encina.validation.failed");
result.ShouldHaveErrorMessage("Validation failed");

// Either extensions
either.Match(
    Right: value => value.Should().BeEquivalentTo(expected),
    Left: error => Assert.Fail($"Expected success but got error: {error.Code}")
);
```
