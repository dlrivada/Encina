## Summary

**Generate API reference documentation** from XML comments using DocFX for comprehensive API docs.

## Motivation

- **Discoverability**: Users can browse and search all public APIs
- **Accuracy**: Generated from code ensures documentation is accurate
- **Examples**: XML docs can include code examples
- **IDE integration**: Same XML docs power IntelliSense in IDEs

## Proposed Solution

### Current State

XML documentation is enabled on all projects (`<GenerateDocumentationFile>true</GenerateDocumentationFile>`).

### DocFX Configuration

DocFX is already configured to generate API docs from XML comments.

COMMENT by dlrivada:
## Proposal: Hybrid Jekyll + DocFX architecture

### Current state (updated)

The "DocFX is already configured" note in the description is outdated. Commit [d951c49c](https://github.com/dlrivada/Encina/commit/d951c49c) (PR #915, 2026-03-27) removed `docs/docfx.json` when migrating the site to Jekyll (`just-the-docs` theme). As a consequence:

- `docs/_config.yml` now drives the site, deployed automatically via `pages-build-deployment`.
- `.github/workflows/docs.yml` still invokes `dotnet docfx metadata docs/docfx.json` and is disabled (only `workflow_dispatch`). It has had no successful run since 2026-03-27.
- No API reference is currently generated ÔÇö only narrative docs exist.

### Recommendation: keep both, with disjoint scopes

Jekyll and DocFX can coexist without conflict if we assign each a clear responsibility:

| Scope | Tool | Output |
|---|---|---|
| Narrative docs, guides, ADRs, getting-started, features index | **Jekyll** (just-the-docs) | `docs/**/*.md` ÔåÆ site root |
| Auto-generated API reference (types, members, XML docs, `cref` links) | **DocFX** | `docs/api/*.html` (static HTML) |

#### Why both are needed

- **Jekyll alone is insufficient** for a project with 112 packages and hundreds of public types ÔÇö documenting every `IOutboxStore.AddAsync(...)` by hand does not scale and drifts from code.
- **DocFX alone loses `just-the-docs`** ÔÇö we'd sacrifice the current (working) narrative UX for the sake of API reference.
- **Each fills the other's gap**: narrative UX Ôåö auto-generated API ref.

### Technical plan

1. **Restore `docs/docfx.json`** scoped to API metadata only (not the full site):
   - `metadata`: scan all `src/**/*.csproj`, output YAML to `docs/api/.metadata/`
   - `build`: consume metadata, render HTML to `docs/api/`
   - No `toc.yml` for narrative content (Jekyll owns that)
2. **Exclude `api/` from Jekyll** in `docs/_config.yml`:
   ```yaml
   exclude:
     - api/          # DocFX-generated, serve as static assets
   ```
3. **Rewrite `.github/workflows/docs.yml`** so the build order is:
   - Restore deps ÔåÆ build solution ÔåÆ `dotnet docfx metadata` ÔåÆ `dotnet docfx build` ÔåÆ commit `docs/api/` (or upload as Pages artifact alongside Jekyll output)
4. **Link from Jekyll nav** to `/Encina/api/` via `aux_links` in `_config.yml`.
5. **Baseurl alignment**: DocFX `_appBaseUrl` must match Jekyll `baseurl: /Encina` to avoid broken cross-links.

### Known tradeoffs (accepted)

1. **Theme inconsistency**: `/api/*` pages use DocFX's Modern theme, not just-the-docs. Mitigable with custom CSS, never perfect. Acceptable because users visiting API reference are in a different mental mode (code lookup) than users reading guides.
2. **Separate search indexes**: Jekyll search covers narrative; DocFX search covers API. A global search would require a third tool (Algolia DocSearch) ÔÇö out of scope.
3. **CI complexity**: two build tools, two sets of deps (`dotnet-tools.json` already has DocFX; Jekyll runs on the Pages side). Par [...]

## Implementation summary ÔÇö PR #1031

Hybrid Jekyll + DocFX architecture implemented per the [proposal above](#issuecomment-4279235731). PR open: #1031 (awaiting final review; not merged yet so this issue remains open until then).

### What landed

**New files:**
- `docs/docfx.json` ÔÇö DocFX configured for API-only scope. Metadata `dest: "api"` ÔåÆ flat layout via `src: "api", dest: "."` in `build.content` so output lives at `_api-build/*.html` (not `_api-build/api/*.html`). `separatePages` member layout, `nested` namespace layout. Private members and explicit interface implementations excluded.
- `docs/filterConfig.yml` ÔÇö includes `Encina.*`, excludes `System.*`, `Microsoft.*`, and anything marked `[EditorBrowsable(Never)]`.
- `docs/_api-landing/index.md` ÔÇö human-written landing page served at `/api/`, introduces the reference and links back to the Jekyll site.

**Modified files:**
- `docs/_config.yml` ÔÇö adds `aux_links["API Reference"]: /api/` to the navbar, excludes `docfx.json`, `filterConfig.yml`, `_api-build/`, `_api-landing/`, `api/` from Jekyll processing.
- `.github/workflows/docs.yml` ÔÇö full rewrite. Triggers on push/PR to `docs/**`, `src/**/*.cs`, `src/**/*.csproj`, `Directory.Build.{props,targets}`, or the workflow itself. Pipeline: `dotnet tool restore` ÔåÆ `dotnet restore Encina.slnx` ÔåÆ `dotnet build` ÔåÆ `dotnet docfx metadata` ÔåÆ `dotnet docfx build` ÔåÆ `configure-pages` ÔåÆ `jekyll-build-pages` ÔåÆ `sudo chown -R _site` ÔåÆ `Preserve sibling Pages subtrees` (main-only) ÔåÆ `Merge DocFX into _site/api/` ÔåÆ `upload-pages-artifact` (main-only) ÔåÆ `deploy-pages` (main-only).
- `.gitignore` ÔÇö ignores `docs/_api-build/` (CI intermediate).
- `.github/lychee.toml` ÔÇö consolidated `docs.nestjs.com` + `courses.nestjs.com` into a single `nestjs.com` pattern that also covers the root (was blocking CI with flaky timeouts).

### Architectural properties preserved from the proposal

- Ô£à Jekyll owns narrative content; DocFX owns the auto-generated API reference. No overlap.
- Ô£à `/Encina/api/` subpath; `_config.yml` excludes prevent Jekyll from touching DocFX territory.
- Ô£à CI does a single atomic deploy ÔÇö Jekyll `_site/` + DocFX output merged under `_site/api/` before `upload-pages-artifact`. Unblocks Pages redeployments (stale since 2026-03-29 when the dead DocFX-only workflow was disabled).
- Ô£à DocFX intermediates never committed to git.
- Ô£à Sibling Pages subtrees (`/coverage/`, `/benchmarks/`, `/load-tests/`, `/mutations/`) preserved by fetching live copies of `*/data/*.json` and `*/badge.{svg,json}` before upload ÔÇö mirrors the pattern in `publish-benchmarks.yml`.
