## Description

**Consolidate ValidationPipelineBehavior** into core Encina package, moving from satellite validation packages to provide a unified validation experience.

Currently, validation behavior is duplicated across FluentValidation and DataAnnotations packages. Users need to choose a validation library before getting pipeline behavior. Core validation orchestration should be provider-agnostic. This simplifies the validation architecture.

## Location
- **File(s)**: `src/Encina.FluentValidation/`, `src/Encina.DataAnnotations/`, `src/Encina/`
- **Package(s)**: Encina (core), Encina.FluentValidation, Encina.DataAnnotations, Encina.MiniValidation

### Usage

```csharp

    config.UseValidation = true; // Enables ValidationPipelineBehavior

// Choose your validation provider

// or

```

## Root Cause

The validation architecture was initially designed with each satellite package providing its own pipeline behavior, leading to code duplication and potential inconsistencies between providers.

## Proposed Fix

1. Move `IValidationProvider` to Encina core
2. Move `ValidationOrchestrator` to Encina core
3. Move `ValidationPipelineBehavior` to Encina core
4. Update `Encina.FluentValidation` to implement `IValidationProvider`
5. Update `Encina.DataAnnotations` to implement `IValidationProvider`
6. Update registration extensions
7. Unit tests
8. Documentation

## Alternatives Considered

1. **Keep duplicate behaviors**: Maintaining separate ValidationPipelineBehavior in each package. This leads to code duplication and potential inconsistencies.

2. **Shared package dependency**: Creating a new Encina.Validation.Core package. This adds another package to the dependency graph.

3. **Abstract base class approach**: Sharing logic via inheritance. This couples implementations and makes testing harder.
