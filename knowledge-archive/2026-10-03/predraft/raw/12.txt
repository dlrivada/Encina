## Description

SonarCloud reports 5.66% code duplication (threshold: Ôëñ3%). The Dapper and ADO.NET providers have intentionally similar implementations to keep each provider self-contained and independent.

## Location

- **File(s)**: Multiple files across Dapper and ADO providers
- **Package(s)**: Encina.Dapper.*, Encina.ADO.*

## Current Behavior

Each provider has its own independent implementations:
- OutboxStoreDapper/ADO
- InboxStoreDapper/ADO
- SagaStoreDapper
- ScheduledMessageStoreDapper
- InboxPipelineBehavior

This intentional duplication causes SonarCloud to report 5.66% duplication, exceeding the Ôëñ3% threshold.

## Expected Behavior

Code duplication should be Ôëñ3% while maintaining provider independence.

## Root Cause

Providers are intentionally similar to keep each one self-contained and independent. No cross-provider dependencies by design.

## Proposed Fix

### Options Considered

#### Option 1: Abstract Base Classes
Create `OutboxStoreBase<T>`, `InboxStoreBase<T>` etc. with provider-specific SQL injected.
- **Pros**: Reduces duplication significantly
- **Cons**: Adds complexity, tighter coupling between providers

#### Option 2: SQL Template Approach (Recommended)
Use string templates with placeholders for provider-specific SQL functions (e.g., `{UTC_NOW}` ÔåÆ `GETUTCDATE()` / `NOW()` / `CURRENT_TIMESTAMP`).
- **Pros**: Maintains readability
- **Cons**: Still some duplication in structure

#### Option 3: Accept Intentional Duplication
Mark as accepted technical debt with justification:
- Each provider is fully independent
- Easier to maintain and understand
- No cross-provider dependencies

**Recommendation**: Option 2 (SQL templates) provides good balance between DRY principle and maintainability. However, this is low priority since the duplication is architectural and intentional.

COMMENT by dlrivada:
## Resolved: Intentional Duplication Excluded from SonarCloud

### Decision
The code duplication in Dapper/ADO store implementations is **intentional** and has been excluded from SonarCloud analysis.

### Why Intentional?
The Store implementations (OutboxStore, InboxStore, SagaStore, ScheduledMessageStore) have similar structure but different SQL dialects:

| Provider | LIMIT syntax | UTC timestamp |
|----------|--------------|---------------|
| SQL Server | `TOP (@n)` | `GETUTCDATE()` |
| PostgreSQL | `LIMIT @n` | `NOW() AT TIME ZONE 'UTC'` |
| MySQL | `LIMIT @n` | `UTC_TIMESTAMP()` |
| SQLite | `LIMIT @n` | `datetime('now')` |
| Oracle | `FETCH FIRST n ROWS` | `SYSTIMESTAMP AT TIME ZONE 'UTC'` |

### Benefits of Keeping Separate
1. **Independence**: Modify one provider without affecting others
2. **Clarity**: Full SQL visible in each provider, no abstraction hunting
3. **Performance**: No abstraction overhead or dynamic SQL generation
4. **Maintainability**: Each provider is self-contained

### Implementation
Created `sonar-project.properties` with:
```properties
sonar.cpd.exclusions=\
  src/Encina.Dapper.*/Outbox/*.cs,\
  src/Encina.Dapper.*/Inbox/*.cs,\
  src/Encina.Dapper.*/Sagas/*.cs,\
  src/Encina.Dapper.*/Scheduling/*.cs,\
  src/Encina.ADO.*/Outbox/*.cs,\
  src/Encina.ADO.*/Inbox/*.cs
```

### Already Centralized (from previous work)
- Ô£à InboxPipelineBehavior ÔåÆ `Encina.Messaging.Inbox`
- Ô£à OutboxPostProcessor ÔåÆ `Encina.Messaging.Outbox`
- Ô£à Factory interfaces for provider-specific entities
- Ô£à SagaOrchestrator, SchedulerOrchestrator

The remaining duplication is architectural and acceptable.
