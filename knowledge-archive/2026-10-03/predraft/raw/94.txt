BODY:
## Summary

**Create SECURITY.md** with vulnerability reporting instructions, supported versions, response timeline, and disclosure policy.

## Motivation

- **Responsible disclosure**: Provide secure channel for vulnerability reports
- **User trust**: Show commitment to security
- **Legal protection**: Clear policy protects both maintainers and reporters
- **GitHub integration**: SECURITY.md enables GitHub's security features

## Proposed Solution

### Content Structure

```markdown
# Security Policy

## Supported Versions

| Version | Supported          |
| ------- | ------------------ |
| 1.x     | :white_check_mark: |
| < 1.0   | :x:                |

## Reporting a Vulnerability

Please report security vulnerabilities via email to security@example.com.

**Do not** report security issues via public GitHub issues.

### What to Include
- Description of vulnerability
- Steps to reproduce
- Affected versions
- Potential impact

## Response Timeline

- Initial response: 48 hours
- Triage: 7 days
- Resolution: Depends on severity

## Disclosure Policy

We follow responsible disclosure...
```

### Tasks

- [ ] Create SECURITY.md
- [ ] Define supported versions
- [ ] Set up private reporting channel (email or GitHub Security Advisories)
- [ ] Define response timeline
- [ ] Document disclosure policy

## Alternatives Considered

1. **No security policy**: Handle vulnerabilities ad-hoc. Unprofessional, may discourage responsible disclosure.

2. **Public issue reporting only**: Report vulnerabilities via regular issues. Exposes vulnerabilities before fix.

3. **Bug bounty program**: Paid security research. Overkill for pre-1.0 open source project.

- [ ] Encina (core)
- [x] Other: SECURITY.md, GitHub Security settings
