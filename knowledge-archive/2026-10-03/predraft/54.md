## Decisions
- The issue was closed as "Won't Fix" because handler-level API versioning provides limited or no value, as `Asp.Versioning` natively handles HTTP-layer versioning in .NET 10 (Source: comment by dlrivada)
- API versioning should operate at the HTTP layer (controllers/endpoints) rather than at the internal CQRS handler level (Source: comment by dlrivada)
- Encina handlers are internal implementation details and do not require version attributes, as the public API surface (endpoints) declares the version (Source: comment by dlrivada)
- The recommended pattern is to use `Asp.Versioning` directly on controllers, which then call internal Encina handlers without version awareness (Source: comment by dlrivada)

## Rejected alternatives
- Integrating version-aware handler routing and deprecation support directly into Encina handlers via `[ApiVersion]` attributes on `ICommandHandler` implementations was rejected as redundant, since the endpoint already declares the version (Source: comment by dlrivada)

## Rules and lessons
- CQRS handlers are internal implementation details; API versioning belongs on the public HTTP surface (controllers/endpoints), not on internal handlers (Source: comment by dlrivada)
- Encina should leverage native ASP.NET Core/`Asp.Versioning` capabilities for contract evolution rather than implementing parallel versioning logic at the handler level (Source: comment by dlrivada)

## Candidate destinations
- claude-md: Durable rule that Encina handlers should remain agnostic to API versioning, which is an HTTP-layer concern handled by `Asp.Versioning` on controllers/endpoints
- docs: Clarify that Encina integrates with `Asp.Versioning` at the controller level, not the handler level, for contract evolution scenarios
