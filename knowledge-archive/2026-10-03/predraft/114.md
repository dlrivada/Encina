## Decisions
- Added `IModuleHealthCheck` interface in `Encina.Messaging.Health` namespace with `ModuleName` property (source: issue body, comment by dlrivada).
- Created `IModuleWithHealthChecks` interface in `Encina.AspNetCore.Modules` namespace for modules to expose health checks via `GetHealthChecks()` method (source: comment by dlrivada). Note: This differs from the issue proposal which suggested an optional `HealthChecks` property on `IModule`.
- Implemented `AddEncinaModuleHealthChecks()` and `AddEncinaModuleHealthChecks<TModule>()` extension methods for registration (source: comment by dlrivada).
- Applied automatic tagging with `encina`, `ready`, and `modules` tags to facilitate endpoint filtering (source: comment by dlrivada).
- Implemented aggregated endpoint `/health/modules` using standard ASP.NET Core health check pipeline with tag predicate `check.Tags.Contains("modules")` (source: comment by dlrivada).
- Added 9 unit tests for module health check functionality (source: comment by dlrivada).
- Updated `Encina.AspNetCore` README with documentation (source: comment by dlrivada).
- Added comprehensive health checks integration guide documentation (source: commit 1a6143d3).

## Rejected alternatives
- None explicitly rejected, but the implementation deviated from the issue's proposed `IModule` optional property approach in favor of a separate `IModuleWithHealthChecks` interface (source: comparison of issue body vs. comment by dlrivada).

## Rules and lessons
- Module health checks are registered via extension methods rather than automatically by `AddEncinaModules` as proposed in the issue; explicit opt-in registration via `AddEncinaModuleHealthChecks()` was implemented (source: comment by dlrivada).
- Health check aggregation relies on standard ASP.NET Core `MapHealthChecks` with tag-based predicates rather than a custom Encina-specific endpoint handler (source: comment by dlrivada).
