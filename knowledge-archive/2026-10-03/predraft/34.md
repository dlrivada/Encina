## Decisions
- Replace `object?` details in `EncinaError` with a type-safe dictionary structure to improve maintainability and reduce complexity. (Source: issue body)
- The implementation uses `IReadOnlyDictionary<string, object?>?` for the `details` parameter in `EncinaErrors` factory methods (`Create()`, `FromException()`) rather than the `ImmutableDictionary` initially proposed in the issue. (Source: comment by dlrivada)
- `EncinaErrorExtensions.GetDetails()` was changed to return `IReadOnlyDictionary<string, object?>` (empty dictionary instead of `None`) to simplify consumer code by removing `Option<>` unwrapping. (Source: comment by dlrivada)
- `EncinaException` normalizes `Details` to `IReadOnlyDictionary<string, object?>` on construction, and the complexity of `NormalizeMetadata()` was removed as it no longer supports arbitrary objects. (Source: comment by dlrivada)
- `GetMetadata()` is retained as an alias for `GetDetails()`. (Source: comment by dlrivada)

## Rejected alternatives
- None explicitly stated as rejected in the input, though the initial proposal for `ImmutableDictionary` was superseded by `IReadOnlyDictionary` in the implementation notes.

## Rules and lessons
- Preferring `IReadOnlyDictionary` over concrete immutable collections in public APIs allows for flexibility while maintaining type safety and simplifies the normalization logic internally. (Source: comment by dlrivada)
- Returning a default empty collection instead of a null or `None` wrapper reduces cognitive load for consumers of the error details API. (Source: comment by dlrivada)

## Candidate destinations
- docs: Update migration guides and API reference to reflect the change from `object?`/`Option<object>` to `IReadOnlyDictionary<string, object?>`.
- reviewer-checklist: Ensure that error creation sites and assertions consistently use dictionary-based details rather than anonymous objects or raw objects.
