## Decisions
- **Decision**: Do not implement the Strategy pattern for messaging transports; keep each transport as an independent package with its full API (source: comment by dlrivada).
- **Reasoning**: Transport-specific APIs (offsets, exchanges, subjects) are the primary value; unifying them would lose features (source: comment by dlrivada).
- **Alternative Approach**: Adopt a "Documentation Only" approach where transports are categorized for guidance but not enforced via code interfaces (source: comment by dlrivada).
- **NATS Handling**: Single package with two explicit modes: `UseNatsCore()` for pub/sub and `UseNatsJetStream()` for streaming (source: comment by dlrivada).
- **Testing**: Do not support runtime strategy switching; use `Encina.InMemory` package for testing (source: comment by dlrivada).
- **Scope of Choice**: Transport choice is per-application architectural, not per-message or per-module (source: comment by dlrivada).
- **gRPC/GraphQL**: Exclude from messaging strategy pattern; classify as "API Bridge" (source: comment by dlrivada).
- **Deliverable**: Create `docs/messaging/transports.md` with decision flowchart and comparison tables (source: comment by dlrivada).

## Rejected alternatives
- **Option A (Three Strategy Types)**: Rejected due to complexity and loss of transport-specific capabilities (source: issue body, comment by dlrivada).
- **Option B (Single Transport Abstraction)**: Rejected as it doesn't capture semantic differences and is easy to misuse (source: issue body, comment by dlrivada).
- **Option C (Two Categories)**: Rejected as it loses the distinction between queue-based and log-based systems (source: issue body, comment by dlrivada).
- **Runtime Strategy Switching**: Rejected; InMemory package is sufficient for testing (source: comment by dlrivada).

## Rules and lessons
- **Rule**: Fundamentally different architectural paradigms (Broker vs Stream vs Pub/Sub) should not be unified under a single abstraction if the differences are the core value (source: comment by dlrivada).
- **Rule**: When different technologies have distinct APIs and use cases, provide clear documentation and decision flowcharts rather than forcing code unification (source: comment by dlrivada).
- **Rule**: Use dedicated in-memory implementations (`Encina.InMemory`) for testing rather than complex runtime switching mechanisms (source: comment by dlrivada).
- **Pattern**: Consistency with Issues #16 (Sagas) and #17 (Event Sourcing) which also chose separation and documentation over unification (source: comment by dlrivada).

## Candidate destinations
- **docs**: Primary destination; the decision mandates the creation and maintenance of `docs/messaging/transports.md` and related TOC entries (source: comment by dlrivada).
