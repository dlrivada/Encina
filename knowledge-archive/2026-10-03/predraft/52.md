## Decisions
- Implemented snapshotting using a marker interface `ISnapshotable<TAggregate>` and snapshot data models `ISnapshot<TAggregate>` / `Snapshot<TAggregate>` (source: comment by dlrivada).
- Introduced `SnapshotOptions` to support both global and per-aggregate configuration (e.g., `SnapshotEvery`, `KeepSnapshots`) (source: comment by dlrivada).
- Created an abstraction `ISnapshotStore<TAggregate>` with a specific implementation `MartenSnapshotStore<TAggregate>` for persistence (source: comment by dlrivada).
- Developed `SnapshotAwareAggregateRepository<TAggregate>` to handle optimized loading (snapshot + remaining events replay) (source: comment by dlrivada).
- Used `SnapshotEnvelope<TAggregate>` for the structure of Marten document storage (source: comment by dlrivada).
- Standardized error handling via `SnapshotErrorCodes` and adopted high-performance logging using `LoggerMessage` source generators (source: comment by dlrivada).
- Configuration was implemented via `services.AddEncinaMarten` with a nested `Snapshots` options object and a separate `services.AddSnapshotableAggregate<T>` registration (source: comment by dlrivada).

## Rejected alternatives
- The issue body states "_Not evaluated yet_" regarding alternatives considered, and no specific rejected alternatives are documented in the comments or commit message.

## Rules and lessons
- Snapshotting should support configurable frequency (`SnapshotEvery`) and retention (`KeepSnapshots`) at both global and per-aggregate levels to accommodate varying aggregate sizes and performance needs (source: issue body and comment by dlrivada).
- Optimized loading must rely on a distinct repository implementation (`SnapshotAwareAggregateRepository`) rather than modifying the base aggregate repository behavior directly, to maintain clear separation of concerns (source: comment by dlrivada).
- Documentation updates (CHANGELOG.md, ROADMAP.md, docs/history) are required as part of the feature delivery, not just code implementation (source: comment by dlrivada).
