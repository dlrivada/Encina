## Decisions
- Apply the Orchestrator pattern to centralize validation logic and reduce code duplication across three validation providers. (Source: issue body)
- Create new abstractions in the `Encina.Validation` namespace within the core package, including `IValidationProvider`, `ValidationResult`, `ValidationError`, `ValidationOrchestrator`, and a generic `ValidationPipelineBehavior<TRequest, TResponse>`. (Source: comment by dlrivada)
- Implement provider-specific classes (`FluentValidationProvider`, `DataAnnotationsValidationProvider`, `MiniValidationProvider`) that implement the `IValidationProvider` interface. (Source: comment by dlrivada)
- Update `ServiceCollectionExtensions` in all three provider packages to register the provider-specific implementation, `ValidationOrchestrator`, and `ValidationPipelineBehavior`. (Source: comment by dlrivada)
- Remove the duplicated `ValidationPipelineBehavior` files from the individual provider packages. (Source: issue body)

## Rejected alternatives
- none

## Rules and lessons
- Centralizing behavior logic into a single generic class with a domain orchestrator ensures uniform behavior and consistency across providers. (Source: issue body - Expected Improvement; comment by dlrivada - Benefits Achieved)
- Refactoring must maintain behavioral guarantees, verified by passing the full test suite for all affected packages. (Source: issue body - Behavioral Guarantee; comment by dlrivada - Tests)

## Candidate destinations
- spec-invariant: The requirement that validation providers must implement `IValidationProvider` and delegate orchestration to `ValidationOrchestrator` defines a structural invariant for the validation subsystem.
- regression-test: The 68 validation tests (28 FluentValidation, 20 DataAnnotations, 20 MiniValidator) serve as the regression guard for this architectural change.
