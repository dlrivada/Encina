## Decisions
- Centralized `InboxPipelineBehavior`, `OutboxPostProcessor`, and `IHasNotifications` into the `Encina.Messaging` package to eliminate duplication across 12 providers (source: comment by dlrivada).
- Introduced a factory pattern with `IInboxMessageFactory`, `IOutboxMessageFactory`, `ISagaStateFactory`, and `IScheduledMessageFactory` in `Encina.Messaging` to allow providers to inject their specific entity types while using centralized logic (source: comment by dlrivada).
- Centralized saga and scheduling logic into new `SagaOrchestrator` and `SchedulerOrchestrator` classes within `Encina.Messaging` (source: comment by dlrivada).
- Accepted intentional code duplication in Store implementations (`OutboxStore`, `InboxStore`, `SagaStore`, `ScheduledMessageStore`) due to SQL dialect differences and excluded these specific files from SonarCloud analysis via `sonar-project.properties` (source: comment by dlrivada, commit c66625f5).

## Rejected alternatives
- **Option 1: Abstract Base Classes**: Rejected because it adds complexity and tighter coupling between providers, contrary to the design goal of provider independence (source: issue body).
- **Option 2: SQL Template Approach**: Not fully implemented for Store classes; instead, specific behavioral components were centralized, and remaining SQL-level duplication was excluded from analysis rather than templated (source: issue body, comment by dlrivada).
- **Option 3: Accept Intentional Duplication**: Partially adopted for the core Store SQL logic, but active refactoring was performed first to centralize non-SQL-specific behaviors (source: issue body, comment by dlrivada).

## Rules and lessons
- Providers must remain independent and self-contained; cross-provider dependencies should be avoided (source: issue body).
- When SQL dialects differ significantly (e.g., `TOP` vs `LIMIT` vs `FETCH FIRST`), maintaining separate implementations for Store classes is preferred over abstraction to ensure clarity and performance (source: comment by dlrivada).
- Shared behavioral logic (piping, post-processing, orchestration) should be centralized in a core messaging package using dependency injection for provider-specific factories (source: comment by dlrivada).

## Candidate destinations

- docs: Add documentation on the factory pattern used for provider-specific entity creation.
