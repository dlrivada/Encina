## Decisions
- The request to increase the global line coverage threshold to 85% was rejected because the "single-percentage coverage model" is obsolete. (source: comment by dlrivada)
- Coverage is now measured per flag (unit, guard, contract, property, integration) against per-package targets defined in `.github/coverage-manifest/`. (source: comment by dlrivada)
- Coverage metrics are computed by `.github/scripts/coverage-report.cs` and displayed on the coverage dashboard. (source: comment by dlrivada)
- Mutation score is tracked per file with no project-wide target. (source: comment by dlrivada)
- Gaps against current targets are to be tracked as individual `[TEST]` issues per package. (source: comment by dlrivada)

## Rejected alternatives
- Keeping the current threshold (45%) was rejected in the original issue as degrading quality. (source: issue body)
- Gradual increases (45%→65%→85%) were rejected in the original issue as delaying quality improvement. (source: issue body)
- Package-specific thresholds were rejected in the original issue as creating inconsistent quality standards, though the final closure decision effectively moved to a per-package manifest model. (source: issue body)

## Rules and lessons
- Do not use a single global percentage threshold for code coverage; use the per-flag, per-package model in `.github/coverage-manifest/`. (source: comment by dlrivada)
- Do not track mutation score with a project-wide target; track it per file. (source: comment by dlrivada)
- Coverage gaps should be managed via specific `[TEST]` issues rather than broad technical debt issues for threshold changes. (source: comment by dlrivada)
- Avoid hard-coding quality or inventory figures in documentation (README, ROADMAP, architecture pages), as this model is dynamic. (source: PR #1300)
