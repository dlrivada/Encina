## Decisions
- To implement architecture testing using **ArchUnitNET** rather than NetArchTest, manual code review, or custom reflection-based checks, because ArchUnitNET was deemed to have better rule composition and more active maintenance. (Source: Issue body - Alternatives Considered)
- To create a new package named **`Encina.Testing.Architecture`** to house the architectural rules, keeping it separate from the core `Encina` package and other infrastructure packages. (Source: Issue body - Affected Packages, Proposed Solution)
- To provide a static class `EncinaArchitectureRules` containing pre-defined `IArchRule` instances for CQRS, Layered Architecture, Messaging, and Pipeline patterns, along with an abstract `EncinaArchitectureTestBase` class to facilitate test setup. (Source: Issue body - Proposed Solution)
- To position this as the first foundational package for the **v0.11.0 Testing Infrastructure milestone**. (Source: Comment by dlrivada)

## Rejected alternatives
- **NetArchTest**: Rejected in favor of ArchUnitNET due to superior rule composition and maintenance status. (Source: Issue body - Alternatives Considered)
- **Manual code review for architecture**: Rejected as it is not scalable, error-prone, and misses violations. (Source: Issue body - Alternatives Considered)
- **Custom reflection-based checks**: Rejected as it reinvents existing solutions and incurs a higher maintenance burden. (Source: Issue body - Alternatives Considered)

## Rules and lessons
- Architecture rules should be codified and enforced in CI/CD to ensure continuous compliance and detect layer violations automatically. (Source: Issue body - Motivation)
- When selecting architectural testing libraries, prioritize those with robust rule composition capabilities and active maintenance. (Source: Issue body - Alternatives Considered)
- Architectural testing features should be isolated in a dedicated package (`Encina.Testing.Architecture`) to maintain modularity and prevent core package bloat. (Source: Issue body - Affected Packages)
