## Decisions
- The issue was closed because the premise of a project-wide 95% mutation score target is no longer valid; Encina now measures coverage per flag (unit, guard, contract, property, integration) against per-package targets (source: comment by dlrivada).
- Mutation score is now tracked per file with no project-wide target (source: comment by dlrivada).
- Gaps against per-package coverage targets are to be tracked as individual [TEST] issues per package (source: comment by dlrivada).
- Hand-typed quality and inventory figures were removed from README, ROADMAP, and architecture pages to align with the new measurement model (source: linked PR #1300).

## Rejected alternatives
- Retaining a global mutation score target of >=95% for the entire project (source: comment by dlrivada explaining the shift away from the old single-percentage model).

## Rules and lessons
- Mutation testing metrics are managed per file rather than as a monolithic project-wide percentage (source: comment by dlrivada).
- Coverage targets are defined per package and per test flag in `.github/coverage-manifest/` rather than in high-level documentation (source: comment by dlrivada).
- Documentation should not contain hardcoded metric figures that diverge from computed coverage reports (source: linked PR #1300 title).

## Candidate destinations
- spec-invariant: The mutation testing methodology has changed from a global target to a per-file tracking model, which is a durable architectural decision for the testing strategy.
- coverage-manifest: The decision to rely on `.github/coverage-manifest/` for per-package targets is a structural invariant for how test success is determined.
- docs: The removal of hand-typed figures from README/ROADMAP supports the lesson that documentation should reference computed sources, not static numbers.
