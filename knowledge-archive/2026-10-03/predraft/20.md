## Decisions
- Code duplication in `Log.cs` and `TransactionPipelineBehavior.cs` was consolidated into the `Encina.Messaging` package (source: issue body / comment by dlrivada)
- A centralized `MessagingLog.cs` and `TransactionPipelineBehavior.cs` were created in `Encina.Messaging` (source: comment by dlrivada)
- Duplicated `Log.cs` and `TransactionPipelineBehavior.cs` files were removed from all 8 provider packages (source: comment by dlrivada)
- Security rule suppressions (S2077) and a ReDoS fix (S6444) were included in the related commits (source: comment by dlrivada)

## Rejected alternatives
- Maintaining provider-specific `Log.cs` and `TransactionPipelineBehavior.cs` implementations (rejected due to high duplication ratio of ~11% and maintenance overhead) (source: issue body)
- Consolidating SQL scripts and Store implementations (rejected as "intentional duplication" due to dialect-specific requirements like TOP vs LIMIT) (source: issue body)

## Rules and lessons
- Provider-specific SQL dialects and entity mappings should remain separate in their respective provider packages (source: issue body)
- Shared behavioral logic (logging, transaction pipeline) should reside in the core `Encina.Messaging` package (source: issue body)
- Refactoring must not change external behavior or break the public API (source: issue body)

## Candidate destinations
- adr: Records the architectural decision to centralize logging and transaction behaviors in Encina.Messaging while preserving provider-specific SQL logic
- reviewer-checklist: Add check for ensuring no new cross-provider code duplication is introduced for non-dialect-specific logic
