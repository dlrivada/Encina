## Decisions
- Implement transparent message encryption/decryption for sensitive data in Outbox/Inbox patterns to meet regulatory compliance (GDPR, HIPAA, PCI-DSS). (Source: issue body)
- Create core abstractions `IMessageEncryptionProvider`, `EncryptedPayload`, and `EncryptionContext`. (Source: issue body)
- Implement attribute-based encryption using `[Encrypted]` (message-level) and `[EncryptedField]` (field-level). (Source: issue body)
- Support multi-tenant environments with tenant-specific keys via `TenantKeyResolver`. (Source: issue body)
- Use a new package family `Encina.Messaging.Encryption` to complement existing `Encina.Security.Encryption` (field-level) by adding payload-level encryption at the messaging storage layer. (Source: comment by dlrivada)
- Encrypt the serialized `Content` field before persistence to protect data at rest and in transit, benefiting all database providers automatically without per-provider implementations. (Source: comment by dlrivada)
- Deliver 4 new satellite packages: `Encina.Messaging.Encryption` (core), `Encina.Messaging.Encryption.AzureKeyVault`, `Encina.Messaging.Encryption.AwsKms`, and `Encina.Messaging.Encryption.DataProtection`. (Source: comment by dlrivada)
- Use AES-256-GCM encryption via `Encina.Security.Encryption`. (Source: comment by dlrivada)
- Implement a `EncryptingMessageSerializer` decorator for transparent encryption with zero changes to existing handlers. (Source: comment by dlrivada)
- Use the attribute `[EncryptedMessage]` per-type or `EncryptAllMessages` globally. (Source: comment by dlrivada)
- Use Railway Oriented Programming, with all operations returning `Either<EncinaError, T>`. (Source: comment by dlrivada)
- Use a compact payload format: `ENC:v1:{KeyId}:{Algorithm}:{Nonce}:{Tag}:{Ciphertext}`. (Source: comment by dlrivada)
- Add observability with OpenTelemetry tracing (2 activities) and metrics (4 instruments), plus a health check for roundtrip verification. (Source: comment by dlrivada)
- Define 9 domain error codes under `msg_encryption.*`. (Source: comment by dlrivada)
- Commit `e2c9259` added the feature, and `c694b16` fixed whitespace formatting. (Source: input)
- Linked PR #1113 promoted nine rules into CLAUDE.md and recorded ADR-027..030. (Source: input)

## Rejected alternatives
- **Transport encryption only** (TLS for message broker connections): Rejected because it does not protect data at rest and is vulnerable to insider threats. (Source: issue body)
- **Application-level encryption** (manual encryption in handlers): Rejected because it is inconsistent, error-prone, and lacks centralized key management. (Source: issue body)
- **Database encryption only** (Database TDE): Rejected because it does not protect data in transit through message brokers. (Source: issue body)
- **Extending existing packages** (Option B in design choices): Rejected in favor of new `Encina.Messaging.Encryption` packages for clean separation and independent observability. (Source: comment by dlrivada)

## Rules and lessons
- Field-level encryption (`Encina.Security.Encryption`) and payload-level encryption (`Encina.Messaging.Encryption`) are complementary layers operating at different points in the lifecycle. (Source: comment by dlrivada)
- Message encryption should wrap the serialized `Content` string before it reaches `IOutboxStore.AddAsync()` to ensure provider-agnostic benefit. (Source: comment by dlrivada)
- The implementation must achieve >90% unit test coverage. (Source: issue body)
- Key rotation must be supported without requiring re-encryption of existing messages. (Source: issue body)
- The feature is categorized as provider-independent, meaning no specific database provider implementation is required for the core encryption logic. (Source: comment by dlrivada)
