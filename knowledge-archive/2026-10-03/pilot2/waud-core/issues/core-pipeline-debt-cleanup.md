## Description

Three small, unrelated findings from the SPEC-003 pilot 2 deep quality audit of the core request pipeline audit unit (`src/Encina/Pipeline/**`, `src/Encina/Core/**`, `src/Encina/Dispatchers/**`), grouped here per SPEC-003 §5.4 because each is a `[DEBT]`-sized fix within the same audit unit:

1. **Compatibility alias without `[Obsolete]` (AUD-18).** `Core/ServiceCollectionExtensions.cs:13-23` declares `AddApplicationMessaging` (two overloads), documented in its own XML summary as a "Legacy alias for `AddEncina(...)`". `CLAUDE.md` states "No Legacy Code" and "No Migration Paths" as mandatory for this pre-1.0 codebase, and AUD-18 explicitly checks for "no `[Obsolete]` member, compatibility alias or migration helper". This is a compatibility alias kept without even an `[Obsolete]` marker.
2. **Coverage manifest misdeclaration (AUD-03).** `.github/coverage-manifest/Encina.json`'s entry for `Core/EncinaConfiguration.cs` has `"reason": "EF entity type configuration"`, which describes an unrelated class shape used elsewhere in the manifest for EF Core entity configuration classes. `EncinaConfiguration.cs` is the mediator's own fluent registration configuration (`RegisterServicesFromAssemblies`, `AddPipelineBehavior`, `AddRequestPreProcessor`, `AddRequestPostProcessor`) and has no EF Core dependency at all.
3. **Coverage manifest under-declaration (AUD-03).** The same entry lists only `"unit"` in `defaultTests`, but `tests/Encina.GuardTests/Core/EncinaConfigurationGuardTests.cs` exists, passes, and was measured exercising 71.1% of the file's lines under the guard flag (2026-09-24) — `guard` should be listed as an applicable flag.
4. **Stale "backward compatibility" wording (adjacent to AUD-18).** `Dispatchers/Strategies/SequentialDispatchStrategy.cs:11`'s XML remarks read "This is the default strategy and maintains backward compatibility with existing behavior." The project is pre-1.0 with no external users to maintain compatibility for (`CLAUDE.md`, "Pre-1.0 Development Status"); the wording should describe why it is the default, not imply a compatibility constraint that does not exist.

## Location

- **File(s)**: `src/Encina/Core/ServiceCollectionExtensions.cs`, `src/Encina/Dispatchers/Strategies/SequentialDispatchStrategy.cs`, `.github/coverage-manifest/Encina.json`
- **Package(s)**: `Encina` (core)

## Current Behavior

See the four points above.

## Expected Behavior

1. `AddApplicationMessaging` is either removed (breaking change, acceptable pre-1.0) or the maintainer decides to keep it as a first-class name rather than a "legacy alias" — either way the "legacy" framing goes away.
2. The manifest's `reason` for `Core/EncinaConfiguration.cs` describes what the file actually is.
3. The manifest's `defaultTests` for `Core/EncinaConfiguration.cs` includes `guard`.
4. `SequentialDispatchStrategy`'s remarks describe its role (fail-fast, in-order dispatch) without invoking backward compatibility.

## Root Cause

1. Likely carried over from an early rename of `AddApplicationMessaging` to `AddEncina` where the old name was kept as a convenience alias and never revisited under the (later-written) "no legacy code" rule.
2. Manifest entries 2-3 were most likely generated by copying a nearby template entry (`*Configuration.cs` → EF entity configuration reason) without checking the specific file.
4. Doc wording pre-dates the CLAUDE.md pre-1.0 philosophy section, or was copied from a template comment.

## Proposed Fix

1. Bring `AddApplicationMessaging` to the maintainer as a decision item: remove it (pre-1.0 breaking changes are expected and encouraged) or keep it and drop the "legacy" language. Do not fix silently — removing a public API is a `mechanical-fixer`-unsuitable, judgement-bearing change.
2. `mechanical-fixer` corrects the `reason` string in the manifest.
3. `mechanical-fixer` adds `"guard"` to the `defaultTests` array for that entry.
4. `mechanical-fixer` rewords the XML remarks.
