## Findings

1. **Blocker** — Five transport packages dispose their DI-singleton client from a scoped publisher: `src/Encina.NATS/NATSMessagePublisher.cs:14,191-194` (`DisposeAsync` awaits `_connection.DisposeAsync()`), `src/Encina.RabbitMQ/RabbitMQMessagePublisher.cs:13,158-162` (closes `_channel` and `_connection`), `src/Encina.MQTT/MQTTMessagePublisher.cs:14,165-173` (`_client.Dispose()` at :172), `src/Encina.AzureServiceBus/AzureServiceBusMessagePublisher.cs:13,201-204` (`DisposeAsync` awaits `_client.DisposeAsync()`; `_client` is the constructor-injected `ServiceBusClient`, :15,26,34) and `src/Encina.Kafka/KafkaMessagePublisher.cs:13,196-200` (`Dispose()` calls `_producer.Flush(TimeSpan.FromSeconds(10))` then `_producer.Dispose()`; `_producer` is the constructor-injected `IProducer<string, byte[]>`, :15,26,34). In every case the disposed object is a DI singleton (`src/Encina.NATS/ServiceCollectionExtensions.cs:42` `TryAddSingleton<INatsConnection>`; `src/Encina.RabbitMQ/ServiceCollectionExtensions.cs:42,56` `TryAddSingleton` for `IConnection` and `IChannel`; `src/Encina.MQTT/ServiceCollectionExtensions.cs:43` `TryAddSingleton<IMqttClient>`; `src/Encina.AzureServiceBus/ServiceCollectionExtensions.cs:47-48` `TryAddSingleton` of `ServiceBusClient`; `src/Encina.Kafka/ServiceCollectionExtensions.cs:42-59` `TryAddSingleton` of the `ProducerBuilder<string, byte[]>(...).Build()` producer) while the publisher that wraps and disposes it is registered `TryAddScoped` (NATS `:61`, RabbitMQ `:62`, MQTT `:72`, AzureServiceBus `:50`, Kafka `:61`). The .NET DI container disposes every disposable service it created when the owning scope ends, so the first time a consumer resolves the publisher inside a scope that later ends (an ASP.NET Core request scope, `IServiceScopeFactory.CreateScope()` in a handler, a background-job scope) the shared singleton connection/channel/client/producer is closed for the rest of the application's lifetime, and every later publish on that transport fails until the app restarts. This is a scope-vs-singleton lifetime defect that `ValidateOnBuild`/`ValidateScopes` do not catch (they catch captive dependencies, not premature disposal of a longer-lived dependency by a shorter-lived owner) and it fails the AGENTS.md §3 registration-completeness expectation that an `AddEncina*` registration is safe to build and use in any composition. Kafka additionally blocks the disposing thread for up to 10 seconds in a synchronous `Flush` inside a container-invoked `Dispose()`. Fix per package: register the publisher as a singleton (none of the five holds per-request state) or remove the publisher's `Dispose`/`DisposeAsync` so only the container's singleton-disposal path owns the connection. Only `Encina.AmazonSQS` (and the non-broker transports listed under Siblings audited) is unaffected.

2. **Major** — `docs/messaging/transports.md:293` and `:305` document `services.AddEncinaNatsCore(options => ...)` and `services.AddEncinaNatsJetStream(options => ...)` as the NATS configuration API, but `src/Encina.NATS/ServiceCollectionExtensions.cs:13-72` exposes only one extension method, `AddEncinaNATS(Action<EncinaNATSOptions>? configure = null)`, with a `UseJetStream` boolean on `EncinaNATSOptions` (referenced at `ServiceCollectionExtensions.cs:34`, `:51`) selecting JetStream mode. A developer following the doc's NATS section verbatim gets a compile error (`'IServiceCollection' does not contain a definition for 'AddEncinaNatsCore'`) for both code samples shown. This is doc/code drift already surfaced by the archivist's own verification and recorded as the knowledge record's one `remediation` item; recording it here too because it is the code-stage's own confirmed finding (re-verified against current `ServiceCollectionExtensions.cs`, unchanged since the archivist's read) and it fails AUD item "doc examples match the shipped public API."

3. **Major** — `src/Encina.RabbitMQ`, `src/Encina.Kafka`, `src/Encina.NATS`, `src/Encina.AzureServiceBus` and `src/Encina.AmazonSQS` each contain only an options class, an `I{X}MessagePublisher` interface, its implementation, `Log.cs`, `ServiceCollectionExtensions.cs` and a health check (confirmed by full directory listing of all five packages) — none has a subscribe, consume or dead-letter-handling type anywhere in the package. Grepping all five for `SubscribeAsync|ConsumeAsync|Subscribe\(` and for `DeadLetter|DLQ|DeadLetterQueue` returns zero matches in every one. This contradicts AGENTS.md §5's Transports row, which lists "subscription management" and "error handling and DLQ" as things "every provider MUST support" for the same category this issue's own decision defines (`docs/messaging/transports.md`'s FAQ, condensed from the issue, is the source of that "every transport keeps its full native API" promise). Only `Encina.MQTT`, `Encina.Redis.PubSub` and `Encina.InMemory` (of the 8 messaging transports; `Encina.gRPC` and `Encina.GraphQL` are API bridges, and `Encina.GraphQL` declares `SubscribeAsync` at `GraphQLMediatorBridge.cs:124` as a bridge API, not as transport subscription management) actually implement `SubscribeAsync`/`Subscribe` — the other 5 (all message-broker/streaming transports, arguably the ones where subscription and DLQ matter most) are send-only. This is a real gap in the coherence the issue's decision asserts as already achieved, not merely a doc claim, against the AGENTS.md rule that applies today. The doc also presents consume samples for four of these five: `docs/messaging/transports.md` shows `IMessageHandler<OrderCreated>` at :235 (RabbitMQ section), `consumer.ConsumeFromAsync(` at :270-273 (Kafka), `consumer.ReplayFromAsync(` at :316 (NATS JetStream) and `consumer.StartAsync(ct)` at :365 (Amazon SQS); only the Azure Service Bus section (:321-344) has none. A `Select-String` for `ConsumeFromAsync|ReplayFromAsync|interface IMessageHandler|IKafkaMessageConsumer|StartAsync\(` over `src/Encina.{RabbitMQ,Kafka,NATS,AzureServiceBus,AmazonSQS}` returns 0 matches, so those consumer APIs shown in the doc do not exist in these packages; the doc therefore over-claims the same gap it was meant to describe.

4. **Minor** — `src/Encina.RabbitMQ/ServiceCollectionExtensions.cs:53` (`factory.CreateConnectionAsync().GetAwaiter().GetResult()`) and `:59` (`connection.CreateChannelAsync().GetAwaiter().GetResult()`), and `src/Encina.MQTT/ServiceCollectionExtensions.cs:67` (`client.ConnectAsync(connectOptions).GetAwaiter().GetResult()`) block synchronously on an async connect inside a singleton factory delegate evaluated at first resolution (typically host startup). This is the same sync-over-async anti-pattern AGENTS.md §3 calls out for database calls (Sonar S6966); it is not a database call here, but the risk (thread-pool stall, potential deadlock under a captured `SynchronizationContext`) is the same class of defect and it fires on every application start, not just in a hot path. Lower severity than finding 1 because ASP.NET Core's default host has no synchronization context and this path runs once per process, but it is a real defect a reviewer should flag today.

## Siblings audited

Method for finding 1's siblings (re-run 2026-10-02 after the verifier's FAIL): `Select-String` over every non-obj/bin `.cs` file of all ten transport packages for `IDisposable|IAsyncDisposable|DisposeAsync|void Dispose\(|\.Dispose\(`, plus `TryAdd*`/`Add*` lines of each package's `ServiceCollectionExtensions.cs`. The first-run claim that Kafka and AzureServiceBus were clean was wrong (it searched only for `IAsyncDisposable`, missing Kafka's `IDisposable`, and missed AzureServiceBus's own `IAsyncDisposable`).

- `Encina.Kafka` (`KafkaMessagePublisher.cs:13,196-200`, `: IKafkaMessagePublisher, IDisposable`, disposes injected `IProducer`; producer singleton `ServiceCollectionExtensions.cs:42`, publisher scoped `:61`) and `Encina.AzureServiceBus` (`AzureServiceBusMessagePublisher.cs:13,201-204`, disposes injected `ServiceBusClient`; client singleton `:47`, publisher scoped `:50`): both **reproduce finding 1**. They also exhibit finding 3 (no subscribe/DLQ).
- `Encina.AmazonSQS`: zero matches for any dispose pattern in the package; `IAmazonSQS` and `IAmazonSimpleNotificationService` are `TryAddSingleton` (`ServiceCollectionExtensions.cs:42,51`) and the publisher `TryAddScoped` (`:60`) without disposing them — does **not** reproduce finding 1 (checked, 0 matches). It exhibits finding 3.
- `Encina.Redis.PubSub`: publisher implements `SubscribeAsync`/`SubscribePatternAsync` (`RedisPubSubMessagePublisher.cs:86,121`) with `RedisSubscription : IAsyncDisposable` (`:164,173`), a per-call subscription handle, not the shared `IConnectionMultiplexer` (singleton `ServiceCollectionExtensions.cs:38`; publisher scoped `:46`); the publisher class itself implements no disposable interface (search above lists only `:164,173` in the implementation file) — does not reproduce finding 1.
- `Encina.InMemory`: `InMemoryMessageBus` is registered `TryAddSingleton` (`ServiceCollectionExtensions.cs:35`), not scoped, and already implements `Subscribe<TMessage>` (`InMemoryMessageBus.cs:151`) — consistent with the category requirement and free of finding 1's lifetime mismatch (singleton depending on singleton).
- `Encina.MQTT`'s per-subscription `MqttSubscription<TMessage>`/`MqttPatternSubscription<TMessage>` (`MQTTMessagePublisher.cs:176,229`) are per-call handles, separate from the publisher-level dispose in finding 1.
- Sync-over-async (finding 4) siblings: `Select-String` for `GetAwaiter().GetResult|.Result|.Wait()` over RabbitMQ, Kafka, NATS, AzureServiceBus, AmazonSQS, Redis.PubSub, InMemory, MQTT returns exactly the three hits in finding 4 and no others.
- `Encina.gRPC`, `Encina.GraphQL`: no dispose pattern in either package (search above, 0 matches); otherwise not read in depth — the issue's own decision classifies both as "API Bridge," explicitly outside the messaging-transport categorization and outside `docs/messaging/transports.md`'s per-transport table (archivist confirmed this), so they were not audited against the transport coherence row.
- `docs/messaging/transports.md`'s other per-transport code samples (RabbitMQ, Kafka, AzureServiceBus, AmazonSQS, Redis.PubSub, MQTT, InMemory) were spot-checked for method names against their packages' `ServiceCollectionExtensions.cs`/public interfaces; only the NATS section (finding 2) showed drift.

## Lessons for the pipeline

- A documentation-only SPIKE whose decision asserts "provider X and Y stay coherent on capability Z" is a standing claim about the current state of `src/`, not just about the day the issue closed; the code stage should grep the category's AGENTS.md-required capabilities (here: subscription management, DLQ) across every sibling package the decision names, not only re-verify the one drift the archivist already found.
- A DI-lifetime bug worth a standing check for any provider package: when a package registers a connection/client type `TryAddSingleton` and a wrapper around it `TryAddScoped`/`TryAddTransient`, check whether the wrapper implements `IAsyncDisposable`/`IDisposable` and, if so, whether its `Dispose`/`DisposeAsync` body touches the injected singleton — the .NET container disposing a scoped service at scope-end will call that method and can prematurely tear down a singleton shared by the whole app. This pattern recurred identically (close/dispose the injected connection in the scoped publisher's `Dispose`/`DisposeAsync`) across five transport packages (NATS, RabbitMQ, MQTT, AzureServiceBus, Kafka), suggesting it was copied from a shared template — worth checking any other package built from the same template (locks, caching decorators) for the same shape.
- A negative sibling claim ("package X does not have this bug") needs a search for every variant of the pattern (`IDisposable`, `IAsyncDisposable`, `Dispose(`, `DisposeAsync`) across the whole package, with the command and result count recorded beside the claim; the first run searched for one interface name and wrongly cleared Kafka (`IDisposable`) and AzureServiceBus (its own `IAsyncDisposable`).
