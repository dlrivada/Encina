## Findings

1. **Major** — No automated gate enforces that each flag reaches its own manifest target, which AGENTS.md section 9 states as a MUST ("Each flag MUST independently reach its own target ... do NOT push or merge until every applicable flag reaches its target"). `.github/scripts/coverage-report.cs:657-661` and `:760` only copy `perFlagTarget` into the JSON; nothing compares a flag's coverage with it and the script's only non-zero exits are the `--check-stale-manifest`/`--check-missing-manifest` modes (`:143-173`). The markdown report's `Gap` column is a hardcoded empty cell (`:715`). The comment at `:604-607` says missing flags "penalize via the flag target check", but no such check exists. `.github/workflows/ci-full.yml:475` runs the script with `|| true` and the only follow-up gate (`:480-496`) fails solely when no index exists or every entry is `noData`. A package's per-flag aggregate silently omits a flag that produced no data (`coverage-report.cs:592-600`, `FlagPct` `:928-935` renders "-"), a Cobertura parse error is printed and skipped (`:507-510`), and the `coverage` job runs `if: always()` (`ci-full.yml:433`), so a run with a failed integration shard is published as if complete. `ci.yml` gates only CRAP on changed methods (`:493-543`); `codecov.yml:15-24` sets project `target: auto` and patch 60%, with `require_ci_to_pass: false`, and no per-flag target. The methodology page even states "the real enforcement happens at the per-package level where manifests carry explicit numbers" (line 192), but the only enforcement is manual. Fails AGENTS.md section 9; the backlog this hides is real (open #1389: guard flag below target in 42 of 99 packages; open #1450 asks for a per-flag PR comment as fallback). Decide: add a per-flag target check (report-only first, with a ratchet) or reword AGENTS.md section 9 to say targets are advisory.

2. **Major** — The issue and PR templates still carry the old 85% single target, and they are the tool that tracks per-package gaps (the issue's own decision: "Gaps ... tracked as [TEST] issues per package"). `.github/ISSUE_TEMPLATE/test_implementation.md:18` ("Coverage Gap (below 85% target)"), `:35` (example row `62.3% | 85% | -22.7%`), `:56` ("Coverage meets ≥85% target"); `.github/ISSUE_TEMPLATE/epic.md:65` ("coverage ≥85%"); `.github/ISSUE_TEMPLATE/feature_request.md:182` ("Code coverage >= 85%"); `.github/pull_request_template.md:20` ("Coverage does not decrease below threshold", a threshold that no longer exists). Open #1627 shows the symptom: it leaves the 85% box unticked and writes "target (55) ... package-wide" in the table by hand. Fails the AGENTS.md section 9 "no project-wide percentage / no hand-typed figures" model; known failure pattern: a rejected rule surviving in a template. Note `.claude/hooks/tests/Test-Hooks.ps1:2484` embeds the example row `| Example.Package | 62.3% | 85% | -22.7% |` as a fixture, so the hook test must be updated together with the template.

3. **Major** — Agent and skill instructions that AGENTS.md section 12 routes to tell agents the opposite of section 9. `.opencode/skills/test-workflow/SKILL.md:28-32` lists per-flag targets "≥85% line" for Unit, Guard, Contract and Integration and "≥80% branch" for Property; `.opencode/agents/encina-test.md:19-23` the same plus "≥90% method"; `.opencode/skills/release-checklist/SKILL.md:32-34` lists "Line ≥85%, Branch ≥80%, Method ≥90% | Overall codebase" as release gates. AGENTS.md section 9 says targets come from `.github/coverage-manifest/{Package}.json` and branch/method are informational (`docs/engineering/AI-DEVELOPMENT-MODEL.md:103,128` already calls this "documentation drift"). An agent following the skill chases 85% per flag against manifests that top out at unit 80 and mostly sit at 55-70 (manifest scan: unit targets 30-80, guard 7-25, contract 5-20). Fails AGENTS.md section 9.

4. **Major** — The public coverage dashboard hard-codes a project-wide "target 85%" line. `docs/coverage/app.js:817-831` draws a dashed line and the label `'target 85%'` on the overall trend chart. No manifest, methodology page or AGENTS.md defines an overall target (methodology lines 184-192 say the overall headline "has no manifest target"). This is the single-percentage model of issue #19 rendered on the page the project cites as the result of the per-flag model. Fails AGENTS.md section 9 (no project-wide percentage; no hand-typed target figures).

5. **Minor** — Open issues still state the old global target: #901 "Increase coverage for 13 low-coverage modules (1-59%) to ≥85%" (body: "well below the project target of ≥85%", per-module "Cov%" table with no flag or manifest target, dated 2026-03-25); #910 "Increase coverage for 8 mejorable modules (60-79%) to reach 85%"; #521 "[DEBT] Web packages coverage below 85% target". 7. **Minor** — `coverage-report.cs` carries a generated HTML dashboard that cannot work and is not published. `GenerateHtmlDashboard` (`:979-1173`) renders from `categories`, `p.category` and `p.target`, none of which is defined ("Categories removed", `:37`, `:370`): `renderCategories()` (`:1087-1095`, called `:1168`) throws a ReferenceError, so the package table and chart never render, and the package JSON (`:987-996`) has `perFlagTarget` but no `target`. The file is uploaded in the `coverage-report` artifact (`ci-full.yml:510-516`) but `publish-coverage.yml:109-120` copies only the JSON and badges; the live dashboard is `docs/coverage/app.js`. 8. **Minor** — Legacy single-threshold artifacts remain. `.github/scripts/coverage-weights.json` (categories with targets up to 85.0, e.g. "Full" at 85.0) is unreferenced by any script, workflow or test (grep: only the methodology page mentions it, line 151, "kept ... as historical documentation"); ADR-023 still records a category target table (`docs/architecture/adr/023-coverage-strategy-codecov-sonarcloud.md:66-83`, "Core Logic 85%") and says per-module thresholds are enforced by Codecov Components (`:35-37`, `:45`), while `codecov.yml:26-27` says Components are unavailable and `.github/coverage-manifest/Encina.json` holds unit 70. 9. **Minor** — Reusable workflow templates expose a single global line-coverage threshold and enforce it with `python`. `.github/workflows/templates/encina-test.yml:44-47` (input `coverage-threshold`, "Minimum line coverage percentage") and `:216-244`, `encina-full-ci.yml:50`, `:276-303` compute one percentage and fail below it; the comparison runs `python3 -c`/`python -c` (`encina-test.yml:240-241`, `encina-full-ci.yml:299-300`), which AGENTS.md section 2 forbids; `encina-test.yml:17` and `encina-full-ci.yml:20` show `coverage-threshold: '80'` as the documented usage, and `tests/Encina.UnitTests/Workflows/WorkflowTemplateTests.cs:160` asserts the input exists. 10. **Minor** — `.github/scripts/check-sonarcloud-coverage.cs:80-98` hard-codes an 80% project-wide coverage verdict ("meets quality gate threshold (80%)", "target is 80%") and nothing references the script (grep finds only its own header); ADR-023 decision 3 says SonarCloud no longer receives coverage, so the output is always "no coverage data". 11. **Minor** — The blocking `crap-gate` job passes vacuously when no coverage was collected. `.github/workflows/ci.yml:538-541` prints "nothing to gate." and `exit 0` when no `coverage.cobertura.xml` was downloaded, while every flag job uploads with `if-no-files-found: ignore` (`ci.yml:171,245,284,323,362,472`); the job comment (`:491-492`) claims a broken gate "fails loudly instead of silently passing every PR". ## Lessons for the pipeline

- When the archivist finds no `src/` scope for a rejected-by-replacement issue, the code stage's real surface is the replacement's own enforcement path (`.github/scripts`, workflows, templates, dashboards, agent skill files). The scope list should name those files so the code stage does not start from nothing.
- For "rejected number" issues, grep the whole tree (templates, skills under `.opencode/` and `.claude/`, dashboard JS, open issue titles and bodies via `gh issue list --search`) for the literal figure; the archivist's search of README/ROADMAP/CLAUDE.md/AGENTS.md found none and missed every real leftover.
- A rule stated as MUST in AGENTS.md needs an enforcing job; the audit should always check "who fails when this is violated?" and record "nobody" as a finding, not accept a documented intent.
