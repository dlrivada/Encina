# Lessons for pr-reviewer

- (2026-09-27, #1459, #1460) Read post-PR file contents from the PR's worktree or `FETCH_HEAD`, never from the main checkout: main does not have the PR's changes yet, so a "missing" symbol there is not a finding. (read post-PR files from the worktree or FETCH_HEAD)
- (2026-09-27, #1507) A worktree may be based one merge behind `origin/main`; before calling something in the worktree a finding, check `git merge-base <branch> origin/main` and `gh pr diff <n>` — an already-fixed file can look broken in a stale worktree while the real PR diff excludes it. (check the merge base and gh pr diff before reporting a worktree-only finding)
- (2026-09-27, #1462, #1465) A knowledge record under `docs/knowledge/issues/` in an open PR is required by SPEC-003 REQ-031, not scope creep; its `prs`/`linked_prs` are filled by the orchestrator after the PR opens. (knowledge records in open PRs are expected)
- (2026-09-27, #1462, #1498) For a leak or rename PR, grep every log-message method name and parameter name repo-wide, including methods with no caller: a dead overload or duplicate log class with a stale `errorMessage` parameter is a trap for the next contributor. (grep log-method and parameter names repo-wide, dead ones included)
- (2026-09-27, #1495) When a PR deletes a `src/` file, check `.github/coverage-manifest/<Package>.json` for an entry that still names it; no CI gate catches a stale entry yet (#1497). (check the coverage manifest when a src file is deleted)
- (2026-09-27, #1496) You are read-only: never try a red/green check by editing source to revert a fix (enforce-path-ownership blocks it, correctly). Trace statically and say so; the orchestrator asks the issue-worker, who owns the worktree, for the red/green proof. (never edit source for red/green; trace statically)
- (2026-09-27, #1500) Independently re-grep any "I grepped and nothing else was missed" claim in the PR, especially across extract-method refactors where a call site moves to a new method name. (re-grep the PR's own completeness claims)
- (2026-09-27, #1502) When a fix removes a capability to make a failure structurally impossible instead of adding the instruction the issue proposed, say so explicitly rather than silently marking the criterion met; for a tools-allowlist PR, grep for a standalone (non-OR'd) tool-name hook matcher to see whether the other tool's path is still guarded. (name mechanism substitutions; grep for standalone tool matchers)
- (2026-09-27, #1508) A PR that changes a blocking gate (crap-gate, coverage, link check) gets an adversarial fixture: build a small input that tries to make a real violation escape (here an unsequenced changed line inside a closure nested in a complex method) and run the PR's script against it. When a rule picks one candidate among several, ask what happens to the discarded ones. (build an escape fixture for every gate PR; check discarded candidates)
- (2026-09-27, #1522) When a mock-signalled TaskCompletionSource replaces a `Task.Delay`, check that `Returns(...)` and `When(...).Do(...)` are both configured (NSubstitute composes them), that the TCS uses `RunContinuationsAsynchronously`, and that a "nothing happens" test is deterministic by construction (for example `ExecuteAsync` returning before any await), not by timing. (verify TCS-based waits and deterministic negative tests)
