# Lessons for test-auditor

- (2026-09-27, #16) The coverage manifest's `targets` block is a package-wide aggregate (e.g., `Encina.Messaging`'s `unit: 70` covers all 145 files), while the per-file `files{}` map is a boolean applicability list (which flags apply to which file), not a per-file percentage target. A brief that says "compare the scoped files against their manifest targets" is ambiguous until you've opened the manifest: there is no per-file number to compare against, only per-file flag applicability plus a package-wide aggregate that a scoped/filtered test run cannot validate. Future test-auditor runs should report measured per-file line coverage directly (as I did here) and treat the package `targets` block only as "which flags exist for this package," not as a per-file pass/fail threshold. (the manifest targets block is a package-wide aggregate and files{} is flag applicability, not per-file thresholds; report measured per-file coverage and never call a scoped run a pass/fail against the aggregate)
- (2026-09-27, #16) The masking pattern the code stage found (a test fixture's synchronous `.Open()` hiding a broken async-open code path) is not just a code-review finding — it is *also* the reason the corresponding regression test does not exist: the integration test literally cannot exercise the broken branch as currently written, because the fixture never hands the store a closed connection. When a code-stage finding says "masked by the fixture," the test stage should always check whether that same masking is why no regression test exists (findings 3-6 here all follow this shape: a bug the auditor found and a happy-path-only test that structurally cannot catch it). (when the code stage says a bug is masked by a fixture, check whether that same masking is why no regression test exists)
- (2026-09-27, #16) For a "no implementation, only interfaces + options" folder like Choreography, the test-audit conclusion is symmetric with the code stage's: zero implementation means Integration/Load/Benchmark are correctly not-applicable, and Unit/Guard obligations shrink to just the options/error-code POCOs — worth stating explicitly so a later reviewer doesn't mistake the resulting near-zero test count for negligence rather than a consequence of the feature not existing yet. (for interfaces-only folders state explicitly that integration/load/benchmark are not applicable and unit/guard shrink to the POCOs, so a low test count is not read as negligence)
- (2026-09-27, #16) Before turning a coverage gap into a manifest-violation finding, quote the file's exact `defaultTests` array from the manifest and diff it against what the finding claims is "required" — this stage's own coverage table two sections above the dropped finding already had the correct answer (unit only, no guard) for `ChoreographyOptions.cs`, so the contradiction was self-detectable by re-reading the same document rather than needing a separate verification pass to catch it. (quote the file's defaultTests array from the manifest before turning a coverage gap into a manifest-violation finding)
- (2026-09-27, #16) A "zero files reference X" grep claim must state (and a verifier re-checking it must reproduce) which branch/commit it ran against, not just which directory. This audit worktree (`audit/16`) forked from `main` at `85b457ed` on 2026-09-25 and was never rebased; by the time the pass-6 verifier ran, `main` had gained 25 more commits, two of which (`28fc999f`/#1333/#1399, `832db393`/#1398/#1421) added `ISagaNotFoundDispatcher` DI-resolution smoke checks to `tests/`. The verifier's grep found those and failed this stage — but those commits are not ancestors of `audit/16`, so the references genuinely do not exist in the worktree this stage (and the verifier's own stage) is supposed to be analyzing. `git merge-base --is-ancestor <commit> HEAD` is the cheap, decisive check to run before trusting any "I found X in the repo" claim during a long-running audit: it answers whether X is even reachable from the branch under audit, independent of which physical directory a tool happened to be pointed at. This is a new failure mode, distinct from the prior lesson about substring/interface-name collisions in a "zero files" grep (that risk is about matching too narrowly within the correct branch; this one is about checking the wrong branch entirely) — both are real and a stage/verifier needs to guard against each independently. (a "zero files reference X" claim names the branch/commit it ran on; long-running audit worktrees are not rebased, so check git merge-base --is-ancestor before trusting a hit found elsewhere)
- (2026-09-27, #16) A parenthetical line count in a finding's prose (e.g., "`SagaNotFoundDispatcher.cs` (28 lines)") can silently mean "coverable lines per the coverage tool" rather than "total lines in the file" when the same document's coverage table uses the same number for a 0/N coverage cell. This is not a file:line citation error (no specific line is misquoted) and should not be flagged as a correction on its own, but a stage should say "28 coverable lines (per the cobertura report)" rather than the bare "(28 lines)" so a reader — or a future verifier — does not have to infer which count is meant from a different section of the document. (say "N coverable lines (per the cobertura report)" rather than a bare "(N lines)" when the number comes from the coverage table)
- (2026-09-27, #17) For a SPIKE issue whose only diff is a deletion commit, "measure the archivist's scope list" resolves almost entirely to "confirm there is nothing to measure": the deleted package has no source and (verified via `git log --all --diff-filter=A -- "tests/*<Package>*"`) never had a test project in this repository's reachable history, and the "kept" package the archivist lists for context was not touched by the issue's diff at all (verified via `git show --stat <sha> -- <package-path> tests`). The one useful test-stage action left is a narrow, test-name-filtered coverage run of exactly the files the archivist named as the kept implementation — not a full per-flag package run — to confirm the kept strategy's own tests exist, pass and are not vacuous, without duplicating the eventual audit of whichever issue actually wrote that package. (For a deletion-only issue, prove there is nothing to measure (git log --diff-filter=A on tests, git show --stat) and run only a narrow filtered coverage check of the kept implementation the archivist named.)
- (2026-09-27, #17) Two independently-verified pairs of duplicate guard-test classes (`Infrastructure\<Package>\*GuardTests.cs` next to a newer `<Package>\<Feature>\*GuardTests.cs`) turned up as a side effect of confirming the "kept" strategy's tests aren't vacuous. Worth checking for this same folder-doubling pattern whenever a future stage reads a package's guard tests — it is exactly the shape the active Test Consolidation plan is meant to catch, and it was cheap to find once the file list from a targeted `Glob` was in hand. (When reading a package's guard tests, Glob for the folder-doubling pattern (Infrastructure\<Package>\*GuardTests.cs next to <Package>\<Feature>\*GuardTests.cs) and report duplicates.)
- (2026-10-02, #18) Record the build configuration next to every coverage figure and command. Debug and Release builds produce different sequence points and therefore different covered/valid line counts, so a faithful re-run under the other configuration looks like a mismatch. Use `-c Release` (the configuration CI and `AGENTS.md` §9's workflow use) and say so in the stage. (Record the build configuration (-c Release, as CI) next to every coverage figure and command.)
- (2026-10-02, #18) A `FullyQualifiedName~<namespace>` filter that includes a dot-separated *suffix* after the package namespace (e.g. `Encina.UnitTests.Kafka.Publishing`) silently drops sibling test classes that sit directly in the parent namespace (`Encina.UnitTests.Kafka.ServiceCollectionExtensionsTests`, namespace `Encina.UnitTests.Kafka`) without any error: the run reports "N passed, 0 failed" for whatever it did match. Use the bare package namespace (`Encina.UnitTests.{Package}`) and, if suffixed sub-filters are preferred for speed, verify the total pass count against the sub-filters' union (here 384 became 398). (Filter tests by the bare package namespace (Encina.UnitTests.<Package>); a suffixed filter silently drops classes in the parent namespace. Check pass counts against the union. CI shards have the same gap: #1607.)
- (2026-10-02, #18) A test file's name is not evidence of what it covers: `NATSMessagePublisherRequestAsyncTests.cs` contains a class named `NATSMessagePublisherAdditionalTests` whose only `RequestAsync` test stops at the null guard, and the first version of this stage inferred "RequestAsync covered" from the file name. Read the per-line uncovered list for the method's line range before writing that a method is covered. (A test file name is not evidence of coverage: read the per-line uncovered list for the method range before saying a method is covered.)
- (2026-10-02, #18) A "this package has no disposal test" claim needs the same all-variants search a sibling-bug claim needs (`DisposeAsync`, `\.Dispose\(`, `CreateScope`, over every `.cs` of the package's test folders in every test project); this stage's first version generalized from the NATS/MQTT/RabbitMQ tests and missed that Kafka's test asserts the buggy behaviour and that AzureServiceBus has none. (A "package has no disposal test" claim needs the all-variants search (DisposeAsync, .Dispose(, CreateScope) over every test project folder of the package.)
- (2026-10-02, #18) tests 1: cited `RabbitMQ/ServiceCollectionExtensionsTests.cs:89`, which is the comment line; the test method `AddEncinaRabbitMQ_RegistersPublisher` starts at line 81. (Cite a test by its method declaration line, not a nearby comment line.)

- (2026-10-02, #18) tests 3: cited `MQTTMessagePublisherTests.cs:299-342` as the subscription tests; the null-argument subscription tests extend to line 353. (Cite the full line range of a test group: read to the last test of the group before writing the range.)

- (2026-10-02, #18) tests 5: called `NATSMessagePublisherRequestAsyncTests.cs:71` the only test of `RequestAsync`; `NATSMessagePublisherTests.cs:185` is a second null-request test. - (2026-10-03, #19) The `guard-orchestrator-writes` hook blocked both `pwsh -File .github\scripts\crap-gate-selftest.ps1` and `dotnet run .github\scripts\generate-coverage-manifest.cs -- --self-test` (run from inside the worktree after `Set-Location`) with: "Blocked: A test-auditor subagent (not a governed writing agent) does not edit src/ or tests/; brief an issue-worker (worker-brief skill), which also resolves rebase conflicts there. runs '.github\scripts\crap-gate-selftest.ps1' (pwsh -File), whose script path the hook cannot resolve, so it cannot rule out writes to src/ or tests/; pass its literal path (#1181; .claude/agents/README.md, Delegation)." (Run .github/scripts self-tests with their literal absolute path inside the wia worktree from the start (D:\Proyectos\Encina\.claude\worktrees\wia-<n>\.github\scripts\...); audit-verifier ran both self-tests that way unblocked, so the hook is right and needs no change.)
- (2026-10-03, #19) For tooling-only audits the test stage has no coverage flag to measure: the stage definition and the `tests.md` template should say "not measured: no src/ scope" and ask for self-test runs and presence of CI wiring instead. (When the scope has no src/ code, write "not measured: no src/ scope" for the coverage flags and measure self-test runs and their CI wiring instead.)
- (2026-10-03, #19) Check not only that a self-test exists but that CI runs it and on which path filters: two of the three self-tests here (`generate-coverage-manifest.cs --self-test` never, `crap-gate-selftest.ps1` only on `src/**` changes) do not guard changes to their own tool. - (2026-10-03, #21) For an issue closed "created in error" with no diff, the test stage can end at confirming the empty diff (`git show --stat`, ancestry of the successor's commit) and a narrow filtered run of the successor's tests; the coverage figures are informational and any gap goes to the successor's audit, not to the empty issue.
