# Lessons for docs-reviewer

- (2026-09-27, #16) When a spike's deliverable is a single doc commit with no linked PR (as here, `8301a07c` pushed directly), no CI gate (`coverage-citations`, `markdownlint`, the docs build) ever ran against it, and none has run since — a stale or aspirational code example in such a page can survive indefinitely with no gate to catch it. The docs stage of this audit pipeline is, in practice, the first automated-adjacent check this page has ever had; future audits of doc-only spikes should treat "no linked PR" as a signal to check every code block against `src/` line by line rather than spot-checking, since the normal CI safety net for docs never applied. (a doc-only spike commit with no linked PR never passed CI docs gates; check every code block in such a page against src/ line by line)
- (2026-09-27, #16) The same "interfaces exist, implementation does not" pattern the code stage flagged for Choreography (lesson: "a strong signal the docs were written aspirationally") is independently visible from the docs side as a distinct symptom: the *individual* Choreography interface members named in the doc's code (`IChoreographySaga`, `IEventReaction<T>.ReactAsync`, `IEventHandlerScope.PublishAsync`/`AddCompensation`, `IChoreographyStateStore.GetPendingCompensationsAsync`/`MarkCompensationCompletedAsync`/`GetStuckSagasAsync`) all exist and match their signatures exactly, while the *registration* surface (`AddEncinaChoreography`, `UseChoreography`) does not exist at all. A docs reviewer who only checks "does this type/member exist" symbol-by-symbol, as SKILL.md §5/§6 literally instructs, would pass every individual code example in the Choreography section and still miss that the feature as a whole cannot be wired up — the registration call is the one line that actually falsifies the whole section, and it is exactly the line a symbol-only search across a large interface surface is easiest to skim past. Future docs reviews of a page with many small code blocks should specifically isolate and separately verify the one or two DI-registration lines per pattern, not just every named type. (isolate and separately verify the DI-registration line(s) of each pattern; symbol-by-symbol checks pass a section whose feature cannot be wired up)
- (2026-09-27, #16) The Encina.Messaging package README's "Fluent Builder (Alternative Syntax)" section (finding 4) was not in this stage's original assigned scope (`sagas.md`, `index.md`, "the README sections on sagas and choreography") but was found by reading the same README top-to-bottom for a `Saga|Choreography` grep and noticing the adjacent section a few lines below the Saga section. A future docs-stage brief that says "the README sections on X" should expect the reviewer to also skim the whole README once, since fabricated API surfaces are not confined to the section nominally about the audited feature. (when the scope names README sections, skim the whole README once; fabricated API surfaces sit next to the audited section)
- (2026-09-27, #17) Two independent, still-current docs (`AGENTS.md:70`, `docs/INVENTORY.md:89`) both say "EventStoreDB (future)", while a third (`ROADMAP.md:803`) correctly says "Deprecated" — a decision reaching one destination doesn't mean it reached all of them; check every doc that mentions the same fact, not just the first one found. (A decision reaching one doc does not mean it reached all: grep every current doc that states the same fact and check each one.)
- (2026-09-27, #17) A stale cross-reference to a deprecated decision is not confined to the files the closing commit touched or the files an archivist's `docs/`-only destination sweep finds: it recurs independently in the project's most-read binding-rules file (`AGENTS.md`), its package inventory (`docs/INVENTORY.md`), a pre-decision architecture analysis page (`docs/architecture/extensibility-analysis.md`), and a later, unrelated ADR's comparison table (`ADR-019`). A docs-stage review of a deprecation SPIKE should grep every `docs/*.md` and root-level `.md` hit for the deprecated name, not just the files an earlier stage already named as "destinations," and should check the file's own frozen/historical status (an explicit "snapshot, not maintained" banner, or `nav_exclude` plus a dated changelog-entry style) before deciding whether staleness is a defect or an accurate historical record. (For a deprecation, grep every docs/**/*.md and root .md for the deprecated name, and check each hit's frozen or historical status (snapshot banner, nav_exclude, dated entry) before calling staleness a defect.)
- (2026-09-27, #17) The same "the ADR restates a fact the filesystem contradicts" defect appears twice with the same root cause (`.backup/deprecated-packages/` does not exist in this checkout) in two independent files — `docs/architecture/adr/027-marten-as-the-event-sourcing-provider.md:30` and `ROADMAP.md:805` — both apparently copied from the original 2025-12-23 commit message's "moved to `.backup/`" claim without anyone verifying it against the checkout. A single unverified claim in a commit message can propagate into multiple "current" docs; checking `Test-Path` once and then grepping every doc for the same claim is cheaper than checking each doc for it independently. (When a doc states a filesystem fact copied from a commit message, Test-Path it once and grep every doc for the same claim.)
- (2026-09-27, #17) A citation must be re-verified against the *cited file*, not just confirmed to exist somewhere in the repository: the previous draft of finding 5 quoted a real, verbatim line but attributed it to `extensibility-analysis.md:332` when it actually lives in `ENGINEERING-HANDBOOK.md:332` (a different, frozen file this stage's own scope excludes). Before citing a file:line + quote, grep the specific cited file for the exact quoted string and confirm a hit there, not just a hit somewhere in the tree — and check the finding against every open issue whose title or body names the same file/table row before treating it as new, since a near-identical claim may already be tracked (here, correctly, for a different file: #1347 covers `CLAUDE.md`/`ENGINEERING-HANDBOOK.md` only, not `extensibility-analysis.md`). (Before citing file:line with a quote, grep that exact file for the exact string (Select-String -Path <file>) and cite only the lines that hit; the same applies to every range in a multi-range citation (pass 5 found a fabricated second range).)
- (2026-10-02, #18) A documentation-only SPIKE with no linked PR (lesson already recorded from #16) reproduces at a larger scale here: of the ~11 per-transport code samples plus the InMemory testing sample and the Polly FAQ sample in `docs/messaging/transports.md`, all but two (`AzureServiceBus.ScheduleAsync`'s parameter list and `RabbitMQ.PublishAsync`'s `routingKey` parameter) name an option property, method or type that does not exist in `src/`. When a docs page's only gate was a single unreviewed commit nine months ago, checking "does this identifier exist" symbol-by-symbol for *every* code block — not spot-checking a sample per package — is the only way to catch this; a spot-check of one or two blocks per package would have missed most of these. (For a docs-only spike page with no PR, check that every identifier in every code block exists in src/, not a sample per package.)
- (2026-10-02, #18) The same fabrication pattern recurs in a specific shape across packages: the option class in the doc example almost always has the *right general idea* (a connection setting, a topic/queue setting) but the *wrong property name* (`ConnectionString`/`Exchange`/`ExchangeType` vs real `HostName`/`ExchangeName`; `ConsumerGroup`/`DefaultTopic` vs real `GroupId`/`DefaultCommandTopic`; `QueueName` vs `DefaultQueueName`; `QueueUrl` vs `DefaultQueueUrl`; `BrokerAddress` vs `Host`; `ServerAddress` vs no such property; `RetryCount`/`CircuitBreakerThreshold` vs no such properties). This is consistent with the doc having been written from the issue's own aspirational code samples or from memory of a similar library's API (e.g. `ExchangeType.Topic` reads like raw `RabbitMQ.Client`, not `Encina.RabbitMQ`), never copied from the actual `*Options.cs` file as SKILL.md §3 requires ("find the method in `src/`, copy its exact name"). Future docs review of any page from this era should default to reading the real options class file in full before trusting a single property name in the sample. (Read the real *Options.cs in full before trusting any option property in a sample; this era's pages invent plausible names (ConnectionString, QueueName, BrokerAddress).)
