# Lessons for issue-auditor

- (2026-09-27, #16) When a spike's "no code change" scope includes an abstraction folder (`Sagas/`, `Choreography/`), the code stage must still walk out to that abstraction's provider implementations and any cross-cutting decorators (OpenTelemetry, in this case) — the archivist's scope list stops at the interfaces, but AGENTS.md §5 provider coherence and known failure patterns (leaking `EncinaError.Message`, fake-async connection handling) live in the implementations, not the interfaces. All five findings here were in files one hop outside the literal scope list. (walk from the scoped abstraction folder out to every provider implementation and cross-cutting decorator (OpenTelemetry, caching); the defects live one hop outside the archivist's scope list)
- (2026-09-27, #16) A "no implementation, only interfaces + options + error codes" folder (Choreography) is a distinct, checkable smell worth a standing check in this agent's method: grep the folder's public types across `src/` outside their own directory; zero hits plus a documented, complete usage example in `docs/` is a strong signal the docs were written aspirationally, not against working code. (a folder with only interfaces/options/error codes and zero uses of its public types outside itself, plus a complete usage example in docs/, signals aspirational docs; check the registration surface exists)
- (2026-09-27, #16) The masking mechanism in finding 4 (a test fixture's synchronous `connection.Open()` hiding a broken async open path) is a pattern worth naming for future audits: whenever a store checks `if (_connection.State != ConnectionState.Open)` before executing, verify what actually happens in the branch, not just that a branch exists — and separately verify what the *production* DI registration hands to the constructor, since integration tests commonly construct these stores directly with a pre-opened connection instead of going through the real `AddEncinaADO` factory. (when a store checks connection state before executing, verify what the branch actually does AND what the production DI registration passes in; test fixtures often hand in a pre-opened connection that masks a broken async-open path)
- (2026-09-27, #16) When a finding draws a compound conclusion from two file citations (e.g., "X can appear in both the stuck and expired batches at once"), verify the second citation's filter logic as carefully as the first before asserting the compound claim — a citation can be line-accurate and still support a conclusion the cited code does not actually produce. Finding 5's "appears in both batches" clause did not survive this check on re-read (`GetExpiredSagasAsync`'s own status filter excludes `TimedOut` by construction) even though the underlying defect it was trying to describe (permanent stuck-misclassification) was real; state the narrower, directly-supported claim rather than the broader one that sounds more alarming. (verify the second citation of a compound claim as carefully as the first and state only the narrower claim the cited code supports)
- (2026-09-27, #17) A SPIKE issue whose only code change is a deletion commit still has a code stage worth running: the check shifts from "is the new code correct" to "is the deletion complete," and the right method is a repository-wide grep for the deleted package's name/namespace across `src/`, `tests/`, `.github/`, `.vscode/`, centralized-package-management files and solution files — not just the files the archivist listed as touched by the original commit. Three of this audit's four findings were leftover references the archivist's `docs/`-focused destination sweep did not check because they live in `.vscode/`, `.github/ISSUE_TEMPLATE/` and `Directory.Packages.props`, none of which are "docs." (For a deletion issue, audit completeness: grep the deleted name repo-wide (src, tests, .github, .vscode, Directory.Packages.props, solution files), not only the files the original commit touched.)
- (2026-09-27, #17) When a deletion-only issue's scope tempts a full re-audit of the sibling package the decision "kept" (here, `Encina.Marten`'s 48 files), stop at reading the two-to-three files the archivist actually scoped for design-smell leftovers and do not expand into a full implementation audit of code written under different issues — that duplicates work the pipeline will do anyway when those issues are audited, and blows the "as if it were issue #17's PR" framing since #17's real diff never touched `Encina.Marten`. (Do not expand into a full audit of a sibling package the issue's diff never touched; stay on the files the archivist scoped, since that package gets its own audit; targeted greps across sibling providers, as the #16 and #18 lessons ask, are expected.)

- (2026-10-02, #18) A DI-lifetime bug worth a standing check for any provider package: when a package registers a connection/client type `TryAddSingleton` and a wrapper around it `TryAddScoped`/`TryAddTransient`, check whether the wrapper implements `IAsyncDisposable`/`IDisposable` and, if so, whether its `Dispose`/`DisposeAsync` body touches the injected singleton — the .NET container disposing a scoped service at scope-end will call that method and can prematurely tear down a singleton shared by the whole app. This pattern recurred identically (close/dispose the injected connection in the scoped publisher's `Dispose`/`DisposeAsync`) across five transport packages (NATS, RabbitMQ, MQTT, AzureServiceBus, Kafka), suggesting it was copied from a shared template — worth checking any other package built from the same template (locks, caching decorators) for the same shape. (Standing check: a scoped/transient wrapper that disposes an injected singleton client (Dispose/DisposeAsync) tears down the app-wide connection; check every package built from the same template.)
